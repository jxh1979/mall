# P0 terminal device credential idempotency fix

日期：2026-06-14

## 根因

`TerminalDeviceService.bindDevice()` 会为 kiosk 生成一次性明文 `deviceToken`，并把包含该 token 的 `DeviceBindingResponse` 交给 `IdempotencyService.execute(...)`。旧的 `IdempotencyService.runAndComplete()` 会直接把返回给调用方的 response JSON 写入 `idempotency_records.response_body`，因此 kiosk 首次绑定响应中的明文 token 会进入幂等缓存；同一个 `idempotency_key` 重放时也会再次返回该 token。

凭据主表本身已经只保存 `terminal_device_credentials.token_sha256`，但幂等缓存形成了第二条明文持久化路径。

## 修复

- `IdempotencyService.execute(...)` 保留原签名，并新增 stored-response transformer overload。
- `runAndComplete()` 仍返回 action 产生的原始 response 给首次调用方，但写入 `response_body` 前先应用 transformer。
- `TerminalDeviceService.bindDevice()` 使用 transformer，把写入幂等缓存的 `DeviceBindingResponse.deviceToken` 置为 `null`。
- 因此 kiosk 首次 bind 仍返回一次性 `deviceToken`；同一 `idempotency_key` replay 从 `response_body` 读回的 `deviceToken` 为 `null`。
- `returnDevice()` / `unbindDevice()` 在状态变更后把已有 `terminal_device_credentials` 从 `active` 标记为 `revoked`，保留 SHA-256 digest，不保存明文 token。
- 审计 metadata 仍为空 `Map.of()`，状态事件只记录业务状态/reason/staff，不写 token。

## 行为结论

1. kiosk bind 只在首次执行 action 时返回明文 `deviceToken`。
2. `idempotency_records.response_body` 不再持久化明文 token；保存的是 `deviceToken: null` 的响应副本。
3. 同一请求使用相同 `idempotency_key` replay 时不会再次返回 token。
4. `terminal_device_credentials` 仍只保存 SHA-256 digest 和状态。
5. return/unbind 会撤销已有 credential，状态变为 `revoked`。
6. 没有新增 token metadata/log/status-event 写入路径。
