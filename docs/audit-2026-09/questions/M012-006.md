HTML 原文（出处：三份 HTML 中无任何相关条目；最接近：docs/business-system-map-for-operations-v0.1.html 第509–510行「先管清楚基础盘子」）：
> 三份 HTML 中无任何相关条目
> 哪个综合体、谁在经营、在哪经营、签了什么合同、谁能操作、谁负责。

添加了什么：
apps/web/src/admin/pages/OrganizationMerchantPage.tsx 的「新建商户」引导流预填「二期测试商户」「运营联系人」「13800000000」「租赁」，并在用户看不见的情况下随请求提交：经营主体 entities[0] 或「org-1」、合同主体「contract-subject-1」、结算主体「settlement-subject-1」、区块「1F-A」、面积 128.5/120、备用联系人「备用联系人/13900000000」、租金 12.3、状态 active、操作备注「完整后台组织与商户档案验收创建」、证据附件「att-merchant-profile-create」。apps/web/src/admin/pages/SubjectBindingsPage.tsx 的「提交绑定变更」原因预填「完整后台验收变更」，并提交证据附件「evidence-full-admin」。这些值都是验收阶段的脚手架默认值，三份 HTML 没有规定任何默认商户名、默认电话、默认租金、默认主体或默认证据。

添加后的代价：
验收数据可进生产库（merchants 三主体列无外键，假主体 id 可落库）；审计留痕指向不存在的附件；页内「不在本页替代四类主体绑定」文案与静默提交三主体相反；后台校验主体存在（M009-006），当前库无「contract-subject-1」，创建必然失败 404；无主体查看权限的账号首次创建也会提交「org-1」。

删除的代价：
表单不再预填，用户须自己填写商户名/联系人/电话，并从真实经营主体列表选择经营/合同/结算主体（或按四类主体绑定流程另行绑定）；变更原因须用户填写；证据附件改为真实附件或后台允许的空列表；相应测试断言随改。不会失去任何业务能力。建议删除。

## 席甲勘误（2026-09-09，答复之后追加；不改上方首行答复「删除」）

「添加后的代价」中「后台校验主体存在（M009-006），当前库无『contract-subject-1』，创建必然失败 404」一句有误：后台对**绑定创建**校验主体存在（M009-006，PlatformService.createBusinessEntityBinding），而**商户创建**（saveMerchant）对经营/合同/结算主体只去空白、不校验存在、允许为空。实际后果是这些假主体 id 会静默写入商户档案成为悬空引用（merchants 三主体列无外键），比 404 更有害。其余事实与「删除」的处置不变；处置细节按 findings 定稿：创建请求不再携带三主体与其它隐藏字段（三主体由四类主体绑定流程承接，与页内「不在本页替代四类主体绑定」一致），不需要新增主体选择控件。
