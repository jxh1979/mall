## 一、四层组织实体(定死)

| 层 | 名词 | 定义 | DB 落点 |
|---|---|---|---|
| L1 | **平台** | 最大管理实体,可辖多城市多项目 | `business_entities`(entity_role=platform) |
| L2 | **项目公司** | 某城市的项目经营体(如长沙 NEXT PARK) | `business_entities`(entity_role=project_company) |
| L3 | **管理公司 / 业态主体(SPV)** | 项目公司与商户之间的分账主体 | `business_entities`(entity_role=management_company / spv …) |
| L4 | **商户** | 具体经营单位 | `merchants` 表 |

## 二、当前实现落点（不得反向解释业务术语）

- **无 `organizations` / `org_type` 表**;四层主体统一用 **`business_entities` 一表多角色**(`entity_role` 文本,无 CHECK)承载。
- **层级父链(V318)** = `business_entities.parent_entity_id`:L3 管理公司 → L2 项目公司,L2 → L1 平台,L1=NULL。「一个项目公司下多个管理公司主体」= 多行 `parent_entity_id` 指向同一项目公司。
- **`projects` 表 ≠ 项目公司** —— 它是**业态经营单元 / 场馆**(`venue_type` = bar / amusement / ticketing);`project_id` = 综合体维度。两者是两回事,勿混。
- **四主体绑定** = `business_entity_bindings`(binding_type=four_party;每商户至多一条 `active`,重复激活报 409 `ACTIVE_BINDING_EXISTS`);"后续可拆" = 换一条新 active 绑定,不是改 `merchants` 快照列。
- `merchants` / `contracts` 的 `*_entity_id` / `*_subject_id` = 档案 / 签约时快照,与当前绑定可不一致。
- 商户 ↔ 铺位 ↔ 合同 = `merchants`(1)-<`contracts`(N,续约链)-<`contract_spaces`>- `spaces`(多对多);`spaces.status` 仅 `active` / `unavailable`(6 态租赁着色是看板派生视图,非 DB status);无转租(换租户=先退租再招商)。

## 四、混用词纠正规则

| 旧词 | 纠正 |
|---|---|
| "综合体" | 指单个经营体 → **项目公司**;多项目汇总 → **平台 / 集团视图** |
| "集团" | **平台 / 集团视图**(多项目汇总,当前无独立实体) |
| "项目" | 按语境区分:**项目公司**(经营体)vs **`projects` 表**(业态场馆);文中明确指出 |
| "组织 / organization" | 权限侧保留 `organization_id`(仅角色/用户权限用);业务主体一律 `business_entities` |
| "娱乐运营平台"(2026-07-28 废) | **娱乐平台公司**;全仓不再出现旧称 |
| "酒吧 SPV / 酒吧经营主体"(2026-07-28 收敛) | **各酒吧商户**(L4 独立商户,娱乐平台公司参股);不再作为独立 L3 业态主体单列 |
| "资产公司"(2026-07-28 澄清) | = **长沙项目公司**,同一主体两个叫法;资产业态不单设主体 |
| "平台承担/平台出资"(涉赠送权益时) | 明确写 **娱乐平台公司**承担/出资,不用笼统的"平台" |

## 五、结算核心术语（三份业务 HTML 最终解释，结算 PRD 承接）

- **通票分账瀑布(2026-07-28 口径)**:通票的钱进来后按固定顺序——① 扣**第三方渠道抽成**(比例/金额可配)→ ② 扣**赠送权益预估成本**(归娱乐平台公司)→ ③ 扣**门票综合服务费**(= 娱乐平台公司留存 / 项目管理费,**同一项只扣一次**,归娱乐平台公司)→ ④ 剩余全部进**可分配池,仅各酒吧分**,**不再从池内二次扣留存**。
- **按核销结算 / 未核销归项目**:通票权益在核销时才结算给商户;未核销部分票款归项目公司留存。
- **门票综合服务费**〔规则正文以三份业务 HTML 为准，本表不复述；2026-08-03 起术语表只定名词与主体对应关系〕:**只适用于酒吧相关票务**（原写「所有门票项目都收一道」已作废）,与「娱乐平台公司留存 / 项目管理费」为同一项、分账瀑布中只扣一次、不在酒吧可分配池内再拆;比例或固定额及封顶(项目 × 商户 × 票种)后台可配;**收入归娱乐平台公司**。
- **赠送权益(2026-07-28 口径,替代旧「通票赠酒两段口径」)**:票里加赠的酒水 / 小食 / 餐饮 / 零售,**每一样都是独立权益**,各自绑定提供它的酒吧 / 餐厅 / 零售商户,客人须到对应商户核销;每个权益的成本按**提供方的内部结算价**计。
  - **预扣两种模式(按票种配置)**:**按件计** = 票面各权益数量 × 内部结算价之和;**按票计** = 该票种赠送部分的售价整额。
  - **赠酒按酒吧分配**:一张通票覆盖的每个酒吧**至少赠一杯**,各酒吧分别赠几杯在售票时**写明票面**;**A 酒吧的赠酒只能在 A 酒吧核销**,不得跨吧。
  - **兑付与差额**:核销后由**娱乐平台公司**按该权益可配内部结算价与提供商户结算(核销一件结一件、未核销不结算);对商户的兑付由娱乐平台公司承担,不进入酒吧可分配池、不计酒吧销售提成;成本**按提供方商户业态(酒吧/餐厅/零售)分开记账**;**预扣与核销实付的差额留在娱乐平台公司**,按可配规则调账留痕。
- **综合／联合通票定价构成(2026-07-28 A)**:售价 =(**游乐业态价** + **酒吧业态价** + **收费的餐饮/零售价**)× 票种折扣;**免费的(票面价 0)不计入价值**。
- **业态份额拆分(2026-07-28 B)**:综合／联合通票**整单先扣第三方渠道抽成**,剩余**按各业态票面原价占比**拆成各业态份额——游乐份额归**游乐公司**、餐饮归**餐厅商户**、零售归**零售商户**;**仅酒吧份额**再依次扣赠送权益预估成本、门票综合服务费,剩余进可分配池。拆份额**只按业态大分类**;**依附于某业态产生的加赠权益不作为业态层拆分对象**(其价值已含在所属业态的价格内)。⚠️ 与「每样赠品都是独立权益」不矛盾:后者说的是**核销/绑定/成本**层,前者说的是**业态份额拆分**层,两层别混。
- **票面原价 vs 内部结算价(2026-07-28 B,不可混用)**:**票面原价**用于**定价**与**业态份额拆分占比**;**内部结算价**用于**与提供商户结算成本**。每个权益同时带这两个价、分别录入,**禁止互相回退顶替**。
- **可分配池两段分配(2026-07-28 D,替代原「三选一」)**:第一段——约定为「每客单价」或「固定额」的酒吧按**绝对金额先拿**;第二段——**余额**(= 池 − 第一段合计)由其余「排名档位」酒吧按档位比例**分尽**;**拿了第一段的不再参与第二段**。守恒式 `可分配池 = 第一段合计 + 第二段合计 + 尾差`。
- **免费权益成本承担两类(2026-07-28 C)**:票面价 0 的免费权益按成本承担方分——①**商户让利型**(餐饮/零售自行让利搭进通票):平台**不承担成本、不结算**;②**平台出资型**(平台向商户采购后免费赠客):平台按**内部结算价**与提供商户结算、**计入赠送权益预估成本**。两类**均不参与份额拆分**;承担方须在票种配置**标明**。原「价格可为 0 的纯赠送/兑换也按内部结算价结算」一刀切口径**作废**。
- **内部结算 SKU 目录(2026-07-28 E,🆕 新需求·未开发)**:全平台内部结算价**集中一个目录、成本侧唯一真源**;每条绑**提供商家**(业态随商家)+ 归**品类**,商家/业态/品类三维可筛;多处可引用并就地新建、但**只进同一目录**;**目录是唯一可编辑处**,改价走**草案 → 他人复核转正 → 对后续生效**;**核销/结算时把当时价固化到流水**,已发生的账不受后续改价影响、固化价**只读**;条目可下线归档不影响历史引用;内部结算价属**敏感信息、仅授权后台可见**。
- **中央餐饮开关**(`central_catering_enabled`):2026-07-28 起**现行口径默认=关**——订台低消 / 二次消费 / 额外酒水直接归**该酒吧商户**;开关保留,仅在将来税务方案成立、重议归中央餐饮时才置开(见 §三 可重议项)。
- **可配置铁律**:一切业务策略(比例/费率/单价/阈值/限额)后台可配、禁硬编码;成本 = 真实费用归集,不用"收入×成本率"估算。
