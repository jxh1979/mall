## 1. 背景与定位

- **业务场景**：客人在酒吧可以点专项服务（比如点舞）。所有服务费由**公司统一收款、全额进公司账**（此处「公司」即该服务发生地所属酒吧商户的经营主体，见 §4.1）——**不存在钱不进账的情况**；分给服务人员的部分，是**入账之后按薪资/提成/成本名录列支的支出**，不是"从客人手里直接给人"的现金流。（依据 **BSM「服务点单：客人点专项服务，公司统一收款、再按名录分账」章导语**）
- **本 PRD 定位**：承接服务点单的**服务目录配置、下单与收款、履约完成、自动分账与月结、退款边界、人员归属与成本**，以及 BSM 同章承载的**营销人员/派驻人员报酬路径**与**演出相关收款主体与艺人演出结算**口径。
- **非目标**：不定义酒水账单、低消、桌台与转并台规则（见 `bar-business-operations-product-prd-v0.1.md`）；不定义票务分账与收入归属模型（见 `settlement-rebuild-prd-v1.0.md` / `finance-settlement-product-prd-v0.1.md`）；不定义薪资域的工资薪金代扣模型（见 `platform-governance-prd-v0.1.md` §12B）。

## 2. 角色分离：点单员 ≠ 服务提供人

> 依据 **BSM「本章的「点单员」指帮客人下单、向客人出示收款码」条**。

| 角色 | 定义 | 职责 |
|---|---|---|
| **点单员** | 帮客人下单、向客人出示收款码、确认收款并点完成履约的**酒吧现场服务员** | 代客下单（下单时**即指定由哪位服务提供人履约**）、出示收款码、确认收款、点完成履约 |
| **服务提供人** | 被点到、**实际提供专项服务并参与分账**的人员 | 实际履约；**工作时不带手机**（见 §4.3） |

**硬约束**

1. **两者是不同的人，本 PRD 及下游文档、配置、代码、页面、报表一律不得混称**——不得用同一字段、同一角色名或同一权限位表达两者。
2. **下单时即指定服务提供人**：服务订单在创建时必须绑定服务提供人，未指定不得提交。
3. **分账只认服务提供人**：管理费之外的份额记到**服务提供人**名下（见 §8.1），**不记点单员名下**；点单员的经手事实按责任链留痕，不因经手取得该笔服务的分账份额。

## 3. 服务目录

> 依据 **BSM「后台维护服务目录」条** 与 **ENUM「管理费方式」条**。

### 3.1 目录项字段

| 字段 | 口径 | 必填 |
|---|---|---|
| 服务名称 | 专项服务的名称（如点舞） | 是 |
| **固定价格** | 每项服务定**固定价格**；不设按人、按台阶浮动的现场议价 | 是 |
| **时长** | 每项服务定**时长** | 是 |
| **上下架** | 每项服务可**上架 / 下架**；下架后不得被新单选中，已产生的在途单据不受影响 | 是 |
| **管理费方式** | 见 §3.2，**三值互斥**，按**服务目录项**配置 | 是 |

### 3.2 管理费方式（三值，按目录项配置）

> ENUM「管理费方式」条 原文口径：**不收、按比例、固定金额**（按服务目录项配置；服务费全额入公司账，管理费归公司收入，其余份额按薪资/提成名录进服务人员月结薪资）。

| 取值 | 口径 |
|---|---|
| **不收** | 该服务项不计管理费，服务费全额（扣税前）记服务提供人名下 |
| **按比例** | 按配置比例从该笔服务费中计取管理费，余额记服务提供人名下 |
| **固定金额** | 按配置固定金额计取管理费，余额记服务提供人名下 |

**硬约束**

1. **三值互斥**，一个目录项同期只能选定一种；**未选定管理费方式的目录项不得上架**（与「每项可配管理费」的必填口径一致）。
2. 管理费方式与其数值**随订单固化**：每笔服务订单在**下单时**固化当时目录项的价格、时长与管理费方式及数值；**事后改目录不追改已产生的订单**。
3. **管理费归公司收入**——即归该服务发生地所属酒吧商户的收入并计入其净利润基数（见 §8.1），不进入服务提供人分账份额。
4. **保存边界（DEC-R8-90）**：按比例时配置值必须在 0% 至 100%（含边界）之间；固定金额必须在 0 至服务售价（含边界）之间；任一越界值在保存时直接拒绝，不得静默截断、封顶或改写。

### 3.3 管理费的配置与变更规则（比照销售提成，2026-08-19 补，依据 BSM「后台维护服务目录」条 / ENUM「管理费方式」条现文；DEC-R8-97-07）

> HTML 现文：**服务点单管理费的配置主体与审批、出厂默认值、变更版本化与指定生效日、单据下单时锁定费率版本、变更前向受影响方通告、不收管理费的排除项、退款时的冲回与反向结算，一律比照销售提成的对应规则执行；上下限约束按 §3.2 第 4 项的区间。**

逐项比照对象为 `bar-business-operations-product-prd-v0.1.md` §11 已确认第 5b～5f 条与 §9 的销售提成对应规则：

1. **配置主体与审批**：比照销售提成费率——由后台在结算配置中心维护，改动落草案、复核转正后生效，不得代码写死。
2. **出厂默认值**：比照销售提成——必须给出出厂默认值，且**须同时配置上下限**（本项区间见 §3.2 第 4 项：按比例 0%～100%、固定金额 0～服务售价）。
3. **变更版本化与指定生效日**：比照销售提成——**费率变更形成新版本并指定生效日期，只对生效日之后发生的单据有效**。
4. **单据下单时锁定费率版本**：比照销售提成——**每笔在下单时锁定当时的版本**，重新月结**只重算金额、不改已锁定的版本**（与 §3.2 硬约束第 2 项同向）。
5. **变更前向受影响方通告**：比照销售提成——变更生效前须向受影响的服务提供人与商户通告，通告与生效日一并留痕。
6. **不收管理费的排除项**：比照销售提成的不计提成项——排除项由后台标志位配置，**排除项内的服务不计管理费**；**退款时的冲回与反向结算**同样比照：按订单最终保留收入重新计算并冲回差额，**生成一笔反向结算记录，不覆盖原归属、原计算与原结算记录**；**已收款但服务未完成而取消的，管理费随之冲回**。


## 4. 下单与收款

### 4.1 公司统一收款码与全额入账铁律

> 依据 **BSM「客人扫公司统一收款码付款」条** 与 **BSM 章导语**。

1. **客人扫公司统一收款码付款，钱直接进公司账户（即该服务发生地所属酒吧商户的账户）**，财务可对账。
2. **所有服务费由公司统一收款、全额进公司账——不存在钱不进账的情况**。**本 PRD 与 BSM 服务点单章所称「公司」，一律指该服务发生地所属酒吧商户的经营主体**，与 BSM 收入归属表所写的「酒吧商户」为同一主体；该句的对立面是服务人员个人私收（防钱不进账），不是把收款主体定到平台或项目公司（依据 DEC-R8-70 与 BSM 三处互认括注）。
3. **禁止任何形式的账外收款**：不得由点单员或服务提供人以个人收款码、现金、私下转账等方式收取服务费；发现即按异常处置并进责任链留痕。
4. 分给服务人员的部分是**入账之后按薪资/提成/成本名录列支的支出**，**不是收款环节的分流**——收款侧永远是"整笔进公司账"。

### 4.2 下单时间与支付时间双时点

> 依据 **BSM「每一笔服务点单都分别记录两个时间」条**。

1. **每一笔服务点单都分别记录两个时间**：
   - **下单时间** = 点单员帮客人提交这笔服务的时刻；
   - **支付时间** = 这笔钱**支付成功**的时刻。
2. **两个时间各记各的**，**不能拿下单时间当支付时间用**。
3. **还没付钱的，支付时间就空着**——不得以下单时间、系统当前时间或任何默认值回填。

### 4.3 到账回传是完成履约的硬门槛

> 依据 **BSM「服务提供人工作时不带手机；支付成功后由支付渠道自动回传到账信息」条**。

1. **服务提供人工作时不带手机**——服务提供人侧不承载任何下单、收款或确认动作。
2. **支付成功后由支付渠道自动回传到账信息**，系统据此**确认收款并记录支付时间**，**不需要点单员人工确认**。
3. **没有收到渠道回传的到账信息不能点完成履约**（硬门槛）：未到账的订单，"完成履约"动作一律拒绝，不设人工放行、不设主管例外。

> **✅ HTML 内部措辞差异——已裁决（2026-08-05 用户裁决，DEC-R7 第二批）**
> **已裁决：以支付渠道自动回传为准，ENUM「服务订单状态」条已按裁决改写，冲突关闭。** ENUM「服务订单状态」条的「已收款」现行原文为「已收款（客人扫公司统一收款码付款，支付渠道回传到账信息后系统自动确认收款到公司账户，不需要点单员人工确认）」，「已完成」现行原文为「已完成（完成时自动分账；没有收到渠道回传的到账信息不能点完成）」，与 BSM 条 一致；原「服务员现场确认收款到公司账户」表述已作废。
> - 本 PRD 的实现路径（渠道回传自动确认收款）与两份 HTML 现行原文**完全一致**；
> - **不得开发"人工确认收款"入口**——该口径现已由 ENUM 与 BSM 双份 HTML 明文授权，非仅 BSM 单侧口径。

### 4.4 终端限制：一律在公司工作手机上办理

> 依据 **BSM「点单员代客下单、向客人出示收款码、确认收款和点完成履约都是现场操作」条**。

1. 点单员的**代客下单、向客人出示收款码、确认收款、点完成履约**四个动作**都是现场操作**，**一律在公司工作手机上办理，不在自己的私人手机上办**。
2. 与终端开关口径对齐：服务点单模块挂在 **`staff_work_phone`（员工工作手机）** 端下（终端十端见 **ENUM「终端十端」条**）；**员工私人手机（`staff_personal_phone`）端不开放服务点单模块**——服务点单**不属于**私人手机可承载的低风险功能清单（见 `platform-governance-prd-v0.1.md` §6.9）。
3. 后端必须**独立校验终端身份并拒绝**，不得只靠前端隐藏（与 `operation-traceability-and-terminal-switch-prd-v0.1.md` §5.4「终端开关后端拒绝铁律」一致）。

## 5. 服务订单状态机（四态）

> 依据 **ENUM「服务订单状态」条**（2026-08-05 DEC-R7 第二批裁决后的现行原文）：已下单、已收款（客人扫公司统一收款码付款，支付渠道回传到账信息后系统自动确认收款到公司账户，不需要点单员人工确认）、已完成（完成时自动分账；没有收到渠道回传的到账信息不能点完成）、已取消（已收款后取消标「已收款待退」线下退）。

| 状态 | 进入条件 | 关键动作与副作用 |
|---|---|---|
| **已下单** | 点单员代客提交、且已指定服务提供人 | 记录**下单时间**；**支付时间留空**；固化服务目录项价格、时长、管理费方式与数值 |
| **已收款** | **收到支付渠道回传的到账信息** | 记录**支付时间**；款项已进公司账户（即该酒吧商户账户，见 §4.1）。**不需要点单员人工确认**（见 §4.3 与该处的 HTML 措辞差异登记） |
| **已完成** | 服务履约完毕，点单员在公司工作手机上点"完成履约"；**前置硬门槛 = 已收到渠道回传到账信息** | **完成时自动分账**（见 §8.1）；**完成后不可退**（见 §6） |
| **已取消** | 取消动作 | **已收款后取消的，标「已收款待退」**，走**线下退款、全程留痕**（见 §6） |

**状态机约束**

1. **四态为全集**，不新增第五态；"已收款待退"是**已取消**态下的**待退标记**，不是独立状态。
2. **已完成为终态**，不可回退、不可撤销、不可转已取消。
3. 状态流转与每次流转的操作人、终端、时刻一律留痕（与 `evidence-risk-control-product-prd-v0.1.md` §3 留痕清单一致）。

## 6. 退款与不可退边界

> 依据 **BSM「已收款后客人取消」条**。

1. **已收款后客人取消**：单子标「**已收款待退**」，**线下退款、全程留痕**。
2. **服务完成后不可退**——进入「已完成」态即不可退款，不设人工放行、不设主管例外、不设密钥逐笔开放通道。
3. 线下退款须记录退款经办人、退款时刻、退款凭证与复核人；退款动作本身进责任链留痕。
4. **未收款的取消**不进入「已收款待退」，直接取消，无退款动作。

## 7. 单据独立性

> 依据 **BSM「服务点单是独立单据，不并入客人桌台的酒水账单」条**。

1. **服务点单是独立单据，不并入客人桌台的酒水账单**——不合并出单、不合并结账、不合并打印。
2. **但公司账上（即该酒吧商户账上，见 §4.1）每一笔都全额入账、可追可查**。
3. **对低消与酒吧账单口径的影响**：服务点单金额**不进入酒吧桌台账单**，因此不参与该台位的最低消费判定、不参与酒水账单的拆单/合单/转台/并台归集（酒吧侧口径见 `bar-business-operations-product-prd-v0.1.md` §7.3A、§11 第 5 条）。
4. 服务点单单据与酒水账单**分别统计、分别对账**，不合并计数。

## 8. 分账与月结

### 8.1 服务完成后系统自动分账

> 依据 **BSM「服务完成后系统自动分账」条** 与 **ENUM「管理费方式」条**。

1. **服务完成后系统自动分账**——由「已完成」状态触发，**无人工发起入口**。
2. **管理费部分归该服务发生地所属酒吧商户的收入，并计入其净利润基数**（按 §3.2 下单时固化的管理费方式与数值计算；依据 BSM 收入归属表「服务点单」行「管理费部分归该酒吧商户收入并计入其净利润基数」——该口径影响主理人分红）。
3. **其余份额记到该服务人员名下**，**月结时自动进其薪资提成**。
4. 分账口径的两条边界：
   - 分账是**入账之后的支出列支**，不是收款分流——公司账上（即该酒吧商户账上）仍是整笔服务费全额入账（见 §4.1）；
   - 分账份额记在**服务提供人**名下，**不记点单员**名下（见 §2）。
5. **归属月份（2026-08-19 补，依据 BSM「服务完成后系统自动分账」条 / ENUM「管理费方式」条现文；DEC-R8-97-07）**：**服务点单份额与管理费的归属月份按服务完成时点所在营业日确定**（营业日定义见 `finance-settlement-product-prd-v0.1.md` §4A.1），不按自然日、也不按收款时点切分。

### 8.2 月结按劳务报酬法定税率表代扣个人所得税

> 依据 **BSM「月结发放时，按劳务报酬的法定税率表代扣个人所得税」条**。

1. **月结发放时，按劳务报酬的法定税率表代扣个人所得税**。
2. **扣多少必须在薪资单上写明白**——薪资单须列示该笔服务点单分账的**应发额、代扣税额与实发额**，可逐笔追溯到服务订单。
3. **税目区分（硬约束）**：本项代扣适用的税目是**劳务报酬所得**，**与薪资域的"工资薪金所得"代扣是两套税目、两张税率表**，不得合并计算、不得共用同一税率参数、不得在同一栏内混列。
   - 对照：**服务费**按后台分配方式发放给当班服务提供人，**按工资薪金所得代扣个人所得税**（ENUM「服务费」条）；**小费**在当月薪资单中作为独立一栏全额发放，**代扣个人所得税，适用税目按发放时有效的国家法律、纳税主体身份和交易实质确定**（ENUM「小费」条现文；2026-08-19 改，DEC-R8-97-10——原「按规定代扣个人所得税」未点明税目确定方式）。三者在薪资单上**分栏列示**，不合并。

## 9. 营销人员的归属与报酬

> 依据 **BSM「营销人员的归属与报酬」条**（与台账 H-10 一致）。

1. **统一管理**：营销人员由**娱乐平台公司统一管理**。
2. **基本报酬路径**：其**基本薪资、社保及其他常规报酬由娱乐平台公司承担并直接支付给本人**。
3. **提成路径（不经转付）**：营销在**某家酒吧促成的订单产生的提成**，**由该酒吧直接支付给营销本人，不经由娱乐平台公司转付**——该笔提成**不形成娱乐平台公司与该酒吧之间的公司间结算款项**。
4. **归属铁律**：**娱乐平台公司不设直属营销挂在平台名下经营，营销一律挂到所在酒吧**。
5. **派驻期间的现场管理**：**排班、现场考勤和履约调度由所在酒吧负责**。
6. **记录颗粒度**：营销人员的所属主体、挂靠酒吧、由娱乐平台公司支付的常规报酬与由酒吧直接支付的提成**须分别记录、可分别统计**。

## 10. 派驻人员的成本与报酬

> 依据 **BSM「派驻人员的成本与报酬」条**（与台账 H-10 一致）。

1. **现场管理归使用方**：其他公司的人员派驻到某家酒吧工作期间，**由该酒吧负责排班、现场考勤和履约调度**。
2. **所属主体只承担基本项**：人员所属主体**只承担该人员的基本薪资、社保和其他常规报酬**，**由人员所属主体直接支付给本人**。
3. **其余一切费用由使用方酒吧承担并直接对接本人**：**除此之外的一切费用一律由使用方酒吧承担，并由该酒吧直接与本人对接支付，不经由人员所属主体转付、不形成公司间结算款项**——包括但不限于该人员在该酒吧促成订单产生的**提成**、该酒吧要求的**专用服装、专属培训、专用物料**，以及**其他因在该酒吧工作而发生的费用**。
4. **记录颗粒度（硬约束）**：每一名派驻人员的**所属主体、派驻酒吧、派驻起止时间**，以及**由人员所属主体支付**和**由酒吧直接支付**的**各项金额**，**均须分别记录、可分别统计，不得只保存合并后的净额**。
5. **合规意义**：第 3、4 条共同构成"不形成公司间往来 + 成本可分列举证"的税务与关联交易边界；实现侧**不得**以"净额入账""合并列支"简化。

## 11. 演出相关收款主体与艺人演出结算

### 11.1 演出相关门票的收款主体按销售地判定

> 依据 **BSM「演出相关门票的收款主体按该票在哪里销售确定」条**。

| 情形 | 收款主体 | 后续处理 |
|---|---|---|
| **酒吧门票上的演出加价部分** | **娱乐平台公司**（随酒吧门票由娱乐平台公司售票收款） | 收款后**分给传媒公司** |
| **传媒公司自办场次的独立演出票** | **传媒公司**（自行定价、售票、收款） | 由传媒公司自行处理 |

**边界说明**：本条判定的是**收款主体**（谁收这笔钱），与结算域「演出票收入归属传媒公司」是**两件事**——收入归属见 `settlement-rebuild-prd-v1.0.md` / `finance-settlement-product-prd-v0.1.md`；本条只解决"票在哪儿卖、谁收款"。

### 11.2 传媒公司艺人到酒吧演出的结算（三情形逐场配置）

> 依据 **BSM「传媒公司艺人到酒吧演出的结算」条**。

按演出合同**可以同时存在三种情形，也可以只有其中一种或两种**：

| 编号 | 情形 | 口径 |
|---|---|---|
| **①** | **涉及门票的** | 该场演出**加收的门票金额由娱乐平台公司售票收款后**，按演出合同**逐场约定的比例或金额**分给传媒公司，并在**后台配置页面逐场填写、随合同固化版本** |
| **②** | **签订固定费用的** | 由**该酒吧**向传媒公司支付合同约定的**固定费用** |
| **③** | **约定酒水提成的** | 按合同约定的比例分给传媒公司；**计提基数不含通票赠饮和酒吧门票赠饮的酒水**。基数口径与比例由**酒吧与传媒公司在演出合同中约定并随合同固化版本**；后台提供**按演出时段、按当场全店**等多种基数模板供选择 |

**硬约束**

1. **逐场记录**：**每场演出适用哪几种情形、各自的数值与合同版本，必须逐场记录**——不得按合同一次性套用到全部场次而不落场次级记录。
2. **随合同固化版本**：情形①与情形③的数值与基数口径**随合同固化版本**；合同改版**不追改已发生场次**。
3. **③的基数排除项是防重复计提的关键约束**：**通票赠饮**与**酒吧门票赠饮**的酒水**不进入**酒水提成计提基数（与 `bar-business-operations-product-prd-v0.1.md` §9「娱乐平台公司出资的通票免费酒水不计提成」同向，两者分别适用于艺人分成与员工销售提成，不互相替代）。

## 13. P0 验收标准

1. 服务目录项可配置**固定价格、时长、上下架**与**管理费方式三值（不收/按比例/固定金额）**；**未选定管理费方式的目录项不得上架**。
2. **点单员与服务提供人为两个不同角色**，下单时必须指定服务提供人；系统内不存在把两者合并为同一字段/角色的路径。
3. 客人扫**公司统一收款码**付款，款项**直接进公司账户（即该服务发生地所属酒吧商户的账户）**；系统内**不存在**任何个人收款码/现金/私下转账的收款入口。
4. 每笔服务点单**分别记录下单时间与支付时间**；**未支付的支付时间为空**；不存在用下单时间回填支付时间的代码路径。
5. **未收到支付渠道回传到账信息的订单，"完成履约"一律被拒绝**（无人工放行、无主管例外）。
6. 点单员的四个现场动作**只能在公司工作手机上完成**；私人手机端请求被后端独立校验并拒绝，并写终端拒绝留痕。
7. 服务订单严格按**四态**流转；**已完成为终态**；已收款后取消标**「已收款待退」**并走线下退款留痕；**已完成不可退**。
8. **服务完成即自动分账**：管理费归该服务发生地所属酒吧商户收入并计入其净利润基数、其余份额记服务提供人名下并进月结薪资提成；分账无人工发起入口。
9. 月结按**劳务报酬法定税率表**代扣个税，**薪资单上分栏写明应发/代扣/实发**，且与工资薪金所得税目**不混算、不混列**。
10. 服务点单单据**独立**，不并入桌台酒水账单，不参与该台位低消判定。
11. 营销人员**一律挂所在酒吧**；平台**无直属营销**；某酒吧促成订单的提成**由该酒吧直付本人**，系统内不产生"经娱乐平台公司转付"的往来单据。
12. 派驻人员的**所属主体/派驻酒吧/起止时间/各项金额分别可查**；系统**不得只保存合并净额**；酒吧直付部分**不生成公司间结算款项**。
13. 演出相关门票**按销售地判定收款主体**：酒吧门票演出加价 → 娱乐平台公司收款后分给传媒公司；传媒自办场次独立演出票 → 传媒公司自行收款。
14. 艺人演出结算支持**三情形并存并逐场记录**；情形③的**计提基数排除通票赠饮与门票赠饮酒水**；数值与基数口径随合同固化版本。
15. 管理费比例 0% 与 100%、固定金额 0 与等于服务售价均可保存；比例大于 100% 或固定金额大于服务售价时保存失败，且不得静默截断、封顶或改写。
