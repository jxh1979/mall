# 综合体管理系统 P0 实施任务清单

> **口径修订（2026-08-06 R10）：「场次容量」已废止**——BSM「容量控制」条 明确「**只按单个游乐项目的实时在玩人数控制容量，不再按场次/时段或点位/设备另设容量；排队人数不占用容量**」（DEC-R5-2026-08-04-04；R8 用户裁决 D-02）。本文原「场次容量」一律改称「**项目容量（实时在玩人数）**」；双阈值不变（运营容量软上限告警放行、安全容量硬上限阻断并自动停运）。仍按场次/时段或点位/设备维度罗列的页面、接口、组件与字段只作历史结构参考，容量口径一律以本条为准，相关字段待代码轮下线，期间不得据以新增受控维度。

> **口径修订（2026-08-06 R10）：「人工放行」已废止**——ENUM「核销记录状态」条 明确「**系统不提供人工放行：核销要么成功、要么拒绝或失败，任何岗位、任何权限都不能以人工方式让一笔不满足规则的核销通过**」（DEC-CFG-2026-08-03-12 / DEC-R6-08）。本文原有的「人工放行」取值、端点、按钮、指标、权限点与复核类型**一律废止**，废止处就地标注「原含『人工放行』，已废止·见文首口径」；已实现的端点、权限点与状态取值待代码轮下线，期间不得新增调用、不得新写入。**注意**：合同或基础定义违规被卡住后「由更高级审核放行」的准入场景仍然存在，那是准入阻断的升级放行，与核销域无关，不得回读为「可以人工放行一笔核销」。

本文档用于把现有开发设计文档转换为可直接分派、编码和验收的 P0 任务。

P0 目标不是一次性做完整系统，而是先完成“可登录、可配置、可出票、可核销、可经营、可留痕、可部署、可查看风险”的最小运营闭环。

## 2. P0 默认决策

以下默认值用于减少等待。若总控后续调整，按变更记录同步更新。

> 修订说明（2026-06-07）：本节为 **P0/P1/P2 边界的单一权威**，其他文档（master-roadmap、business-systems-breakdown、各 development-design、audit）出现的 NFC/机器人/视频/对账/企微 AI 等优先级以本节为准。统一裁决（依据《统一口径基准》D8/D9 及 finding pboundary-1~6）：
> - **NFC**：P0 仅预留设备凭证字段与界面入口；二维码核验通过摄像头/扫码模块完成，NFC 仅读取外部 NFC 腕带/标签/卡等介质，不能读取二维码；员工身份**改用设备指纹/Keystore 设备公钥凭证**（废止"读手机本机 NFC 唯一标识"，D8）；NFC 真核销接入 = **P1**；闸机/NFC 设备厂商深度联动 = **P2**。
> - **机器人**：交接留痕 = P0；**真实调度与状态联动 = P2**（android 文档原"P1 联动"统一改 P2，pboundary-4）。
> - **支付退款**：P0 做"退款/撤销记录与权益冲正 + 基础退款对账"（客人侧按订单/票发起，内部按权益冲正与金额拆分）；**复杂退款规则引擎 = P1**（D9）。见下方 TKT 退款任务。
> - **企微 AI 质检及下游 AI 分析（服务评分/履约分析/健康评分/异常解释）= P2**（基础会话同步/每日归档/基础质检为 P0）；全系统统一 **P2=平台侧深度接入、P3=AI 增强占位** 的细分，消除"同一能力既 P2 又 P3"（pboundary-1）。
> - **视频监控**：P0 仅留点位/时间/设备证据字段；真实调阅绑定 = P1；AI 异常识别 = P2。

| 市场基准增强 | P0 只承接 MDM/企业微信/支付/权限初始化等上线前置，以及商户合同关键日期、证照/资质/保险到期字段余量；商户服务工单、费用账龄、酒吧高级账单与卡座会话调整、游乐预约排队等进入 P1/P2 | 防止成熟系统对照导致 P0 范围膨胀 |

## 19. P0 完成判定

P0 不是以“页面数量”判定，而是以以下端到端链路判定：

1. 平台管理员可以登录后台。
2. 平台管理员可以创建商户、门店、区域、点位、员工、角色和权限。
2a. 平台管理员可以创建、复制、应用和撤销权限模板；临时模板能按有效期和单次有效规则自动失效并留痕。
3. 平台管理员可以创建票种、配置权益、发布票种。
4. 系统可以生成权益实例。
5. 商户员工或设备终端可以扫码预览并核销权益。
5a. 客人侧可以按订单/票发起退款，系统记录退款并对权益做冲正、进入基础退款对账（修订说明 2026-06-07 新增，pboundary-3/D9）。
5b. 客人端可以登录、购票、查票/权益、展示在线防伪二维码、订台付定金、查看积分摘要；礼物兑换独立页面和接口进入 P1。
6. 酒吧可以完成订台、定金、桌台点单、最低消费校验、账单记录、酒水权益使用和支付留痕。
6d. 酒吧正式生产入场/售酒年龄核验必须通过第三方人脸/年龄核验接口或等效设备；供应商未配置时只能测试模拟，不能生产通过。
6a. 供应链可以管理供应商、供应合同、采购周期、库房/库位、库存余额、吧台消耗、客人存酒、盘点报损和积分兑换扣库存。
6b. 平台可以创建并复核经营对象、运营主体、合同主体和结算主体的唯一绑定关系，合同、结算、权限、看板和第三方接入引用同一绑定关系。
6c. 财务可以生成、确认、收付款登记、调整和导出 P0 应收应付台账，覆盖账龄、到期日、主体、来源、差异、附件和留痕。
7. 游乐可以完成项目场次、项目容量（实时在玩人数）控制、项目核销、开放前安全巡检、阻断项暂停、整改复检、主管恢复和异常记录（原含「人工放行」，已废止·见文首口径）。
8. 第三方相关接口可访问，mock adapter、统一 Webhook、轮询校验和差异补偿框架可验收；真实供应商字段待资料到位后补齐。
9. 所有关键业务动作都有事件、审计或调用日志，并能按 P0 操作事件与证据矩阵查询。
10. 平台可以查看经营总览、商户排行摘要和风险预警；商户经营专题看板进入 P1。
11. 160 服务器可以运行前端、后端、数据库、对象存储、备份、日志和回滚流程。
12. P0 验收问题清单已形成，并能作为 P1 排期输入。
