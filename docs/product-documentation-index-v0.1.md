# 产品文档总索引与完成审计 V0.1

> **口径修订（2026-08-06 R10）：「人工放行」已废止**——ENUM「核销记录状态」条 明确「**系统不提供人工放行：核销要么成功、要么拒绝或失败，任何岗位、任何权限都不能以人工方式让一笔不满足规则的核销通过**」（DEC-CFG-2026-08-03-12 / DEC-R6-08）。本文原有的「人工放行」取值、端点、按钮、指标、权限点与复核类型**一律废止**，废止处就地标注「原含『人工放行』，已废止·见文首口径」；已实现的端点、权限点与状态取值待代码轮下线，期间不得新增调用、不得新写入。**注意**：合同或基础定义违规被卡住后「由更高级审核放行」的准入场景仍然存在，那是准入阻断的升级放行，与核销域无关，不得回读为「可以人工放行一笔核销」。

## 1. 文档定位

本文档用于汇总当前综合体管理系统的产品侧文档，确认“从总纲到平台治理，再到业务经营和支撑层”的产品拆解是否完整。

本文档不替代任何 PRD，只作为总控索引、完成审计和后续任务分派依据。

> 当前第一阅读入口为 `00-current-effective-document-entry-v0.1.md`。新接手的产品、开发、测试、运营、供应商和外部机器智能体必须先阅读该文档，再进入本文档和各模块 PRD/开发设计。
>
> 业务事实源：三个业务 HTML 拥有最终解释权；PRD、其他文档、后台配置、设计和实现均不得覆盖。会员、成长值、积分、兑换券和商户积分结算的产品细化见 `member-and-tier-product-prd-v1.0.md`、`points-and-voucher-product-prd-v1.0.md`、`merchant-points-settlement-rules-v1.0.md`，不得把这三份 PRD 写成可替代 HTML 的新权威。不以实现反向解释业务规则。

总纲已经明确：
- 系统是综合体统一管理平台，不是单点票务、酒吧或 POS 系统。
- 当前先管理一个综合体，所有核心对象预留项目归属，未来可扩展多个综合体。
- 合同核心摘要是后续业务准入依据；超出合同、空间、业态或有效期，以及资质异常时一律先阻断，阻断后未命中七类红线的事项才可按层级升级审批并留痕放行；操作人权限不足须换由具备相应权限的人办理，不设放行通道。
- 公司自有员工由本人在私人手机 App 注册、提交资料后由所属公司后台审批；商户员工由商户代该员工提交注册申请，经对应域公司（按商户所属经营域为城市项目公司、娱乐平台公司或游乐公司）批准后账号生效；商户档案标注为自营的视同公司自有。员工设备凭证绑定后，与公司发放的工作手机建立一一对应关系；私人手机不做现场业务。
- 门票和权益二维码必须具备防伪串码、签名、有效期、随机串、哈希核对和事后追溯能力。
- P0 要先建立基础档案、票/权益/核销、酒吧基础经营、游乐基础运营、第三方接入边界、事件留痕、业务过程留痕、基础结算和基础看板。
- 餐饮、零售、机器人、视频监控、企业微信等成熟能力优先第三方接入。
- 权限按“角色 + 基础模板 + 临时模板 + 员工级授予/拒绝”计算，模板可复制，临时模板支持有效期和单次有效，详见 `p0-operation-permission-matrix-v0.1.md`。
- 关键业务动作必须有事件、证据和复核路径，详见 `p0-action-event-evidence-matrix-v0.1.md`；P0 验收按 `p0-end-to-end-acceptance-and-edge-cases-v0.1.md` 执行。
- 第三方供应商未确定时不写死供应商字段，先按 `third-party-supplier-integration-kit-v0.1.md` 固化接口、适配器、映射占位、Webhook+轮询校验和补偿策略。
- 业务功能拓扑图已把平台治理、业务经营、第三方接入、证据风控、财务经营、数据分析和终端展示串成运营人员可读的总图。
- 业务人员版 HTML 已把复杂拓扑改成可点击的子系统说明页，便于完全不懂产品技术的人逐项理解。
- 市场基准建议不自动改变 P0 范围；除 MDM/Android 设备管控、企业微信配置、合规留存、支付通道、权限初始化等上线前置项外，商业地产工单/费用、酒吧高级账单、游乐预约排队等成熟系统能力默认进入 P1/P2。
