### 执行方案

**策略选择：放弃复现判定式，改为全池人工判定。**
理由：判定式不可复现（第 4 点），任何「只判命中行」的方案都建立在一个既不可验证、
又已证明 13%–58% 误报的过滤器上；而 667 行「未命中」的阴性从未被人复核过一行。
既然 669 和 667 只差 2 行，**过滤毫无收益，直接全判**。这同时一并解决 `BEQ-0117`、`BSM-0099`。

**判定标准（沿用 final §T1，不新造口径，只补两条）**

回填条件（满足任一，且必须是**实体陈述**而非提及）：
- (a) 资金／权益的**归属或流向**（谁的钱、归到哪、按什么份额分）
- (b) **费用或成本由谁承担**
- (c) **金额如何入账／结算／冲正／收付／计费**（含税率、费率、单价、上下限默认值）

判无钱路（沿用 §T1 八类，逐条留理由）：
① 状态或方式枚举名；② 功能清单与模块连接句；③ 留痕字段清单与证据要求；
④ 审批层级、复核强制项与不相容职责；⑤ 对账核对与差异处理机制（不陈述金额归属）；
⑥ 流程前置要求（未及款项归属／计算／处置）；⑦ 积分与成长值的计算人次口径；
⑧ 通知义务与异议期起算。

补两条（本方案新增，理由随附）：
- ⑨ **可配参数的「须配上下限／须经三审」这类治理要求，如果同句同时给出了法定/默认取值
  （如 `BEQ-0117` 的「出厂默认 20%」），按 (c) **回填**；只讲配置流程不给取值的不回填。
  ——`BEQ-0117` 正是这一类，不补这条它会被判成「④审批层级」而漏掉。
- ⑩ **HTML 现文已删该口径的行**（source_text 已被门禁⑤实检对齐现文），按现文判，
  不得按记忆中的旧口径回填。——`BSM-0099` 正是这一类。

**回填值的硬约束（沿用 sync1/final，不得放松）**
回填值必须是该行 `source_text` 的**逐字连续子串**，脚本逐行 `assert`。
不连续拼接一律不许（final §T2 已证明拼接格是漂移温床，6 格全部返工）。
**只写 `value_flow` 一列**，其余 17 列一个字节不动。

### deferred 安全性

**为什么本轮不做它，不会让本轮的 PRD 修复出错：**

1. **`value_flow` 列不是 PRD 修复的输入。** 本轮 PRD 修复的输入是
   `rounds/final/code-round-input-money.md` / `code-round-input-nonmoney.md` 两份报告
   与 `html-prd-coverage.csv`，都不消费 `authority-rule-ledger.csv` 的 `value_flow` 列。
   账本该列的唯一下游是审计自身的钱路盘点。
2. **禁令已在位且是「保守方向」。** SYNC1-01 与 FINAL-05 两处 disposition 都明写
   「不得据该列缺值推断『HTML 未写钱路』」。这条禁令使缺值**只能导致漏查、不能导致误改**：
   任何 agent 看到 `NOT_STATED` 都不许下「HTML 没写钱」的结论，只能回去读 HTML 原文。
   本轮 PRD 修复一律以三份 HTML 现文为准，账本只作索引。
3. **缺值是「保守缺失」不是「错误断言」。** 784 行里没有一行写了**错的**钱路，
   全是空着。空着的最坏后果是某条钱路没被本轮盘到——这是**下一轮补得回来**的，
   不会让本轮改出一条与 HTML 相悖的 PRD。
4. **唯一真实风险已单独隔离。** `BEQ-0117`（分红代扣个税 20%）是本次复核新发现的、
   确凿的钱路缺值，且它**从未被扫过**。它已在本 shard 点名，本轮 PRD 修复若触及分红税务，
   必须直接读 ENUM 现文而不是查账本——这一条已足以堵住本轮的具体口子。

### 风险

- **【高】判定式不可复现导致口径漂移。** 五个 agent 各判一批，即使给同一套 ①–⑩，
  边界案例仍会不一致。缓解＝R2 交叉复核只复核 `NO_MONEY`（假阴性是这项的主要风险，
  假阳性有脚本断言兜底）。
- **【高】并发写同一 CSV。** 五批可并发**判定**，但**写回必须串行**。
  账本是 CRLF+BOM 单文件，两个 agent 同时原位改单元格必然互相覆盖。
  参照记忆铁律「complex_test 共享库迁移代理不能并发」，此处同理。
- **【中】`NO_MONEY` 无机检兜底。** `FILL` 有「逐字连续子串」断言，`NO_MONEY` 没有任何
  机器可验证的东西——它只是「保持原值 + 一句理由」。这意味着一个偷懒的 agent 可以把
  整批判成 `NO_MONEY` 而所有门禁全绿。R2 交叉复核是唯一防线，**不可省**。
- **【中】与 G-2 耦合。** 若 G-2（镜像列机检）先落地并触发新一轮 `source_text` 重取，
  已回填的 `value_flow` 会再次漂移。**建议 G-2 先做、G-1 后做**；
  若并行，G-1 收口时必须重跑一次「逐字连续子串」全表断言。
- **【低】35 行 `NOT_EXTRACTED_R9` 被误并入。** 那是另一个哨兵值、另一笔欠账。
  任何脚本必须用 `== "NOT_STATED"` 精确匹配，不得用 `startswith("NOT_")`。

**3. `PGM-0243`「去空格改写版」失效模式——重跑实证**

`rounds/b6/worklog.md:397` 原文：

> **漏网原因**：三裁的账本同源重取用的是与 HTML **完全一致**的替换串
> `公司持股超过 51%（业务参数，…）的商户视同公司自有`（`51%` 前后带空格）；
> 而该格是早期抽取时写下的**去空格改写版** `公司持股超过51%的商户视同公司自有`，
> 既不含括注、也没有空格，故整行替换零命中。

拿真实历史 HTML 跑那个陈旧串：

```
$ node /tmp/g2b.mjs
PGM@r9(3bff6692)     : 含「去空格改写版」? true
PGM@regext(d9c48602) : 含「去空格改写版」? true
PGM@b6pre(a0d805d9^) : 含「去空格改写版」? true
PGM@head(1c5c0c7d)   : 含「去空格改写版」? false
```

**结论——这是本项最关键的一条，它决定选哪条路线：**

「去空格改写」打败的是**同源重取／替换脚本**（那类脚本必须精确匹配旧串，
少个空格、少个括注就零命中，而且**零命中不报错、静默跳过**）。
它**打不败 containment 门禁**——因为 `norm()` 两侧都剥空白，去空格版照样能命中。

所以门禁的抓法根本不是「识别同义改写」，而是**换个问题问**：

> 替换脚本问的是「旧串长什么样、能不能替掉」→ 改写过就抓不住；
> containment 门禁问的是「这格的字**现在**还在不在 HTML 里」→ **不需要知道旧串长什么样**。

`PGM-0243` 的时间线正好证明这一点：`b6pre` 时那格 `true`（门禁应绿——那时 51% 口径确实还在
HTML 里，账本没错）；`a0d805d9` 一废除 51% 门槛，同一格立刻变 `false`（门禁应**当场红**）。
而实际发生的是：替换脚本零命中、静默跳过，门禁⑤ 不检 `preconditions`，
于是**整整一轮无人发现**，直到人工复核 NEEDS_FIX 才捞出来。

**这就是必须纳入的用例**（见下「反向测试」）。

### 规模判据

满足 3 项：

1. **涉不可自动裁决的数据模型** —— `trigger` 列 547 格是合成描述、其余 8 列是逐字片段，
   同一张表里两种语义混存，schema 上没有任何字段区分，要么改 schema 要么定例外规则。
2. **需逐项人工语义判定** —— `trigger` 的 316 个失配格无法机械分类为「合成」还是「漂移」；
   路线②（镜像列不存正文）更是要对 1718 格逐格重新定义存什么。
3. **>100 独立证据单元** —— 路线① 若不豁免 `trigger` 则 344 格待判；路线② 则 1718 格。
   （若采纳推荐方案 = 路线① 豁免 `trigger`，实际待清只有 5–28 格，**这部分本身不是大工程**，
   大工程的是 `trigger` 列的定性和路线② 的全表重构。）

### 执行方案

#### 路线①：给门禁加镜像列实检

**改动面**

- `tools/verify-entry-anchors.mjs`：在检查④ 循环里，把现有 4 行的 `source_text` 检查
  改成对 `MIRROR_COLS` 数组循环。新增代码约 25–35 行，无新依赖。
- 需要三个新规则：
  - **(i) 片段级而非整格**：切分符 `。；｜|` 与**连续空白**，每片 `norm` 后 ≥12 字才检。
    理由：实测把整格失败 108 降到 87，非 `trigger` 从 22 降到 5；
    账本里确有「多段逐字摘录用空格拼接、HTML 侧两段之间另有他句」的合法格
    （final §T2 点名 6 格 + 另 22 格），整格口径会把它们全判红。
  - **(ii) `trigger` 列豁免**：改用弱检——只要求 `trigger` 不等于同行 `source_text`
    （现有 127 格违反，须先清）。逐字检对它无意义。
  - **(iii) 长度阈值 ≥12 字**：低于此的短片段在 6 万字 HTML 里必然偶然命中，
    检了等于没检。阈值必须写进脚本注释并说明理由。
- 数据侧：先清 5 格（片段级、非 trigger），门禁才能落地即绿。

**风险**

- **【中】阈值即盲区。** ≥12 字以下、和 `trigger` 全列，仍然无机检。
  必须在门禁 PASS 文案里**明写豁免范围**（照检查⑤ 现有做法：
  「未登记条目不在保护范围，见 R8-U-02」），否则下轮又出「以为检了其实没检」。
- **【中】偶然命中假阴性。** containment 只问「在不在」，
  一格从 A 条抄到 B 条、两条都在同一份 HTML 里，门禁照样绿。这是 containment 的固有上限。
  升级路径＝把比对范围从「整份 HTML」收窄到「该条目正文」（脚本里已有 `flatEntry()` 现成可用），
  但那要求 `line_now` 准确，会把门禁和注册表行号耦合回去——**本轮不做，记为已知上限**。
- **【低】性能。** 1718 格 × `String.includes` 于 6 万字符串，毫秒级，不成问题。

**工作量**：1 agent × 1 轮。脚本 30 行 + 清 5 格 + 反向测试。

#### 路线②：镜像列不再存正文片段

**改动面**

把 9 列从「存 HTML 正文片段」改成存**指针或受控值**，两种子方案：

- **②-a 存偏移**：每格存 `source_text` 内的 `[start,end)` 字符区间（如 `12-58`）。
  漂移不可能发生（`source_text` 本身受检查⑤ 保护）。
  代价：**1718 格全部重算**；账本从「打开就能读」变成「必须跑脚本才能读」——
  而这份账本的主要读者是**人**（审计 agent 逐行读语义），可读性是它的核心用途。
- **②-b 存受控词表**：如 `value_flow` 只填 `INFLOW`／`OUTFLOW`／`SPLIT`／`NONE` 之类。
  代价：**1718 格全部重判**（不是重算，是重新做语义判定），
  且会**丢失信息**——现有 406 个 `value_flow` 里的具体金额口径无处安放。

**风险**

- **【高】全表重构 + 与 G-1 直接冲突。** G-1 正要回填 669 格 `value_flow`；
  若同期改 schema，G-1 的 669 格白填。两项**不能并行**。
- **【高】可读性倒退。** 见 ②-a。
- **【中】下游 992 处 Markdown 引用**（门禁自报）里若有引账本单元格文字的，全部要跟改。

**工作量**：②-a 约 3 agent × 2 轮；②-b 约 6 agent × 2 轮（等同重做一遍全表抽取）。

#### 推荐：**路线①，且限定为「8 列片段级 + `trigger` 弱检 + 阈值 ≥12 且写明豁免」**

理由，按分量排：

1. **成本差两个数量级。** 路线① 是 30 行脚本 + 清 5 格（1 agent × 1 轮）；
   路线② 是 1718 格全表重构（3–6 agent × 2 轮）。
2. **路线① 对 `PGM-0243` 那一类失效模式是完全免疫的**（上文实证）：
   它不需要知道旧串长什么样，只问「现在还在不在」。而这正是本项唯一有实证的失效模式。
3. **路线② 解决的是一个没有实证的问题。** 没有任何一条记录显示漂移是因为
   「镜像列存了正文」这个**存储形式**造成的；漂移全部是因为**没人检**。
   把存储形式改掉是在治症状不治病根——病根是门禁少检了 9 列。
4. **实测数据不支持路线② 的前提。** 「镜像列存正文所以必然漂移」若成立，
   非 `trigger` 列的失配率应该很高；实测是 **5/886 = 0.56%**。
   8 个列里 7 个列已经事实上保持了逐字同源，没有推倒重来的理由。
5. `trigger` 一列的确该按路线② 的思路处理（它本来就不是逐字列），
   但**只需要在文档里承认这一点 + 加一条弱检**，不需要改 schema。

**反向测试（必须做，否则等于没加门禁）**

记忆铁律「门禁注册≠会执行 / 反向测试必须从含该门禁的分支切」在此适用。三条用例：

| # | 用例 | 造法 | 期望 |

**2. 机检算法已找到、可复算，但它证明不了承接**

脚本在本机 `D:\AI\ccwork\prd-audit-r8\scripts\find_prd.py`（R8 报告点名的那一份），核心 10 行：

```python
NOISE = re.compile(r"[\s*`_>#\-|\[\]]+")   # markdown 标记与空白一并去掉
norm  = lambda s: NOISE.sub("", TAG.sub("", s))

def probe(text, topn=3):
    t = norm(text)
    shingles = [t[i:i+14] for i in range(0, max(1, len(t)-14), 7)][:24]
    score = {}
    for name, body in corpus.items():
        s = sum(1 for sh in shingles if sh and sh in body)   # 只数「在不在」
        if s: score[name] = s
    return len(shingles), sorted(score.items(), key=lambda x: -x[1])[:topn]
```

判定规则（`ledger-rebuild-report.md:229` 原文）：

> **命中片段 ÷ 取样片段 ≥ 0.5 记 FULL，>0 且 <0.5 记 PARTIAL**

**这个算法的四个结构性盲区（前两个是致命的）：**

- **(i) `[:24]` 取样上限——长条目只看开头 175 字。**
  窗口 14、步长 7、最多 24 片 → 取样覆盖 **最多 (24−1)×7+14 = 175 个归一字符**。
  实测：45 条 PARTIAL 里 **27 条**（60%）触到这个上限，
  被截掉、**完全没参与判定**的字符合计 **7614 个**；`source_text` 归一后长度中位数 219、最长 2846。
  一条 2846 字的规则，判定只看了它的前 175 字（6.1%）。
- **(ii) 无序袋装匹配（bag of shingles）——不要求相邻、不要求同段、不要求同章。**
  24 个 14 字片段可以散落在一份三千行 PRD 的任意角落，命中 12 个就判 FULL。
  **PRD 在「背景」章里原样引一遍 HTML 而正文里什么都没实现，同样满分。**
- **(iii) 步长 7 < 窗口 14，相邻片段重叠 50%**，命中高度相关；
  分母写 24，实际独立样本约 12。所以 0.5 这个门槛比表面上更宽。
- **(iv) 尾部 <14 字永不取样**（`range(0, len(t)-14, 7)`），
  规则末尾的例外条款、上下限、兜底句正好是最容易被漏承接的部分。

结论：**这套机检只能回答「这份 PRD 里出现过这条规则的字面」，
不能回答「这条规则的口径被 PRD 完整、正确、无矛盾地承接了」。**

### deferred 安全性

**为什么本轮不做它，不会让本轮的 PRD 修复出错：**

1. **`PARTIAL` 本身就是「未确认」标签，方向保守。** 它不声称承接了，
   它声称「机检看见了字面、没人逐句核过」。任何 agent 读到 `PARTIAL`
   都不能据此认为 PRD 已正确承接，只能回去读 HTML 原文——
   与本轮「三份 HTML 现文为唯一真源」的作业方式一致。
2. **`recommended_change` 已把处置写在行内。** 43 条明写「需逐句核验并补齐缺口口径。」，
   另 2 条（`BSM-0540`／`BSM-0541`）已给出具体改法与 P1 finding。
   本轮若碰到这些条目，行内就有指引，不会走错。
3. **这 45 条的性质是「PRD 可能缺口径」，不是「PRD 写错了」。**
   缺口径的后果是漏做功能，不是做反功能。而本轮 PRD 修复是**按 HTML 补齐 PRD**，
   补的方向与这 45 条要查的方向**同向**——本轮改 PRD 只会缩小这 45 条的缺口，不会扩大。
4. **两条已知的真缺口已带 P1 落地指引，本轮可以直接顺手修**：
   `BSM-0540`（结算 PRD 未承接「允许尾数集合为业务参数、可配」，R8-F03）、
   `BSM-0541`（积分结算规则未承接「滚动取价窗口须配上下限」与「空窗口自动向前延长」，R8-F04/F05）。
   这两条不必等专项批。
5. **本轮真正需要警惕的不是这 45 条 PARTIAL，而是那 12 条 FULL**（第 3 点）。
   它们的绿标会让本轮 agent 直接跳过。**已在本 shard 逐条点名并给出未取样比例**，
   本轮若触及 `BEQ-0151/0152/0154/0156/0157`、`BSM-0534/0536` 这 7 条，
   **不得凭 FULL 标签跳过，必须回读 HTML 现文**。这一条足以堵住本轮的具体口子。

### 风险

- **【高】12 条 FULL 是「已确认」假象，比 45 条 PARTIAL 危险。**
  实测 7/12 触到取样上限、5/12 超过一半正文未参与判定，且集中在钱路条目。
  绿标的作用就是让人不再看。**建议本轮就把这 12 条降级或加注**，
  不必等专项批——这是本项 deferred 里唯一我建议**不要**完全 defer 的部分。
- **【高】抽查证伪率 100%。** R8 只抽查了 6 条，6 条全部证伪
  （`R8-F01`～`R8-F06`）。这是本项唯一的实证样本，样本量小但方向明确：
  **不能假设剩下的大多是好的**。
- **【中】ENUM 条目占 41/45，是钱路取值高浓度区。**
  票种、券三类、结算主体、税率、服务费、最低消费、分红税务——
  这些条目一旦 PRD 没承接完整，缺的就是具体数值和边界，直接影响钱。
- **【中】「逐句核验」本身可能退化。** 一个 agent 可以把 45 条全判 `FULL` 而所有门禁全绿
  （矩阵没有任何机检能验证语义承接）。缓解＝上述「四条硬规矩」中的第 1、2 条
  是**可机检的行为约束**（`conflict_summary` 非空、`prd_anchor_or_line` 无占位串），
  它们不能验证判断对不对，但能验证**有没有真去看**。
- **【中】与 G-1／G-2 抢同一批文件？** 不抢。G-1／G-2 改 `authority-rule-ledger.csv`，
  G-3 改 `html-prd-coverage.csv`，两份不同。但门禁④⑥ 会交叉校验 `entry_name` 与
  `rule_id` 一一对应，**任何一侧动了行都要重跑门禁**。三项串行最稳。
- **【低】`prd_path` 本身可能错配。** R8 报告 §4.3 已发现 5 行错指到
  `business-decision-log-v0.1.md`（决策日志不是 PRD）并已改指。
  核验时若定位不到，先怀疑 `prd_path` 而不是直接判 `MISSING`。
