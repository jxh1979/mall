## M1 整体说明（overview）

### F1.1 系统管辖范围三段式摘要
- 模块：M1 整体说明
- 功能名称：管辖范围说明（先管基础盘子 / 再管经营动作 / 最后管结果）
- 页面：`section#overview`（L503）
- 用户流程：阅读理解，无操作流程
- 页面元素：`h2`（L504）、`p.lead`（L505）、`div.summary-grid` 三栏（CSS 三列，L172–L177）内三个 `div.summary-box`（L507–L518）
- 交互：静态
- 输入：无
- 输出：三段职责边界：①基础盘子＝哪个综合体、谁在经营、在哪经营、签了什么合同、谁能操作、谁负责；②经营动作＝客人从哪买票、产生什么权益、在哪核销、酒吧如何点酒、酒水物品如何消耗、游乐如何履约；③结果＝收入、退款、核销、会员积分、异常、对账、结算、商户表现和经营看板
- 状态：无
- 权限：无
- 异常：无
- 依赖：L505 明确「当前先管理一个综合体，但系统要按未来多个综合体统一管理来设计」——这是 M5 基础管理多综合体扩展要求的上位依据
- 证据位置：`L505 · 综合体里不是只有一个业务`

### F1.2 全局原则：业务策略一律可配置（含版本化与追溯规则）
- 模块：M1 整体说明
- 功能名称：可配置原则 + 涉钱配置版本化 + 生效日期 + 追溯例外
- 页面：`section#overview` 内 `p.lead#principle-configurable`（L520，带独立 id，可被外部锚点引用）
- 用户流程：运营/财务在后台改配置 → 存为草案 → 填写生效起始日期 → 高敏权限「转正」审批 → 按指定日期生效
- 页面元素：（推断）后台各配置页的参数项、版本列表、生效日期字段、草案/转正状态标识
- 交互：（推断）编辑参数 → 保存草案 → 提交转正审批 → 审批通过后按日生效
- 输入：税率与计税档位、提成与分账比例、费率（物业费/租金/分摊）、退款与授权额度上限、预警阈值、有效期与提醒天数、评分权重；每项须填写取值上限与下限、生效起始日期
- 输出：新的配置版本；单据生成时把所用配置版本固化在单上
- 状态：草案 → 已转正待生效 → 已生效；配置版本的历史版本仍对生效日之前的业务适用
- 权限：有权限的运营/财务人员可编辑；「转正」须高敏权限审批；追溯到生效日之前属例外，须单独申请并经**最高权限**审批
- 异常：①未填写上下限的参数**不得上线**；②超出上下限区间的配置**一律拒绝生效**；③不即改即生效；④重新月结只重算金额、不改单据上已锁定的版本；⑤重新月结**不因账目计算出错发起**，只由实际业务事件触发（冲账、客人退款、多付少付、货款出错）；⑥无法判断是否涉及钱的一律按涉及钱处理
- 依赖：约束全系统所有涉钱参数；与 M6 票务规则版本、结算版本固化直接耦合
- 证据位置：`L520 · 一条贯穿全局的原则：业务策略一律可配置`
- 明确的**非可配范围**（同样在 L520）：技术性内部运行参数不在此列；**业务分类定义不在此列**——红线有哪几类、退款有哪几种情形、会员有哪几个等级、终端有哪几类、合作模式有哪几种等「有哪几种」的清单属业务口径本身，不做后台可配，增删必须先经批准写入三份 HTML，不得后台自增删。可配的只是阈值、比例、时长、次数、金额、时刻、档位取值这类策略参数；每处可配参数须标明属法定值/安全阈值/业务参数及配置粒度

## M2 一笔业务怎么走（journey 主流程）

### F2.1 客人买票并进场消费五步主流程
- 模块：M2 主流程
- 功能名称：端到端主流程说明（5 步）
- 页面：`section#journey`（L523）
- 用户流程：①客人看信息 →②下单购票 →③生成并履行票务权益 →④现场核销/点酒 →⑤库存、财务和看板
- 页面元素：`h2`（L524）、`p.lead`（L525）、`div.journey` 五列网格（CSS L192–L197）内 5 个 `div.step`，每个含 `.step-number` 圆形序号 +`strong` 标题 +`span` 说明
- 交互：静态展示（无点击跳转）
- 输入：无
- 输出：五步口径——
  1. **客人看信息**（L529）：在 App、小程序或 Web 上看票、套餐、游乐项目、酒吧规则
  2. **下单购票**（L534）：门票主路径客人自助（官方 App/小程序或第三方平台）；单店门票客人自助；少量到店场景授权服务人员在启用售票能力的一体机辅助购票
  3. **生成并履行票务权益**（L539）：一张票可拆成入场、游乐、赠饮等权益；票务系统记录订单、支付、履约、退款、冲正和核销事实；**会员与等级系统据此算票务成长值，积分系统据此算票务积分**
  4. **现场核销/点酒**（L544）：工作手机扫客人二维码核销；酒吧平板绑定卡座后点酒下单
  5. **库存、财务和看板**（L549）：订单、核销、退款、酒吧账单、库存消耗、存酒、积分、第三方回流进入对账和经营看板
- 状态：无（说明性）
- 权限：无
- 异常：原文未在本节描述异常分支（异常口径见 M6/M8 及 L940 之后的 #risk 章）
- 依赖：串联 M6 票务、M7 客人端、M8 平板/工作手机、以及 L940 之后的酒吧管理/供应链/财务对账/经营看板
- 证据位置：`L534 · 下单购票（步骤 2）`

## M3 系统通用能力（common-abilities）

> 章节定位（L557）：「下面这几条不属于某一个子系统，而是整套系统都遵守的通用规则。」

### F3.1 配置数据存档（先下线）
- 模块：M3 通用能力
- 功能名称：配置类主数据存档 / 取消存档
- 页面：后台各配置页；另设**「已存档内容」页**（L562 明确）
- 用户流程：发现配错或暂不用 → 点「存档」→ 从各处选择列表隐藏 → 需要时点「取消存档」恢复
- 页面元素：「存档」按钮、「取消存档」按钮、「已存档内容」页（按分类查阅、可逐条恢复）
- 交互：点击存档/取消存档；批量存档触发审批
- 输入：存档对象；**存档理由必填**（L569、L570 两处均明确「存档及删除都需要填写理由」）
- 输出：对象从新业务选择列表隐藏；历史仍可查、可对账
- 状态：正常 / 已存档；适用对象＝商户档案、票种、价格规则、酒吧商品/分类/套餐等配置类主数据（L560）
- 权限：**逐条存档属日常操作，不用审批**；一次性存档超过后台配置条数的、或整店整类存档的，须经审批后执行（**业务参数，按综合体可配，须同时配置上下限**）
- 异常：已存档的票种、商品等不能再被下单、配价、组套餐——杜绝「明明下线了还能卖出去」（L566）
- 依赖：与 F3.2 删除、F3.4 删前占用检查串联
- 证据位置：`L562 · 存档（先下线）`

### F3.2 配置数据删除（走审批 · 软删除）
- 模块：M3 通用能力
- 功能名称：申请删除 → 审批 → 软删除
- 页面：后台各配置页 + 审批页
- 用户流程：**先存档 → 再「申请删除」→ 填写删除理由 → 具备最高权限的人审批通过 → 执行**
- 页面元素：「申请删除」按钮、删除理由输入框、审批单
- 交互：提交申请 → 审批人处理
- 输入：删除理由（必填）
- 输出：数据转入后台留存、前台各处不再显示；**数据始终留在库里可查、可审计、可恢复**；按分类（票种、商品、商户、员工、设备、工单、预订等）分门别类归拢
- 状态：已存档 → 申请删除中 → 已删除（软删除，可恢复）
- 权限：须**具备最高权限的人**审批；**申请人不能审批自己的申请**（L563、L569、L570 三处重申）；**持授权 U 盘密钥的最高权限本人发起的操作，不需要经过任何审批**（L569、L570）
- 异常：删前自动查占用——系统自动检查是否被合同、账单、结算、订单、已发权益、库存等占用，**只要还有占用就拦住不让删**（L565）
- 依赖：F3.1 存档为前置；与 F3.5 数据清理工具同源审批规则
- 证据位置：`L563 · 删除（走审批·软删除）`

### F3.3 交易类数据只存档不删
- 模块：M3 通用能力
- 功能名称：钱账数据删除禁止规则
- 页面：后台订单/核销/结算流水/账单相关页
- 用户流程：需要纠错 → 走**冲正**，不走删除
- 页面元素：（推断）这些页面不提供「申请删除」入口
- 交互：仅允许存档
- 输入：无
- 输出：交易类数据永久保留
- 状态：只有「存档」态，无「已删除」态
- 权限：任何权限均不可彻底删除
- 异常：**出于税务与审计留存要求**，纠错走冲正而不是删除（L568）
- 依赖：与 M6 票务退款冲正、财务对账口径一致
- 证据位置：`L568 · 交易类只存档不删`

### F3.4 删前自动查占用
- 模块：M3 通用能力
- 功能名称：删除前占用校验
- 页面：后台删除入口
- 用户流程：点击删除 → 系统自动检查占用 → 有占用即拦截
- 页面元素：（推断）占用拦截提示
- 交互：自动触发，无需人工发起
- 输入：待删对象
- 输出：可删 / 拦截
- 状态：有占用 / 无占用
- 权限：不可绕过
- 异常：占用来源明确列举——**合同、账单、结算、订单、已发权益、库存**；目的是「避免删出一堆'找不到主人'的记录」
- 依赖：横跨合同、票务、结算、库存各系统
- 证据位置：`L565 · 删前自动查占用`

### F3.5 集中数据清理工具
- 模块：M3 通用能力
- 功能名称：「数据清理工具」页（批量清理）
- 页面：后台**「数据清理工具」页**
- 用户流程：选清理范围（**已存档、且超过设定天数的配置数据**）→ **先「试运行」预览会删掉多少条** → 提交 → 具备最高权限的人审批 → 批量清理
- 页面元素：清理范围选择器、天数设定、「试运行」按钮、预览条数、提交按钮、审批单
- 交互：试运行（只读预览）→ 正式提交 → 审批 → 执行
- 输入：清理范围、存档天数阈值、理由
- 输出：批量清理结果；**全程留痕**
- 状态：试运行 / 待审批 / 已执行
- 权限：**须具备最高权限的人审批通过后执行，不设例外，申请人不得审批自己的申请**；持授权 U 盘密钥的最高权限本人发起的不需要任何审批
- 异常：**绝不碰在用的活数据**
- 依赖：F3.1 存档态、F3.4 占用检查
- 证据位置：`L569 · 集中数据清理工具`

### F3.6 业务记录也能存档删除
- 模块：M3 通用能力
- 功能名称：业务记录的存档与审批删除
- 页面：员工档案页、设施设备页、商户服务工单页、卡座预订页
- 用户流程：同 F3.1/F3.2
- 页面元素：存档/申请删除入口、理由输入
- 交互：存档不用审批；删除走审批
- 输入：理由（必填）
- 输出：存档/软删除结果
- 状态：正常 / 已存档 / 已删除

| # | 红线内容 | 最高权限（持 U 盘密钥）可否逐笔开放 |
|---|---|---|

### F6.14 渠道费两层结构与域间拆分顺序
- 模块：M6 票务权益
- 功能名称：通路费 / 销售渠道费两层扣除 + 跨域分配
- 页面：（推断）后台结算配置 + 分账明细
- 用户流程：整单收款 → 扣通路费 → 扣销售渠道费（如经第三方渠道）→ 扣积分发行成本 → 按各业态价格占比分到各域
- 页面元素：（推断）分账明细、合同版本字段
- 交互：系统自动分账
- 输入：整单金额、渠道类型、合同版本
- 输出：各域份额
- 状态：**域内通票不按经营域比例拆分**——酒吧通票按酒吧域规则结算，纯游乐通票按游乐域规则结算
- 权限：渠道合同**只能约定佣金费率、收付款方式和对账方式，不得改变承担方式**
- 异常：**零元免费权益不参与域间分配，酒吧域份额不得再次扣渠道费用**
- 依赖：F6.17 可分配池、F6.19 定价构成、F6.36 退款逐段冲回
- 证据位置：`L741 · 域内通票不按经营域比例拆分`
- 两层费用定义（性质不同**不可混用**）：
  - **通路费**：银行、微信、支付宝等**支付通路**收取，**所有支付都会产生、官方渠道同样产生**
  - **销售渠道费**：第三方售票平台佣金，**只有经第三方渠道售出才产生**，在通路费之上再扣一层
  - 共同规则：**一律在拆分给各域之前从整单扣除且只扣一次**，由各域按分配份额**自然共担**、不由该笔业务的收款主体单独承担，域内通票同样适用；**官方渠道售出的票不扣销售渠道费，但仍扣通路费**；每笔分摊须记录所用合同版本
  - **票务订单产生的积分发行成本**：同样在域间拆分之前从整单扣除且只扣一次
  - 跨域组合通票扣完上述两项后，**再按各业态价格占比分到各域**——各业态价格在**售票时刻随订单一并固化、事后不得变更**
  - **餐饮与零售的域主管公司为城市项目公司**（与内部结算价审批、业态归属口径一致），其份额由跨域组合通票的**收款主体（娱乐平台公司）直接与实际提供的餐饮、零售商户结算**
- 修订注释：`L740 · 2026-08-04 第三轮用户裁决（DEC-R6-01）`——与 ENUM 同步：渠道费分通路费/销售渠道费两层，均在拆分给各域之前从整单扣除、由各域按分配份额自然共担；官方渠道免销售渠道费但仍扣通路费

### F6.17 酒吧通票可分配池与两段分配
- 模块：M6 票务权益
- 功能名称：可分配池金额计算 + 两段分配 + 未核销减除 + 事前超池试算
- 页面：（推断）后台票种配置的分配规则页 + 结算明细
- 用户流程：售票时固化池金额 → 第一段按固定金额/固定单价分配 → 余额按排名档位分配 → 未核销酒吧按规则减除 → 余额进入分配
- 页面元素：（推断）第一段配置、第二段排名档位配置、试算入口
- 交互：配置前**必须先按该票种的可分配池金额试算**
- 输入：固定金额/固定单价、排名档位比例、赠送权益预估成本口径（**按件计**或**按票计**，按票种配置）
- 输出：各酒吧分配金额；未分配池余额
- 状态：**池金额在售票时随订单固化**
- 权限：娱乐平台公司确需让第一段合计高于池金额的，须在**配置生效前**提交**短期经营激励申请**并经**项目之上的平台权限**审批
- 异常：①**试算不通过的配置不得生效**；②**超池的判定与审批一律在事前完成，结算环节不再设「超池待审批」**；③超出部分由**娱乐平台公司承担**；④**单次激励期限不得超过后台配置的上限（业务参数，按项目可配，出厂默认三个月），期限届满须重新提交审批，不得自动续期**；⑤**没有第一段对象则全池进入第二段**；⑥**没有合格第二段对象或权重为零时，余额单列为未分配池余额并归娱乐平台公司**
- 依赖：F6.14 渠道费扣除、F6.20 门票综合服务费
- 证据位置：`L744 · 酒吧通票可分配池`
- 池金额公式（L744 原文）：池金额 ＝ 该票**扣完第三方渠道费用、票务积分发行成本**后拆出的**酒吧份额**，再扣掉**赠送权益预估成本**与**门票综合服务费**后的剩余
  - **赠送权益预估成本**：按件计＝票面各权益数量 × 提供方内部结算价之和；按票计＝该票种赠送部分售价整额；**该笔预扣归娱乐平台公司，预扣数与实付数的差额也留在娱乐平台公司**
  - **门票综合服务费**：与「娱乐平台公司留存」「项目管理费」**是同一笔钱，全程只扣一次、不在池内再扣**
- 两段分配规则：第一段按固定金额或固定单价分配，余额再按排名档位分配，**第一段对象不参加第二段**
- 未核销酒吧减除规则：**可分配池只在实际发生核销的酒吧之间分配**——本张通票覆盖但当期未被核销入场的酒吧不参与分配；该酒吧若参加第一段，先按第一段的固定金额或固定单价减除；剩余部分按该酒吧在第二段排名档位所对应的比例减除，**减除后的余额才进入分配**

### F6.19 综合/联合通票定价构成与凑整

### F6.20 门票综合服务费
- 模块：M6 票务权益
- 功能名称：娱乐平台公司门票综合服务费
- 页面：后台票种发布配置（按物理项目维护）
- 用户流程：票种发布前先选定计费方式并填数值 → 售票 → 计收服务费 → 退款时同比例退回
- 页面元素：计费方式选择（按比例 / 按固定金额，**两种方式互斥**）、数值输入、月度封顶配置
- 交互：发布前强制选定
- 输入：比例或固定金额；月度封顶
- 输出：服务费金额
- 状态：**只适用于酒吧相关票务并归娱乐平台公司**；**纯游乐票、纯游乐通票和演出票不收取**
- 权限：（推断）票务/财务配置权限
- 异常：**未选定或未填写的票种不得发布上架**；单一酒吧门票的综合服务费**按物理项目分别维护，初始为空、不自动继承酒吧通票的默认比例**
- 依赖：F6.17 池金额（同一笔钱只扣一次）、F6.33 收款主体
- 证据位置：`L747 · 门票综合服务费只适用于酒吧相关票务并归娱乐平台公司`
- 单一酒吧门票收入规则：由**酒吧商户定价、销售并确认已核销部分的门票收入**；**票款由娱乐平台公司统一收款后结付**；**到期未核销部分不归酒吧商户、按未核销票款规则归娱乐平台公司**；娱乐平台公司**不取得已核销门票的收入**，只按每张票的比例或固定金额另收综合服务费
- 计费基数：按比例收取时，基数一律是**该张票订单上保存的最终选中价（客人实付价）**，**不使用基础价或动态价，也不先扣第三方渠道费用**；该张票退款时**已计收的综合服务费按实退金额同比例退回**
- 封顶规则：单一酒吧门票**可设月度封顶**；**酒吧通票和跨域组合通票中的酒吧部分也可按生效规则收取，但不得封顶**
- 现场收款规则：单店门票**以现金或刷卡方式在现场收取的**，票款**当场计为该酒吧商户对娱乐平台公司的应付款，按三个付账日结清**；该票的门票综合服务费**另行单独收取，同样走三个付账日**
- 内部往来规则：**平台内部各主体之间的应收应付，一律按总额收付、收支两条线，不得轧差——因涉及税务处理**

#### F6.41 权益转赠
- 模块：M6 票务权益 / 核销规则表
- 功能名称：完整权益单位转赠 + 确认领取 + 竞态处置
- 页面：客人端转赠页 / 领取页
- 用户流程：持有人发起转赠（微信、二维码、手机号）→ 接收人打开 → **点击「确认领取」** → 权益归接收人
- 页面元素：转赠入口、转赠链接/二维码、**「确认领取」按钮**
- 交互：发起转赠 → 确认领取；先到先得
- 输入：转赠方式（微信 / 二维码 / 手机号）
- 输出：权益归属变更
- 状态：**发起转赠后不冻结该权益**——在接收人点击「确认领取」之前，原持有人仍可自己使用，也可再次转赠给其他人
- 权限：**手机号转赠只允许被指定的人确认领取**；**微信链接或二维码允许多人打开，由最先点击「确认领取」的人取得权益**
- 异常：
  - **仅打开转赠页面不算领取**
  - **转赠链接由持有人自行发出，其后被转发导致他人领取的风险由持有人自负**
  - 竞态处置：接收人确认领取、原持有人自行核销、原持有人再次转赠——**以先处理成功的那个动作为准，其余动作自动失效并提示**；确认领取后权益归接收人，原持有人先核销或先改转他人的，**原转赠自动作废**
  - **转赠不设自动到期时间**；**接收人确认领取后可以继续再次转赠，转赠次数不受限制**
- 依赖：F3.8（转赠完成后原持有人的码立即全部作废）
- 证据位置：`L796 · 权益转赠`
- 三条完整单位规则：①**单人通票转赠时必须将该张单人通票的全部权益一并转赠，不允许只转赠其中部分权益**；②**多人票允许将其中某一个人的完整票务权益转赠给他人，但不允许切割或只转赠该个人票务权益的一部分**；③**一人多次票在首次核销前如需转赠，必须将整张票及全部可用次数一并转赠；首次核销后即绑定首次使用人，剩余次数只能由该人继续使用，不允许再转赠给其他人**
- 卡座开卡人特权：**可以在邀请函中将该陌生人移出、收回其名额；但该人一经核销门票权益即不得再移出**

- 模块：M6 票务权益 / 会员与积分表
- 功能名称：储值卡两类 + 充值 + 退卡规则 + 双时间戳

- 交互：充值 / 扣减 / 冻结 / 解冻
- 输入：充值金额；消费时指定的卡
- 输出：余额变动

- 依赖：F7.7 账户注销时放弃的余额归发卡主体；F6.37 双时间戳同规则
- 证据位置：`L819 · 储值`
- 修订注释：`L818 · 2026-08-04 第二轮裁决`——「综合体通用卡默认全额可退」澄清为「未消费本金默认全额可退，赠送金不退现、未使用部分按活动规则作废或收回」，与枚举速查表储值卡条一致；**用户逐项批准**
