## T6c-01 · DIFF-A-009 留痕状态六态 → 事件状态七态

- **日期**：2026-08-05
- **文件**：`docs/platform-governance-prd-v0.1.md`
- **章节**：§7.9 平台基础留痕（状态行）、§10 关键状态模型（操作留痕行）
- **修改前**：`| 状态 | 已记录、待复核、已确认、已驳回、已作废、已归档 |`；`| 操作留痕 | 已记录、待复核、已确认、已驳回、已作废、已归档 | 控制留痕是否完成确认 |`（**六态**，含 HTML 明确禁止的「已作废」状态值，缺「待补充」「已关闭」）
- **修改后**：两处均改为**七态**「已记录、待补充、待复核、已确认、已驳回、已关闭、已归档」，并注明「平台基础留痕即留痕事件本身，与 ENUM「事件状态」为同一状态枚举，承接 PRD 见 `evidence-risk-control-product-prd-v0.1.md` §5」「**「作废/冲正」是对留痕内容的处置动作，不是状态取值**，原「已作废」态就此作废——HTML 原文为「只能作废/冲正，不能删除」」
- **依据**：DIFF-A-009；ENUM「事件状态」条 L168（现行原文：已记录、待补充、待复核、已确认、已驳回、已关闭、已归档（只能作废/冲正，不能删除；仅最高权限本人插入授权 U 盘密钥后可以清理，清理动作另行留痕））
- **来源**：三份 HTML（ENUM 八·留痕与风控）＋ 承接 PRD `evidence-risk-control-product-prd-v0.1.md` §5
- **原因**：核对结论为**同一业务对象**（详见 T6c 报告第 1 项）：HTML 侧只存在一套留痕/事件状态枚举，PGM HTML「留痕和复核」章列举的必须留痕动作即 §7.9 所述治理动作，未另定独立状态枚举；六态与七态并存会造成同一对象两套状态机，且「已作废」把处置动作误作状态值
- **执行者**：`opus-implementer-T6c`

## T6c-03 · DIFF-A-046 新增「七类红线」独立小节

- **日期**：2026-08-05
- **文件**：`docs/platform-governance-prd-v0.1.md`
- **章节**：新增 §2A.4 七类红线（不可绕过、不可关闭）
- **修改前**：全 25 份 PRD 检索「七类红线」命中 0；仅 §12 第 14A 条覆盖「四类 + 税费」高危授权审批（另一个闸口），红线机制本身（不可绕过、不可关闭、密钥逐笔开放分级）无承接

- **原因**：红线是「审批不是万能通行证」的唯一书面依据，缺失会被实现成「审批通过即可放行一切」
