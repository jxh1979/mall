# P2-B 游乐团体/包场预订与容量锁定完成审计 V0.1

> **口径修订（2026-08-06 R10）：「场次容量」已废止**——BSM「容量控制」条 明确「**只按单个游乐项目的实时在玩人数控制容量，不再按场次/时段或点位/设备另设容量；排队人数不占用容量**」（DEC-R5-2026-08-04-04；R8 用户裁决 D-02）。本文原「场次容量」一律改称「**项目容量（实时在玩人数）**」；双阈值不变（运营容量软上限告警放行、安全容量硬上限阻断并自动停运）。仍按场次/时段或点位/设备维度罗列的页面、接口、组件与字段只作历史结构参考，容量口径一律以本条为准，相关字段待代码轮下线，期间不得据以新增受控维度。

## 1. 审计结论

P2-B 已完成可编码闭环。系统现在支持后台创建团体/包场预订、人工审批锁定容量、释放归还容量，并且普通核销会扣除已锁定容量，避免场次超容。

P2-B 明确不覆盖收费、退款、改期和销售归属，避免把未决业务压入当前切片。

## 3. 验收覆盖

- 创建预订不锁容量。
- 审批预订锁容量。
- 容量不足审批失败。
- 重复审批不会重复增加锁定容量。
- 释放预订归还容量。
- 重复释放不会重复扣减锁定容量。
- 普通核销使用 `used_capacity + locked_capacity < capacity`。
- 控制器权限和幂等键已覆盖。
- JDBC 集成测试覆盖迁移、字段和权限。

## 4. 对抗式审计

| 发现 | 结论 | 处理 |
| --- | --- | --- |
| 容量锁定可能导致并发超卖 | 高风险 | 使用数据库原子更新和容量条件校验 |
| 创建后立即锁容量会造成误占 | 已规避 | 创建只进入 `pending_approval` |
| 释放重复执行可能导致容量负漂移 | 已规避 | 仅 `approved` 可释放 |
| 价格/退款/改期未定义 | 不压入本期 | 文档明确后置 |
