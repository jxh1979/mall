## 1. 范围边界

| 范围 | 当前是否可开发 | 说明 | 下一步 |
|---|---|---|---|
| 现有 P0/P1/P2/T3 自有系统能力 | 可以 | 入口、OpenAPI、operation matrix、验收、Runbook 已闭合。 | 按现有文档继续开发和验收。 |
| 完整后台管理端 | 条件可以 | 当前 Web 已有轻量管理/运营入口和 UI 自动化，但不是完整后台系统规格。 | 已形成 full-admin SRS、页面/权限/字段矩阵和 UI 验收矩阵；下一步按矩阵拆开发批次。 |
| 真实机器人/视频/设备/人脸/支付/企业微信供应商接入 | 条件可以 | 已有双向开放、adapter、Webhook+轮询、字段映射、补偿策略边界，但真实 SDK/API 未到位。 | 每个供应商到位后补接入规格、签名、回调、错误码、限流和对账口径。 |

## 2. 完整后台管理端 SRS 最小结构

完整后台不是把现有轻量 Web 页面加菜单。必须按页面、角色、权限、字段、接口、状态和验收逐项定义。

| 页面/能力 | 路由建议 | 目标角色 | 权限点 | 数据源/接口 | 主操作 | 状态流 | 必须验收 |
|---|---|---|---|---|---|---|---|
| 总控驾驶舱 | `/admin/overview` | 总控、运营负责人、财务负责人 | `dashboard:view` | analytics / finance / ticketing / bar summary | 查看综合经营、风险和待办 | 正常、空数据、部分接口失败 | 指标口径可追溯；接口失败不误导为 0。 |
| 主体与合同管理 | `/admin/entities`, `/admin/contracts` | 法务、财务、运营 | `entity:*`, `contract:*` | 主体、合同、附件、审批流 | 建档、绑定、审批、归档、变更 | 草稿、待审、通过、驳回、归档 | 四类主体唯一绑定；合同附件不可静默覆盖。 |
| 票务策略管理 | `/admin/ticketing` | 票务运营、总控 | `ticketing:*` | ticketing pricing/rules/orders | 配置日历价、多人/新人/学生/渠道价、动态规则 | 草稿、发布、停用、模拟 | 草稿不影响正式订单；发布命中订单必须留价格轨迹。 |
| 核销与权益追踪 | `/admin/verifications` | 运营、风控、财务 | `verification:*` | verification events / tickets / benefits | 查询核销、撤销申请、导出 | 已核销、撤销中、已撤销、异常 | 高风险撤销有审批和留痕。 |
| 酒吧与卡座管理 | `/admin/bar` | 酒吧经理、总控、财务 | `bar:*`, `table:*` | bar tables/orders/billing/saved bottles | 卡座、订台、合并、转卡、续卡、低消、账单 | 可订、已订、入场、进行中、结账、取消 | 通票不抵低消；卡座入场只限所在酒吧和规定人数。 |
| 销售提成管理 | `/admin/commission` | 财务、销售主管 | `commission:*` | card-seat orders / staff roles | 查看、复核、结算提成 | 待结、已结、争议 | 销售人员卡座 15%；非销售人员 10%；不含通票。 |
| 游乐安全管理 | `/admin/amusement` | 游乐主管、巡检员、总控 | `amusement:*`, `safety:*` | facility / inspection / incident | 巡检、阻断、整改、复检、恢复开放 | 待巡检、通过、阻断、整改中、复检通过 | 未通过巡检不得开放；恢复需主管权限。 |
| 库存与存酒 | `/admin/inventory` | 仓管、酒吧经理、财务 | `inventory:*`, `saved-bottle:*` | inventory/saved bottle/batch | 入库、扣减、盘点、存取酒 | 正常、冻结、异常、已核销 | 高价值酒水核销保持在线；盘点差异留原因。 |
| 财务应收应付 | `/admin/finance` | 财务、总控 | `finance:*` | ar/ap ledger / settlement | 建账、核对、冲销、结算、导出 | 待收、部分收、已收、逾期、争议 | P0 完整台账；主体、合同、订单可追溯。 |
| 第三方接入管理 | `/admin/integrations` | 技术、运营、供应商管理员 | `integration:*` | adapter / webhook / polling / reconciliation | 配置供应商、查看回调、重放、补偿 | 正常、失败、重试中、补偿完成 | Webhook + 定时轮询校验；失败可追踪和补偿。 |
| 生产前置证据 | `/admin/ops/evidence` | IT、运维、安全、总控 | `ops:evidence:*` | production evidence / blockers | 上传证据、复核、关闭 blocker | template、submitted、verified、rejected | 模板不得当作已验证证据。 |
| 权限模板管理 | `/admin/access` | 超管、安全管理员 | `access:*` | users/roles/templates/audit | 创建基础/临时模板、复制、授权、回收 | 生效、过期、单次已用、停用 | 临时模板按时效/单次失效；每次授权有留痕。 |

## 3. 后台页面通用验收规则

每个页面必须满足以下规则，否则不得进入“完整后台已实现”的结论：

1. 每个可点击主操作都有权限点，权限拒绝时显示明确拒绝原因，并记录审计事件。
2. 每个表单字段有必填、格式、范围、重复、业务冲突校验。
3. 每个列表有空状态、加载状态、错误状态、分页/筛选/排序状态。
4. 每个高风险动作有二次确认、幂等键或防重复提交策略。
5. 每个涉及金额的页面以“分”为后端存储单位，前端展示人民币格式。
6. 每个涉及第三方结果的页面必须显示本系统状态、第三方状态和最后同步时间。
7. 每个涉及客户、员工、凭证、支付、核销、合同的操作必须有审计日志。
8. 移动端或窄屏不要求完整后台全能力，但关键查看、审批、异常处理页面不得错位或遮挡。

## 4. 真实供应商接入规格模板

每个供应商到位后，必须补一份独立接入规格，至少包含：

| 章节 | 必填内容 | 验收要求 |
|---|---|---|
| 供应商身份 | 公司、产品、环境、联系人、接口文档版本 | 可追溯到真实文档和合同/采购记录。 |
| 鉴权与签名 | appId、credential_ref、签名算法、时间戳、nonce、重放窗口 | 错签、过期、重放、缺字段测试必须失败。 |
| 字段映射 | 本系统字段、供应商字段、类型、枚举、必填、默认值、脱敏规则 | 字段级映射表完整，无口头映射。 |
| Webhook | URL、事件类型、重试、验签、幂等、错误码 | 重复回调不重复入账；失败可重试。 |
| 轮询校验 | 轮询频率、窗口、差异比对、限流 | Webhook 丢失时可被轮询发现。 |
| 对账口径 | 订单、支付、核销、退款、设备状态或视频状态口径 | 差异可定位到订单/事件/供应商流水。 |
| 异常补偿 | 重放、人工复核、失败队列、告警 | 补偿前后状态可追踪。 |
| 安全与隐私 | 最小权限、IP 白名单、脱敏、日志保留 | 不记录明文密钥和敏感原文。 |
| 验收数据 | 沙箱账号、测试订单、测试设备、测试回调 | 能在非生产环境完成端到端验收。 |

## 6. 开发前置闸口

1. 新增/变更接口：先改 OpenAPI，再生成 operation matrix 和 closure appendix，再写后端/前端/测试。
2. 新增后台页面：先补页面矩阵、权限矩阵、字段表和 Playwright 验收，再实现页面。
3. 新增第三方能力：没有真实 SDK/API/签名/回调/错误码，不允许写成生产级能力。
4. 涉及支付、核销、凭证、客户数据、员工行为、合同、财务的操作：必须有审计日志、权限点、幂等/补偿和异常流程。
5. 生产上线：必须关闭 blocker register，并把 evidence 从 template/submitted 推进到 verified。
