## 1. 背景与目标

### 1.1 问题
现状系统在**出票时**就把票款按定价一次性分摊入各商户账(`issued_entitlements.allocated_revenue_cent`,`TicketOrderService.allocateRevenue`),**与是否核销无关**。这导致:
- 客人买了含 5 个权益的票只用了 4 个,第 5 个权益的钱**仍已计入对应商户账**,项目公司无法回收;
- 无"按核销结算"、无"未用权益归项目"、无各业态公司(SPV)分账层、无手续费预扣、无单独门票服务费、无套票折扣归属、无场次入场规则——这些要么文档有代码无,要么全新。

### 1.2 目标
把结算从"**发放即分摊**"重构为"**按实际核销逐笔结算 + 未用权益归项目公司**",并建立一套**全可配置的多主体分账体系**,精确复现财务底稿的商业逻辑,支撑地产全链的财务与经营口径。

### 1.3 非目标(本期不做/另批)
- 财务预测/IRR/敏感性测算(那是底稿的事,不进系统);
- 各业态公司的完整会计核算/报税(系统只做**营收分账与结算单**,出具给财务,不替代财务软件);
- 资产公司折旧、CapEx 等纯财务项。

## 3. 核心设计原则

1. **按核销结算**:权益收入在**核销发生时**才确认结算给商户/SPV;未核销 = 不结算给商户。
2. **未用权益归项目公司**:票有效期结束(或作废)后仍未核销的权益,其对应收入**归项目公司**(平台留存),不结给商户。
3. **全可配置、禁硬编码**:分账方案、留存比例、内部结算价、权益单价、服务费率、手续费率、赠酒单价、访问点位数、折扣归属、中央餐饮开关、**各项税费(增值税/文建费/附加,有无+费率)**等,一律走配置表 + 后台页 + 权限。
4. **逐笔可追溯**:每笔结算能追溯到票→权益→核销记录→结算明细→结算单,支持对账。
5. **幂等与防混账**:核销/结算/退款全幂等;权益归属严格隔离(project_id / merchant_id / spv_id),不串户。
6. **向后兼容迁移**:提供从 `allocated_revenue_cent`(发放即分摊)到新引擎的迁移与并行校验路径(§11)。
7. **业务规则 ≠ 财务测算假设(2026-07-04 用户纠偏,关键)**:财务底稿里大量"公式"是**预测假设**——用来在财务模型里估算营收数字(如"50% 通票客人会买额外酒水、平均 1.5 杯、每杯 20 元""客流 7100 人/日""满台率 70%")。这类假设**一律不进系统**——系统按**真实交易/核销逐笔记账**(客人实际买几杯记几杯、实际访问几个点位算几个)。只有"每一笔钱怎么算、怎么分"的**结算规则**(留存比例、服务费率、内部结算价、佣金率、手续费率、折扣归属、税率)才进系统做配置。**成本同理:系统成本 = 真实费用归集,不用"收入×成本率"估算。** 附录 A 已据此把参数分为"进系统"与"仅财务测算"两栏。

## 5. 通票分账引擎(本次重构的核心)

### 5.0 通票分账全流程(2026-07-28 用户拍板,业务 HTML `f19ea732` 为准,批 2 权威)
一张通票收入按下列**固定顺序**逐笔分账(以 99 元为例):

| 步 | 算法 | 例(99 元) |
|---|---|---|
| ① 通票收入 | — | 99 |
| ② 扣第三方渠道抽成 | 第三方抽成(美团/抖音等)**最先扣,在所有费用之前**;比例/金额后台可配 | − 渠道费 |
| ③ 扣**赠送权益预估成本** | **归娱乐平台公司**。票内加赠的酒水/小食/餐饮/零售**每样都是独立权益**,绑提供方商户、须到对应商户核销,成本按提供方**内部结算价**计。预扣金额**按票种配置**:**按件计** = Σ(票面各权益数量 × 内部结算价);**按票计** = 该票种赠送部分的**售价整额** | − 赠送权益预估成本 |
| ④ 扣**门票综合服务费** | = **娱乐平台公司留存 / 项目管理费**,与「娱乐平台公司留存」为**同一项、只扣一次**;比例或固定额及封顶(项目×商户×票种)后台可配;**归娱乐平台公司** | − 综合服务费 |

### 5.0c 综合／联合通票的定价构成与分账(2026-07-28 用户拍板 A/B,业务 HTML `e314c595` 为准)

> **本节不是第二套瀑布**,而是 §5.0 瀑布在**多业态票**上的分支写法:§5.0 的四道扣项顺序与归属**一条都没变**,变的是**"作用在哪一层"**——单业态通票(纯酒吧通票)整单走 §5.0;综合／联合通票先拆业态份额,**②③两道只作用在酒吧份额上**。渠道抽成在两种票上都是**整单先扣**。

**① 定价构成(A)**

售价 =(**游乐业态价** + **酒吧业态价** + **收费的餐饮/零售价**)× **票种折扣**。

- **免费的(票面价 0)不计入价值**——纯赠送/兑换类权益不进相加基数,不影响售价,也不影响下面的份额拆分;其成本承担另见 §6.6。
- 折扣是**票种级配置**,不写死;折扣归属(平台吸收/商户分摊/按比例)沿用 §7.4 `discount_bearer`。

**② 分账顺序(B)**

| 步 | 算法 | 归属 |
|---|---|---|
| ① 整单扣**第三方渠道抽成** | 在拆份额**之前**、对整张票扣一次(比例/金额可配) | 第三方渠道 |
| ② 按**各业态票面原价占比**拆份额 | 份额ᵢ =(扣完渠道抽成的余额)× 该业态票面原价 ÷ Σ各业态票面原价 | — |
| ③ **游乐份额** | 直接归属,不再扣本瀑布其它项 | **游乐公司** |
| ③ **餐饮份额** | 直接归属 | **餐厅商户** |
| ③ **零售份额** | 直接归属 | **零售商户** |
| ④ **酒吧份额**再扣**赠送权益预估成本** | 口径同 §5.0 ③ / §5.3 ① | **娱乐平台公司** |
| ⑤ 酒吧份额再扣**门票综合服务费** | 口径同 §5.0 ④(= 娱乐平台公司留存/项目管理费,同一项只扣一次) | **娱乐平台公司** |
| ⑥ 酒吧份额剩余 → **可分配池** | 按 §5.1 **两段分配**给各酒吧商户 | **各酒吧商户** |

**③ 拆份额的粒度铁律**

- 拆份额**只按业态大分类**进行:先区分这份产出**由哪个业态产生**,再按**该业态自己的内部规则**处理(游乐按 §6.3、酒吧按 §5.1/§5.3、餐饮/零售按核销直付商户)。
- **依附于某业态产生的加赠权益,不作为业态层的拆分对象**——其价值**已含在所属业态的价格内**。例:酒吧通票里加赠的一杯酒,不在业态层单独切一份"酒水份额",它的价值已在"酒吧业态价"里;它只在酒吧份额内部按 §5.3 走「赠送权益预估成本」预扣与核销兑付。
  > 与 §5.3「每样赠品都是**独立权益**」**不矛盾,是两层**:§5.3 说的是**核销/绑定/成本**层——每样赠品各绑提供方商户、各自核销、各按内部结算价计成本;本条说的是**业态份额拆分**层——加赠权益不在这一层单独占份额。读的时候别把两层混成一层。

**④ 两个价,不可混用(B)**

| 价 | 用途 | 不得用于 |
|---|---|---|
| **票面原价** | ① 定价相加(A)② 业态份额拆分占比(B ②) | 与提供商户结算成本 |
| **内部结算价** | ① 与提供商户结算兑付成本(§5.3 ③)② 赠送权益预估成本按件计(§5.3 ①) | 定价、份额拆分占比 |

- 每个权益**同时**带这两个价,票种配置时**分别录入**,读写两条独立字段,禁止互相回退顶替。
- 现状缺口:`entitlement_templates` 现只有 `value`(定价)与 `agreement_price_cent`(虚拟签约价),实物走 `bar_item_ref`→`bar_products.internal_settlement_price_cent`;**"票面原价"未作为独立字段固化**,业态份额拆分所需的**业态标签与业态原价合计**也不存在。

**⑤ 实装现状与缺口(如实标注)**

- **已实装**:§5.0 单业态瀑布(渠道抽成为 0 占位)、`by_component_price_ratio`(按权益定价占比,**权益级**近似,**不是业态级**)、§7.4 套票折扣落库与 `discount_bearer` 应用。
- **未实装(待开发)**:① 业态大分类标签与"业态票面原价合计";② 整单渠道抽成后的**业态份额拆分**这一层(现引擎直接走单业态瀑布);③ ②③两道扣项**只作用在酒吧份额**的收敛(现对整单扣);④ 票面原价与内部结算价的**双价独立字段**与混用防护;⑤ 免费权益(价 0)不进相加基数与不进份额拆分的显式过滤。以上属本轮 HTML 口径新增,**代码尚未跟上**。

### 5.0a 金额精度与分账尾差(R-7·2026-07-22 用户拍板 D15.1·已落地)

> 权威口径:治理地图 HTML「全局原则 · 金额一律精确到分」+ 基准 D15.1 + 产品总纲 §42。
> 落地:公共入口 `com.complex.platform.common.money.MoneyRounding`(唯一舍入/尾差 API);迁移 **V343**。

- **四舍五入到分(HALF_UP),不再整除截断**。一切「金额 × 比例」一律走 `MoneyRounding.bpsOf/prorate`。
  旧写法 `金额 * bps / 10000` 是**向零截断**:收费方(项目公司/平台/员工)系统性少收、余数悄悄留在付款方且不留痕,
  与「四舍五入」字面口径不符。本轮已改:渠道费、项目留存、按排名档位分池、套票折扣项目承担额、
  单独门票综合服务费、过期未核销归项目切分、核销累计增量公式(原 `Math.round((double)…)` 有浮点失精且对负数不对称)。
- **符号对称**:HALF_UP 远离零进位,`f(−x) = −f(x)`。跨月红冲取原行之反时逐分精确对消,
  P6「每笔实收 fee 落库 + 冲正取反」的守恒性不被舍入破坏。
- **不溢出**:全程 BigDecimal,消除 `金额 × bps` 先乘后除在 long 上回绕的风险。
- **多档只舍入一次**:阶梯型算式(如营业额抽成阶梯提成)先累精确份额、末尾收敛一次,避免逐档误差累积。

**尾差单列留痕(不得静默吞掉)**

| 项 | 口径 |
|---|---|
| 定义 | 尾差 = **应分总额**(对各方精确份额合计只四舍五入一次) − **Σ各方已舍入份额** |
| 归属 | 统一由**项目公司/平台兜底**,绝不并进任一商户 |
| 落点 | `settlement_bills.rounding_residual_cent`(**V343**,BIGINT 带符号,默认 0) |
| 符号 | 正数=各家舍入后合计偏少、差额留在平台;负数=各家舍入后合计偏多、由平台补足 |
| 量级 | 尾差绝对值 ≤ 参与分账商户数(每家最多贡献 0.5 分);越界 = 分配算法出错,引擎 fail-loud 拒绝出单 |
| 守恒 | `Σ池分账明细 + 尾差 ≡ 应分总额`,逐分严格相等 |
| 自检 | `TicketDistributionSettlementService.verifyConservation` 运行期校验①池链 `可分配池 = 留存 + 各酒吧总池`②分账链尾差恒等式③尾差量级;任一不成立抛 `SETTLEMENT_CONSERVATION_VIOLATED`,宁可拒绝出单也不出一张不守恒的结算单 |

- **越池判定改按「应分总额」**(= Σ已舍入 + 尾差)而非 Σ已舍入:特批闸管的是「业务上分超了池」,
  不该被 ±n/2 分的舍入尾差触发(尾差本就由平台兜底,不需要为几分钱把整月单打回待特批)。
  无舍入场景(按客数/固定额/比例除得尽)应分总额 ≡ Σ已舍入 → 与改造前逐分同判,**零行为变更**。
- **不产生尾差的补数式拆分**:渠道费/池、留存/总池、综合服务费/商户净额、过期核销/未核销——
  后者恒取前者的整数补数,两侧相加恒等于总额,故无尾差,不占 `rounding_residual_cent`。
- **超池两段拆(§5.0 超额 C 口径)保持向下取整,属本口径的合规特例**:`pool_i = ⌊a_i×spvPool/poolDistributed⌋`
  向下取整使 `Σpool ≤ spvPool` 硬约束恒成立,且余数落在 `excess_i = a_i − pool_i`(**由 L3 平台承担**)——
  方向上已是「尾差归平台」,且已**单列**在 `platform_incentive_subsidy` 独立台账行上,满足留痕要求;
  改 HALF_UP 反而会同时破坏「不得超总池」与「尾差归平台」两条。故此处**刻意不改**,以本条为准。

### 5.1 分账两问,均可配置

**第二层——可分配池在各酒吧商户间分配**(按核销 + 整月排名/客数月结):

  - `by_entitlement_price`(**推荐默认**):按各权益**实际核销**× 单价精分——实物权益按**内部结算价**、虚拟权益按**签约权益单价**(§6);

  - `by_component_price_ratio`:按权益定价占比(近似现状 allocated 逻辑,过渡用);
  - `by_venue_per_guest`(**2026-07-04 用户明确落地口径**):按**入场客数 × 各酒吧协议单价**分账——"每进一个客人给几元",**各酒吧协议不同、后台按门店可配**(配置项 `spv_per_guest_rate`);按各酒吧协议单价×客数分给对应酒吧商户。**赠酒补偿走 §5.3 第一段(bar 域按内部结算价挂应付),D5(2026-07-21)后不再从池预留赠酒成本(每杯 3 元池扣已删)**。此为用户拍板的现实结算方式。**2026-07-28 改**:本方式属下文「两段分配」的**第一段**(绝对金额优先拿),不再与 `by_rank_tier` 并列二选一。
  - `by_rank_tier`(**排名档位比例**,2026-07-04 用户口径):按**通票核销排名**分档比例分——例:第 1 名 16%、2–4 名各 12%、5–8 名各 9%、最后 2 名各 6%(1+3+4+2=10 家,合计 100%);**档位区间与比例后台可配**。**2026-07-28 改**:比例的基数**不再是整个可分配池,而是第二段余额**(见下「两段分配」)。
  - `by_fixed_amount`(**固定金额**):每家酒吧后台直接填分账固定额,属**第一段**绝对金额;总额 ≤ 可分配池(超出走 §5.0 特批)。

**两段分配(2026-07-28 用户拍板 D,替代原「三选一并列可配」表述)**

原写法「`by_venue_per_guest`/`by_rank_tier`/`by_fixed_amount` 三种是并列可配方案、项目公司级选一种」**已作废**。现行口径:三种方式**同时并存于一个池内**,分**两段**执行——

| 段 | 参与者 | 算法 | 基数 |
|---|---|---|---|
| **第一段(绝对额优先)** | 约定为 `by_venue_per_guest`(每客单价)或 `by_fixed_amount`(固定额)的酒吧 | 按各自约定的**绝对金额**先拿(每客单价 × 当月客数;或直接固定额) | 可分配池 |
| **第二段(比例分尽余额)** | 其余约定为 `by_rank_tier`(排名档位)的酒吧 | 按各自档位比例**分尽**第二段余额,Σ比例 = 100% | **第二段余额 = 可分配池 − 第一段合计** |

- **互斥铁律**:**拿了第一段的酒吧不再参与第二段**。一家酒吧的约定方式决定它落在哪一段,不能两段都拿。
- **守恒**:`可分配池 = 第一段合计 + 第二段合计 + 尾差`(尾差口径与归属见 §5.0a,由平台兜底,不并进任一商户)。
- **边界**(本轮 HTML 未逐条写死,按现有铁律推导,**落地前建议向用户确认**):① 第一段合计 ≥ 可分配池 → 第二段余额为 0、排名档位酒吧当月分 0,且第一段超池部分走 §5.0 超池特批;② 池内**没有**排名档位酒吧 → 第二段余额留在娱乐平台公司,不倒回第一段追加;③ 池内**只有**排名档位酒吧 → 第一段为 0、第二段基数 = 全池,与改造前 `by_rank_tier` 行为一致。
- `by_entitlement_price` / `by_visited_point_average` / `by_component_price_ratio` 是**权益级精分/过渡口径**,不属于本两段模型;项目公司级选用哪套,后台可配。
- 未核销权益不参与二层分配 → 其对应余额**留在平台**(=未用归项目,原则 2)。

> **实装现状与缺口(如实标注)**:引擎现按**单一 `spv_distribution_method` 整池一次分完**(`TicketDistributionSettlementService`),**两段分配未实现**;`verifyConservation` 现校验的池链恒等式是「可分配池 = 留存 + 各酒吧总池」,两段化后需扩为「池 = 第一段Σ + 第二段Σ + 尾差」,**待开发**。

### 5.2 结算触发(按核销,非发放)
```
出票    → 记录票款、各权益定价与归属(不入商户收入账,仅"待核销")
核销    → 对该权益:①判定结算价(实物内部价/虚拟权益单价)②计入对应主体"已核销结算"
```

### 5.3 赠送权益(通票内加赠的酒水/小食/餐饮/零售)结算 — 2026-07-28 用户拍板重写

**权益模型**:票里加赠的酒水、小食、餐饮、零售等,**每一样都是一个独立权益**,各自**绑定提供它的酒吧 / 餐厅 / 零售商户**,客人**须到对应商户核销**;每个权益的成本按**提供方的内部结算价**计。

**① 池前预扣「赠送权益预估成本」→ 归娱乐平台公司**(§5.0 ③)
- 预扣金额**按票种配置**,两种模式二选一:
  - **按件计** `by_item`:Σ(票面各权益数量 × 该权益提供方的内部结算价);
  - **按票计** `by_ticket`:该票种**赠送部分的售价整额**。
- 模式与所有单价/金额**后台可配、禁写死**;预扣发生在**可分配池之前**,池 = 收入 − 渠道抽成 − 赠送权益预估成本 − 门票综合服务费。

**② 赠酒按酒吧分配(票面规则)**
- 一张通票覆盖的**每个酒吧至少赠一杯**;
- **各酒吧分别赠几杯,在售票时写明票面**;
- **A 酒吧的赠酒只能在 A 酒吧核销**,不能拿到其他酒吧核销;跨吧核销一律拒绝。
- 核销顺序不变:同一酒吧须**先核入场权益、再核该吧酒水权益**。

**③ 核销兑付 → 由娱乐平台公司承担**
- 客人核销后,由**娱乐平台公司**按该权益的可配**内部结算价**与**提供它的那家商户**结算——**核销一件结一件、没核销就不结算**;
- 对商户的兑付**由娱乐平台公司承担**,**不进入酒吧可分配池**,**不计酒吧销售提成**;
- 成本**按提供方的商户业态(酒吧 / 餐厅 / 零售)分开记账**;
- **预扣与核销实付的差额留在娱乐平台公司**,按可配规则调账留痕(不回流可分配池、不改已结酒吧分账)。

**④ 可分配池的分配(与赠送权益解耦)**
- 可分配池(§5.0 ⑤)按 §5.1 第二层方式分给各酒吧商户,具体分成按**整月排名 / 客数**等参数在**月度结算**时结出;赠送权益兑付**不占用**该池。

**实装现状与缺口(如实标注)**
- **已实装**:核销时由 bar 域按该商品内部结算价给出品酒吧挂应付(`pass_drink_settlement`·幂等 + 可冲正)——对应上文 ③ 的兑付动作,但**承担主体口径需由「平台」收敛为「娱乐平台公司」**,且**成本尚未按商户业态分记**。
- **未实装(待开发)**:① 池前「赠送权益预估成本」预扣(按件计 / 按票计两模式与票种级配置);② 预扣与实付差额在娱乐平台公司侧的调账留痕;③ 赠酒按酒吧配额(每吧至少一杯、杯数写票面)与**跨吧核销拒绝**;④ 门票综合服务费归属主体由项目公司改娱乐平台公司。以上属本轮 HTML 口径新增,**代码尚未跟上**。

### 6.2 酒吧入场资格——场次规则(用户口径 4,全新)
- 入场资格权益的核销单位是**场次**(一个"开业→歇业"周期):
  - 客人当场次**入过场**后,该场次内可**持续进出**(不重复消耗);
  - 即使门票有效期未到,一旦某场次已入场,**过了该场次(下一个开歇业周期)即作废**,不能再用;
- 新建 `venue_sessions`(场次/营业周期)+ `entitlement_entry_records`(入场记录);核销校验按场次状态机。
- **场次自动触发(2026-07-04 定)**:系统按各酒吧**营业时间表**(新增 `venue_business_hours` 配置)自动划场次——开业开场、歇业关场;入场资格权益随场次结束自动作废,无需人工开关。

> ✅ **已落地(批3-2,V226,main=98a7c50)**:新引入 `consumption_window`(per_use/per_session/per_day/unlimited_in_day)判别位,`per_session`=入场资格;建 `venue_business_hours`(营业时间表)+`venue_sessions`(场次实例)+`entitlement_entry_records`(入场记录);核销惰性开场(按营业时间表判当前是否营业·跨零点延续归同场次·非营业时段拒 `VENUE_NOT_IN_SESSION`);同场次二次核销放行不消耗、跨场次已入过场 `ENTRY_PASS_PAST_SESSION_VOID` 作废、唯一键防并发重扣。

### 6.3 游乐——当天无限 + 票种规则(用户口径 5,2026-07-04 扩)
- **当天无限核心机制**:游乐权益按**自然日**核销——每次核销激活「一个整天无限」:当天首刷即消耗一次、当天内再刷卡/扫码/多人再进=放行**不重复消耗不重复计费**;跨自然日=新的一天从剩余次数再消耗一次。
- 权益模板增 `consumption_window ∈ {per_use, per_session, per_day, unlimited_in_day}`(`unlimited_in_day`=当天无限)。
- **票种规则(2026-07-04 用户拍板,游乐票同酒吧通票:有有效期、期内可用)**:
  - **单人票**:有效期内任选一天首刷→当天无限玩→**跨日作废**(即使有效期未到,次日票即废)。靠 `total_times=1`(次日核销即 `ENTITLEMENT_USED_UP`)。
  - **多人票(N 人)**:规则同单人票,唯一差异=**当天可核销 N 次**(N 人当天各入场随便玩);同天用不完的额度**跨日作废剩余**。(单日型+跨日废剩余标记 → **批 4 票种**。)
  - **多次票(N 次)**:有效期内 N 次、**每次核销=一整天无限**、**跨日保留剩余**(买 3 次,第 1 次核销完,有效期内第 2/3 天还能各核销一次)。靠 `total_times=N`(天天各扣一次)。
  - **新人票/学生票**:规则+作废规则**同酒吧通票**。
  - 票种细分(单人/多人/新人/学生)、多人票「同天 N 次+跨日废剩余」、`num_people` 语义 → **批 4 票种**集中实现。

> ✅ **已落地(批3-3,V227,main=d36d0a5)**:`unlimited_in_day` 的「按自然日激活」——建 `entitlement_day_activations`(唯一键 entitlement_id+usage_date);
> 当天已激活放行不消耗、当天首刷且剩余>0 才扣次(唯一键防并发重扣)、剩余=0 不插激活让其走 `ENTITLEMENT_USED_UP`;
> **复用现有 `total_times`**——单人票 total=1 天然跨日作废、多次票 total=N 天然跨日保留,不重造次数模型。

### 6.6 免费权益(票面价 0)的成本承担分两类(2026-07-28 用户拍板 C,业务 HTML `88eba70c` 为准)

票面价格为 0 的免费权益,**按成本由谁承担**分成两类,**在票种配置里逐权益标明成本承担方**:

| 类 | 定义 | 平台是否承担成本 | 是否与提供商户结算 | 是否计入赠送权益预估成本 |
|---|---|---|---|---|
| ① **商户让利型** | 餐饮 / 零售等商户**为引流自行让利**、搭进通票的免费优惠 | ❌ 不承担 | ❌ 不结算 | ❌ 不计入 |
| ② **平台出资型** | 平台为做活动**向商户采购后免费赠送**给客人的权益 | ✅ 承担 | ✅ 按**内部结算价**与提供商户结算(核销一件结一件,§5.3 ③) | ✅ 计入(§5.0 ③ / §5.3 ①) |

- **两类都不参与业态份额拆分**(§5.0c ②)——票面价为 0,占比分子为 0。
- **成本承担方是必填项**:票种配置未标明的免费权益,视为配置不完整,不得启用(fail-closed,同 AUD-015 赠饮模板启用前置校验范式)。

> ⚠️ **旧口径作废**:2026-07-06 裁决 `D-20260706-1`/`D-20260706-2` 里「通票餐饮优惠……价格可以设为 0(纯赠送或兑换)……核销时平台按内部结算价与这家餐厅商户结算」的**一刀切**写法**已作废**——价格为 0 的赠送/兑换**是否由平台按内部结算价结算,取决于该权益标明的成本承担方**。餐饮结算归餐厅商户这条本身不变(核销后那笔钱归提供餐品的餐厅商户),变的只是"平台要不要为这 0 元权益向商户付成本"。

## 7. 各票种结算规则

### 7.1 通票(仅项目公司可售 —— 用户口径 1)
- 售卖主体限制:通票类票种**只有项目公司(平台)角色**能创建/售卖,商户不能;后端加销售主体校验(权限点 + 主体身份双重)。
- 结算走 §5 分账引擎。

### 7.2 单独门票——综合服务费(用户口径 8 + "所有门票都抽",用户裁定)
> ✅ **已落地(V268)**:建 `comprehensive_service_fee_configs`(项目×商户×票种范围可配·`fee_bps` 默认 0=不抽·禁硬编码)。落点=月度分账引擎专属商户直付线(单独门票走此线):直付前项目公司按配置费率抽综合服务费,商户拿净额(收入−服务费),服务费归项目记入 `settlement_bills.comp_service_fee_cent`。**默认费率 0 → 商户拿全额 → 零行为变更**(现有 batch34 专属直付测试断言全额不变、仍绿)。通票的"留存 20%"仍是同族另一条规则(`platform_retention_rules` §5.1 第一层),本表专管单独/专属门票那道。
- 客人购买某商户的单独门票(任意渠道):项目公司先抽**综合服务费/项目管理费**(= 平台留存规则 §5.1,费率项目↔商户可洽谈、可配),余额结给该商户;
- **所有门票**(含通票)都过平台留存这一道——通票的"留存 20%"与单独门票的"综合服务费"是**同一条留存规则**的不同费率实例。
> ✅ **已落地(V328)**:综合服务费现支持**比例或固定额二选一**——配固定额(`fixed_amount_cent`)则费率(`fee_bps`)须为 0(DB 约束 `chk_csfc_fee_mode` 保证二者不并存);默认仍费率 0 → 零行为变更。
> ✅ **月度封顶(V336·批2·用户 2026-07-21 拍板 A「按费率规则各自封」)**:综合服务费加**可配月度封顶** `monthly_cap_amount_cent`(绝对分值·比例与固定额两模式**共用**同一上限)。封顶配在**每条费率规则上**(项目×商户×票种作用域)。引擎按**【商户 × 解析到的规则 id】聚合**封顶前原始费后再 clamp `fee = min(Σraw, cap)`——因费率规则可跨票种(商户级规则 entitlement_type=NULL)或跨商户(全局默认 merchant_id=NULL),故封顶**不能**逐 (商户×票种) 聚合行各自压(否则同商户多票种落同一规则被压 N 次=N×封顶):商户级规则=该商户当月封顶、票种级规则=该票种封顶、全局规则=各商户各自封顶(不跨商户合并)。**默认 NULL = 不封顶 → 零行为变更**;`chk_csfc_monthly_cap` 保证 ≥0;封顶只压不抬(未触顶 fee 原样)。全链:引擎两趟(读侧 ServiceFeeConfig 带规则 id)+ 写侧(草案→差人转正)+ 前端总控页输入框;`SettlementV268Tests` 11 绿(比例/固定额/未触顶/**跨商户多票种聚合封顶回归锁**)+ 写侧往返绿。**(对抗自查修:初版逐 (商户×票种) 各自压致同商户多票种被 N×封顶,已改聚合封。)**
>
> ✅ **P6 综合服务费守恒架构改已修复(2026-07-21)**:原封顶 `min(raw,cap)` 与固定额毛额钳 `min(fixed×张数,gross)` 是**月度非线性**运算,不满足核销↔冲正的「带符号线性可加」(`f(-x)=-f(x)`),过账开启后跨月红冲落当月、聚合行 gross 带负、引擎按费率/毛额**重算** fee ≠ 原月实收之反 → 触顶场景项目倒亏商户多拿、`net<0` 撞 `chk_si_amount` 崩(固定额自 B1-2 潜伏、封顶叠加放大)。**修法(V337)**:综合服务费改为**每笔核销落库实收 fee**——`SettlementSettledConsumer` 核销时按**每笔 + 「商户×规则」当月增量封顶**算实收 fee 存 `settlement_transactions.comp_service_fee_cent`;`SettlementReversedConsumer` 冲正时严格取原 `ST-VS` 行 fee 之反(不可变红冲事实);`settleMonth` 改为**线性求和**各行 `comp_service_fee_cent` 替代月末重算。固定额/封顶/比例三模式跨月红冲全守恒(验收 `SettlementServiceFeeConservationTests`:触顶固定额红冲取反 -500 非旧 min 重算的 -800、封顶两笔各取原行之反)。共享计算器 `ComprehensiveServiceFee` 供核销消费者与结算引擎同源防漂移。**过账管道随之可安全激活**(本阻断解除)。
> **固定额口径(用户 2026-07-21 拍板 A)**:固定额=**每张票固定额 × 核销张数**(对齐「所有门票都过一道」=每张都过),**非**「每票种/每月整包一口价」;引擎实扣 `min(固定额 × 核销张数, 本笔毛额)`(上限本笔收入防净额为负)。比例口径不受影响(比例天然随每张收入缩放)。

### 7.4 套票(用户口径 10,全新)
> **2026-07-28**:套票 / 综合票 / 联合通票的**定价构成**(各业态价相加 × 折扣、免费的不计入价值)与**分账**(整单扣渠道抽成 → 业态份额拆分 → 仅酒吧份额走后续三道)见 **§5.0c**;本节只管**折扣归属**这一件事。
- 套票 = 跨域权益组合(如酒吧+游乐)且整体打折;
- 折扣归属可配 `discount_bearer ∈ {platform_absorb, merchant_absorb, split_by_ratio}`:
  - 平台承担:各权益按原单价结算,折扣差额由平台留存吸收;
  - 商户分摊:折扣按各权益单价占比分摊到各商户结算价;
  - 按比例:可配比例拆分。
> ✅ **已落地(V268 配置 → D6/V331 折扣额落库应用)**:建 `ticket_combo_discount_configs`(项目级可配 `discount_bearer ∈ {platform_absorb, merchant_absorb, split_by_ratio}` + `split_platform_bps`)。默认 `platform_absorb`(项目承担折扣)=商户结算不受折扣影响,与现状一致,**零行为变更**。
> **D6(V331)套票折扣额已走真实售卖/核销路径落库**:售卖时快照满额价 `issued_entitlements.component_full_price_cent` → 核销时算折扣增量 `settlement_transactions.discount_amount_cent` 下传 #179 append-only 账本;结算按 `discount_bearer` 应用——`platform_absorb`(商户拿满额、折扣记 `settlement_bills.combo_discount_cent` 归项目)/ `merchant_absorb`(商户拿净额)/ `split_by_ratio`(按 `split_platform_bps` 拆)。**满额价空 → 折扣 0 → 零行为变更。**
> **跨月冲正(V335·套票真上线前必修)**:项目承担折扣<b>带符号</b>——核销为正(平台吸收),该核销在<b>后续已过账月</b>被冲正时为负(平台<b>追回</b>先前吸收),与收入侧 `verified_amount_cent` 带符号跨月净掉一致。原 `platformBorneDiscount` 的 `discountCent≤0` 钳0 会丢弃跨月负向追回 → 收入 -R 追回了、折扣 -D 没追回,项目多付;V335 放开 `combo_discount_cent` 的 ≥0 约束、去钳。⚠️ 已知天花板:冲正当月须有抵充收入(否则 `ticket_revenue<0` 撞 `chk_sb_amount`,与收入侧同限,非本修引入)。
