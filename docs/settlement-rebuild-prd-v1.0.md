# 通票权益结算重构 PRD V1.05

> **状态**：受三个最高业务解释权 HTML 约束的现行 PRD（2026-08-01 同步）。
> **解释权边界**：三个业务 HTML 是最终业务口径；本文、财务底稿、术语表、实现规格、数据库和代码均只能作为产品细化、测算资料或当前实现证据，不得覆盖 HTML。本文新增而 HTML 尚未记载的业务规则，在用户批准并写入相应 HTML 前不生效。**三份 HTML 之间若出现冲突，按确认时间线判定：凡经用户确认过的内容，确认时间越晚的优先级越高，后确认的覆盖先确认的（以决策台账记录的裁决时间为准）；无法确定确认时间先后的，仍须逐项重新裁决**（2026-08-05 R7 补，依据 DIFF-A-051、PGM「解释权声明」条）。
> **现行结算边界**：域内通票不做域间比例拆分；只有跨域组合通票先从整单扣一次第三方渠道费用，再按收费权益有效价格分到各域，零元权益不参与域间分配。各域取得份额后由对应域主管公司按本域已生效规则与实际提供方结算，商户无权自行决定分配方式。
> **实现状态纪律**：内部结算 SKU 目录已由 V379/V380 落地；既有 S1—S11、其他迁移和代码仍只能说明当前实现。凡统一把赠送权益成本归娱乐平台公司、绕过域主管公司已生效规则直接改变域份额归属、让酒吧份额重复扣渠道费、让全部门票收服务费或让通票服务费封顶的实现，均属于待改造缺口；餐饮／零售域按城市项目公司已生效规则，由跨域组合通票收款主体（娱乐平台公司）直接向实际提供商户付款，是现行合规路径，不属于“绕过域主管公司规则”，本次文档同步不修改实现。
> **待改造缺口登记（2026-08-04 PRD 同步 B5 新增两条，依据 ENUM「跨域通票分配」条）**：
> - **缺口 ①：渠道费未拆通路费 / 销售渠道费两层。** 现实现只有单层「第三方渠道费」，未区分「所有支付（含官方渠道）都产生、由各域按分配份额自然共担的通路费」与「仅第三方渠道产生、在通路费之上再扣一层的销售渠道费」。按原单层口径，官方渠道每一笔线上支付都过不了守恒校验。口径见 §5.0。
> - **缺口 ②：分账瀑布未含票务积分发行成本扣项。** 现行瀑布 `P = R − C − G − F_pool` 尚未包含「票务订单产生的积分发行成本在域间拆分之前从整单扣除且只扣一次」这一层。口径见 §5.0。
> 两条均为**待改造缺口**，不构成业务规则；改造完成前实现结果不得反向写成业务口径。

## 1. 背景与目标

### 1.1 问题
现状系统在**出票时**就把票款按定价一次性分摊入各商户账(`issued_entitlements.allocated_revenue_cent`,`TicketOrderService.allocateRevenue`),**与是否核销无关**。这导致:
- 客人买了含 5 个权益的票只用了 4 个,第 5 个权益的钱**仍已计入对应商户账**,项目公司无法回收;
- 无"按核销结算"、无"未用权益归项目"、无各业态公司(SPV)分账层、无手续费预扣、无单独门票服务费、无套票折扣归属、无场次入场规则——这些要么文档有代码无,要么全新。

### 1.2 目标
把结算从“发放即分摊”重构为“按实际核销逐笔结算”，并按票种经营域、域主管公司和实际提供方建立可追溯的多主体结算体系。财务底稿只用于测算，不自动成为业务规则。

### 1.3 非目标(本期不做/另批)
- 财务预测/IRR/敏感性测算(那是底稿的事,不进系统);
- 各业态公司的完整会计核算/报税(系统只做**营收分账与结算单**,出具给财务,不替代财务软件);
- 资产公司折旧、CapEx 等纯财务项。

## 2. 主体协作关系与职责

平台、城市项目公司、各域主管公司和商户通过项目、经营域、合同及主体绑定关系协作，不建立“项目公司必然下辖域主管公司和全部商户”的固定层级。一家公司可以服务多个项目，一个项目也可以由多家公司共同经营。

| 主体 | 结算职责 |
|---|---|
| 顶层平台 | 审批跨域规则和跨项目治理规则，不因处于顶层自动取得某类收入 |
| 城市项目公司 | 每个城市项目公司同时承担本城市资产公司职责，负责资产物业、招商租赁、直接管理第三方商户及自身人员设备；不负责酒吧、游乐、演出等域的定价、售票和结算 |
| 娱乐平台公司 | 负责酒吧域、酒吧通票及跨域组合通票酒吧部分，审批酒吧项目内部结算价并决定酒吧域内规则；参股并管理独立酒吧商户的相关经营关系 |
| 游乐公司 / 传媒公司 | 分别负责游乐域、演出与传媒域的定价、售票、收款和域内结算 |
| 中央餐饮公司 | 负责其供应的酒水、小食和餐饮供应链、供货收入及供应部分的内部结算价审批 |
| 独立酒吧商户 | 负责自身人员、设备、经营和履约；取得单一酒吧门票、订台低消、二次消费、额外酒水和非散台服务费收入 |

商户只能提交价格资料、履约事实和异议，不能自行决定域内采用内部结算价、固定金额、固定单价、排名档位或比例规则；域内规则由对应域主管公司选择、配置和审批，跨域规则由项目之上的平台权限审批。

**内部结算价的审批主体两档（2026-08-07 补，依据 BSM「每个项目分别建立“内部结算价管理”页面和独立价格目录」条；REGX-10）**：①**餐饮与零售商户（含独立、联营、租赁各种合作模式）统一由城市项目公司审批**——BSM 同条另有「独立餐饮商户由城市项目公司审批，但中央餐饮供货部分仍由中央餐饮公司审批」，两句并存不冲突（后一句已由 `merchant-points-settlement-rules-v1.0.md` §9 项目级内部结算价承接）；②**业态为「其他」的商户，由其商户档案上指定的主管公司审批**。**任何商户在没有获批内部结算价之前，不得为其开通需要该价格结算的权益或券。**

## 3. 核心设计原则

1. **按核销结算**：权益只有在核销成功后，才按已生效规则形成对提供方的实际结算；未核销不结算给提供方，也不得通过配置把“未核销”改成“已核销”。
2. **到期未核销按门票所属经营域归属**（依 ENUM「到期未核销款」条、「域归属对照」条）：本条**只适用于从未完成检票环节的票或人份**（**H-24，2026-08-06**）；已完成检票环节、但权益未在该场次内核销的，按**场次终结制**作为未核销份额进入分账减除、按「域归属对照」条归属，不走本条。**多人票中本人从未刷码的人份**，因各人须在同一场次内完成入场，同票已开启的那个场次一经结束即永无法入场，**于该场次结束时即按本条处理，不等票面有效期届满**；该人份票款按「域归属对照」条逐域归属，与本条其余情形**同一立项、不另立名目**。未核销款结算须以**人份（持有人维度）**为最小记账单位，触发挂在**场次结束事件**上，不能只挂有效期到期的定时作业。有效期内未核销款不提前结算；票到期后先且**只扣一次**第三方渠道费用，余额按票种经营域归属：**酒吧域（单一酒吧门票及酒吧通票）→ 娱乐平台公司；游乐域（纯游乐票及纯游乐通票）→ 游乐公司；餐饮域与零售域 → 城市项目公司；演出传媒域 → 传媒公司**；跨域组合通票按已拆分的各域份额分别归对应域主管公司。该对照与 ENUM「商户业态」条确定的业态—主管公司关系一致，不另设第二套口径；顶层平台不因本条取得任何份额。酒吧份额不得再次扣渠道费。
3. **配置不能改变责任边界**：金额、比例、固定单价、排名档位、封顶、期限及税务参数应由系统配置并留版本；配置只能在三份业务 HTML 允许的范围内生效，不能把主管公司、审批主体、成本承担方或收入归属改成其他主体。
4. **逐笔可追溯**:每笔结算能追溯到票→权益→核销记录→结算明细→结算单,支持对账。
5. **幂等与防混账**:核销/结算/退款全幂等;权益归属严格隔离(project_id / merchant_id / spv_id),不串户。
6. **向后兼容迁移**:提供从 `allocated_revenue_cent`(发放即分摊)到新引擎的迁移与并行校验路径(§11)。
7. **业务规则 ≠ 财务测算假设(2026-07-04 用户纠偏,关键)**:财务底稿里大量"公式"是**预测假设**——用来在财务模型里估算营收数字(如"50% 通票客人会买额外酒水、平均 1.5 杯、每杯 20 元""客流 7100 人/日""满台率 70%")。这类假设**一律不进系统**——系统按**真实交易/核销逐笔记账**(客人实际买几杯记几杯、实际访问几个点位算几个)。只有"每一笔钱怎么算、怎么分"的**结算规则**(留存比例、服务费率、内部结算价、佣金率、手续费率、折扣归属、税率)才进系统做配置。**成本同理:系统成本 = 真实费用归集,不用"收入×成本率"估算。** 附录 A 已据此把参数分为"进系统"与"仅财务测算"两栏。

## 4. 收入类型与主体归属

依据 `03_收入流向图`。**关键口径列只写业务结算规则,不写财务预测公式**(如"张数×50%×1.5杯"是财务测算假设,系统按实际交易记账,见 §3.7):

| 客人付款 | 收款主体 | 收入归属主体 | 税务属性 | 关键口径（系统按实际交易入账） |
|---|---|---|---|---|
| **单一酒吧门票** | **娱乐平台公司**（统一收款后结付） | **对应酒吧商户** | 按中国税法及实际业务性质处理 | 酒吧商户定价、销售、退款并确认门票收入；**票款由娱乐平台公司统一收款后结付给该酒吧商户**；娱乐平台公司不取得门票收入（2026-08-05 R7 同步，依据 DEC-R6-02／UD-16；ENUM／BSM「定价、售票与收款主体」条） |
| **酒吧通票** | **娱乐平台公司** | **娱乐平台公司** | 按中国税法及实际业务性质处理 | 酒吧域内按 §5 的酒吧可分配池规则结算 |
| **纯游乐票及纯游乐通票** | **游乐公司** | **游乐公司** | 按中国税法及实际业务性质处理 | 仅在游乐域内结算，与娱乐平台公司无关 |
| **演出票** | **传媒公司** | **传媒公司** | 按中国税法及实际业务性质处理 | 仅在演出域内结算，与娱乐平台公司无关 |
| **跨域组合通票** | **娱乐平台公司**（统一收款） | **各域主管公司分别取得其域份额** | 按中国税法及实际业务性质处理 | 整单渠道费只扣一次后拆域；各域按域内规则继续结算 |
| **门票综合服务费** | **娱乐平台公司** | **娱乐平台公司** | 按中国税法及实际业务性质处理 | 仅酒吧相关票种收取：单一酒吧门票可按比例或固定金额并可封顶；酒吧通票及跨域组合通票的酒吧部分不封顶 |
| 订台低消 / 二次消费 | **对应酒吧商户** | **对应酒吧商户** | 按中国税法及实际业务性质处理 | 按实际消费入账；订台价由有权主体在后台设定 |
| 额外酒水 | **对应酒吧商户** | **对应酒吧商户** | 按中国税法及实际业务性质处理 | 按实际销售逐笔入账 |
| 非散台服务费(仅包厢/卡座) | **各酒吧商户**（代收） | **各酒吧商户** | 娱乐服务 | 服务费率(默认 10%,可配)× 实际低消+二次消费,散台不收 |
| **向商户供货的货款** | **中央餐饮公司** | **中央餐饮公司** | 货物销售 / 供应链服务 | 供应链主体:向各商户供货并收货款,主要面向内部及参股商户,少量第三方商户;按实际供货逐笔结算 |
| 场地租金 / 商业租金 | **对应城市项目公司** | **对应城市项目公司（同时承担本城市资产公司职责）** | 按中国税法及实际业务性质处理 | 仅处理资产、物业、招商租赁及其直接管理第三方商户相关收入，不介入酒吧、游乐和演出域收入 |

**收款主体不等于收入归属主体（2026-08-05 R7 补，依据 DIFF-A-031；BSM／ENUM「定价、售票与收款主体」条原文）**：娱乐平台公司**只把拆分后归属酒吧域的份额确认为自身收入**；**其余各域份额自收款之日起即为应付给对应域主管公司的款项**，按已审批的域间规则结算，**不得计入自身收入、不得挪用**。分账实现不得把整单票款计入收款主体收入；代收部分只能落应付，不得确认为收入。

**平台侧收费必须先入 HTML 方可设立（2026-08-05 R7 补，依据 DIFF-A-037；ENUM「主要收入归属」条＝BSM FIN-14 收入归属表）**：顶层平台只制定与审批跨项目、跨经营域的统一治理规则，**不因为处于顶层就自动取得**某张票、某个项目或某个商户的收入；**任何面向平台收取的费用，都必须先在三份 HTML 中写明名目、计费基数与承担方，未写明的不得设立**。本 PRD、配置或实现中出现而三份 HTML 未写明的平台侧收费一律无效。

## 5. 通票分账引擎(本次重构的核心)

### 5.0 通票分账全流程（三份业务 HTML 约束）

先判断票种是域内通票还是跨域组合通票，二者不能套用同一套拆分逻辑：

- **域内通票**：不按经营域比例拆分。酒吧通票进入酒吧域规则；纯游乐通票进入游乐域规则；演出域产品进入传媒公司规则。
- **跨域组合通票**：先从整张票实付额中按下条口径扣一次渠道费用（通路费 + 经第三方渠道售出时的销售渠道费）与票务积分发行成本，再按各收费权益的项目内有效价格拆分经营域份额；零价赠送权益不参与拆域。各域份额进入对应域主管公司的域内结算规则。
- **渠道费分两层，性质不同、不可混用（2026-08-04 补，依据 ENUM「跨域通票分配」条、DEC-R3-2026-08-04-08；与 `finance-settlement-product-prd-v0.1.md` §3A 同一口径）**：
  - **通路费**——银行、微信、支付宝等支付通路收取的费用。**所有支付都会产生通路费，官方渠道同样产生**；**在拆分给各域之前从整单扣除，由各域按分配份额自然共担，不由该笔业务的收款主体单独承担**（2026-08-05 R7 同步，依据 DEC-R6-01／UD-15；ENUM「跨域通票分配」条、BSM「域内通票不按经营域比例拆分」条。原「由该笔业务的收款主体承担」表述已作废）。
  - **销售渠道费**——第三方售票平台收取的佣金。**只有经第三方渠道售出的才产生**，**在通路费之上再扣一层**；任何票种经第三方渠道售出时**一律先从整单扣除且只扣一次**，**域内通票同样适用**，不因不做域间拆分而免扣。
  - **官方渠道售出的票不扣销售渠道费，但仍扣通路费**。渠道合同只能约定佣金费率、收付款方式和对账方式，**不得改变佣金的承担方式与分摊口径**，每笔分摊结果与合同版本必须留痕。
- **票务积分发行成本（DEC-R8-87）在域间拆分之前从整单扣除且只扣一次，由各经营域按该订单的域间分配份额自然共担，不由售票收款主体单独承担，也不向核销环节的提供商户再次分摊。** 例：100 元订单先扣 10 元积分发行成本，再将剩余 90 元按 60%／40% 分配为 54 元／36 元；成本只扣一次。
- **禁止重复扣费**：已经在整单扣过的通路费、销售渠道费与积分发行成本，不得在酒吧份额或任何其他域份额中再次扣除。

### 5.0c 综合／联合通票的定价构成与分账(2026-07-28 用户拍板 A/B,业务 HTML `e314c595` 为准)

> 本节只描述跨域组合通票。域内通票不拆经营域；跨域组合通票整单只扣一次第三方渠道费，然后拆分各域份额，最后由各域按自身规则结算。

**① 定价构成(A)——✅ 已落地(V369)**

售价 =(**游乐业态价** + **酒吧业态价** + **收费的餐饮/零售价**)× **票种折扣**,**由系统自动算出**。

- **免费的(票面价 0)不计入价值**——纯赠送/兑换类权益不进相加基数,不影响售价,也不影响下面的份额拆分;其成本承担另见 §6.6。
- 折扣是**票种级配置**,不写死:`ticket_types.combo_discount_rate`(百分数,100=不打折,V369);折扣归属(平台吸收/商户分摊/按比例)沿用 §7.4 `discount_bearer`。
- **系统算出售价** = `Σ(ticket_type_entitlements.component_price_cent × quantity) × combo_discount_rate ÷ 100`,四舍五入到分(走 §5.0a `MoneyRounding`)。

| ①-c 整单扣**票务积分发行成本** | 在拆份额**之前**扣一次 | 全国积分结算中心；全国积分结算中心不是独立公司时为顶层平台公司。该列是积分发行费收款方，不改变各经营域按份额自然共担。 |
| ② 按**各业态价格占比**拆份额 | 份额ᵢ =(扣完①-a/①-b/①-c 后的余额)× 该业态价格 ÷ Σ各业态价格 | — |
| ③ **酒吧域份额** | 进入酒吧域规则；不得再扣渠道费；酒吧相关门票综合服务费不封顶 | **娱乐平台公司负责域内结算** |
| ③ **游乐域份额** | 进入游乐域规则 | **游乐公司负责域内结算** |
| ③ **演出域份额** | 进入演出域规则 | **传媒公司负责域内结算** |
| ③ **餐饮域份额** | **域主管公司＝城市项目公司**（管本域内部结算价审批、业态归属与已生效规则）；**结算执行＝娱乐平台公司（本票收款主体）直接与实际提供的餐饮商户结算**，款项**不经城市项目公司过账** | **规则：城市项目公司；付款：娱乐平台公司直付商户** |
| ③ **零售域份额** | 同上：**规则归城市项目公司，钱由娱乐平台公司直付实际提供的零售商户** | **规则：城市项目公司；付款：娱乐平台公司直付商户** |
| ③ **资产或其他域份额** | 进入相应域主管公司的内部结算价或比例规则，不直接跳过域主管公司结给商户 | **对应域主管公司负责域内结算** |

- **各业态价格在售票时刻随订单一并固化、事后不得变更（2026-08-05 R7 补，依据 DIFF-A-032；BSM「域内通票不按经营域比例拆分」条、ENUM「跨域通票分配」条原文）**：拆域所用的各业态价格**在售票时刻随订单一并固化**，**事后不得变更**；固化的不只是份额比例，**价格本身也不得再改**。目录改价、票种改价或权益重新定价**一律不追改已售出的票**（与 §9.7「核销和结算时把当时生效价固化到流水，后续改价不追改历史」同一纪律，本条把它前移到**售票时刻**并覆盖**价格本身**）。

**③ 拆份额的粒度铁律**

- 拆份额只按经营域进行：先确定收费权益属于哪个经营域，再由该域主管公司按域内已生效规则结算。任何域份额都不能绕过主管公司**的规则**直接改归提供商户。
  > **餐饮/零售的例外只在「谁付钱」这一层（2026-08-04 F5 明确，ENUM「跨域通票分配」条）**：餐饮与零售的**域主管公司是城市项目公司**（规则、内部结算价审批、业态归属归它管），但**款项由本票收款主体娱乐平台公司直接付给实际提供的餐饮、零售商户**。这**不是**「绕过主管公司」——规则仍由城市项目公司定；只是资金**不再经城市项目公司过一道账**。反过来，把这笔钱改成先付城市项目公司、再由其转付商户，才是与 HTML 不符。
- **依附于某业态产生的加赠权益,不作为业态层的拆分对象**——其价值**已含在所属业态的价格内**。例:酒吧通票里加赠的一杯酒,不在业态层单独切一份"酒水份额",它的价值已在"酒吧业态价"里;它只在酒吧份额内部按 §5.3 走「赠送权益预估成本」预扣与核销兑付。
  > 与 §5.3「每样赠品都是**独立权益**」**不矛盾,是两层**:§5.3 说的是**核销/绑定/成本**层——每样赠品各绑提供方商户、各自核销、各按内部结算价计成本;本条说的是**业态份额拆分**层——加赠权益不在这一层单独占份额。读的时候别把两层混成一层。

**④ 两个价,不可混用(B)**

| 价 | 用途 | 不得用于 |
|---|---|---|
| **各业态价格** | ① 定价相加(A)② 业态份额拆分占比(B ②) | 与提供商户结算成本 |
| **内部结算价** | 域内与提供方结算实物权益或经批准采用内部结算价的特殊权益 | 跨域份额拆分占比 |

> **【DEC-R7-P7】2026-08-05 已获批准并落地（DEC-R7 第二批），原术语待批注撤销**：术语统一为「**各业态价格**」（原称「票面原价」，该词在三份 HTML 中**零命中**，HTML 分账与定价一律写「各业态价格」）。术语表 `docs/terminology-canonical-v1.0.md` T-09 条已同步改写为「各业态价格 vs 内部结算价」，**本文已按 L-24（DEC-R3-2026-08-04-10）完成全文批量替换**；「各业态价格」与「内部结算价」两条价线不可互串的语义不变（见 §5.0c 与 K21）。

- 收费权益用于跨域拆分的价格与域内结算价格是两条独立价线，禁止互相回退或顶替；免费权益不参与跨域份额拆分。

### 5.0a 金额精度与分账尾差(R-7·2026-07-22 用户拍板 D15.1·已落地)

> 权威口径:治理地图 HTML「全局原则 · 金额一律精确到分」+ 基准 D15.1 + 产品总纲 §42。
> 落地:公共入口 `com.complex.platform.common.money.MoneyRounding`(唯一舍入/尾差 API);迁移 **V343**。

- **四舍五入到分(HALF_UP),不再整除截断**。一切「金额 × 比例」一律走 `MoneyRounding.bpsOf/prorate`。
  旧写法 `金额 * bps / 10000` 是**向零截断**:收费方(项目公司/平台/员工)系统性少收、余数悄悄留在付款方且不留痕,
  与「四舍五入」字面口径不符。本轮已改:渠道费、池前扣项(现为门票综合服务费,S4 前称项目留存)、按排名档位分池、套票折扣项目承担额、
  单独门票综合服务费、过期未核销归项目切分、核销累计增量公式(原 `Math.round((double)…)` 有浮点失精且对负数不对称)。
- **符号对称**:HALF_UP 远离零进位,`f(−x) = −f(x)`。跨月红冲取原行之反时逐分精确对消,
  P6「每笔实收 fee 落库 + 冲正取反」的守恒性不被舍入破坏。
- **不溢出**:全程 BigDecimal,消除 `金额 × bps` 先乘后除在 long 上回绕的风险。
- **多档只舍入一次**:阶梯型算式(如营业额抽成阶梯提成)先累精确份额、末尾收敛一次,避免逐档误差累积。

**尾差单列留痕(不得静默吞掉)**

| 项 | 口径 |
|---|---|
| 定义 | 尾差 = **应分总额**(对各方精确份额合计只四舍五入一次) − **Σ各方已舍入份额** |
| 归属 | 由产生该尾差的结算规则所对应的**实际结算责任主体**承担，不统一归项目公司或平台，也不得静默并入任一无责任商户 |
| 落点 | 金额 `settlement_bills.rounding_residual_cent`(**V343**,BIGINT 带符号,默认 0)+ 责任主体快照 `settlement_bills.rounding_residual_entity_id`(**V383**,VARCHAR(64),尾差为 0 时为空;解析自 `revenue_stream_attribution` 的 `all_pass_ticket` 流=娱乐平台公司,与 `attributed_entity_id` 同源、后台可配、项目级可覆盖) |
| 合列范围(V383) | 该列＝**池分账舍入尾差 + 渠道费按业态分摊尾差**。两者同为「按比例拆分四舍五入」成因,合成一笔单列;与 `pool_undistributed_cent`(第二段无参与者的整段余额)成因不同,仍分列 |
| 符号 | 正数表示各方舍入后合计偏少；负数表示合计偏多；两种情况都由实际结算责任主体处理并留痕 |
| 量级 | 尾差绝对值 ≤ 参与分账商户数(每家最多贡献 0.5 分);越界 = 分配算法出错,引擎 fail-loud 拒绝出单 |
| 守恒 | `Σ池分账明细 + 尾差 ≡ 应分总额`,逐分严格相等 |
| 自检 | 运行期两道:`verifyFormatSplit` 校验拆份额链 `Σ各业态净份额 + Σ各业态渠道费 + 赠送权益预估成本 + 池链综合服务费 ≡ 通票收入` 且 `Σ各业态渠道费 + 渠道费分摊尾差 ≡ 整单渠道费`(V383 起分摊尾差单列,不再由酒吧拿补数)(S4/V370 起原「可分配池 = 留存 + 各酒吧总池」随留存链删除;S6/V372 起 G 入链,且 Σ各业态渠道费/G/综合服务费 分别与各自合计互核);`verifyConservation` 校验分账链尾差恒等式与尾差量级;任一不成立抛 `SETTLEMENT_CONSERVATION_VIOLATED`,宁可拒绝出单也不出一张不守恒的结算单 |

> 票务积分发行成本本身若以任意分值计量，扣除后域间份额的尾差只复用本节既有域间分配尾差规则；不得另行发明积分专用舍入或尾差算法（DEC-R8-87）。

> **【恒等式依赖登记（2026-08-04 F5）：两个缺口层必须先改恒等式，反序必炸】**
>
> §5.0c ⑤ 登记的两个待改造缺口——**①通路费层（渠道费现为单层，未建通路费层）**、**②积分发行成本层（瀑布 `P = R − C − G − F_pool` 未含该扣项）**——**都不能只加扣项**。两道运行期自检写死了当前的项数与配平关系：
>
> - `verifyFormatSplit` 现校验 `Σ各业态净份额 + Σ各业态渠道费 + 赠送权益预估成本 + 池链综合服务费 ≡ 通票收入`，且 `Σ各业态渠道费 + 渠道费分摊尾差 ≡ 整单渠道费`；
> - `verifyConservation` 现校验分账链尾差恒等式与尾差量级。
>
> **正确顺序（不可颠倒）**：
> 1. **先改恒等式**——把通路费与销售渠道费拆成**两个独立项**分别入式（不能合并成一个「渠道费」项，否则两层的承担主体与适用范围区分不出来）；把**积分发行成本**作为**独立扣项**入式；
> 2. **同步改 `verifyFormatSplit` / `verifyConservation`** 的项数、分项互核与尾差归集；
> 3. **再接扣项落库**。
>
> **反序（先接扣项、后改恒等式）必炸**：新扣项一落，`Σ各项 ≢ 通票收入` 当场成立，`SETTLEMENT_CONSERVATION_VIOLATED` 会**拒绝出单**——不是「少算一点」，是**整月账单出不来**。同理，只改恒等式不改自检，等于把守恒校验放空。
>
> 另注：**通路费承担主体已裁决（原 E-07，2026-08-04 第三轮用户裁决 UD-15 / DEC-R6-01）**——**整单预扣、各域按分配份额自然共担**，不由收款主体单独承担；官方渠道同样产生通路费（见 `finance-settlement-product-prd-v0.1.md` §3A）。恒等式里通路费项**挂在「拆分前的整单扣项」一侧**，与销售渠道费同为整单预扣层、通路费在下、销售渠道费在上。**「不得编码」的阻断已解除，但本节的改造顺序仍然适用**——仍须先改恒等式与两道自检、再接扣项，反序仍会触发 `SETTLEMENT_CONSERVATION_VIOLATED` 拒绝出单。

- **越池判定改按「应分总额」**(= Σ已舍入 + 尾差)而非 Σ已舍入:特批闸管的是「业务上分超了池」,
  不应被 ±n/2 分的舍入尾差触发；尾差由实际结算责任主体承担，不另行改变超池审批边界。
  无舍入场景(按客数/固定额/比例除得尽)应分总额 ≡ Σ已舍入 → 与改造前逐分同判,**零行为变更**。
- **不产生尾差的补数式拆分**:池链综合服务费/可分配池(S4 起费为逐笔计提之和,池取整数补数)、
  综合服务费/商户净额、过期核销/未核销——后者恒取前者的整数补数,两侧相加恒等于总额,故无尾差,不占 `rounding_residual_cent`。
  ⚠️ **渠道费按业态分摊不再属于此类**(V383):原实现让酒吧支拿补数=把分摊尾差压给一个参与方,与「不得悄悄并进任一参与方」冲突;
  现各业态(含酒吧)一律按精确占比 HALF_UP,分摊尾差单列进 `rounding_residual_cent` 并挂责任主体。
- **超池两段拆(§5.0 超额 C 口径)保持向下取整,属本口径的合规特例**:`pool_i = ⌊a_i×可分配池/poolDistributed⌋`
  向下取整使 `Σpool ≤ 可分配池` 硬约束恒成立，余数单列留痕；若属于酒吧可分配池超额激励，则由娱乐平台公司承担，不能归城市项目公司。

- **第二段(项目级方式)**:`ticket_distribution_configs.method_type` 语义收窄为「第二段方式」,**仅 `by_rank_tier`(排名档位)合法**——写入口拒其它值、引擎对旧值 fail-loud(`SETTLEMENT_CONFIG_INVALID`);按**通票核销排名**分档,档位为**动态百分比**、**不是相对权重、不做归一化**(DEC-R8-24/25):一张票能进哪几家酒吧,就由那几家参加第二段的按其在**第二段参与者内部**的排名分第二段余额（拿了第一段的不占名次、其后名次前移）,**各档合计恒为 100%**;按本张票的**第二段参与家数**查「参与家数档位表」（原称「覆盖家数档位表」，同一张表两个叫法）取对应一行,行内各名次的百分比即该名次酒吧应分得的比例,`final_i = round_half_up(P2 × pct_i)`;比例基数 = **第二段余额**。**并列名次取均分（DEC-R8-36）**:当期核销入场人数相同的酒吧为并列名次,并列各家共同占用其本应占据的连续名次,`pct_i` 取这几个名次百分比之和的算术平均值(例:参与 5 家、两家并列第 4 → 各 (20%+15%)/2 = 17.5%),其后名次顺延;**该均分值不取整**(只在金额层 `round_half_up` 一次),未核销减除同用该值;均分尾差走既有 `rounding_residual_cent`。参与家数档位表为业务参数、后台可配,出厂默认见 ENUM「酒吧通票可分配池」条内嵌表（第二段参与 1 家 100%；2 家 57/43；3 家 40/30/30；4 家 31/23×3；5 家 25/20×3/15；6 家 23/17×3/13×2；7 家 22/15×3/11×3；8 家 18/14×3/10×4；9 家 15/13×3/10×4/6；10 家 16/12×3/9×4/6×2）,**每行百分比合计必须＝100%,不等于 100% 的配置不得生效**;排名一律在**本张票第二段参与者内部**编列,不用跨票全局名次,**按各酒吧当期核销入场人数由多到少排定**;第二段参与家数决定取哪一行,**与是否核销无关**——未核销酒吧那一份按未核销减除规则减除并按域归属,**不换行取表、也不由其余酒吧分掉(核销才拿)**;档位表变更须**提前向受影响的酒吧商户发出通告**,自送达之日起经可配通告期(出厂默认 1 个月)后方可生效,**只对通告生效后新售出的票适用**,不追溯已售出票已固化的池金额与档位。**【矛盾5，2026-08-06 扩表制】「参与家数档位表」不设家数上限**——按第二段参与家数**逐行配置**，出厂默认的 1~10 家十行**不构成上限**，`by_rank_tier` 的取表逻辑**不得再以 10 家为上界**；结算时遇到本张票的第二段参与家数**尚未配置对应行**的，该张票的第二段分配**暂挂、不出结果**（结算侧新增「**暂挂**」状态），并向后台发出「补配该家数档位行」的待办，**系统不得自行编列该家数的比例、不得就近取用其他家数的行、不得把该票余额转记为未分配池余额**；补配某一家数行**同样按档位表变更规则提前通告并经过通告期**，**通告期届满生效后，因缺该行而暂挂的票按该行续算结算**——此为「只对通告生效后新售出的票适用」的**唯一例外**（否则暂挂票永远无法用上任何一行、票款永远分不出去），已配置行的后续数值调整仍只对通告生效后新售出的票适用。**【H-22，2026-08-06】第一段的参与酒吧名单与固定金额／固定单价，其变更（含新增酒吧进入第一段、将酒吧移出第一段、调整金额或单价）与档位表变更同规则**：提前通告、经通告期后方可生效、**只对通告生效后新售出的票适用**，已售出的票按售票时固化的第一段名单与固定额结算、不追溯；实现上第一段配置须与档位表**共用同一套通告—生效—版本固化机制**（不新建第二套），**订单固化快照须一并保存第一段名单与金额**。

**两段分配(2026-07-28 用户拍板 D,替代原「三选一并列可配」表述)**

原写法「`by_venue_per_guest`/`by_rank_tier`/`by_fixed_amount` 三种是并列可配方案、项目公司级选一种」**已作废**。现行口径:三种方式**同时并存于一个池内**,分**两段**执行——

| 段 | 参与者 | 算法 | 基数 |
|---|---|---|---|
| **第一段(绝对额优先)** | 约定为 `by_venue_per_guest`(每客单价)或 `by_fixed_amount`(固定额)的酒吧 | 按各自约定的**绝对金额**先拿(每客单价 × 当月客数;或直接固定额) | 可分配池 |
| **第二段(比例分尽余额)** | 其余约定为 `by_rank_tier`(排名档位)的酒吧 | 按各自档位比例**分尽**第二段余额,Σ比例 = 100%(成立前提:**按第二段参与家数取行**——按覆盖家数取行会在有第一段时留下无人认领的百分比) | **第二段余额 = 可分配池 − 第一段合计** |

- **互斥铁律**:**拿了第一段的酒吧不再参与第二段**。一家酒吧的约定方式决定它落在哪一段,不能两段都拿。
- **守恒**：`可分配池 = 第一段合计 + 第二段合计 + 未分配余额 + 尾差`；尾差由实际结算责任主体承担。
- **边界(用户已拍板·S8 已实现)**:① 第一段合计 Q > 可分配池 P → **不削任何一家金额**、第二段整段为 0。**【2026-08-04 F5 改写】按事前口径，这一情形本不应出现**——第一段的固定额/单价在**配置生效前**已按池金额试算过、不通过即不得生效（§5.0 超池条）。若因历史配置或口径改造前的存量配置仍算出 Q > P，**引擎按未削减金额出单并 fail-loud 告警**，同时**登记为配置期试算闸未生效的遗留**；**不再新建「结算期超池待审批」出口**。原「整月单落既有超池特批路径(draft 待平台负责人特批)」属**历史实现**（错误码 `BILL_NOT_OVERPOOL_DRAFT`，见 §5.0 历史实现登记），不作业务规则；② 第二段**无参与者**(排名档位酒吧为空)而余额非 0 → 余额**显式归娱乐平台公司**,单列落 `settlement_bills.pool_undistributed_cent`(+归属主体快照列)并告警留痕,**不静默沉淀**;当月完全无酒吧参与同此出口。**【DEC-R8-20，2026-08-06】「通票未核销减除额」是另一栏**:不得落在 `pool_undistributed_cent`,也不得并入 `rounding_residual_cent`;减除额、未分配池余额、金额尾差三者即使同归一个主体也必须分三栏列示;减除额归属改为**按域路由**(见 ENUM「域归属对照」条:酒吧域→娱乐平台公司、游乐域→游乐公司、餐饮与零售域→城市项目公司、演出传媒域→传媒公司)。原触发条件中的「档位权重全 0」随动态百分比制作废;③ 池内**只有**排名档位酒吧 → 第一段为 0、第二段基数 = 全池**带符号直传**(负池月分负额=向酒吧追回,R-3 不变);④ **【DEC-R8-24/25，2026-08-06 整条推翻重写】第二段不做归一化分光**:**【DEC-R8-37，2026-08-07 改按参与家数取表】**按**本张票的第二段参与家数**取「参与家数档位表」对应一行,`final_i = round_half_up(P2 × pct_i)` 只舍入一次,`pct_i` 为该酒吧在**第二段参与者内部排名**所对应的百分比(并列名次按 DEC-R8-36 取均分);原「按覆盖家数取表」与 ⑤ 的「参与者内部排名」两句算术上不相容(5 家覆盖、1 家走第一段时只分掉 85%),故取表口径随 ⑤ 收敛;**配置写入口与引擎均须强校验「所取表行百分比合计＝100%」,不等于 100% 即 fail-loud 拒绝**;原「一次归一化分光 `P2 × w_i / Σw`、档位只是相对权重、权重和不足 100% 也分尽」口径**整体作废**;尾差走既有 `rounding_residual_cent`;⑤ 排名在**第二段参与者内部**编(拿了第一段的不占名次)。
- 未核销权益不参与两段分配。**【DEC-R8-21/22/31，2026-08-06 场次终结制】已完成检票环节（刷码核销成功）的票，其未在该场次内核销的权益在**场次结束时**即确认为未核销份额，不等票到期**；从未完成检票环节的票，到期后按 §3.2 的门票所属经营域规则归属。两类钱一律按 ENUM「域归属对照」条逐域归属，**各自单独立项留痕、不合并**。**⚠ 确认时点前移会改变跨月票的入账月份，进而改变月度排名与分账基数。**

**可分配池只在实际发生核销的酒吧之间分配（2026-08-04 F5 补，依据 ENUM「酒吧通票可分配池」条、BSM「酒吧通票可分配池的池金额，是该票扣完第三方渠道费用」（该条含「可分配池只在实际发生核销的酒吧之间分配……减除后的余额才进入分配」一段）条）**

「未核销不参与」不只是「不给它钱」，而是**要先把它那一份从池里减除**，剩下的才进入分配。**逐票执行，不按月度汇总近似**：

| 步 | 对象 | 动作 |
|---|---|---|
| **前置 0** | 本张通票 | 取该票**固化的可分配池金额** `P`（售票时随订单固化，见 §5.0c） |
| **前置 1** | 本张票覆盖、但**当期未被核销入场**的酒吧中，**参加第一段**的 | 按其**第一段的固定金额或固定单价**从 `P` 中**一次减除**；**【H-21，2026-08-06】不得再按第二段档位对同一家另行减除**（参加第一段的酒吧本就不占第二段名次，无第二段比例可用） |
| **前置 2** | 本张票覆盖、但**当期未被核销入场**的酒吧中，**参加第二段**的 | 按其**在本张票的第二段适用比例**（并列名次取均分值）**一次减除**，基数为**前置 1 之后的余额（＝第二段余额）**；**同一家酒吧只按其所属分段减除一次，两段不叠加（H-21）** |
| **分配** | 本张票**实际发生核销**的酒吧 | 对**减除后的余额** `P'` 执行 §5.1 两段分配 |

- **减除的钱不进任何酒吧**：`P − P'` 是「本张票覆盖但没人来核销」对应的那部分，**不得**因为别的酒吧核销了就被它们分掉。**【DEC-R8-20，2026-08-06】该笔的去向已定**：按票种经营域归属（见 ENUM「域归属对照」条，酒吧域即娱乐平台公司），在该张票的分账结果中单列为第三栏「通票未核销减除额」，**不并入未分配池余额、也不并入金额尾差**；三者即使同归一个主体也必须分三栏列示。**【矛盾2，2026-08-06】只要该票存在第二段参与者，无论其当期是否被核销入场，一律按本段规则逐家减除并计入该栏，不因全部未核销而改记为未分配池余额。**
- **守恒式**（逐票，逐分严格相等）：

```
P（本票固化可分配池）
  = Σ未核销酒吧第一段减除额            → 归属：按「域归属对照」路由（酒吧域＝娱乐平台公司）· 单列「通票未核销减除额」栏
  + Σ未核销酒吧第二段适用比例减除额    → 归属：同上，同一栏（两项减除额合成一栏，与下列两栏分列）；同一家只落其中一项、两项互斥不重复（H-21）
  + 第一段实分合计（已核销酒吧）        → 归属：各该酒吧商户
  + 第二段实分合计（已核销酒吧）        → 归属：各该酒吧商户；动态百分比制下 ＝ P2 × Σ(已核销各家的 pct_i)
  + 未分配池余额                        → 归属：娱乐平台公司 · 落 `pool_undistributed_cent`
  + 尾差                                → 归属：实际承担结算责任的主体 · 落 `rounding_residual_cent`
```

- 该守恒式**并入 `verifyConservation` 的逐票校验**，不成立即抛 `SETTLEMENT_CONSERVATION_VIOLATED` 拒绝出单（与 §5.0a 同一处置）。**同批增加「所取参与家数档位表行的百分比合计＝100%」断言（DEC-R8-24；取行入参已按 DEC-R8-37 改为第二段参与家数），不成立同样 fail-loud。**
- **验收用例**：
  - **U-1 全核销**：本票覆盖 3 家酒吧、3 家均有核销 → 两项减除额均为 0，`P' = P`，结果与改造前逐分一致（零行为变更）。
  - **U-2 部分未核销·第一段**：覆盖 3 家，其中 1 家参加第一段且**未核销** → 先按其第一段固定额/单价减除，余额再分给其余 2 家；**未核销那家分得 0**，且**其余两家分得的合计 = P − 减除额 − 未分配余额 − 尾差**。**新增断言（H-21，2026-08-06）：该家只被减除一次，不得再按第二段档位二次减除**——串行两次扣减即为真实资金差错点。
  - **U-3 部分未核销·第二段**：覆盖 3 家，其中 1 家参加第二段且**未核销** → 按其档位比例从前置 1 后的余额中减除；减除额**不流向**其余酒吧。
  - **U-4 全未核销**：本票无任何酒吧核销 → 减除后 `P' = 0`，无人分账。**【DEC-R8-20，2026-08-06 修正】此时全部池金额落在两项减除额栏，`pool_undistributed_cent` 应为 0**——不走边界②的未分配池余额出口，而走**「通票未核销减除额」第三栏**，按域归属（酒吧域即娱乐平台公司）单独立项留痕，**不得静默沉淀**。原写法（走边界②）与本节守恒式自相矛盾，已作废。
  - **U-5 守恒断言**：以上四例逐票执行守恒式，任一例不逐分相等即判失败。
  - **U-6 参与家数取表（DEC-R8-24/25/37）**：第二段参与 1~10 家各造一票 → 逐票断言所取表行的百分比合计 ＝ 100%，且各家 `pct_i` 取自其在**第二段参与者内部**的排名；**【矛盾5，2026-08-06 改扩表制，原「超表即不参与」作废】第二段参与家数尚未配置对应行的，该票第二段分配暂挂、不出结果并发「补配该家数档位行」待办**；断言：**不得插值、不得就近取行、不得转记未分配池余额**；补配行经通告期生效后，暂挂票按该行**续算结算**。**新增断言：5 家覆盖、1 家走第一段 → 取「参与 4 家」行、合计 ＝ 100%；反例（取「覆盖 5 家」行、合计 85%）须 fail-loud。****新增并列均分断言（DEC-R8-36）：参与 5 家、两家并列第 4 → 各 17.5%，全行合计仍 ＝ 100%；参与 3 家全并列 → 各 33.3333…%，池 100.00 元时各 33.33 元、1 分尾差落 `rounding_residual_cent` 不塞给任何一家。**另断言：3 家覆盖、1 家未核销时**不换成 2 家行**（否则减除额恒为 0，DEC-R8-20 被架空）。

### 5.1a 主理人分账透明度（2026-08-04 F5 补，依据 ENUM「酒吧通票可分配池」条「通票分账的计算规则对该酒吧主理人完全可见」）

**通票分账的计算规则对该酒吧主理人完全可见**，具体可见项如下（在商户专区按酒吧 scope 展示）：

| 可见项 | 说明 |
|---|---|
| **本店当期核销入场人数** | 用于第一段 `per_guest` 计算与第二段排名的原始口径数 |
| **本店在第二段的排名与流量名次** | 名次本身、以及命中的档位 |
| **本店适用的第一段固定额或固定单价** | 该店约定的绝对额规则（`per_guest` 单价或 `fixed` 固定额）与其生效版本 |
| **每一张票本店能分到多少** | 逐票的本店分得金额，可下钻到该票的分账依据 |

- **脱敏边界（硬约束）**：**仅其他酒吧分得的具体金额不对其开放**。
  - 主理人**可以**看到自己在第二段的**名次**（名次本身不泄露他人金额）；

  - 其他酒吧的**核销人数、第一段单价/固定额**同属他店经营数据，不对本店主理人开放。
- **与分红可见性的关系**：主理人作为股东对**本商户**全部经营数据完全可见（见 `dividend-engine-prd-v0.1.md` §7），与本条一致；两条共同的边界都是「**本店全开、他店金额不开**」。
- **验收**：
  - 主理人账号能查到本店当期核销入场人数、第二段名次与档位、第一段固定额/单价及其版本、以及逐票本店分得金额；
  - 同一页面**查不到**任何其他酒吧的分得金额（接口返回也不含该字段，不是仅前端隐藏）；
  - 越权请求他店明细返回跨商户禁止错误，不返回脱敏后的近似值。

### 5.3 赠送及套票权益结算

**权益模型**：票内酒水、小食、餐饮、零售或特殊权益均作为独立权益，绑定实际提供方并单独核销。发放或出票只记录权益和预算占用，核销成功后才形成对提供方的实际结算。

- **每项权益必须绑定实际提供方和审批版本，避免悬空账（2026-08-05 R7 补，依据 DIFF-A-042；BSM FIN-20「通票结算审阅台账」条）**：权益上的**实际提供方**与**审批版本**两项**均为必填**，**缺任一项不得上架、不得核销、不得结算**；财务侧独立审阅台账按项目、经营域、责任主体和实际提供方列示时，**任何一项权益都不得出现无提供方或无审批版本的悬空行**。

**① 先识别成本承担方式**

- 商户让利型免费权益：核销后也不与商户另行结算。
- 域主管公司承担型权益：核销后按出票时锁定的内部结算价与提供方结算；如果主管公司批准的权益价格低于内部结算价，由作出该决定的主管公司承担差额；高于内部结算价的余额归该主管公司。
- 采用内部结算价还是比例结算，由对应域主管公司决定并在系统中配置和审批，商户只能提交资料和履约事实，无权选择。
- 酒吧入场资格是目前唯一不设置内部结算价的酒吧权益，进入酒吧可分配池按固定金额、固定单价或排名档位规则分配；其他酒吧权益不得据此例外。

**② 赠酒按酒吧分配(票面规则)**
- 一张通票覆盖的**每个酒吧赠酒杯数不得低于后台按票种配置的最低赠酒杯数（出厂默认 1 杯）**;
- **各酒吧分别赠几杯,在售票时写明票面**;
- **A 酒吧的赠酒只能在 A 酒吧核销**,不能拿到其他酒吧核销;跨吧核销一律拒绝。
- 核销顺序不变:同一酒吧须**先核入场权益、再核该吧酒水权益**。

**③ 核销兑付 → 由作出权益规则决定的域主管公司承担**

- 客人核销后，按该权益已锁定的结算方式与实际提供方结算；核销一件结一件，未核销不结算。
- 酒吧域由娱乐平台公司负责，游乐域由游乐公司负责，演出域由传媒公司负责，资产及其直接管理第三方商户由城市项目公司负责，中央餐饮供应的酒水、小食和餐饮供应链权益由中央餐饮公司负责。
- 各域成本、差额和收益分开记账，不得统一转给娱乐平台公司或城市项目公司。

**④ 酒吧可分配池的分配**

- 酒吧入场资格进入 §5.1 两段池；采用内部结算价结算的实物或特殊权益不重复进入该池。

> **当前实现缺口**：下列历史实现记录中，把全部赠送权益预扣、兑付及差额统一归娱乐平台公司的部分，只能说明现状，必须按上述域主管公司和成本承担方式改造后才符合业务规则。

## 6. 权益结算规则

### 6.1 权益结算价选择

不得按“实物／虚拟”简单二分结算方式。权益先确定所属经营域、成本承担方式和实际提供方，再读取该域已批准的结算规则：

- 商户让利型免费权益不结算。
- 域主管公司承担型权益，核销后按锁定内部结算价或主管公司批准的比例规则结算。
- 酒吧入场资格是目前唯一不设置内部结算价的酒吧权益，进入酒吧可分配池；除该例外外，不得仅因权益是非实物就改用“签约权益单价”。
- 票面价格用于跨域组合通票的域间份额计算，内部结算价用于域内结算，两条价线不得回退或互相顶替。

> **实现状态**：V379/V380 已将改价入口收敛为内部结算 SKU 目录草案链，并把原 `agreement_price_cent` 改为只读快照。现有解析器中仍按“实物／虚拟”二分或回退签约价的历史分支，如与上述规则不一致，属于待改造缺口；实现不得反向定义业务规则。
>
> **改价口径（资金，批 10 起）**：普通权益及不属于积分兑换虚拟券第②类的券，若其业务规则读取项目内部结算价目录，继续在核销或结算时锁定届时生效价；已经核销或结算的历史按流水中已锁定价格执行，后续改价不追改。**积分兑换虚拟券第②类“店内实物／服务”是明确特例**：发券时锁定项目、内部结算价、方案和成本承担版本；发券时只预占库存或履约能力、不与商户结算，实际核销或完成履约后按发券时锁定的该项目该商品内部结算价形成商户补偿。发券后、核销前目录改价不得改动该券的锁定价。第①类商户折扣券按抵扣处理、不预占库存；第③类平台或外部合作伙伴按约定结算；不得把第②类的库存与补偿规则外推到第①类、第③类。现有 `SettlementPriceResolutionJdbcIntegrationTests#catalogPriceChangeDoesNotMoveAlreadyVerifiedMoney` 只证明普通目录路径的草案不生效、历史不追改和后续核销取新生效价，不能覆盖或推翻第②类的发券锁价特例。

### 6.6 免费权益(票面价 0)的成本承担分两类(2026-07-28 用户拍板 C,业务 HTML `88eba70c` 为准)

票面价格为 0 的免费权益,**按成本由谁承担**分成两类,**在票种配置里逐权益标明成本承担方**:

| 类 | 定义 | 平台是否承担成本 | 是否与提供商户结算 | 是否计入赠送权益预估成本 |
|---|---|---|---|---|
| ① **商户让利型** | 餐饮 / 零售等商户**为引流自行让利**、搭进通票的免费优惠 | ❌ 不承担 | ❌ 不结算 | ❌ 不计入 |
| ② **平台出资型** | 平台为做活动**向商户采购后免费赠送**给客人的权益 | ✅ 承担 | ✅ 按**内部结算价**与提供商户结算(核销一件结一件,§5.3 ③) | ✅ 计入(§5.0 ③ / §5.3 ①) |

- **两类都不参与业态份额拆分**(§5.0c ②)——票面价为 0,占比分子为 0。
- **成本承担方是必填项**:票种配置未标明的免费权益,视为配置不完整,不得启用(fail-closed,同 AUD-015 赠饮模板启用前置校验范式)。

## 7. 各票种结算规则

### 7.1 通票

- 酒吧通票由娱乐平台公司负责定价、售票、收款和域内结算；纯游乐通票由游乐公司负责；演出域产品由传媒公司负责；跨域组合通票由有项目之上权限的平台主体组织，拆域后由各域主管公司负责其域内结算。
- 城市项目公司不负责酒吧、游乐或演出域通票的本地定价、售票和分账。
- 结算按 §5 执行。

### 7.2 单一酒吧门票与门票综合服务费

- 单一酒吧门票由对应酒吧商户定价、销售、处理退款并确认门票收入；**票款由娱乐平台公司统一收款后结付给该酒吧商户**（2026-08-05 R7 同步，依据 DEC-R6-02／UD-16；ENUM／BSM「定价、售票与收款主体」条。原句中的「收款」已删除）；娱乐平台公司不取得该门票收入。
- 娱乐平台公司按已生效规则，向酒吧商户逐张收取门票综合服务费。规则可选择比例或固定金额，并可以设置封顶。
- 封顶只适用于单一酒吧门票；酒吧通票及跨域组合通票酒吧部分不封顶。
- 纯游乐票、纯游乐通票和演出票不收取娱乐平台公司的门票综合服务费。
- **实装现状（FS-013，2026-10-19，V506）**：计费月按操作员裁决 2026-10-19 第 3 条（所选选项原文）：「售出月，只退款剔除」：按客人付款成功（售出）所在月计入；之后只有整张退款成功才从原月剔除重算；到期没用的票照常计费。出票即逐票锁定计费基数（订单客人实付按张均分，即该张票订单上保存的最终选中价）、费率或固定额与规则；同一项目×酒吧×计费月首张票写入时锁定该月封顶，之后改配置不影响原月。月应收＝min(Σ未退票逐票费, 锁定封顶)，月结过账时（生产月结出平台单、覆盖全部项目）单独挂酒吧应收（`single_bar_service_fee`，项目取计费月锁定的售票项目），走三个付账日，与票款应付分别收付、不轧差；售出时已锁定的票核销时不再另抽。整张退款成功回原计费月重算，只登记台账未覆盖的差额：先调减原应收未收部分（V344 原行不动＋冲正行＋重述行），超出部分列应退；调整记在当前账期、关联原计费月。

> 2. **锚点**:`settlement_transactions` 加 `parent_ticket_id`(V367,父票=`issued_entitlements.parent_ticket_id`,V285 起每次出票都建父票实例)。核销行从权益带上(`SettlementSettledEvent` 新增 `parentTicketId`,`TicketVerificationService` 两条成功路径都带);冲正行**原样沿用**被冲那行的值。
> 3. **判定**:固定额模式计提前查「该票已落服务费净额」(`sumTicketServiceFeeCent`,核销正 + 冲正负,不切月窗——「一张票一道」是票的属性不是月的属性,与月度封顶两道闸并行)。净额非零 → 本笔置 0(这张票收过了);比例模式**不设闸**——比例费本就是同一道费按核销增量的线性拆分(Σ = 费率 × 该票总收入),设闸反而漏钱,故**比例模式逐分不变**。
> 4. **冲正取反 + 锚点复位**:冲正行费取原行之反、父票锚点沿用 → 该票净额抵回 0 → 下一笔核销**重新收一道**(票还在、费该收,不能因为退过一次核销就永远免单);全生命周期净额恒 = 一道。
> 5. **无锚点 = 不合规数据,直接拒绝计提**:`parent_ticket_id` 为空的核销一律不提这道费(核销流水本身照落),**不退化成「按核销笔数各收一道」、不做任何兼容分支**——开发环境数据最终全部清除,存量不合规数据清掉重造(2026-07-28 用户口径)。
> 6. **验收**(`SettlementFeePerTicketS3Tests` 5 绿):K7 固定额同一张票核销 5 次只收 1 次(改前 5 次);不同票各收各的一道;比例模式结算单整行 `SELECT *` **全列比对**与改前逐分一致 + 每笔费逐笔相等;冲正取反 + 复位后重收;无锚点拒提。既有守恒/封顶/换维测试全绿(封顶用例已按「固定额=每张票一道」把两笔核销改为两张票)。

## 8. 退款

- 原则上售出门票不退款；未到场、忘记使用或主动放弃均不是退款理由，未核销也不得自动转成已核销。
- **仅在下列五种情形退款**（2026-08-04 F5 与票务口径统一，依据 BSM「官方和第三方渠道门票售出后原则上不退款；未到场」（该条含「只有票种规则明确允许……这五种情形才允许退款」一段）条、BSM「退款」条）：
  1. **票种规则明确允许**；
  2. **活动或场次取消**；
  3. **平台或履约方无法提供服务**；
  4. **重复扣款**；
  5. **法律法规要求**。
- **「或完成特殊审批」已删除**：「获授权特殊审批」**不再作为退款理由**。确需在五种情形之外退款的，**只能由持授权 U 盘密钥的最高权限逐笔放行，每次只对当前这一笔生效**，并记录**原因、责任、审批、规则版本与冲正**。这是**逐笔例外放行**，不是第六种退款理由，**不得据此建立常规审批入口或批量放行**。
- **另一处例外单列**（BSM「退款」条）：客人出现**重大情绪不稳定、安全问题或其他必要问题**时，由**夜班值班经理及以上**批准免除其通票费用——**此时即使已核销也予以退款**，须记录原因、批准人与当时情形。除该例外外，**退款只发生在完全未核销的票上**，因此**不存在同一订单既「部分核销」又「部分退款」的情形**。
- 合同不得改变平台统一退款原则。
- 退款成功后按原核销和结算事实逆向冲正；跨月冲正带符号落当月红冲，并保留原单、原因、审批和冲正链路。**原月已结付后才撤销的核销**（操作员裁决 2026-10-19 第 4 条「单独列追收、按原月重算」，FS-021）：不并入当月分池与专属净额，当月应付照常全额；被撤销那笔另列追收明细——单店（专属直付）按该次核销原结付金额，分池按原月剔除该次核销后重算各家应得的差额逐家追回（`settlement_item_recoveries` 回指原月结算单），过账为追收应收（`ticket_distribution_recovery`），与当月应付分别收付；原月账单与已付款不回改。
- 不另设退款手续费预扣规则。

### 9.7 内部结算 SKU 目录（2026-08-01 已由 V379/V380 落地）

每个项目独立维护内部结算价目录，不是全国统一价格。不同项目价格互不覆盖、不得跨项目引用；只有取得项目之上相应权限的人员才可以跨项目查看，但查看权不自动包含编辑权。普通权益及不属于积分兑换虚拟券第②类的券，若其业务规则读取本目录，在核销或结算时把届时生效价固化到流水，后续改价不追改历史；积分兑换虚拟券第②类按发券时锁定的项目、内部结算价、方案和成本承担版本执行，核销时不重新读取目录新价。

实际提供商品或服务的主体提交本项目 SKU 的价格资料，由对应域主管公司审批，提交人与审批人必须分离：酒吧由娱乐平台公司审批；游乐由游乐公司审批；演出传媒由传媒公司审批；餐饮与零售商户（含独立、联营、租赁各种合作模式）统一由城市项目公司审批，其中中央餐饮供货部分仍由中央餐饮公司内部差人审批；中央餐饮公司供应的酒水、小食和餐饮供应链商品由中央餐饮公司内部差人审批；城市项目公司直接管理的第三方商户由城市项目公司审批；业态为“其他”的商户，必须在商户档案上指定一家主管公司并说明理由，由该主管公司审批；未指定的不得开通任何结算与分账。商户不能批准自己的价格，也不能决定采用内部结算价还是比例规则。

“中央餐饮供货部分”与“中央餐饮公司供应的酒水、小食和餐饮供应链商品”是同一例外的范围说明，不得被解释成两次审批或两个价格。

**开通前置闸（2026-08-05 R7 补，依据 DIFF-A-038；BSM FIN-01「内部结算价目录」条原文）**：**任何商户在没有获批内部结算价之前，不得为其开通需要该价格结算的权益或券。** 该闸发生在**配置期**，早于核销期；与「核销时取不到价一律 fail-closed 拒绝核销」是**两道独立闸口**，后者不得顶替前者。

**边界：内部结算价审批不等于基础消费积分发放审批。** “未获批内部结算价”的开通前置闸只约束需要该内部结算价结算的权益或券；不得解释为基础消费积分必须由商户申请、同意或批准。凡纳入会员计划覆盖范围的在营商户，必须参加积分计划并强制发放消费积分；其发生符合已生效业态规则的有效消费时，积分按规则自动产生。商户不得私自关闭发分；商户是否同意、是否另行申请以及内部结算价是否获批，均不得成为基础消费积分产生的前置条件。“其他”业态未指定主管公司时不得开通结算与分账，是独立于内部结算价的主体路由闸，不得把两道闸混成一条。

内部结算价、成本价、进货价、毛利、采购协议价、结算比例、底价及系统识别出的其他敏感经营数据均按敏感数据管理。查看、导出和编辑分别授权；普通用户、会员、前线员工及无价格权限的商户即使业务流程使用了内部结算价，也不得查看或修改该价格。

**当前落点**：统一目录为 `internal_price_catalog`，目录条目使用稳定 `item_code`；酒吧商品、酒吧套餐、票务权益模板和券定义四处保存 `catalog_item_code` 引用及只读价格快照。直填内部价的旧入口已封闭，改价走目录草案、他人复核转正和后续生效，已核销历史不追改。

> 完整落地形态和目录字段见 `finance-settlement-product-prd-v0.1.md` §3B；该文档是产品细化，不拥有高于三份业务 HTML 的解释权。取价时点依 §6.1 与本节上文的分类执行：普通目录路径在核销或结算时锁定届时生效价；积分兑换虚拟券第②类在发券时锁定项目、内部结算价、方案和成本承担版本，实际核销或完成履约后按该发券快照补偿。不得再用“所有取价路径均在核销时固化”覆盖第②类特例。

## 10.2D 跨域组合通票分账口径与 S11 实现差距

> 最终业务解释以三份业务 HTML 为准。S11 是历史实现证据，其中把域内通票也拆域、或把酒吧份额重复扣渠道费的行为均不符合现行规则。
>
> **【2026-08-04 F5 更正】** 原句中「把餐饮／零售域份额直接给商户」一项**系误登记，已删除**：按 ENUM「跨域通票分配」条，餐饮与零售的**域主管公司为城市项目公司（管规则与审批）**，而**其份额由跨域组合通票的收款主体（娱乐平台公司）直接与实际提供的餐饮、零售商户结算**——**直付即合规路径**，不是缺口。

**定价**:综合/联合通票售价 =(游乐业态价格 + 酒吧业态价格 + 收费的餐饮/零售业态价格)× 折扣。免费的(各业态价格 0)不计入价值。

**分账**：域内通票不拆域；只有跨域组合通票按下列顺序处理：

```
售价 → 整单扣一次第三方渠道费
     → 按收费权益的有效价格拆经营域份额（免费权益不参与）
          酒吧域 → 娱乐平台公司按酒吧域规则结算，不再扣渠道费
          游乐域 → 游乐公司按游乐域规则结算
          演出域 → 传媒公司按演出域规则结算
          餐饮域 → 规则归城市项目公司（域主管）；款项由娱乐平台公司（收款主体）直付实际提供的餐饮商户
          零售域 → 规则归城市项目公司（域主管）；款项由娱乐平台公司（收款主体）直付实际提供的零售商户
          其他域 → 对应域主管公司按本域规则结算，不直接跳过主管公司结给商户
```

- **份额比例在出票时就定死**:`TicketOrderService.allocateRevenue` 按各权益 `component_price_cent`(各业态价格)占比把订单实付拆到每张权益(`issued_entitlements.allocated_revenue_cent`),核销时逐笔落 `settlement_transactions`;月度引擎只是把权益级份额**按提供方商户的业态归堆**,不另发明分摊算法。
- **各业态价格的 NULL / 0 语义(收紧)**:**0 = 免费**(0 元餐饮/零售券、加赠酒水小食)→ 权重 0、不参与拆份额,它的价值本就含在别的业态价格里,再分一份就是让提供方**双收**(既拿营收份额、又按内部结算价被兑付);**NULL = 没配价** = 不合规 → **票种发布直接拒**(`TICKET_COMPONENT_PRICE_REQUIRED`),漏到出票也拒(`TICKET_COMPONENT_PRICE_MISSING`)。**废除「全没配价就按数量均摊」的兜底**——均摊会把免费权益和赠品也算成收入,且账面上每一分都分掉了、事后查不出分错了谁。
- **第三方渠道费**：跨域组合通票在拆域前从整单只扣一次；拆域后的任何份额不得再次扣同一费用。V381 已支持比例／固定金额二选一，但既有“按业态分摊后尾差归酒吧”的实现不符合现行规则；尾差应由该笔渠道费的实际结算责任主体承担并单列留痕。
- **折扣承担方补回口径扩到所有业态**:`platform_absorb` 时**每个业态**都按满额份额计、`merchant_absorb` 时每个业态都按折后净额计、`split_by_ratio` 按配置比例。旧实现只补酒吧那一路,同一张票里各业态两套口径。
- **排名/客数只算酒吧**:`aggregateMerchantStats` 加业态过滤——一家餐厅核销几张餐券就能在「按核销数排名分池」里占掉一个名次、把本该属于某家酒吧的档位挤掉,是真会分错钱的。
- **两条价线不可互串(K21)**:拆份额只允许出现**各业态价格**(`ticket_type_entitlements.component_price_cent`);与提供方结算成本只允许出现**内部结算价**(`bar_products.internal_settlement_price_cent` / `entitlement_templates.agreement_price_cent`)。任何一条 SQL / 计算路径都不得互相替代或回退。
- **守恒(K20,运行期 fail-loud)**:`Σ各业态净份额 + 整单渠道费 ≡ 通票收入`;`Σ各业态渠道费 ≡ 整单渠道费`;`Σ各业态净额 ≡ 当月进池核销合计`(业态分组不重不漏)。任一条不成立立即拒绝出账,不出一张不守恒的结算单。
- **本批范围**:只保证「份额算得出、归属定得住、非酒吧业态不进酒吧池」并单列留痕;游乐/餐饮/零售各自的**完整结算单**不在本批范围。
- **配置面**:票种组合配置页(ADM-TKT 票务政策)各行补「各业态价格(元)」输入(酒吧行/游乐行/餐饮行/单条绑定),免费的填 0。

- 历史已出票据:按票有效期,新引擎从切换日起对未来核销生效;存量已分摊数据保留为历史口径,不追溯重算(除非财务要求)。
