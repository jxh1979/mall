## 1. 背景与目标

### 1.1 问题
现状系统在**出票时**就把票款按定价一次性分摊入各商户账(`issued_entitlements.allocated_revenue_cent`,`TicketOrderService.allocateRevenue`),**与是否核销无关**。这导致:
- 客人买了含 5 个权益的票只用了 4 个,第 5 个权益的钱**仍已计入对应商户账**,项目公司无法回收;
- 无"按核销结算"、无"未用权益归项目"、无各业态公司(SPV)分账层、无手续费预扣、无单独门票服务费、无套票折扣归属、无场次入场规则——这些要么文档有代码无,要么全新。

### 1.2 目标
把结算从"**发放即分摊**"重构为"**按实际核销逐笔结算 + 未用权益归项目公司**",并建立一套**全可配置的多主体分账体系**,精确复现财务底稿的商业逻辑,支撑地产全链的财务与经营口径。

### 1.3 非目标(本期不做/另批)
- 财务预测/IRR/敏感性测算(那是底稿的事,不进系统);
- 各业态公司的完整会计核算/报税(系统只做**营收分账与结算单**,出具给财务,不替代财务软件);
- 资产公司折旧、CapEx 等纯财务项。

## 3. 核心设计原则

1. **按核销结算**:权益收入在**核销发生时**才确认结算给商户/SPV;未核销 = 不结算给商户。
2. **未核销权益款归娱乐平台公司(S8 已切,2026-08-01)**:票有效期结束(或作废)后仍未核销的权益,其对应收入不结给商户——按业务 HTML 逐字「没有被核销的权益,那部分钱归**娱乐平台公司**留存;游乐通票的未核销权益款归**游乐公司**」。按**提供该权益的商户业态**(`merchants.merchant_type`,与 S11 池基过滤同一判定源)分流:游乐 → `amusement_ticket` 流 → 游乐公司;其余 → `all_pass_ticket` 流 → 娱乐平台公司。主体经 `revenue_stream_attribution` 后台可配解析(V375 种全局默认 `be_ent_platform`/`be_amusement`),解析不到主体 fail-loud 拒绝落账;账本落 `beneficiary_type='entity'` + `beneficiary_entity_id`。(原「归项目公司」口径作废;切换前已落的 `project` 旧行为 append-only 事实,报表口径兼读不改写。)
3. **全可配置、禁硬编码**:分账方案、留存比例、内部结算价、权益单价、服务费率、手续费率、赠酒单价、访问点位数、折扣归属、中央餐饮开关、**各项税费(增值税/文建费/附加,有无+费率)**等,一律走配置表 + 后台页 + 权限。
4. **逐笔可追溯**:每笔结算能追溯到票→权益→核销记录→结算明细→结算单,支持对账。
5. **幂等与防混账**:核销/结算/退款全幂等;权益归属严格隔离(project_id / merchant_id / spv_id),不串户。
6. **向后兼容迁移**:提供从 `allocated_revenue_cent`(发放即分摊)到新引擎的迁移与并行校验路径(§11)。
7. **业务规则 ≠ 财务测算假设(2026-07-04 用户纠偏,关键)**:财务底稿里大量"公式"是**预测假设**——用来在财务模型里估算营收数字(如"50% 通票客人会买额外酒水、平均 1.5 杯、每杯 20 元""客流 7100 人/日""满台率 70%")。这类假设**一律不进系统**——系统按**真实交易/核销逐笔记账**(客人实际买几杯记几杯、实际访问几个点位算几个)。只有"每一笔钱怎么算、怎么分"的**结算规则**(留存比例、服务费率、内部结算价、佣金率、手续费率、折扣归属、税率)才进系统做配置。**成本同理:系统成本 = 真实费用归集,不用"收入×成本率"估算。** 附录 A 已据此把参数分为"进系统"与"仅财务测算"两栏。

### 5.0 通票分账全流程(2026-07-28 用户拍板,业务 HTML `f19ea732` 为准,批 2 权威)

> **终态全链一览(2026-08-01 已全部落地)**:通票收入 R → ① 整单扣**第三方渠道抽成 C**(拆份额之前,`channel_fee_configs` 项目×渠道可配)→ ② 按**各业态票面原价占比拆业态份额**(S11/V366:游乐份额→游乐公司、餐饮/零售份额→提供方商户,单列留痕)→ ③ 酒吧份额内扣**赠送权益预估成本 G**(S6/V372-V373,按件计/按票计两模式,归娱乐平台公司)→ ④ 扣**门票综合服务费 F_pool**(S2/S3/S4·V365/V367/V370:按票种维、所有门票一道、一张票只收一道、与留存同一项,归娱乐平台公司)→ ⑤ **可分配池 `P = R − C − G − F_pool`** → ⑥ **两段分配**(S8/V374-V375:第一段商户级固定规则按绝对额先拿,第二段排名档位对余额归一化分尽,互斥;无人分的余额显式落 `pool_undistributed_cent` 归娱乐平台公司)。**未核销权益款**按提供方业态分流:归娱乐平台公司、游乐通票归游乐公司(原则 2,V375 种子,fail-loud)。纯酒吧票 = 业态集合只有酒吧的退化情形,同一条链不开第二套瀑布。

一张通票收入按下列**固定顺序**逐笔分账(以 99 元为例):

| 步 | 算法 | 例(99 元) |
|---|---|---|
| ① 通票收入 | — | 99 |
| ② 扣第三方渠道抽成 | 第三方抽成(美团/抖音等)**最先扣,在所有费用之前**;比例/金额后台可配 | − 渠道费 |
| ③ 扣**赠送权益预估成本** | **归娱乐平台公司**。票内加赠的酒水/小食/餐饮/零售**每样都是独立权益**,绑提供方商户、须到对应商户核销,成本按提供方**内部结算价**计。预扣金额**按票种配置**:**按件计** = Σ(票面各权益数量 × 内部结算价);**按票计** = 该票种赠送部分的**售价整额** | − 赠送权益预估成本 |
| ④ 扣**门票综合服务费** | = **娱乐平台公司留存 / 项目管理费**,与「娱乐平台公司留存」为**同一项、只扣一次**;比例或固定额及封顶(项目×商户×票种)后台可配;**归娱乐平台公司** | − 综合服务费 |
| ⑤ **可分配池** | 收入 − 渠道费 − 赠送权益预估成本 − 门票综合服务费;**仅用于各酒吧分配**,**不再从池内二次扣娱乐平台公司留存** | 剩余全部 |
| ⑥ 各酒吧分配 | 可分配池按 §5.1 **两段分配**(2026-07-28 D):第一段「每客单价 / 固定额」的酒吧按约定**绝对金额先拿**,第二段**余额**由其余「排名档位」酒吧按档位比例**分尽**,**拿了第一段的不再参与第二段**;总额 ≤ 可分配池;具体分成按**整月排名、客数**等参数在**月度结算**时结出 | ≤ 可分配池 |

### 5.0c 综合／联合通票的定价构成与分账(2026-07-28 用户拍板 A/B,业务 HTML `e314c595` 为准)

> **本节不是第二套瀑布**,而是 §5.0 瀑布在**多业态票**上的分支写法:§5.0 的四道扣项顺序与归属**一条都没变**,变的是**"作用在哪一层"**——单业态通票(纯酒吧通票)整单走 §5.0;综合／联合通票先拆业态份额,**②③两道只作用在酒吧份额上**。渠道抽成在两种票上都是**整单先扣**。

**① 定价构成(A)——✅ 已落地(V369)**

售价 =(**游乐业态价** + **酒吧业态价** + **收费的餐饮/零售价**)× **票种折扣**,**由系统自动算出**。

- **免费的(票面价 0)不计入价值**——纯赠送/兑换类权益不进相加基数,不影响售价,也不影响下面的份额拆分;其成本承担另见 §6.6。
- 折扣是**票种级配置**,不写死:`ticket_types.combo_discount_rate`(百分数,100=不打折,V369);折扣归属(平台吸收/商户分摊/按比例)沿用 §7.4 `discount_bearer`。
- **系统算出售价** = `Σ(ticket_type_entitlements.component_price_cent × quantity) × combo_discount_rate ÷ 100`,四舍五入到分(走 §5.0a `MoneyRounding`)。

**①-b 凑整近似售价与允许误差闸(2026-07-28 用户拍板,业务 HTML `060eaa86`:741)——✅ 已落地(V369)**

> **为什么要这道闸(业务人员角度)**:改造前运营在票种上直接填一个售价、又在每条权益上分别填票面原价,两处各填各的、系统从不比对。
> 想填 178 手滑填成 160,票照样上架照样卖——少收的 18 块在月度结算里被当成**套票折扣**(满额−净额),按 `discount_bearer` 默认由项目公司吃掉,**没有任何人会收到提醒**。
> 等财务发现毛利不对,票已经卖出去几百张,只能一张张翻单子人工调账。

- 运营可在系统算出的售价上填一个**近似售价用于凑整**(使最终售价为整元、且尾数 8/9/0),**上调下调均可**。
- 近似售价与系统算出售价的**差额不得超过后台配置的允许误差**,**超出即拒绝发布**(`TICKET_PRICE_OUT_OF_TOLERANCE`,中文报文含:算出多少、填了多少、上调/下调多少、超出多少、凑整可填哪个数)。
- **允许误差后台可配**:`ticket_combo_discount_configs.rounding_tolerance_cent`(分,出厂 500=5 元),与 §7.4 折扣归属**同表同行、同一「通票分账」栏目、同一套草案转正闸**——凑整差额走的正是这条折扣承担口径,运营只在一处维护,不另立第二套配置面。
- **闸位**(三处,同一份计算):① **发布时**(`publishTicketType`)——HTML 原话「超出即拒绝发布」;② **改售价保存时**(`PUT /ticketing/ticket-types/{id}/pricing`)——不让运营先存下一个明知超限的价、等到发布才白填一遍;③ **加绑/改权益票面原价时**——已上架的票若因此对不上新的业态构成,**自动退回草稿**(不阻断「先建票再一次性配组合权益」这条正常流程,改完价重新发布即再过一次闸)。
- **只卡平日价**:算出售价只有一个数(业态票面原价是单值的),周末价/节假日价是同一张票上叠的**日历加价**,本就该更高。三档都拿这一个数卡,运营为了让周末价过闸只能把允许误差调到几十元,**那道闸就等于没有了**。故闸卡在平日价(=该票基准售价),周末/节假日加价按日历规则走(真要差很多按 HTML:721 另设「周末票」票种)。
- **凑整差额不新建口径**:出票时每张权益照旧记「满额份额=票面原价」(`issued_entitlements.component_full_price_cent`)与「实付份额」(`allocated_revenue_cent`),两者之差即折扣,由 §7.4 `discount_bearer` 决定谁承担——凑整多出/少收的那点钱自然并入同一条路。
- 前端:票务策略页「组合式套票配置 → 定价核算」展示票面原价合计/折扣/系统算出售价/当前填的售价/允许误差/凑整建议,运营边填边看差多少、超没超。

**② 分账顺序(B)**

| 步 | 算法 | 归属 |
|---|---|---|
| ① 整单扣**第三方渠道抽成** | 在拆份额**之前**、对整张票扣一次(比例/金额可配) | 第三方渠道 |
| ② 按**各业态票面原价占比**拆份额 | 份额ᵢ =(扣完渠道抽成的余额)× 该业态票面原价 ÷ Σ各业态票面原价 | — |
| ③ **游乐份额** | 直接归属,不再扣本瀑布其它项 | **游乐公司** |
| ③ **餐饮份额** | 直接归属 | **餐厅商户** |
| ③ **零售份额** | 直接归属 | **零售商户** |
| ④ **酒吧份额**再扣**赠送权益预估成本** | 口径同 §5.0 ③ / §5.3 ① | **娱乐平台公司** |
| ⑤ 酒吧份额再扣**门票综合服务费** | 口径同 §5.0 ④(= 娱乐平台公司留存/项目管理费,同一项只扣一次) | **娱乐平台公司** |
| ⑥ 酒吧份额剩余 → **可分配池** | 按 §5.1 **两段分配**给各酒吧商户 | **各酒吧商户** |

**③ 拆份额的粒度铁律**

- 拆份额**只按业态大分类**进行:先区分这份产出**由哪个业态产生**,再按**该业态自己的内部规则**处理(游乐按 §6.3、酒吧按 §5.1/§5.3、餐饮/零售按核销直付商户)。
- **依附于某业态产生的加赠权益,不作为业态层的拆分对象**——其价值**已含在所属业态的价格内**。例:酒吧通票里加赠的一杯酒,不在业态层单独切一份"酒水份额",它的价值已在"酒吧业态价"里;它只在酒吧份额内部按 §5.3 走「赠送权益预估成本」预扣与核销兑付。
  > 与 §5.3「每样赠品都是**独立权益**」**不矛盾,是两层**:§5.3 说的是**核销/绑定/成本**层——每样赠品各绑提供方商户、各自核销、各按内部结算价计成本;本条说的是**业态份额拆分**层——加赠权益不在这一层单独占份额。读的时候别把两层混成一层。

**④ 两个价,不可混用(B)**

| 价 | 用途 | 不得用于 |
|---|---|---|
| **票面原价** | ① 定价相加(A)② 业态份额拆分占比(B ②) | 与提供商户结算成本 |
| **内部结算价** | ① 与提供商户结算兑付成本(§5.3 ③)② 赠送权益预估成本按件计(§5.3 ①) | 定价、份额拆分占比 |

- 每个权益**同时**带这两个价,票种配置时**分别录入**,读写两条独立字段,禁止互相回退顶替。
- **落点(终态)**:票面原价 = `ticket_type_entitlements.component_price_cent`(S11 收紧语义:0=免费不占份额、NULL=未配价发布/出票双拒,配置页可录);业态标签沿用 `merchants.merchant_type` 五值(V348);内部结算价经 `InternalSettlementPriceResolver`(S5)唯一解析,两条价线互串由 K21 专项断言防护。内部结算价的**存放**仍散在四处,收敛为目录见 §9.7(批 10 遗留)。

### 5.0a 金额精度与分账尾差(R-7·2026-07-22 用户拍板 D15.1·已落地)

> 权威口径:治理地图 HTML「全局原则 · 金额一律精确到分」+ 基准 D15.1 + 产品总纲 §42。
> 落地:公共入口 `com.complex.platform.common.money.MoneyRounding`(唯一舍入/尾差 API);迁移 **V343**。

- **四舍五入到分(HALF_UP),不再整除截断**。一切「金额 × 比例」一律走 `MoneyRounding.bpsOf/prorate`。
  旧写法 `金额 * bps / 10000` 是**向零截断**:收费方(项目公司/平台/员工)系统性少收、余数悄悄留在付款方且不留痕,
  与「四舍五入」字面口径不符。本轮已改:渠道费、池前扣项(现为门票综合服务费,S4 前称项目留存)、按排名档位分池、套票折扣项目承担额、
  单独门票综合服务费、过期未核销归项目切分、核销累计增量公式(原 `Math.round((double)…)` 有浮点失精且对负数不对称)。
- **符号对称**:HALF_UP 远离零进位,`f(−x) = −f(x)`。跨月红冲取原行之反时逐分精确对消,
  P6「每笔实收 fee 落库 + 冲正取反」的守恒性不被舍入破坏。
- **不溢出**:全程 BigDecimal,消除 `金额 × bps` 先乘后除在 long 上回绕的风险。
- **多档只舍入一次**:阶梯型算式(如营业额抽成阶梯提成)先累精确份额、末尾收敛一次,避免逐档误差累积。

**尾差单列留痕(不得静默吞掉)**

| 项 | 口径 |
|---|---|
| 定义 | 尾差 = **应分总额**(对各方精确份额合计只四舍五入一次) − **Σ各方已舍入份额** |
| 归属 | 统一由**项目公司/平台兜底**,绝不并进任一商户 |
| 落点 | `settlement_bills.rounding_residual_cent`(**V343**,BIGINT 带符号,默认 0) |
| 符号 | 正数=各家舍入后合计偏少、差额留在平台;负数=各家舍入后合计偏多、由平台补足 |
| 量级 | 尾差绝对值 ≤ 参与分账商户数(每家最多贡献 0.5 分);越界 = 分配算法出错,引擎 fail-loud 拒绝出单 |
| 守恒 | `Σ池分账明细 + 尾差 ≡ 应分总额`,逐分严格相等 |
| 自检 | 运行期两道:`verifyFormatSplit` 校验拆份额链 `Σ各业态净份额 + 渠道费 + 赠送权益预估成本 + 池链综合服务费 ≡ 通票收入`(S4/V370 起原「可分配池 = 留存 + 各酒吧总池」随留存链删除;S6/V372 起 G 入链,且 Σ各业态渠道费/G/综合服务费 分别与各自合计互核);`verifyConservation` 校验分账链尾差恒等式与尾差量级;任一不成立抛 `SETTLEMENT_CONSERVATION_VIOLATED`,宁可拒绝出单也不出一张不守恒的结算单 |

- **越池判定改按「应分总额」**(= Σ已舍入 + 尾差)而非 Σ已舍入:特批闸管的是「业务上分超了池」,
  不该被 ±n/2 分的舍入尾差触发(尾差本就由平台兜底,不需要为几分钱把整月单打回待特批)。
  无舍入场景(按客数/固定额/比例除得尽)应分总额 ≡ Σ已舍入 → 与改造前逐分同判,**零行为变更**。
- **不产生尾差的补数式拆分**:渠道费/池、池链综合服务费/可分配池(S4 起费为逐笔计提之和,池取整数补数)、
  综合服务费/商户净额、过期核销/未核销——后者恒取前者的整数补数,两侧相加恒等于总额,故无尾差,不占 `rounding_residual_cent`。
- **超池两段拆(§5.0 超额 C 口径)保持向下取整,属本口径的合规特例**:`pool_i = ⌊a_i×可分配池/poolDistributed⌋`
  向下取整使 `Σpool ≤ 可分配池` 硬约束恒成立,且余数落在 `excess_i = a_i − pool_i`(**由 L3 平台承担**)——
  方向上已是「尾差归平台」,且已**单列**在 `platform_incentive_subsidy` 独立台账行上,满足留痕要求;
  改 HALF_UP 反而会同时破坏「不得超总池」与「尾差归平台」两条。故此处**刻意不改**,以本条为准。

**两段分配(2026-07-28 用户拍板 D,替代原「三选一并列可配」表述)**

原写法「`by_venue_per_guest`/`by_rank_tier`/`by_fixed_amount` 三种是并列可配方案、项目公司级选一种」**已作废**。现行口径:三种方式**同时并存于一个池内**,分**两段**执行——

| 段 | 参与者 | 算法 | 基数 |
|---|---|---|---|
| **第一段(绝对额优先)** | 约定为 `by_venue_per_guest`(每客单价)或 `by_fixed_amount`(固定额)的酒吧 | 按各自约定的**绝对金额**先拿(每客单价 × 当月客数;或直接固定额) | 可分配池 |
| **第二段(比例分尽余额)** | 其余约定为 `by_rank_tier`(排名档位)的酒吧 | 按各自档位比例**分尽**第二段余额,Σ比例 = 100% | **第二段余额 = 可分配池 − 第一段合计** |

- **互斥铁律**:**拿了第一段的酒吧不再参与第二段**。一家酒吧的约定方式决定它落在哪一段,不能两段都拿。
- **守恒**:`可分配池 = 第一段合计 + 第二段合计 + 尾差`(尾差口径与归属见 §5.0a,由平台兜底,不并进任一商户)。
- **边界(用户已拍板·S8 已实现)**:① 第一段合计 Q > 可分配池 P → **不削任何一家金额**、第二段整段为 0,整月单落既有超池特批路径(draft 待平台负责人特批,§5.0);② 第二段**无参与者**(排名档位酒吧为空/档位权重全 0)而余额非 0 → 余额**显式归娱乐平台公司**,单列落 `settlement_bills.pool_undistributed_cent`(+归属主体快照列)并告警留痕,**不静默沉淀**;当月完全无酒吧参与同此出口;③ 池内**只有**排名档位酒吧 → 第一段为 0、第二段基数 = 全池**带符号直传**(负池月分负额=向酒吧追回,R-3 不变);④ 第二段**一次归一化分光**:`final_i = round_half_up(P2 × w_i / Σw)` 只舍入一次,档位只是相对权重(权重和不足 100% 也分尽),尾差走既有 `rounding_residual_cent`;⑤ 排名在**第二段参与者内部**编(拿了第一段的不占名次)。
- 未核销权益不参与二层分配 → 其对应余额按原则 2 归**娱乐平台公司**(游乐通票归**游乐公司**)。

### 5.2 结算触发(按核销,非发放)
```
出票    → 记录票款、各权益定价与归属(不入商户收入账,仅"待核销")
核销    → 对该权益:①判定结算价(实物内部价/虚拟权益单价)②计入对应主体"已核销结算"
票失效  → 定时作业扫描未核销权益 → 其余额按提供方业态归娱乐平台公司/游乐公司(原则 2,S8)
```

### 5.3 赠送权益(通票内加赠的酒水/小食/餐饮/零售)结算 — 2026-07-28 用户拍板重写

**权益模型**:票里加赠的酒水、小食、餐饮、零售等,**每一样都是一个独立权益**,各自**绑定提供它的酒吧 / 餐厅 / 零售商户**,客人**须到对应商户核销**;每个权益的成本按**提供方的内部结算价**计。

**① 池前预扣「赠送权益预估成本」→ 归娱乐平台公司**(§5.0 ③)
- 预扣金额**按票种配置**,两种模式二选一:
  - **按件计** `by_item`:Σ(票面各权益数量 × 该权益提供方的内部结算价);
  - **按票计** `by_ticket`:该票种**赠送部分的售价整额**。
- 模式与所有单价/金额**后台可配、禁写死**;预扣发生在**可分配池之前**,池 = 收入 − 渠道抽成 − 赠送权益预估成本 − 门票综合服务费。

**② 赠酒按酒吧分配(票面规则)**
- 一张通票覆盖的**每个酒吧至少赠一杯**;
- **各酒吧分别赠几杯,在售票时写明票面**;
- **A 酒吧的赠酒只能在 A 酒吧核销**,不能拿到其他酒吧核销;跨吧核销一律拒绝。
- 核销顺序不变:同一酒吧须**先核入场权益、再核该吧酒水权益**。

**③ 核销兑付 → 由娱乐平台公司承担**
- 客人核销后,由**娱乐平台公司**按该权益的可配**内部结算价**与**提供它的那家商户**结算——**核销一件结一件、没核销就不结算**;
- 对商户的兑付**由娱乐平台公司承担**,**不进入酒吧可分配池**,**不计酒吧销售提成**;
- 成本**按提供方的商户业态(酒吧 / 餐厅 / 零售)分开记账**;
- **预扣与核销实付的差额留在娱乐平台公司**,按可配规则调账留痕(不回流可分配池、不改已结酒吧分账)。

**④ 可分配池的分配(与赠送权益解耦)**
- 可分配池(§5.0 ⑤)按 §5.1 第二层方式分给各酒吧商户,具体分成按**整月排名 / 客数**等参数在**月度结算**时结出;赠送权益兑付**不占用**该池。

**实装现状(2026-08-01 终态)**

### 6.2 酒吧入场资格——场次规则(用户口径 4,全新)
- 入场资格权益的核销单位是**场次**(一个"开业→歇业"周期):

- 新建 `venue_sessions`(场次/营业周期)+ `entitlement_entry_records`(入场记录);核销校验按场次状态机。
- **场次自动触发(2026-07-04 定)**:系统按各酒吧**营业时间表**(新增 `venue_business_hours` 配置)自动划场次——开业开场、歇业关场;入场资格权益随场次结束自动作废,无需人工开关。

### 6.3 游乐——当天无限 + 票种规则(用户口径 5,2026-07-04 扩)
- **当天无限核心机制**:游乐权益按**自然日**核销——每次核销激活「一个整天无限」:当天首刷即消耗一次、当天内再刷卡/扫码/多人再进=放行**不重复消耗不重复计费**;跨自然日=新的一天从剩余次数再消耗一次。
- 权益模板增 `consumption_window ∈ {per_use, per_session, per_day, unlimited_in_day}`(`unlimited_in_day`=当天无限)。
- **票种规则(2026-07-04 用户拍板,游乐票同酒吧通票:有有效期、期内可用)**:
  - **单人票**:有效期内任选一天首刷→当天无限玩→**跨日作废**(即使有效期未到,次日票即废)。靠 `total_times=1`(次日核销即 `ENTITLEMENT_USED_UP`)。
  - **多人票(N 人)**:规则同单人票,唯一差异=**当天可核销 N 次**(N 人当天各入场随便玩);同天用不完的额度**跨日作废剩余**。(单日型+跨日废剩余标记 → **批 4 票种**。)
  - **多次票(N 次)**:有效期内 N 次、**每次核销=一整天无限**、**跨日保留剩余**(买 3 次,第 1 次核销完,有效期内第 2/3 天还能各核销一次)。靠 `total_times=N`(天天各扣一次)。
  - **新人票/学生票**:规则+作废规则**同酒吧通票**。

### 6.6 免费权益(票面价 0)的成本承担分两类(2026-07-28 用户拍板 C,业务 HTML `88eba70c` 为准)

票面价格为 0 的免费权益,**按成本由谁承担**分成两类,**在票种配置里逐权益标明成本承担方**:

| 类 | 定义 | 平台是否承担成本 | 是否与提供商户结算 | 是否计入赠送权益预估成本 |
|---|---|---|---|---|
| ① **商户让利型** | 餐饮 / 零售等商户**为引流自行让利**、搭进通票的免费优惠 | ❌ 不承担 | ❌ 不结算 | ❌ 不计入 |
| ② **平台出资型** | 平台为做活动**向商户采购后免费赠送**给客人的权益 | ✅ 承担 | ✅ 按**内部结算价**与提供商户结算(核销一件结一件,§5.3 ③) | ✅ 计入(§5.0 ③ / §5.3 ①) |

- **两类都不参与业态份额拆分**(§5.0c ②)——票面价为 0,占比分子为 0。
- **成本承担方是必填项**:票种配置未标明的免费权益,视为配置不完整,不得启用(fail-closed,同 AUD-015 赠饮模板启用前置校验范式)。

> ⚠️ **旧口径作废**:2026-07-06 裁决 `D-20260706-1`/`D-20260706-2` 里「通票餐饮优惠……价格可以设为 0(纯赠送或兑换)……核销时平台按内部结算价与这家餐厅商户结算」的**一刀切**写法**已作废**——价格为 0 的赠送/兑换**是否由平台按内部结算价结算,取决于该权益标明的成本承担方**。餐饮结算归餐厅商户这条本身不变(核销后那笔钱归提供餐品的餐厅商户),变的只是"平台要不要为这 0 元权益向商户付成本"。

> **实装现状(2026-08-01 终态)**:成本承担方已落 **`ticket_type_entitlements.cost_bearer`**(S6/V372,票种绑定级,`platform_funded` 平台出资型 / `merchant_concession` 商户让利型)——让利型**不进 G 预扣**、兑付**不挂商户应付**(冲正侧由「原应付存在性守卫」对称保护);S5 起 0 = 让利型合法价、NULL = 没配价拒绝核销(fail-closed,不再回退票面价)。
> ✅ **「必须显式标明」强校验已落地(2026-08-01 用户拍板,V376)**:`cost_bearer` **必填、无默认**(V376 撤 DEFAULT/撤 NOT NULL,NULL=未标)。**赠送类权益**(票面原价 0 且提供方兑付类,谓词与 S5 `providerRedeemed` 同源:赠饮/实物/专属直付)漏标 → 绑定面拒保存、发布闸 `requireCostBearers` 兜底拒发布(`TICKET_COST_BEARER_REQUIRED`,中文点名是哪条权益没标);非赠送类(入场/付费组成)无成本承担概念,允许 NULL 不误伤。前端(组合配置酒水/餐饮行、通票组装绑定表单)同步改必选下拉(平台出资型/商户让利型),漏选前置拦。原「缺省 `platform_funded`」口径作废——运营漏标让利型赠品时平台不再默默按出资型多付成本。

## 10.2D 联合/综合通票的分账口径(S11,2026-07-28)

> **权威依据**:`docs/business-system-map-for-operations-v0.1.html` :741(定价构成)、:742(收入分账)、:737(免费权益的成本承担)、:1141(商户业态五值)。已按 HTML 原文逐字回核:**分账侧(:742)与免费权益不参与拆分(:737)逐条一致**;定价侧(:741)「售价由各业态价格相加后统一打折得出」在 S11 时点只落了拆份额一半,**后由 V369(凑整闸,PR #282)补齐**——售价由系统自动相加打折算出,运营只可在允许误差内填凑整近似价,超出拒绝发布(§5.0c ①-b),终态与 HTML 一致。

**定价**:综合/联合通票售价 =(游乐票面原价 + 酒吧票面原价 + 收费的餐饮/零售票面原价)× 折扣。免费的(票面原价 0)不计入价值。

**分账**(共用同一条瀑布,不开第二条链路;纯酒吧票 = 业态集合只有酒吧的退化情形,占比 100%):

```
售价 → 先扣第三方渠道抽成(整单,在拆份额之前)
     → 剩余按【各业态票面原价占比】拆份额
          游乐份额 → 游乐公司(主体)
          餐饮份额 → 餐厅商户;零售份额 → 零售商户
          酒吧份额 → 赠送权益预估成本 → 门票综合服务费 → 可分配池 → 分配
```

- **份额比例在出票时就定死**:`TicketOrderService.allocateRevenue` 按各权益 `component_price_cent`(票面原价)占比把订单实付拆到每张权益(`issued_entitlements.allocated_revenue_cent`),核销时逐笔落 `settlement_transactions`;月度引擎只是把权益级份额**按提供方商户的业态归堆**,不另发明分摊算法。
- **票面原价的 NULL / 0 语义(收紧)**:**0 = 免费**(0 元餐饮/零售券、加赠酒水小食)→ 权重 0、不参与拆份额,它的价值本就含在别的业态价格里,再分一份就是让提供方**双收**(既拿营收份额、又按内部结算价被兑付);**NULL = 没配价** = 不合规 → **票种发布直接拒**(`TICKET_COMPONENT_PRICE_REQUIRED`),漏到出票也拒(`TICKET_COMPONENT_PRICE_MISSING`)。**废除「全没配价就按数量均摊」的兜底**——均摊会把免费权益和赠品也算成收入,且账面上每一分都分掉了、事后查不出分错了谁。
- **渠道抽成整单前移**:渠道抽的是客人实付那一整笔的成,按 `channel_fee_configs`(项目 × 渠道可配,默认 0)算出整单渠道费后,**按各业态毛额占比分摊**下去;分摊尾差归酒吧支兜底。旧实现把渠道费记在池链上,等于让酒吧一家替全场交费。**费率 0(官方直销/未配)→ 各家 +0 → 逐分不变**。
- **折扣承担方补回口径扩到所有业态**:`platform_absorb` 时**每个业态**都按满额份额计、`merchant_absorb` 时每个业态都按折后净额计、`split_by_ratio` 按配置比例。旧实现只补酒吧那一路,同一张票里各业态两套口径。
- **排名/客数只算酒吧**:`aggregateMerchantStats` 加业态过滤——一家餐厅核销几张餐券就能在「按核销数排名分池」里占掉一个名次、把本该属于某家酒吧的档位挤掉,是真会分错钱的。
- **两条价线不可互串(K21)**:拆份额只允许出现**票面原价**(`ticket_type_entitlements.component_price_cent`);与提供方结算成本只允许出现**内部结算价**(`bar_products.internal_settlement_price_cent` / `entitlement_templates.agreement_price_cent`)。任何一条 SQL / 计算路径都不得互相替代或回退。
- **守恒(K20,运行期 fail-loud)**:`Σ各业态净份额 + 整单渠道费 ≡ 通票收入`;`Σ各业态渠道费 ≡ 整单渠道费`;`Σ各业态净额 ≡ 当月进池核销合计`(业态分组不重不漏)。任一条不成立立即拒绝出账,不出一张不守恒的结算单。
- **本批范围**:只保证「份额算得出、归属定得住、非酒吧业态不进酒吧池」并单列留痕;游乐/餐饮/零售各自的**完整结算单**不在本批范围。
- **配置面**:票种组合配置页(ADM-TKT 票务政策)各行补「票面原价(元)」输入(酒吧行/游乐行/餐饮行/单条绑定),免费的填 0。

**A5 · 会员积分规则（历史测算值不得作为业务规则）**

“消费 1 元 = 1 积分”“1000 积分 = 10 元”、固定可兑品类和固定计提基数均属于历史测算或旧口径，**不得进入系统成为默认业务规则**。消费积分由 `points-and-voucher-product-prd-v1.0.md` 按全国业态规则、有效消费金额、等级倍率和订单锁定版本计算；兑换定价、内部结算价、核销补偿由 `merchant-points-settlement-rules-v1.0.md` 定义。结算侧只接收已确认积分发行费和已核销券补偿等结算事实，不自行推导积分价值。

- **赠送权益兑付实装(2026-07-28 口径)**:核销时按该商品内部结算价与**提供它的商户**结算(`pass_drink_settlement`·幂等+可冲正),**由娱乐平台公司承担**;池前另有一道**「赠送权益预估成本」预扣**(按件计/按票整额,归娱乐平台公司,**S6/V372-V373 已落地**),预扣与实付**差额留在娱乐平台公司**(差额调账留痕为遗留,见 §5.3);**不采用"商户先垫再核销"**的账务。原 D5「不从分账池预留赠酒成本」已被本口径取代(删的是「每杯 3 元」假设,不是取消预扣)。
- **中央餐饮开关=关(2026-07-28 起现行口径)的分账**:订台低消/二次消费/额外酒水收入直接进**该酒吧商户账**(不进分账池、无场地返佣);**通票分账仍按 §5.0 瀑布**,不受开关影响。中央餐饮向商户**供货收货款**的业务与本开关无关、始终有效。
- **中央餐饮返佣触发**:开关开时,按实际酒水销售逐笔/周期(按配置)计算返给对应 SPV;是结算规则(A2),非财务平均分利。
