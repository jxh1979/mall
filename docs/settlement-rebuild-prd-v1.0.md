# 通票权益结算重构 PRD v1.0

> **状态**：受三个最高业务解释权 HTML 约束的现行 PRD（2026-08-01 同步）。
> **解释权边界**：三个业务 HTML 是最终业务口径；本文、财务底稿、术语表、实现规格、数据库和代码均只能作为产品细化、测算资料或当前实现证据，不得覆盖 HTML。本文新增而 HTML 尚未记载的业务规则，在用户批准并写入相应 HTML 前不生效。
> **现行结算边界**：域内通票不做域间比例拆分；只有跨域组合通票先从整单扣一次第三方渠道费用，再按收费权益有效价格分到各域，零元权益不参与域间分配。各域取得份额后由对应域主管公司按本域已生效规则与实际提供方结算，商户无权自行决定分配方式。
> **实现状态纪律**：内部结算 SKU 目录已由 V379/V380 落地；既有 S1—S11、其他迁移和代码仍只能说明当前实现。凡统一把赠送权益成本归娱乐平台公司、把域份额直接给商户、让酒吧份额重复扣渠道费、让全部门票收服务费或让通票服务费封顶的实现，均属于待改造缺口，本次文档同步不修改实现。
> **待改造缺口登记（2026-08-04 PRD 同步 B5 新增两条，依据 ENUM L43）**：
> - **缺口 ①：渠道费未拆通路费 / 销售渠道费两层。** 现实现只有单层「第三方渠道费」，未区分「所有支付（含官方渠道）都产生、由收款主体承担的通路费」与「仅第三方渠道产生、在通路费之上再扣一层的销售渠道费」。按原单层口径，官方渠道每一笔线上支付都过不了守恒校验。口径见 §5.0。
> - **缺口 ②：分账瀑布未含票务积分发行成本扣项。** 现行瀑布 `P = R − C − G − F_pool` 尚未包含「票务订单产生的积分发行成本在域间拆分之前从整单扣除且只扣一次」这一层。口径见 §5.0。
> 两条均为**待改造缺口**，不构成业务规则；改造完成前实现结果不得反向写成业务口径。

## 1. 背景与目标

### 1.1 问题
现状系统在**出票时**就把票款按定价一次性分摊入各商户账(`issued_entitlements.allocated_revenue_cent`,`TicketOrderService.allocateRevenue`),**与是否核销无关**。这导致:
- 客人买了含 5 个权益的票只用了 4 个,第 5 个权益的钱**仍已计入对应商户账**,项目公司无法回收;
- 无"按核销结算"、无"未用权益归项目"、无各业态公司(SPV)分账层、无手续费预扣、无单独门票服务费、无套票折扣归属、无场次入场规则——这些要么文档有代码无,要么全新。

### 1.2 目标
把结算从“发放即分摊”重构为“按实际核销逐笔结算”，并按票种经营域、域主管公司和实际提供方建立可追溯的多主体结算体系。财务底稿只用于测算，不自动成为业务规则。

### 1.3 非目标(本期不做/另批)
- 财务预测/IRR/敏感性测算(那是底稿的事,不进系统);
- 各业态公司的完整会计核算/报税(系统只做**营收分账与结算单**,出具给财务,不替代财务软件);
- 资产公司折旧、CapEx 等纯财务项。

## 2. 主体协作关系与职责

平台、城市项目公司、各域主管公司和商户通过项目、经营域、合同及主体绑定关系协作，不建立“项目公司必然下辖域主管公司和全部商户”的固定层级。一家公司可以服务多个项目，一个项目也可以由多家公司共同经营。

| 主体 | 结算职责 |
|---|---|
| 顶层平台 | 审批跨域规则和跨项目治理规则，不因处于顶层自动取得某类收入 |
| 城市项目公司 | 每个城市项目公司同时承担本城市资产公司职责，负责资产物业、招商租赁、直接管理第三方商户及自身人员设备；不负责酒吧、游乐、演出等域的定价、售票和结算 |
| 娱乐平台公司 | 负责酒吧域、酒吧通票及跨域组合通票酒吧部分，审批酒吧项目内部结算价并决定酒吧域内规则；参股并管理独立酒吧商户的相关经营关系 |
| 游乐公司 / 传媒公司 | 分别负责游乐域、演出与传媒域的定价、售票、收款和域内结算 |
| 中央餐饮公司 | 负责其供应的酒水、小食和餐饮供应链、供货收入及供应部分的内部结算价审批 |
| 独立酒吧商户 | 负责自身人员、设备、经营和履约；取得单一酒吧门票、订台低消、二次消费、额外酒水和非散台服务费收入 |

商户只能提交价格资料、履约事实和异议，不能自行决定域内采用内部结算价、固定金额、固定单价、排名档位或比例规则；域内规则由对应域主管公司选择、配置和审批，跨域规则由项目之上的平台权限审批。

## 3. 核心设计原则

1. **按核销结算**：权益只有在核销成功后，才按已生效规则形成对提供方的实际结算；未核销不结算给提供方，也不得通过配置把“未核销”改成“已核销”。
2. **到期未核销按门票所属经营域归属**：有效期内未核销款不提前结算；票到期后，单一酒吧门票及酒吧通票归娱乐平台公司，纯游乐票及纯游乐通票归游乐公司，演出票归传媒公司，跨域组合通票按已拆分的各域份额分别归对应域主管公司。第三方渠道费用只在整张票拆域前扣一次，酒吧份额不得再次扣渠道费。
3. **配置不能改变责任边界**：金额、比例、固定单价、排名档位、封顶、期限及税务参数应由系统配置并留版本；配置只能在三份业务 HTML 允许的范围内生效，不能把主管公司、审批主体、成本承担方或收入归属改成其他主体。
4. **逐笔可追溯**:每笔结算能追溯到票→权益→核销记录→结算明细→结算单,支持对账。
5. **幂等与防混账**:核销/结算/退款全幂等;权益归属严格隔离(project_id / merchant_id / spv_id),不串户。
6. **向后兼容迁移**:提供从 `allocated_revenue_cent`(发放即分摊)到新引擎的迁移与并行校验路径(§11)。
7. **业务规则 ≠ 财务测算假设(2026-07-04 用户纠偏,关键)**:财务底稿里大量"公式"是**预测假设**——用来在财务模型里估算营收数字(如"50% 通票客人会买额外酒水、平均 1.5 杯、每杯 20 元""客流 7100 人/日""满台率 70%")。这类假设**一律不进系统**——系统按**真实交易/核销逐笔记账**(客人实际买几杯记几杯、实际访问几个点位算几个)。只有"每一笔钱怎么算、怎么分"的**结算规则**(留存比例、服务费率、内部结算价、佣金率、手续费率、折扣归属、税率)才进系统做配置。**成本同理:系统成本 = 真实费用归集,不用"收入×成本率"估算。** 附录 A 已据此把参数分为"进系统"与"仅财务测算"两栏。

## 4. 收入类型与主体归属

依据 `03_收入流向图`。**关键口径列只写业务结算规则,不写财务预测公式**(如"张数×50%×1.5杯"是财务测算假设,系统按实际交易记账,见 §3.7):

| 客人付款 | 收款及收入主体 | 税务属性 | 关键口径（系统按实际交易入账） |
|---|---|---|---|
| **单一酒吧门票** | **对应酒吧商户** | 按中国税法及实际业务性质处理 | 酒吧商户定价、销售、收款、退款并确认门票收入；娱乐平台公司不取得门票收入 |
| **酒吧通票** | **娱乐平台公司** | 按中国税法及实际业务性质处理 | 酒吧域内按 §5 的酒吧可分配池规则结算 |
| **纯游乐票及纯游乐通票** | **游乐公司** | 按中国税法及实际业务性质处理 | 仅在游乐域内结算，与娱乐平台公司无关 |
| **演出票** | **传媒公司** | 按中国税法及实际业务性质处理 | 仅在演出域内结算，与娱乐平台公司无关 |
| **跨域组合通票** | **各域主管公司分别取得其域份额** | 按中国税法及实际业务性质处理 | 整单渠道费只扣一次后拆域；各域按域内规则继续结算 |
| **门票综合服务费** | **娱乐平台公司** | 按中国税法及实际业务性质处理 | 仅酒吧相关票种收取：单一酒吧门票可按比例或固定金额并可封顶；酒吧通票及跨域组合通票的酒吧部分不封顶 |
| 订台低消 / 二次消费 | **对应酒吧商户** | 按中国税法及实际业务性质处理 | 按实际消费入账；订台价由有权主体在后台设定 |
| 额外酒水 | **对应酒吧商户** | 按中国税法及实际业务性质处理 | 按实际销售逐笔入账 |
| 非散台服务费(仅包厢/卡座) | **各酒吧商户** | 娱乐服务 | 服务费率(默认 10%,可配)× 实际低消+二次消费,散台不收 |
| **向商户供货的货款** | **中央餐饮公司** | 货物销售 / 供应链服务 | 供应链主体:向各商户供货并收货款,主要面向内部及参股商户,少量第三方商户;按实际供货逐笔结算 |
| 场地租金 / 商业租金 | **对应城市项目公司（同时承担本城市资产公司职责）** | 按中国税法及实际业务性质处理 | 仅处理资产、物业、招商租赁及其直接管理第三方商户相关收入，不介入酒吧、游乐和演出域收入 |

## 5. 通票分账引擎(本次重构的核心)

### 5.0 通票分账全流程（三份业务 HTML 约束）

先判断票种是域内通票还是跨域组合通票，二者不能套用同一套拆分逻辑：

- **域内通票**：不按经营域比例拆分。酒吧通票进入酒吧域规则；纯游乐通票进入游乐域规则；演出域产品进入传媒公司规则。
- **跨域组合通票**：先从整张票实付额中按下条口径扣一次渠道费用（通路费 + 经第三方渠道售出时的销售渠道费）与票务积分发行成本，再按各收费权益的项目内有效价格拆分经营域份额；零价赠送权益不参与拆域。各域份额进入对应域主管公司的域内结算规则。
- **渠道费分两层，性质不同、不可混用（2026-08-04 补，依据 ENUM L43、DEC-R3-2026-08-04-08；与 `finance-settlement-product-prd-v0.1.md` §3A 同一口径）**：
  - **通路费**——银行、微信、支付宝等支付通路收取的费用。**所有支付都会产生通路费，官方渠道同样产生**；由该笔业务的**收款主体承担**，**在拆分给各域之前从整单扣除**。
  - **销售渠道费**——第三方售票平台收取的佣金。**只有经第三方渠道售出的才产生**，**在通路费之上再扣一层**；任何票种经第三方渠道售出时**一律先从整单扣除且只扣一次**，**域内通票同样适用**，不因不做域间拆分而免扣。
  - **官方渠道售出的票不扣销售渠道费，但仍扣通路费**。渠道合同只能约定佣金费率、收付款方式和对账方式，**不得改变佣金的承担方式与分摊口径**，每笔分摊结果与合同版本必须留痕。
- **票务积分发行成本同样在域间拆分之前从整单扣除且只扣一次**（ENUM L43）。
- **禁止重复扣费**：已经在整单扣过的通路费、销售渠道费与积分发行成本，不得在酒吧份额或任何其他域份额中再次扣除。
- **酒吧可分配池**：第一段按已生效的固定金额或固定单价分配，第二段由其余参与酒吧按排名档位对余额分配；第一段参与者不再参加第二段。
- **无人可分时**：第一段为空时，全池进入第二段；第二段无合格参与者或权重为零时，未分配余额归娱乐平台公司；只有第一段且仍有余额时，余额同样归娱乐平台公司。
- **超池**：系统不得自动缩放或自动过账。只有娱乐平台公司可以就短期激励提出申请，由结算中心审批；超出可分配池的差额由娱乐平台公司承担。首次批准期限最长三个月，到期必须重新审批，并保留理由、金额、期限和审批轨迹。
- **门票综合服务费**：只适用于酒吧相关票种。单一酒吧门票可以按比例或固定金额收取并设置封顶；酒吧通票及跨域组合通票酒吧部分不设封顶。纯游乐票、纯游乐通票和演出票不收取娱乐平台公司的门票综合服务费。
- **赠送或套票权益**：商户让利的免费权益不结算；由域主管公司承担的权益在核销后按锁定内部结算价结算。由哪个域主管公司决定采用内部结算价或比例规则，该公司承担低于内部结算价的差额并取得高于内部结算价的余额；商户无权决定。

> **当前实现缺口**：S1—S11 等历史实现记录中，凡与上述规则不一致的“所有门票收费”“所有通票归娱乐平台公司”“餐饮/零售份额直接给商户”或“超池由项目公司承担”等行为，均为待改造项，不构成业务规则。

### 5.0c 综合／联合通票的定价构成与分账(2026-07-28 用户拍板 A/B,业务 HTML `e314c595` 为准)

> 本节只描述跨域组合通票。域内通票不拆经营域；跨域组合通票整单只扣一次第三方渠道费，然后拆分各域份额，最后由各域按自身规则结算。

**① 定价构成(A)——✅ 已落地(V369)**

售价 =(**游乐业态价** + **酒吧业态价** + **收费的餐饮/零售价**)× **票种折扣**,**由系统自动算出**。

- **免费的(票面价 0)不计入价值**——纯赠送/兑换类权益不进相加基数,不影响售价,也不影响下面的份额拆分;其成本承担另见 §6.6。
- 折扣是**票种级配置**,不写死:`ticket_types.combo_discount_rate`(百分数,100=不打折,V369);折扣归属(平台吸收/商户分摊/按比例)沿用 §7.4 `discount_bearer`。
- **系统算出售价** = `Σ(ticket_type_entitlements.component_price_cent × quantity) × combo_discount_rate ÷ 100`,四舍五入到分(走 §5.0a `MoneyRounding`)。

**①-b 凑整近似售价与允许误差闸(2026-07-28 用户拍板,业务 HTML `060eaa86`:741)——✅ 已落地(V369)**

> **为什么要这道闸(业务人员角度)**:改造前运营在票种上直接填一个售价、又在每条权益上分别填票面原价,两处各填各的、系统从不比对。
> 想填 178 手滑填成 160,票照样上架照样卖——少收的 18 块在月度结算里被当成**套票折扣**(满额−净额),按 `discount_bearer` 默认由项目公司吃掉,**没有任何人会收到提醒**。
> 等财务发现毛利不对,票已经卖出去几百张,只能一张张翻单子人工调账。

- 运营可在系统算出的售价上填一个**近似售价用于凑整**(使最终售价为整元、且尾数 8/9/0),**上调下调均可**。
- 近似售价与系统算出售价的**差额不得超过后台配置的允许误差**,**超出即拒绝发布**(`TICKET_PRICE_OUT_OF_TOLERANCE`,中文报文含:算出多少、填了多少、上调/下调多少、超出多少、凑整可填哪个数)。
- **允许误差后台可配**:`ticket_combo_discount_configs.rounding_tolerance_cent`(分,出厂 500=5 元),与 §7.4 折扣归属**同表同行、同一「通票分账」栏目、同一套草案转正闸**——凑整差额走的正是这条折扣承担口径,运营只在一处维护,不另立第二套配置面。
- **闸位**(三处,同一份计算):① **发布时**(`publishTicketType`)——HTML 原话「超出即拒绝发布」;② **改售价保存时**(`PUT /ticketing/ticket-types/{id}/pricing`)——不让运营先存下一个明知超限的价、等到发布才白填一遍;③ **加绑/改权益票面原价时**——已上架的票若因此对不上新的业态构成,**自动退回草稿**(不阻断「先建票再一次性配组合权益」这条正常流程,改完价重新发布即再过一次闸)。
- **只卡平日价**:算出售价只有一个数(业态票面原价是单值的),周末价/节假日价是同一张票上叠的**日历加价**,本就该更高。三档都拿这一个数卡,运营为了让周末价过闸只能把允许误差调到几十元,**那道闸就等于没有了**。故闸卡在平日价(=该票基准售价),周末/节假日加价按日历规则走(真要差很多按 HTML:721 另设「周末票」票种)。
- **凑整差额不新建口径**:出票时每张权益照旧记「满额份额=票面原价」(`issued_entitlements.component_full_price_cent`)与「实付份额」(`allocated_revenue_cent`),两者之差即折扣,由 §7.4 `discount_bearer` 决定谁承担——凑整多出/少收的那点钱自然并入同一条路。
- 前端:票务策略页「组合式套票配置 → 定价核算」展示票面原价合计/折扣/系统算出售价/当前填的售价/允许误差/凑整建议,运营边填边看差多少、超没超。

**② 分账顺序(B)**

| 步 | 算法 | 归属 |
|---|---|---|
| ①-a 整单扣**通路费** | 在拆份额**之前**、对整张票扣一次；**所有支付都产生、官方渠道同样产生** | 支付通路（成本由该笔业务的**收款主体**承担） |
| ①-b 整单扣**销售渠道费** | 在通路费**之上再扣一层**、只扣一次；**仅第三方渠道售出的票产生**（官方渠道不扣） | 第三方售票平台 |
| ①-c 整单扣**票务积分发行成本** | 在拆份额**之前**扣一次 | 积分发行方 |
| ② 按**各业态票面原价占比**拆份额 | 份额ᵢ =(扣完①-a/①-b/①-c 后的余额)× 该业态票面原价 ÷ Σ各业态票面原价 | — |
| ③ **酒吧域份额** | 进入酒吧域规则；不得再扣渠道费；酒吧相关门票综合服务费不封顶 | **娱乐平台公司负责域内结算** |
| ③ **游乐域份额** | 进入游乐域规则 | **游乐公司负责域内结算** |
| ③ **演出域份额** | 进入演出域规则 | **传媒公司负责域内结算** |
| ③ **资产、餐饮供应链或其他域份额** | 进入相应域主管公司的内部结算价或比例规则，不直接跳过域主管公司结给商户 | **对应域主管公司负责域内结算** |

**③ 拆份额的粒度铁律**

- 拆份额只按经营域进行：先确定收费权益属于哪个经营域，再由该域主管公司按域内已生效规则结算。任何域份额都不能绕过主管公司直接改归提供商户。
- **依附于某业态产生的加赠权益,不作为业态层的拆分对象**——其价值**已含在所属业态的价格内**。例:酒吧通票里加赠的一杯酒,不在业态层单独切一份"酒水份额",它的价值已在"酒吧业态价"里;它只在酒吧份额内部按 §5.3 走「赠送权益预估成本」预扣与核销兑付。
  > 与 §5.3「每样赠品都是**独立权益**」**不矛盾,是两层**:§5.3 说的是**核销/绑定/成本**层——每样赠品各绑提供方商户、各自核销、各按内部结算价计成本;本条说的是**业态份额拆分**层——加赠权益不在这一层单独占份额。读的时候别把两层混成一层。

**④ 两个价,不可混用(B)**

| 价 | 用途 | 不得用于 |
|---|---|---|
| **票面原价** | ① 定价相加(A)② 业态份额拆分占比(B ②) | 与提供商户结算成本 |
| **内部结算价** | 域内与提供方结算实物权益或经批准采用内部结算价的特殊权益 | 跨域份额拆分占比 |

- 收费权益用于跨域拆分的价格与域内结算价格是两条独立价线，禁止互相回退或顶替；免费权益不参与跨域份额拆分。
- **当前落点**：票面价使用 `ticket_type_entitlements.component_price_cent`；内部结算价已由 V379/V380 收敛到项目隔离的内部结算 SKU 目录，四处业务表只保存 `catalog_item_code` 引用和只读快照。实现取价仍须受本节业务规则约束。

**⑤ 实现状态**

- V369 已提供定价与凑整校验，V379/V380 已完成内部结算 SKU 目录，V381 已支持第三方渠道费比例／固定金额二选一。其余 S4、S6、S8、S11 实现如仍按旧域拆分、旧成本承担或全部门票服务费口径运行，属于待改造缺口，不能标记为现行业务终态。
- **两条新登记的待改造缺口（2026-08-04）**：① **渠道费仍是单层**，V381 的「第三方渠道费比例／固定金额二选一」只覆盖销售渠道费一层，**未建通路费层**，官方渠道支付按现实现不扣任何渠道费，与「所有支付都产生通路费」冲突；② **瀑布 `P = R − C − G − F_pool` 未含积分发行成本扣项**。两项须在改造中补齐，现实现口径不得反向写成业务规则。见文首「实现状态纪律」。

### 5.0a 金额精度与分账尾差(R-7·2026-07-22 用户拍板 D15.1·已落地)

> 权威口径:治理地图 HTML「全局原则 · 金额一律精确到分」+ 基准 D15.1 + 产品总纲 §42。
> 落地:公共入口 `com.complex.platform.common.money.MoneyRounding`(唯一舍入/尾差 API);迁移 **V343**。

- **四舍五入到分(HALF_UP),不再整除截断**。一切「金额 × 比例」一律走 `MoneyRounding.bpsOf/prorate`。
  旧写法 `金额 * bps / 10000` 是**向零截断**:收费方(项目公司/平台/员工)系统性少收、余数悄悄留在付款方且不留痕,
  与「四舍五入」字面口径不符。本轮已改:渠道费、池前扣项(现为门票综合服务费,S4 前称项目留存)、按排名档位分池、套票折扣项目承担额、
  单独门票综合服务费、过期未核销归项目切分、核销累计增量公式(原 `Math.round((double)…)` 有浮点失精且对负数不对称)。
- **符号对称**:HALF_UP 远离零进位,`f(−x) = −f(x)`。跨月红冲取原行之反时逐分精确对消,
  P6「每笔实收 fee 落库 + 冲正取反」的守恒性不被舍入破坏。
- **不溢出**:全程 BigDecimal,消除 `金额 × bps` 先乘后除在 long 上回绕的风险。
- **多档只舍入一次**:阶梯型算式(如营业额抽成阶梯提成)先累精确份额、末尾收敛一次,避免逐档误差累积。

**尾差单列留痕(不得静默吞掉)**

| 项 | 口径 |
|---|---|
| 定义 | 尾差 = **应分总额**(对各方精确份额合计只四舍五入一次) − **Σ各方已舍入份额** |
| 归属 | 由产生该尾差的结算规则所对应的**实际结算责任主体**承担，不统一归项目公司或平台，也不得静默并入任一无责任商户 |
| 落点 | 金额 `settlement_bills.rounding_residual_cent`(**V343**,BIGINT 带符号,默认 0)+ 责任主体快照 `settlement_bills.rounding_residual_entity_id`(**V383**,VARCHAR(64),尾差为 0 时为空;解析自 `revenue_stream_attribution` 的 `all_pass_ticket` 流=娱乐平台公司,与 `attributed_entity_id` 同源、后台可配、项目级可覆盖) |
| 合列范围(V383) | 该列＝**池分账舍入尾差 + 渠道费按业态分摊尾差**。两者同为「按比例拆分四舍五入」成因,合成一笔单列;与 `pool_undistributed_cent`(第二段无参与者的整段余额)成因不同,仍分列 |
| 符号 | 正数表示各方舍入后合计偏少；负数表示合计偏多；两种情况都由实际结算责任主体处理并留痕 |
| 量级 | 尾差绝对值 ≤ 参与分账商户数(每家最多贡献 0.5 分);越界 = 分配算法出错,引擎 fail-loud 拒绝出单 |
| 守恒 | `Σ池分账明细 + 尾差 ≡ 应分总额`,逐分严格相等 |
| 自检 | 运行期两道:`verifyFormatSplit` 校验拆份额链 `Σ各业态净份额 + Σ各业态渠道费 + 赠送权益预估成本 + 池链综合服务费 ≡ 通票收入` 且 `Σ各业态渠道费 + 渠道费分摊尾差 ≡ 整单渠道费`(V383 起分摊尾差单列,不再由酒吧拿补数)(S4/V370 起原「可分配池 = 留存 + 各酒吧总池」随留存链删除;S6/V372 起 G 入链,且 Σ各业态渠道费/G/综合服务费 分别与各自合计互核);`verifyConservation` 校验分账链尾差恒等式与尾差量级;任一不成立抛 `SETTLEMENT_CONSERVATION_VIOLATED`,宁可拒绝出单也不出一张不守恒的结算单 |

- **越池判定改按「应分总额」**(= Σ已舍入 + 尾差)而非 Σ已舍入:特批闸管的是「业务上分超了池」,
  不应被 ±n/2 分的舍入尾差触发；尾差由实际结算责任主体承担，不另行改变超池审批边界。
  无舍入场景(按客数/固定额/比例除得尽)应分总额 ≡ Σ已舍入 → 与改造前逐分同判,**零行为变更**。
- **不产生尾差的补数式拆分**:池链综合服务费/可分配池(S4 起费为逐笔计提之和,池取整数补数)、
  综合服务费/商户净额、过期核销/未核销——后者恒取前者的整数补数,两侧相加恒等于总额,故无尾差,不占 `rounding_residual_cent`。
  ⚠️ **渠道费按业态分摊不再属于此类**(V383):原实现让酒吧支拿补数=把分摊尾差压给一个参与方,与「不得悄悄并进任一参与方」冲突;
  现各业态(含酒吧)一律按精确占比 HALF_UP,分摊尾差单列进 `rounding_residual_cent` 并挂责任主体。
- **超池两段拆(§5.0 超额 C 口径)保持向下取整,属本口径的合规特例**:`pool_i = ⌊a_i×可分配池/poolDistributed⌋`
  向下取整使 `Σpool ≤ 可分配池` 硬约束恒成立，余数单列留痕；若属于酒吧可分配池超额激励，则由娱乐平台公司承担，不能归城市项目公司。

**两段分配(2026-07-28 用户拍板 D,替代原「三选一并列可配」表述)**

| 段 | 参与者 | 算法 | 基数 |
|---|---|---|---|
| **第一段(绝对额优先)** | 约定为 `by_venue_per_guest`(每客单价)或 `by_fixed_amount`(固定额)的酒吧 | 按各自约定的**绝对金额**先拿(每客单价 × 当月客数;或直接固定额) | 可分配池 |
| **第二段(比例分尽余额)** | 其余约定为 `by_rank_tier`(排名档位)的酒吧 | 按各自档位比例**分尽**第二段余额,Σ比例 = 100% | **第二段余额 = 可分配池 − 第一段合计** |

- **互斥铁律**:**拿了第一段的酒吧不再参与第二段**。一家酒吧的约定方式决定它落在哪一段,不能两段都拿。
- **守恒**：`可分配池 = 第一段合计 + 第二段合计 + 未分配余额 + 尾差`；尾差由实际结算责任主体承担。
- **边界(用户已拍板·S8 已实现)**:① 第一段合计 Q > 可分配池 P → **不削任何一家金额**、第二段整段为 0,整月单落既有超池特批路径(draft 待平台负责人特批,§5.0);② 第二段**无参与者**(排名档位酒吧为空/档位权重全 0)而余额非 0 → 余额**显式归娱乐平台公司**,单列落 `settlement_bills.pool_undistributed_cent`(+归属主体快照列)并告警留痕,**不静默沉淀**;当月完全无酒吧参与同此出口;③ 池内**只有**排名档位酒吧 → 第一段为 0、第二段基数 = 全池**带符号直传**(负池月分负额=向酒吧追回,R-3 不变);④ 第二段**一次归一化分光**:`final_i = round_half_up(P2 × w_i / Σw)` 只舍入一次,档位只是相对权重(权重和不足 100% 也分尽),尾差走既有 `rounding_residual_cent`;⑤ 排名在**第二段参与者内部**编(拿了第一段的不占名次)。
- 未核销权益不参与两段分配；票到期后按 §3.2 的门票所属经营域规则归属。

> **实装现状(2026-08-01 S8 已落地)**:`TicketDistributionSettlementService.distribute` 已按两段执行——第一段读商户级固定规则名单(`ticket_distribution_merchant_rates`,**V374** 加 `rule_type` 二选一 NOT NULL + `chk_tdmr_rule` CHECK:`per_guest` 时仅 `per_guest_cent`、`fixed` 时仅 `fixed_amount_cent`),第二段对余额按档位归一化分尽;`ticket_distribution_configs.method_type` **语义收窄为「第二段方式」**,仅 `by_rank_tier` 合法(写入口拒另两值、引擎对旧值 fail-loud `SETTLEMENT_CONFIG_INVALID`、配置页已下线两选项)。守恒 K18:`池 = 第一段Σ + 第二段Σ + 尾差 + pool_undistributed`(**V375** 给 `settlement_bills` 加 `pool_undistributed_cent`/`pool_undistributed_entity_id` 两列,带符号)。逐分不变判据已证:无第一段酒吧且档位和恰 100% 时结算单整行全列与两段化前手算值逐分一致(`SettlementBatch2EngineTests#pennyInvariantWhenNoFixedSetAndTiersSumToFull`)。

### 5.3 赠送及套票权益结算

**权益模型**：票内酒水、小食、餐饮、零售或特殊权益均作为独立权益，绑定实际提供方并单独核销。发放或出票只记录权益和预算占用，核销成功后才形成对提供方的实际结算。

**① 先识别成本承担方式**

- 商户让利型免费权益：核销后也不与商户另行结算。
- 域主管公司承担型权益：核销后按出票时锁定的内部结算价与提供方结算；如果主管公司批准的权益价格低于内部结算价，由作出该决定的主管公司承担差额；高于内部结算价的余额归该主管公司。
- 采用内部结算价还是比例结算，由对应域主管公司决定并在系统中配置和审批，商户只能提交资料和履约事实，无权选择。
- 酒吧入场资格是目前唯一不设置内部结算价的酒吧权益，进入酒吧可分配池按固定金额、固定单价或排名档位规则分配；其他酒吧权益不得据此例外。

**② 赠酒按酒吧分配(票面规则)**
- 一张通票覆盖的**每个酒吧赠酒杯数不得低于后台按票种配置的最低赠酒杯数（出厂默认 1 杯）**;
- **各酒吧分别赠几杯,在售票时写明票面**;
- **A 酒吧的赠酒只能在 A 酒吧核销**,不能拿到其他酒吧核销;跨吧核销一律拒绝。
- 核销顺序不变:同一酒吧须**先核入场权益、再核该吧酒水权益**。

**③ 核销兑付 → 由作出权益规则决定的域主管公司承担**

- 客人核销后，按该权益已锁定的结算方式与实际提供方结算；核销一件结一件，未核销不结算。
- 酒吧域由娱乐平台公司负责，游乐域由游乐公司负责，演出域由传媒公司负责，资产及其直接管理第三方商户由城市项目公司负责，中央餐饮供应的酒水、小食和餐饮供应链权益由中央餐饮公司负责。
- 各域成本、差额和收益分开记账，不得统一转给娱乐平台公司或城市项目公司。

**④ 酒吧可分配池的分配**

- 酒吧入场资格进入 §5.1 两段池；采用内部结算价结算的实物或特殊权益不重复进入该池。

## 6. 权益结算规则

### 6.1 权益结算价选择

不得按“实物／虚拟”简单二分结算方式。权益先确定所属经营域、成本承担方式和实际提供方，再读取该域已批准的结算规则：

- 商户让利型免费权益不结算。
- 域主管公司承担型权益，核销后按锁定内部结算价或主管公司批准的比例规则结算。
- 酒吧入场资格是目前唯一不设置内部结算价的酒吧权益，进入酒吧可分配池；除该例外外，不得仅因权益是非实物就改用“签约权益单价”。
- 票面价格用于跨域组合通票的域间份额计算，内部结算价用于域内结算，两条价线不得回退或互相顶替。

> **实现状态**：V379/V380 已将改价入口收敛为内部结算 SKU 目录草案链，并把原 `agreement_price_cent` 改为只读快照。现有解析器中仍按“实物／虚拟”二分或回退签约价的历史分支，如与上述规则不一致，属于待改造缺口；实现不得反向定义业务规则。
>
> **改价口径(资金,批 10 起)**:统一为**核销固化时点**——转正后的新目录价对**此后的核销/结算**生效(含已发放未核销的权益;原批5「只对之后发放生效」口径被目录口径取代);已核销/已结算的历史各按核销当时固化进 `ticket_verifications.settlement_price_cent` 的那一份走,改价**结构上碰不到**。证伪测试:`SettlementPriceResolutionJdbcIntegrationTests#catalogPriceChangeDoesNotMoveAlreadyVerifiedMoney`(草案不生效 → 起草人自审 403 → 他人转正后已核销记录仍按 8000、商品快照被传播为 3000、此后核销按 3000 固化)。

### 6.2 酒吧入场资格——场次规则(用户口径 4,全新)
- 入场资格权益的核销单位是**场次**(一个"开业→歇业"周期):
  - 客人当场次**入过场**后,该场次内可**持续进出**(不重复消耗);
  - 即使门票有效期未到,一旦某场次已入场,**过了该场次(下一个开歇业周期)即作废**,不能再用;
- 新建 `venue_sessions`(场次/营业周期)+ `entitlement_entry_records`(入场记录);核销校验按场次状态机。
- **场次自动触发(2026-07-04 定)**:系统按各酒吧**营业时间表**(新增 `venue_business_hours` 配置)自动划场次——开业开场、歇业关场;入场资格权益随场次结束自动作废,无需人工开关。

> ✅ **配置面已落地(2026-07-28)**:营业时间表原先只有 DB 表、无任何界面(只能改库),现有后台
> 「场地营业时间」页(ADM-GOV-008)按场地×星期几配开业/歇业时刻,保存即生效;跨零点(歇业早于开业)

### 6.3 游乐——当天无限 + 票种规则(用户口径 5,2026-07-04 扩)
- **当天无限核心机制**:游乐权益按**自然日**核销——每次核销激活「一个整天无限」:当天首刷即消耗一次、当天内再刷卡/扫码/多人再进=放行**不重复消耗不重复计费**;跨自然日=新的一天从剩余次数再消耗一次。
- 权益模板增 `consumption_window ∈ {per_use, per_session, per_day, unlimited_in_day}`(`unlimited_in_day`=当天无限)。
- **票种规则(2026-07-04 用户拍板,游乐票同酒吧通票:有有效期、期内可用)**:
  - **单人票**:有效期内任选一天首刷→当天无限玩→**跨日作废**(即使有效期未到,次日票即废)。靠 `total_times=1`(次日核销即 `ENTITLEMENT_USED_UP`)。
  - **多人票(N 人)**:规则同单人票,唯一差异=**当天可核销 N 次**(N 人当天各入场随便玩);同天用不完的额度**跨日作废剩余**。(单日型+跨日废剩余标记 → **批 4 票种**。)
  - **多次票(N 次)**:有效期内 N 次、**每次核销=一整天无限**、**跨日保留剩余**(买 3 次,第 1 次核销完,有效期内第 2/3 天还能各核销一次)。靠 `total_times=N`(天天各扣一次)。
  - **新人票/学生票**:规则+作废规则**同酒吧通票**。
  - 票种细分(单人/多人/新人/学生)、多人票「同天 N 次+跨日废剩余」、`num_people` 语义 → **批 4 票种**集中实现。

> ✅ **已落地(批3-3,V227,main=d36d0a5)**:`unlimited_in_day` 的「按自然日激活」——建 `entitlement_day_activations`(唯一键 entitlement_id+usage_date);

> **复用现有 `total_times`**——单人票 total=1 天然跨日作废、多次票 total=N 天然跨日保留,不重造次数模型。

## 7. 各票种结算规则

### 7.1 通票

- 酒吧通票由娱乐平台公司负责定价、售票、收款和域内结算；纯游乐通票由游乐公司负责；演出域产品由传媒公司负责；跨域组合通票由有项目之上权限的平台主体组织，拆域后由各域主管公司负责其域内结算。
- 城市项目公司不负责酒吧、游乐或演出域通票的本地定价、售票和分账。
- 结算按 §5 执行。

### 7.2 单一酒吧门票与门票综合服务费

- 单一酒吧门票由对应酒吧商户定价、销售、收款、处理退款并确认门票收入；娱乐平台公司不取得该门票收入。
- 娱乐平台公司按已生效规则，向酒吧商户逐张收取门票综合服务费。规则可选择比例或固定金额，并可以设置封顶。
- 封顶只适用于单一酒吧门票；酒吧通票及跨域组合通票酒吧部分不封顶。
- 纯游乐票、纯游乐通票和演出票不收取娱乐平台公司的门票综合服务费。

## 8. 退款

- 原则上售出门票不退款；未到场、忘记使用或主动放弃均不是退款理由，未核销也不得自动转成已核销。
- 仅在票种规则明确允许、活动取消、无法履约、重复支付、法律要求或完成特殊审批时退款。合同不得改变平台统一退款原则。
- 退款成功后按原核销和结算事实逆向冲正；跨月冲正带符号落当月红冲，并保留原单、原因、审批和冲正链路。
- 不另设退款手续费预扣规则。

### 9.7 内部结算 SKU 目录（2026-08-01 已由 V379/V380 落地）

每个项目独立维护内部结算价目录，不是全国统一价格。不同项目价格互不覆盖、不得跨项目引用；只有取得项目之上相应权限的人员才可以跨项目查看，但查看权不自动包含编辑权。核销和结算时把当时生效价固化到流水，后续改价不追改历史。

实际提供方提交本项目 SKU 的价格资料，由对应域主管公司审批，提交人与审批人必须分离：酒吧由娱乐平台公司审批；游乐由游乐公司审批；演出由传媒公司审批；城市项目公司只审批其直接管理的第三方商户；中央餐饮公司审批其供应的酒水、小食和餐饮供应链商品。商户不能批准自己的价格，也不能决定采用内部结算价还是比例规则。

内部结算价、成本价、进货价、毛利、采购协议价、结算比例、底价及系统识别出的其他敏感经营数据均按敏感数据管理。查看、导出和编辑分别授权；普通用户、会员、前线员工及无价格权限的商户即使业务流程使用了内部结算价，也不得查看或修改该价格。

**当前落点**：统一目录为 `internal_price_catalog`，目录条目使用稳定 `item_code`；酒吧商品、酒吧套餐、票务权益模板和券定义四处保存 `catalog_item_code` 引用及只读价格快照。直填内部价的旧入口已封闭，改价走目录草案、他人复核转正和后续生效，已核销历史不追改。

> 完整落地形态和目录字段见 `finance-settlement-product-prd-v0.1.md` §3B；该文档是产品细化，不拥有高于三份业务 HTML 的解释权。所有取价路径读取本项目已生效目录并在核销时固化价格。

## 10.2D 跨域组合通票分账口径与 S11 实现差距

> 最终业务解释以三份业务 HTML 为准。S11 是历史实现证据，其中把域内通票也拆域、把餐饮／零售域份额直接给商户或把酒吧份额重复扣渠道费的行为均不符合现行规则。

**定价**:综合/联合通票售价 =(游乐票面原价 + 酒吧票面原价 + 收费的餐饮/零售票面原价)× 折扣。免费的(票面原价 0)不计入价值。

**分账**：域内通票不拆域；只有跨域组合通票按下列顺序处理：

```
售价 → 整单扣一次第三方渠道费
     → 按收费权益的有效价格拆经营域份额（免费权益不参与）
          酒吧域 → 娱乐平台公司按酒吧域规则结算，不再扣渠道费
          游乐域 → 游乐公司按游乐域规则结算
          演出域 → 传媒公司按演出域规则结算
          其他域 → 对应域主管公司按本域规则结算，不直接跳过主管公司结给商户
```

- **份额比例在出票时就定死**:`TicketOrderService.allocateRevenue` 按各权益 `component_price_cent`(票面原价)占比把订单实付拆到每张权益(`issued_entitlements.allocated_revenue_cent`),核销时逐笔落 `settlement_transactions`;月度引擎只是把权益级份额**按提供方商户的业态归堆**,不另发明分摊算法。
- **票面原价的 NULL / 0 语义(收紧)**:**0 = 免费**(0 元餐饮/零售券、加赠酒水小食)→ 权重 0、不参与拆份额,它的价值本就含在别的业态价格里,再分一份就是让提供方**双收**(既拿营收份额、又按内部结算价被兑付);**NULL = 没配价** = 不合规 → **票种发布直接拒**(`TICKET_COMPONENT_PRICE_REQUIRED`),漏到出票也拒(`TICKET_COMPONENT_PRICE_MISSING`)。**废除「全没配价就按数量均摊」的兜底**——均摊会把免费权益和赠品也算成收入,且账面上每一分都分掉了、事后查不出分错了谁。
- **第三方渠道费**：跨域组合通票在拆域前从整单只扣一次；拆域后的任何份额不得再次扣同一费用。V381 已支持比例／固定金额二选一，但既有“按业态分摊后尾差归酒吧”的实现不符合现行规则；尾差应由该笔渠道费的实际结算责任主体承担并单列留痕。
- **折扣承担方补回口径扩到所有业态**:`platform_absorb` 时**每个业态**都按满额份额计、`merchant_absorb` 时每个业态都按折后净额计、`split_by_ratio` 按配置比例。旧实现只补酒吧那一路,同一张票里各业态两套口径。
- **排名/客数只算酒吧**:`aggregateMerchantStats` 加业态过滤——一家餐厅核销几张餐券就能在「按核销数排名分池」里占掉一个名次、把本该属于某家酒吧的档位挤掉,是真会分错钱的。
- **两条价线不可互串(K21)**:拆份额只允许出现**票面原价**(`ticket_type_entitlements.component_price_cent`);与提供方结算成本只允许出现**内部结算价**(`bar_products.internal_settlement_price_cent` / `entitlement_templates.agreement_price_cent`)。任何一条 SQL / 计算路径都不得互相替代或回退。
- **守恒(K20,运行期 fail-loud)**:`Σ各业态净份额 + 整单渠道费 ≡ 通票收入`;`Σ各业态渠道费 ≡ 整单渠道费`;`Σ各业态净额 ≡ 当月进池核销合计`(业态分组不重不漏)。任一条不成立立即拒绝出账,不出一张不守恒的结算单。
- **本批范围**:只保证「份额算得出、归属定得住、非酒吧业态不进酒吧池」并单列留痕;游乐/餐饮/零售各自的**完整结算单**不在本批范围。
- **配置面**:票种组合配置页(ADM-TKT 票务政策)各行补「票面原价(元)」输入(酒吧行/游乐行/餐饮行/单条绑定),免费的填 0。
