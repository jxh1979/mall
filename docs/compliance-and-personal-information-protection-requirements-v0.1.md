## 2. 未成年人售酒与酒类销售合规（C1）

**建议 P 级：P0（合规阻断）。关联 bar PRD / bar 开发设计 / evidence-risk-control。**

### 2.1 产品规则
> 决策口径（2026-06-24 售酒豁免收口，取代 2026-06-07/06-10 旧口径）：未成年人售酒法定义务（《未成年人保护法》《预防未成年人犯罪法》）由**全场统一入场刷脸闸**承接——综合体大门设满 18 岁入场年龄核验关卡，全部售酒点都在入场核验范围内；**售酒环节继承入场结论，不再在酒吧门口独立验龄、不做点酒二次复核、不做醉酒拒售**。原"酒吧门口独立年龄核验 + 点酒二次复核 + 醉酒拒售"口径已下线。

1. 综合体**统一入场闸**必须经过"入场年龄核验"：接入第三方人脸/年龄核验接口或等效设备，满 18 岁方可进入；全部售酒点都在该核验范围内。
2. 判定为未成年人时**禁止进入**，记录拒绝并留痕。
3. **售酒环节继承入场闸结论、不逐单验龄、不醉酒拒售**（场内皆已验成年）。
4. **刷脸开关关闭期间**（本期默认关、供应商未接入）：靠**制度管控兜底**（人工证件查验、现场巡查），系统不强制逐单验龄；接入真实供应商前不得把人工口头确认标记为"自动核验已通过"。该核验不扩大第 8 节游客实名范围。
5. 上述入场核验动作进入事件中心留痕（方式、结果、点位、时间）。

### 2.2 需新增字段（统一入场闸侧）
- 入场核验结果落**统一入场闸**记录：`face_provider_code`、`face_provider_result_id`、`face_verify_result`（成年/未成年/不确定）、`face_verify_error_code` 作为供应商结果引用占位；P0 默认只保存最小必要结果和供应商流水引用，不默认保存原始人脸图像。

> 修订说明（2026-06-24 售酒豁免收口）：原回填 bar-operations 入场记录/点酒订单表的 `age_verified`/`age_verify_method`/`age_verify_point`/`refuse_reason`/`refuse_by`/`refuse_at` 等 bar 售酒环节字段已下线（售酒不再独立验龄/拒售）；入场年龄核验结果统一落入场闸侧。bar 侧 `BarAgeVerificationService`、`bar_age_verifications` 表与 refuse 字段已随之移除（详见 bar 开发设计 2026-06-24 修订）。

### 2.3 风控规则
> 2026-06-24 售酒豁免收口：原 `BAR_UNDERAGE_BLOCKED`（未成年售酒拦截）/ `BAR_INTOXICATED_REFUSED`（醉酒拒售）两条风控规则已下线（详见 data-risk-ai §10.9、evidence-risk-control）。未成年人售酒法定义务由统一入场闸 18+ 核验承接；入场闸判未成年即拒入，落 `risk_alerts` 留痕。

## 3. 游客个人信息保护与告知同意（C2）

**建议 P 级：P0（合规阻断，凡收集个人信息的入口）。关联 product-requirements / 票务 PRD / 客人端 PRD / 存酒流程。**

1. 购票、会员注册、存酒登记、支付等**收集个人信息前**，必须展示隐私政策并取得同意（勾选）。

## 4. 企业微信会话处理合规（C3，关联报告 A7）

**建议 P 级：P0（合规阻断）。关联 data-risk-ai §11 / evidence-risk-control §8 / third-party-integration / business-decision-log §22。**

> 现状口径"永久保存 + 不脱敏 + 管理者可查"只解决了"谁能看、看了留痕"，未解决"凭什么合法收集与无限期保存"。PIPL 要求存储期限为实现目的所必要的**最短**时间。

### 4.1 产品规则
1. 明确处理的**合法性基础**（人力资源管理必要性 / 规章制度 / 必要同意），并对员工与客户**事前告知**（员工入职监控告知与签署；客户侧服务场景告知）。
2. 采集范围**限定为工作会话**（企业微信工作号），不及员工私人沟通。
3. 将"永久保存"改为**可配置留存期限**（区分"质检/取证所需最短留存"与"长期归档"），到期归档或销毁/匿名化；若业务确需长期保存，补充其合法性论证。　**【2026-08-03 用户裁决：企业微信会话原文改为永久保存，本条建议不再采纳。该裁决触发本条自身写明的条件——长期保存须补充合法性论证，此项论证尚未完成，列为未了义务。见决策台账 DEC-CFG-2026-08-03-10。】**
4. 管理者查看**不脱敏原文**的最小授权范围 + 审批 + 访问审计（此项现状已有，保留）。
5. 离职/合同终止后、争议关闭后的会话**处置策略**（降级/销毁/匿名化）。

### 4.2 字段/配置
- 会话留存策略：`retention_policy_code`、`retention_days`(或 permanent_with_basis)、`disposal_action`(archive/delete/anonymize)、`legal_basis`、`employee_notice_id`

### 4.3 企微会话违规检测与处置闭环（P0）

> 修正(2026-06-19 R5业务HTML缺口审计 F6)：业务HTML #risk 明确"企业微信会话中的私单、私收款、辱骂、违规承诺、诱导私人微信"应被识别，且"会话每天归档后自动进入规则检查，疑似违规进复核队列"。代码核验：采集侧 `wecom_conversations`/`wecom_messages`/`wecom_access_audits`/`wecom_retention_policies`（V087）真实落地，AI 质检接缝（V096：能力开关默认关 + `wecom_messages.ai_qc_status`/`ai_qc_result` 预留字段）亦在；但**违规判定为空壳**——命中表 `wecom_risk_hits` 在 migration 中无 CREATE TABLE（已 Grep 佐证全库无定义），`analytics_risk_rules`（V017，rule_code UNIQUE）中亦无任何企微违规规则码（STAFF_PRIVATE_PAYMENT/私单/辱骂/诱导等 Grep 全部为空）。即"采集真实、留存/审计真实，但违规命中→复核队列这一闭环缺失"。本小节把该缺口落为 P0 合规口径，规则码与命中表设计见 data-risk-ai-development-design《企微违规规则码与命中表(wecom_risk_hits)》章节。

1. **数据流（合规口径）**：`wecom_conversations` 每日归档后自动进入规则检查（私单/私收款/辱骂/违规承诺/诱导私人微信等）→ 命中产生违规记录（命中表 `wecom_risk_hits`，待建）→ 命中进入统一异常复核队列（与 analytics_risk_alerts 衔接，标 source_domain=wecom），疑似违规由人工复核确认或驳回。这对应业务HTML"归档→规则检查→疑似违规进复核队列"。
2. **留存/到期/脱敏/访问审计已有 V087，但违规判定为空壳**：留存策略（`wecom_retention_policies`）、可配置留存/到期处置（archive/delete/anonymize）、查看访问审计（`wecom_access_audits`）均已真实落地；但规则检查与命中记录这一层本期 P0 必须补齐，否则"识别私单/辱骂/诱导"等合规承诺仍只是口头，无任何命中数据与复核闭环。
3. **不脱敏原文的合规边界（重申）**：会话原文查看须按权限控制；**不脱敏展示仅限有最小授权 + 审批的取证/质检场景**，普通展示场景敏感字段（手机号/证件/支付账号等）按权限脱敏；任何查看不脱敏原文均须写入访问审计（`wecom_access_audits` / `audit_events`）。违规命中样例（`matched_snippet`）展示同样遵循该脱敏策略，仅取证/质检授权场景方可见不脱敏原文。此为 §4.1 第 4 条与 §11.5 第 5 条的重申，避免补违规检测时绕开既有合规边界。
4. **验收口径**：①向 `analytics_risk_rules` 录入企微违规规则码后，归档会话命中规则能产生命中记录并进入复核队列（疑似违规可见、可复核）；②查看命中原文（不脱敏）须最小授权 + 审批并写入访问审计记录（可举证"谁、何时、看了哪条会话原文"）。

> **待业务确认**（修正 2026-06-19 R5业务HTML缺口审计 F6）：
> - 企业微信授权配置由谁一次性完成（治理HTML列为待确认项；合规 §4 现状亦标"企微授权配置由谁完成"待定）。该授权直接决定每日归档采集与规则检查能否真实运转。**业务确认(2026-06-19)** `R6 业务确认回填(2026-06-19)`：企微授权配置责任人确认为**由系统管理员(superadmin)一次性配置授权与密钥，并指定岗位复核**（覆盖原 R6 默认"合规管理员"口径，改为 superadmin 配置 + 指定岗位复核）；此项不再为待定项。
> - 规则误报的人工申诉流程：员工对被判定违规（如辱骂/诱导误判）的申诉入口、复核改判与改判后命中状态（confirmed→dismissed）的处置口径。

## 5. 员工私人手机设备凭证/设备检测合规（C4，关联报告 A6/phone-3）

**建议 P 级：P0（合规阻断）。关联 android §9 / platform-governance §6.9 / 员工注册审批。**

### 5.1 产品规则
1. 安装/注册时向员工**单独告知并取得同意**：将读取设备绑定凭证、做 Root/调试检测、采集必要设备指纹。

3. 解绑即删除对应绑定凭据。
4. 在"员工注册审批"页记录同意凭据。

> 修订说明（2026-06-07 收口）：原第2条示例字段名 `nfc_uid_hash` 改为 `device_key_fingerprint`，并删去原注脚"无论最终采用实体 NFC 工卡还是设备公钥凭证…"的二选一表述——依 D8/A6（2026-06-07 用户拍板），私人手机身份已定为安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹，实体 NFC 工卡方案已废止，不再是未决二选一。依据 finding decision-land-2、D8。

> 注：因 phone-3 指出"读手机本机 NFC 唯一标识"在 Android 不可行，本项与报告 A6 的设备凭证方案改造联动——按 D8/A6 已定为设备公钥/不可逆设备指纹凭证（device_key_fingerprint），本节的告知同意/最小化/删除要求同样适用。

## 6. 个人数据分类留存与销毁策略（C5）

**建议 P 级：P0 定策略、P1 落自动作业。关联 data-risk-ai / foundation 层 / system-breakdown 归档。**

### 6.1 产品规则
- 建立**个人信息分类留存表**：对手机号、证件、支付信息、消费记录、企微会话、视频证据分别设定法定/业务留存期限。
- 到期**自动删除或匿名化**，与软删除/归档机制对齐。
- 现有"事件按类型设保存周期"是成本/审计口径，需叠加 PIPL"最短必要"口径，二者取严。

| 数据类别 | 已确认推荐留存口径 | 到期处置 |
|---|---|---|
| 手机号/姓名 | 业务关系存续期 + 法定追溯期 | 匿名化 |
| 身份证件/人脸 | 实现核验目的后最短期 | 删除 |
| 支付/对账 | 税务/会计法定保存期 | 归档后删除 |
| 企微会话 | 见第 4 节可配置留存 | 归档/销毁/匿名化 |
| 视频证据 | 事件关联期 + 取证期 | 删除 |

> **手机号落库加密实现口径（2026-07-05 立，2026-07-27 扩到全部主体 / V339）**：系统内**任何自然人的手机号**在数据库一律 AES-GCM 加密存储（信封 `enc:v1:`），读时解密、需按值检索处并存不可逆盲索引（HMAC）。存量明文由启动期幂等回填就地加密。密钥由生产环境强随机注入，弱密钥/默认密钥在生产启动即 fail-closed。

> **口径纠正（2026-07-27，v7 综合审计 ★GAP-07 / SEC-04 / P0-A）**：本条 2026-07-05 版曾写「商业联系人手机号（商户、供应商、招商线索、施工入场报备等 B2B 联系人）按运营检索需要保持明文，不属消费者 PII 加密范围」。该口径被审计推翻并作废，理由两条：①商户联系人、供应商联系人、招商线索、费用通知接收人、施工进场报备联系人**都是自然人手机号**，PIPL 不按"消费者/商业伙伴"划线；②审计实证 `merchants` 59/59 全表明文入库，而"按运营检索需要"并不成立——实读全仓代码，这五处手机号**没有任何按手机号的后端检索路径**（后台列表的关键词过滤是前端对已取回行做 JSON 客户端匹配，与落库形态无关），所以加密不影响任何既有检索功能，也无需为它们建盲索引。
>
> **展示脱敏（与加密配套，V339）**：依据业务 HTML「员工日常界面只显示脱敏号码，不见明文」。上述八处手机号在后台读端一律按权限脱敏——持 `pii.contact_phone.view`（高危权限，V339 种子，默认仅平台管理员）才见明文，其余读端见掩码（前 3 后 4，如 `188****0011`）。脱敏统一走 `common.PhoneMask`，且做在 controller 层（service 之外），避免脱敏值污染写幂等缓存后被有权限者重放读到掩码。
>
> **数据库层边界**：V249 / V252 / V339 对上述各列加 `CHECK (... LIKE 'enc:v1:%')`。V339 的六个约束建为 `NOT VALID`——放行加约束之前就存在的存量明文行（由启动期回填负责加密），但**任何新写入/更新必须是信封密文**，仓库以外的手写 SQL、批量导入、运维脚本一律绕不过。

### 6.2 备份与个人信息保护（C5 补充）

> 新增说明（2026-06-07 收口）：系统运维侧对 PostgreSQL、对象存储和基础设施配置做 NAS 备份，与 C5 个人信息"到期销毁/匿名化"、C2 删除权存在真实冲突——用户行使删除权或留存到期销毁后，备份介质中仍可能保留个人信息原文，删除权未真正落地。本节就此给出处置口径。依据 finding critic-9、C5。

1. **备份保留期上限**：备份/灾备介质设定最长保留期（建议与最长法定追溯期对齐、超期自动轮替覆盖），不得无限期堆叠历史快照；备份保留期需在运维设计中显式配置并记录依据。
2. **敏感个人信息在备份中的最小化/加密**：身份证件、人脸、支付账号等敏感个人信息在备份介质中应加密存储（或备份前脱敏/最小化），密钥与备份介质分离保管。
3. **删除/匿名化请求对历史备份的处置口径**：对已落地的删除/匿名化请求，应用层主库即时执行（软删→匿名化/物理擦除）；历史备份采用"随备份轮替自然失效 + 不可单独定位删除"的处置策略——即不在历史快照中逐条擦除（技术上单条定位删除成本与风险过高），但通过①缩短备份保留期使含个人信息的旧快照在保留期内自然轮替覆盖、②恢复演练/真实恢复后对已删除主体做二次清洗作业（重放删除/匿名化日志）兜底，并就该口径保留法务论证记录。
4. **作业留痕**：删除/匿名化请求、恢复后二次清洗、备份轮替均写入操作留痕，作为 PIPL 删除权履行的举证依据。

> 落点：备份保留期/加密策略落运维设计与 foundation 层；二次清洗作业可与 §6.1 分类留存表对应的"个人信息留存与销毁/匿名化作业"（C5/critic-5，到期触发删除或匿名化的批处理）共用同一删除/匿名化日志重放机制。本节为 P0 定口径、P1 落自动作业。

## 11A. 短信/通知个人信息处理合规（C11，新增）

**建议 P 级：P0（合规阻断，凡发送短信处理手机号的入口）。关联 `third-party-supplier-integration-kit-v0.1.md` §3.2C 短信契约、`third-party-sms-notification-and-supplier-field-mapping-placeholders-v0.1.md`、`integration-capability-switches-v0.1.md`（`sms_notification`）。**

> 新增小节（`文档goalP1(2026-06-20)`）：业务已硬依赖短信（登录验证码 `sms_code`、商户催缴、风险告警），手机号属个人信息，发送短信即触发 PIPL 处理义务与商业短信报备规范，但合规文档此前对短信处理零覆盖。本节据实补登。

### 11A.1 法律映射

| 处理环节 | 合法性基础（口径，非法律意见） | 要点 |
|---|---|---|
| 登录验证码 | 履行合同/提供服务必要 | 仅用于本人身份验证，验证码有效期失效后须重新获取，不放行过期码 |
| 商户催缴短信 | 履行合同/合理商业沟通 | 限于商户结算/账务沟通，不得扩散到无关营销 |
| 风险告警短信 | 安全保障必要 | 限于风险处置相关接收人 |
| 营销/通知类短信（如有） | **需单独同意 + 可退订** | 非服务必要的商业短信须取得同意并提供退订方式（商业短信报备规范） |

### 11A.2 产品规则

1. **处理目的限定**：手机号仅用于对应业务目的（登录验证/催缴/告警），不得跨目的复用；模板按 `biz_type`（login/dunning/risk_alert）区分。
2. **告知**：收集手机号的入口（注册/登录/商户绑定）须在 §3 PIPL 告知同意范围内说明短信用途；营销类须单独同意 + 退订。
3. **最小化与脱敏**：日志/审计中手机号按敏感字段脱敏展示；短信模板变量（含验证码）按敏感信息处理，不全量落明文业务日志。
4. **留存**：手机号留存随 §6.1 分类留存表"手机号/姓名"口径（业务关系存续期 + 法定追溯期，到期匿名化）；发送回执/发送记录按运营监控所需最短期保留，不无限期堆叠。
5. **第三方供应商合规**：短信供应商接入须签数据处理协议（供应商作为受托处理方），credential_ref 走人工台账（supplier kit §8）；供应商侧不得留存超出代发必要的手机号。
6. **关闭/降级口径**：`sms_notification` 关闭时登录走 mock OTP（非生产固定码，生产无供应商时 fail-closed 拒绝登录），催缴/告警降级为 manual/站内记录，不静默丢弃（开关矩阵口径一致）。

### 11A.3 字段/配置

- 短信发送记录：`biz_type`、`request_id`（幂等键）、`send_status`（sent/failed/throttled）、`provider_msg_id`、`sent_at`；手机号展示脱敏。
- 同意记录：营销类短信复用 §3.2 `consent_records`（`consent_scope` 含短信营销、`is_sensitive_consent` 按需）。

### 11A.4 验收口径

- 短信仅按 `biz_type` 限定目的发送；营销类有单独同意 + 退订。
- 手机号在日志/审计脱敏；验证码/模板变量不落明文业务日志。
- 短信供应商有数据处理协议，credential_ref 走台账；关闭态 fail-closed 不静默丢弃。

## 11B. 视频监控供应商接入合规（C12，新增）

**建议 P 级：P0（合规阻断）。关联 `third-party-access-layer-spec-v0.2.md` §8.1（视频专项字段）、`third-party-integration-development-design.md` §13.4/§14.12-14.13、`integration-capability-switches-v0.1.md`（`video_platform`）、本文 §6.1 视频证据留存。**

> 新增小节（`文档goalP1(2026-06-20)`）：第三方视频监控接入涉及公共/经营场所图像采集与调阅取证，属敏感个人信息处理。本文 §6.1 已有"视频证据"留存口径、access-layer §9 已有"调阅强制鉴权+写审计+保存期限"字段口径，但缺**采集合法性/告知/调阅审计**的集中合规规则。本节据实补登并与既有口径对齐。

### 11B.1 采集合法性

1. **采集目的限定**：视频监控限于公共安全、经营秩序、纠纷取证等正当目的；不得在更衣室、卫生间等私密空间采集。
2. **合法性基础**：公共场所图像采集依《公共安全视频图像信息系统管理条例》及安全保障必要；涉及可识别个人的图像按 PIPL 敏感个人信息处理。
3. **供应商边界**：平台不自研视频底层平台，仅接入第三方供应商的点位/录像索引/截图/片段链接与告警回调（access-layer §8.2 边界一致）；供应商接入须签数据处理协议。

### 11B.2 告知

1. **现场告知标识**：采集区域须设置视频监控提示标识（告知正在采集）。
2. **员工告知**：涉及员工工作区域监控的，并入 §11 员工监控统一告知（入职协议/规章制度），用途限定。
3. **游客告知**：经营场所入口/区域以标识方式告知；调阅游客可识别图像用于取证时按最小必要。

### 11B.3 调阅与审计（与 access-layer §9、本文 §6.1 对齐）

1. **调阅强制鉴权 + 写审计**：视频证据调阅必须经权限校验，并强制写访问审计（记录**调阅人、调阅时间、关联事件**）；调阅是 `permission` 类事件（集成设计 §13.4 `video.viewed`）。
2. **保存期限**：视频证据/截图/片段必须有保存到期时间（`retention_until`），不无限期保存；到期删除（§6.1 视频证据"事件关联期+取证期"到期删除）。
3. **最小必要调阅**：调阅限于事件取证/安全处置所需，不得无关浏览；高敏调阅按最小授权。
4. **供应商侧留存**：供应商侧录像留存期限纳入合同与对账口径，平台侧只保留证据索引/链接/必要截图，不默认全量落地原始录像。

### 11B.4 字段/配置

- 视频证据：`camera_id`、`clip_url`/截图引用、`retention_until`、关联事件 ID、调阅审计（调阅人/时间/关联事件）。
- 调阅审计：复用 `audit_events` + 视频证据调阅记录，可举证"谁、何时、调阅了哪个点位/时段、关联哪个事件"。

### 11B.5 验收口径

- 视频采集目的限定、私密空间不采集、现场有告知标识。
- 调阅强制鉴权 + 写审计（调阅人/时间/关联事件齐全）。
- 视频证据有保存到期时间，到期删除；供应商有数据处理协议。
