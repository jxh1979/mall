# 业务拍板记录 V0.1

更新时间：2026-06-06

本文档记录总控会话中已经明确拍板的业务规则。后续 PRD、页面、接口、编码任务均应以本记录为上层约束。

## 1. 客人购票入口

- 官方购票入口 App 和小程序同步建设。
- App 与小程序共享订单、票、权益、会员积分、二维码和使用记录口径。
- 所有门票必须由客人自己购买，工作人员平板不得代客购票。

## 2. 第三方团购渠道

> 修订说明（2026-06-18 收口）：第三方团购回流优先级与 requirement-traceability-matrix、business-module-mature-system-gap-analysis 三处统一。统一口径来自 ticketing 设计 R5 业务裁决（verified）：**凡第三方一律预留接口 + 后台开关（默认 off）+ 不阻塞其它功能；P0 = 预留接口/开关/不伪造对账；真实渠道语义解析、external_order_no、双对账实做归 P1（对应 r5-spec-T14）。** 原"当前只聚焦团购购买/回流/核销/对账"不再读作 P0 即实做真实回流，按本统一口径收口。

- 第三方售票渠道首批方向覆盖美团、大众点评、抖音（团购购买、订单回流、券/票核销、对账为目标能力范围）。
- **P0 = 预留接口 + 后台开关（默认 off）+ 不伪造对账、不阻塞其它功能**；本期不强行实现真实回流。
- **真实渠道语义解析、external_order_no、双对账实做归 P1（对应 r5-spec-T14）。**
- 其他第三方营销玩法暂不纳入首批范围。

## 3. 会员积分和兑换

- 会员积分、等级成长和兑换规则按照后台定义的规则执行。
- 消费金额可以作为后台规则条件之一，但不直接固定为唯一积分口径。
- 积分兑换礼物必须扣减库存。
- 兑换结果要进入权益领取、库存消耗、财务对账和经营看板。

## 4. 通票和跨业态组合

- 酒吧可以有酒吧通票。
- 游乐可以有游乐通票。
- 可以有酒吧 + 游乐的联合通票。
- 可以有酒吧 + 游乐 + 餐饮 + 零售的折扣通票。
- 餐饮和零售一定由第三方承接，平台只提供优惠、折扣、券或权益，不自研完整餐饮/零售 POS。

## 5. 订台和支付

- 订台入口包括官方 App、小程序、触摸屏一体机和销售人员后台/工作台。
- 订台需要支付定金。
- 吧台买酒优先线上支付。
- 根据中国法律和现场经营要求，必须允许现场现金和 POS 机支付。
- 现金/POS 支付必须进入账单、留痕、日结和对账口径。

## 6. 供应合同和采购

- 平台可以维护自己的供应商和供应合同，用于满足平台需求。
- 各商户也允许维护自己的供应合同。
- 允许平台统一采购后再分销给各商户。
- 供应链页面和权限需要区分平台采购、商户自采、平台采购分销三种模式。

## 7. 客人存酒

- 存酒使用标签管理，标签从酒瓶最底部开始贴。
- 存酒按标签上显示的数值进行记录。
- 存酒需要拍照并填写人工备注。
- 存酒必须留取客人手机号和姓名/昵称。
- 后续取酒、转赠、作废、争议处理均应保留存酒记录和操作留痕。

## 8. 游乐容量

- 因游乐设施分布在综合体不同位置，P0 建议按具体项目 + 具体场次/时段 + 点位/设备控制容量。
- 项目总量用于上层汇总和安全上限。
- 具体核销放行以场次容量为主控口径。

## 9. 餐饮零售第三方回流和看板

- 餐饮/零售第三方回流同时支持订单级和券核销级。
- 数据看板支持日汇总、半日汇总和小时汇总。
- 单店或小数据量场景应支持实时汇总。

## 10. 票务二维码

- 票务二维码必须有有效期，有效期按票种配置决定，例如日票、周票、月票、年票。
- 二维码刷新频率支持 30 秒或 60 秒自动刷新。
- 截图无效。
- 二维码必须在线核验，不做离线核验。
- 场内建筑物应通过网络连接服务器完成核验。

## 11. 员工私人手机、设备凭证和 Root

> 修订说明（2026-06-07 收口）：本节口径**以 §32 A6（D8）为准**——已废止"读取手机本机 NFC 唯一标识"方案，私人手机身份改为安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint）。原文"App 读取手机 NFC 唯一标识并绑定员工"为已废止口径，现就地改写，消除与 §32 A6 的文内自相矛盾。依据 finding baseline-conf-2、decision-land-5、D8。

- 员工安装私人手机 App 时，安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint）作为唯一可信标识并绑定员工（不再读取手机本机 NFC 唯一标识）。
- 员工换手机时必须先解绑旧设备凭证，再绑定新手机设备凭证。
- Root/调试检测以手机端可检测能力为准；若做不到银行级硬件安全，则 Root 或异常环境应判定为不可信并失效复核。
- （注：工作手机通过摄像头/扫码模块读取外部客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。二维码不能通过 NFC 读取，见 §32 A6。）

## 12. 私人手机寄存

- 员工进入办公区或现场作业区时需要寄存私人手机。
- 员工不绑定固定寄存柜。
- 寄存柜按先来后到自行选择。
- 离开时必须全部取走个人物品。
- 系统记录寄存动作和取走动作即可，不要求固定柜位长期绑定。

## 13. 职级和薪资

- 职级是每个员工的管理等级。
- 后台可配置职级体系，例如管理层 M1 到 M10。
- 每个层级可进一步分上、中、下三个子层级。
- 职级和薪资只绑定大的框架范围，不自动生成具体薪资。
- 具体薪资需要后台填写。

## 14. 工作手机管控

- 工作手机预装软件清单和网站白名单由后台维护。
- 通过 Android Enterprise / Android Management API + 商业 MDM 控制。
- 违规访问原则上直接访问不了。
- 权限被封禁或策略命中需要进入后台留痕。

## 15. 票务优惠自动判断

- 新人优惠、学生票、多人票等票务优惠由后台配置规则。
- 客人符合后台规则时系统自动判断可用。
- 客人不符合后台规则时不允许享受对应优惠或票种。
- 学生票、多人票所需凭证、人数、身份、渠道、时间等条件均由后台规则定义。

## 16. 酒吧最低消费和按杯消耗

- 酒吧最低消费按时间、卡座和位置配置。
- 时间规则应支持平日、周末、节假日以及后台自定义时段。
- 不同卡座、不同位置可以设置不同最低消费。
- 原则上最低消费不按人数计算，人数只作为记录或运营参考。
- 票务权益、通票和卡座预约入场名额不允许抵扣最低消费；票务和卡座预定只解决入场/预约资格，不参与低消金额计算。
- 卡座预定者可以按卡座配置的入场名额携带客人免通票进入预定卡座所在酒吧；不同卡座允许入场人数可以不同，且不得进入其他酒吧。
- 吧台按杯销售时，每杯应配置标准出酒量或标准容量。
- 按杯销售优先按标准容量扣减库存；超过标准容量的部分作为损耗记录。
- 损耗严重时必须进入异常核查。
- P0 库存扣减强制但限定范围：整瓶、按杯标准量、赠饮/酒水兑换、积分兑换、存酒、报损、盘点差异等明确物品/数量/位置/责任人的场景必须扣减或状态转移；复杂 BOM、批次成本精算和自动补货后置。

## 17. 供应链 P0 范围

- 供应链 P0 从酒类、吧台消耗、客人存酒和常用消耗品开始。
- 常用消耗品包括纸巾、色盅、色子、杯子、杯具和类似高频使用物品。
- 其他低频物品可在 P1/P2 继续扩展。

## 18. 高风险库存和经营动作复核

- 高价值酒水报损、盘点差异、存酒作废必须上传拍照和视频证据。
- 上述动作必须主管复核后才能完成。
- 人工放行、免单、退款、调账必须进入主管复核。
- 复核层级可以后台配置，支持上一级、上两级或最高权限逐级上提。

## 19. 一体机游乐设施检修

- 一体机可承接游乐设施定期检修记录。
- 检修由工程师执行，检修单位作为供应商记录。
- 检修记录必须填写检修人员、检修单位、检修结果、时间和异常说明。
- 检修完成后必须由主管确认，游乐设施才能恢复营业。

## 20. 合同和基础定义违规处理

- 所有合同或基础定义违规都必须先卡住流程。
- 所有违规都允许更高级审核后放行。
- 放行层级可后台配置，支持上一级、上两级或最高权限逐级上提。
- 放行结果必须记录原因、审批人、审批层级和留痕。

## 21. Web 前端动作边界

- Web 前端 P0 允许少量确认动作。
- Web 前端仍以查看、查询、看板和业务确认为主，不承接复杂编辑和现场作业。

## 22. 企业微信会话保存

> 修订说明（2026-06-08 三轮收口）：原"企业微信工作会话永久保存"为上游业务拍板原始口径，与已收口的 A7/C3"可配置留存"相反，本轮就地改正并加交叉引用。依据 finding residual-scan-1、R条 A7/合规 C3。

- 企业微信工作会话留存期限可配置（非永久），到期归档/销毁/匿名化（按 A7/合规C3、data-risk §11.5）。保留"按权限查看 + 写审计"。
- 会话原文按权限查看。
- 不脱敏原文仅限最小授权 + 审批的取证/质检场景，一般展示按权限脱敏。
- 查看会话原文必须记录访问人、访问时间、访问范围和访问原因。

## 23. 多综合体和集团视图

- 未来需要集团视图和跨项目汇总视图。
- 当前优先级不高，P0 先保证所有对象都有综合体项目归属，后续按项目汇总到集团视图。
- 集团视图主要用于管理层看跨综合体收入、客流、商户、异常、结算和经营对比。

## 24. 商户侧开放范围和独立 SaaS 方向

- 商户侧在其授权业务范围内全开放。
- 商户不能查看平台全局和其他商户数据。
- 酒吧系统和游乐/乐园系统需要具备独立系统能力，未来可以分别演进为独立酒吧 SaaS 和独立乐园 SaaS。
- 不同商户进入商户侧后，只能看到和操作自己合同、空间、业务范围、员工权限允许的功能。

## 25. 日结锁定后补录

- 日结锁定后原则上不允许补录影响金额。
- 如确需补录，必须发起上级权限申请。
- 上级权限审批通过后，才允许补录并影响金额。
- 补录申请、审批、金额影响、责任人和原因必须留痕。

## 26. 员工权限最小颗粒度

- 员工权限要做到单一功能最小颗粒度。
- 一个单一功能对应一个权限点，例如“票务核销”“查看卡座预定状态”等。
- 权限必须支持完全自定义配置，可按角色配置，也可按员工单独配置。
- 职级可以影响默认权限模板和审批层级，但不能替代单一功能权限点。

## 27. 企业微信会话能力边界

- 企业微信会话能力按企业微信已有功能接入。
- 平台不重新发明会话存档能力，只负责把企业微信工作会话统一同步和存储到本系统。
- 后续实施时完成企业微信后台配置、账号绑定和同步任务即可。

## 28. 第三方接口和 SDK 接入策略

- 当前处于系统设计阶段，暂未确定第三方供应商接口资料。
- 开发顺序先完成自有系统。
- 自有系统所有内容和数据应在鉴权、授权范围和审计前提下，通过开放 API / Webhook / SDK 示例向第三方提供。
- 第三方系统的 SDK、API、接口资料后续拿到后再接入平台。
- 第三方接入分两类：一类是第三方按平台开放接口取数或回写；另一类是平台接入第三方 SDK/API。

## 29. 全链路操作留痕

- 所有有过程的业务动作都必须留痕，主动留痕和被动留痕都要进入统一事件中心。
- 酒水、礼品、高价值物料和需要追责的耗材必须有平台唯一二维码，可在入库时贴码，也可在出库时打印码。
- 酒从库房出库时，订单核验人或出库核验人必须扫码确认订单和酒水二维码。
- 如使用机器人配送，机器人到达取货点、库管交给机器人、机器人到达酒吧后厨都必须形成事件。
- 后厨接收人、服务员从后厨取走、服务员送达客人或卡座，都必须通过扫码、设备确认或必要的人工确认留痕。
- 留痕必须记录员工、设备、时间、地点、订单、物品码、结果和异常原因。

## 30. 终端开关和 SaaS 化准备

- 所有端都必须有开关接口，包括客人 App、小程序、Web 前端、工作人员平板 App、员工工作手机、员工私人手机 App、商户侧 App/Web、触摸屏一体机和移动管理端。
- 端开关支持按全局、综合体项目、商户、业务系统、模块、设备和版本控制。
- 开关关闭后，该端或模块不可用；开关打开后仍然要继续经过登录、设备可信、商户范围、角色权限、单一功能权限和数据权限校验。
- 终端开关是为了支持后续酒吧系统和乐园系统独立 SaaS 化。

## 31. 全业务过程留痕

- 留痕不只包括物品交接，也包括订单获取、销售归属、订台、服务、核销、收款、退款、异常首响、转派升级、复核关闭、人工补录和调账。
- 原则是“凡是有过程的业务动作都要留痕”。
- 订单必须能追溯来源渠道、创建人、销售人员、终端、支付结果和后续状态变化。
- 卡座和桌台必须能追溯主责服务员、协助服务员、加单人、送达人、换人记录和清台结果。
- 异常必须能追溯谁发现、谁第一个处理、谁接手、谁升级、谁复核、谁关闭以及关闭结论。
- 留痕设计要尽量自动化，优先通过登录账号、设备绑定、班次、点位、扫码、支付回调、终端动作、机器人状态、企业微信同步和第三方回调自然生成；人工只补原因、照片、视频、签名和复核意见。
- 视频监控前期不作为 P0 强依赖，但所有事件要记录点位、设备和发生时间，为后续与监控视频一一对应预留条件。

### A5 — 门票资格 P0 口径（依据 D9、ticket-1/2/3/4）

> 编号说明（2026-06-07 收口）：原标"A9"，与报告 A9=合规专章冲突，现更正为 **A5=门票资格**，与《文档审查与完善报告》§2/§2.1 权威编号一致。依据 finding decision-land-5。

- **新人优惠**：以手机号为准，注册必须登记手机号并短信验证；同一手机号未购买/未享受过即判新人，**系统自动判定**，不符不可用。

- **多人票**：必须同一时段全部核销（如同一晚同场次集中核销，不可拆到不同日期/场次）；`product_entitlement_template`/`issued_entitlement` 增 `num_people`，核销记录放行人数与时段约束。
- 同步消除新人票"自动/人工/P1"三处冲突，以本条为准（覆盖原 §15 等处的旧表述）。

### A6 — 员工设备身份改用设备指纹/Keystore 凭证（依据 D8、phone-3/7、compliance-4）

- **废止**"安装时读取手机本机 NFC 唯一标识"（Android 技术不可行）与实体 NFC 工卡方案。
- **私人手机身份 = 安装期生成并存于设备 Keystore 的设备公钥 / 不可逆设备指纹**；换机=先解绑旧设备凭证再绑新；Root/调试/异常判不可信失效复核。
- 仅持久化不可逆哈希/公钥指纹，不存原始标识（PIPL 数据最小化）。
- 工作手机通过摄像头/扫码模块读取**外部**客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。二维码不能通过 NFC 读取；NFC 真核销=P1，厂商深度联动=P2。
