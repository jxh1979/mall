# 业务拍板记录 V0.1

更新时间：2026-06-06

本文档记录总控会话中已经明确拍板的业务规则。后续 PRD、页面、接口、编码任务均应以本记录为上层约束。

## 1. 客人购票入口

- 官方购票入口 App 和小程序同步建设。
- App 与小程序共享订单、票、权益、会员积分、二维码和使用记录口径。
- 所有门票必须由客人自己购买，工作人员平板不得代客购票。

## 2. 第三方团购渠道

- P0 第三方售票渠道首批覆盖美团、大众点评、抖音。
- 当前只聚焦团购购买、订单回流、券/票核销和对账。
- 其他第三方营销玩法暂不纳入首批范围。

## 3. 会员积分和兑换

- 会员积分、等级成长和兑换规则按照后台定义的规则执行。
- 消费金额可以作为后台规则条件之一，但不直接固定为唯一积分口径。
- 积分兑换礼物必须扣减库存。
- 兑换结果要进入权益领取、库存消耗、财务对账和经营看板。

## 4. 通票和跨业态组合

- 酒吧可以有酒吧通票。
- 游乐可以有游乐通票。
- 可以有酒吧 + 游乐的联合通票。
- 可以有酒吧 + 游乐 + 餐饮 + 零售的折扣通票。
- 餐饮和零售一定由第三方承接，平台只提供优惠、折扣、券或权益，不自研完整餐饮/零售 POS。

## 5. 订台和支付

- 订台入口包括官方 App、小程序、触摸屏一体机和销售人员后台/工作台。
- 订台需要支付定金。
- 吧台买酒优先线上支付。
- 根据中国法律和现场经营要求，必须允许现场现金和 POS 机支付。
- 现金/POS 支付必须进入账单、留痕、日结和对账口径。

## 6. 供应合同和采购

- 平台可以维护自己的供应商和供应合同，用于满足平台需求。
- 各商户也允许维护自己的供应合同。
- 允许平台统一采购后再分销给各商户。
- 供应链页面和权限需要区分平台采购、商户自采、平台采购分销三种模式。

## 7. 客人存酒

- 存酒使用标签管理，标签从酒瓶最底部开始贴。
- 存酒按标签上显示的数值进行记录。
- 存酒需要拍照并填写人工备注。
- 存酒必须留取客人手机号和姓名/昵称。
- 后续取酒、转赠、作废、争议处理均应保留存酒记录和操作留痕。

## 8. 游乐容量

- 因游乐设施分布在综合体不同位置，P0 建议按具体项目 + 具体场次/时段 + 点位/设备控制容量。
- 项目总量用于上层汇总和安全上限。
- 具体核销放行以场次容量为主控口径。

## 9. 餐饮零售第三方回流和看板

- 餐饮/零售第三方回流同时支持订单级和券核销级。
- 数据看板支持日汇总、半日汇总和小时汇总。
- 单店或小数据量场景应支持实时汇总。

## 10. 票务二维码

- 票务二维码必须有有效期，有效期按票种配置决定，例如日票、周票、月票、年票。
- 二维码刷新频率支持 30 秒或 60 秒自动刷新。
- 截图无效。
- 二维码必须在线核验，不做离线核验。
- 场内建筑物应通过网络连接服务器完成核验。

## 11. 员工私人手机、设备凭证和 Root

> 修订说明（2026-06-07 收口）：本节口径**以 §32 A6（D8）为准**——已废止"读取手机本机 NFC 唯一标识"方案，私人手机身份改为安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint）。原文"App 读取手机 NFC 唯一标识并绑定员工"为已废止口径，现就地改写，消除与 §32 A6 的文内自相矛盾。依据 finding baseline-conf-2、decision-land-5、D8。

- 员工安装私人手机 App 时，安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint）作为唯一可信标识并绑定员工（不再读取手机本机 NFC 唯一标识）。
- 员工换手机时必须先解绑旧设备凭证，再绑定新手机设备凭证。
- Root/调试检测以手机端可检测能力为准；若做不到银行级硬件安全，则 Root 或异常环境应判定为不可信并失效复核。
- （注：工作手机通过摄像头/扫码模块读取外部客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。二维码不能通过 NFC 读取，见 §32 A6。）

## 12. 私人手机寄存

- 员工进入办公区或现场作业区时需要寄存私人手机。
- 员工不绑定固定寄存柜。
- 寄存柜按先来后到自行选择。
- 离开时必须全部取走个人物品。
- 系统记录寄存动作和取走动作即可，不要求固定柜位长期绑定。

## 13. 职级和薪资

- 职级是每个员工的管理等级。
- 后台可配置职级体系，例如管理层 M1 到 M10。
- 每个层级可进一步分上、中、下三个子层级。
- 职级和薪资只绑定大的框架范围，不自动生成具体薪资。
- 具体薪资需要后台填写。

## 14. 工作手机管控

- 工作手机预装软件清单和网站白名单由后台维护。
- 通过 Android Enterprise / Android Management API + 商业 MDM 控制。
- 违规访问原则上直接访问不了。
- 权限被封禁或策略命中需要进入后台留痕。

## 15. 票务优惠自动判断

- 新人优惠、学生票、多人票等票务优惠由后台配置规则。
- 客人符合后台规则时系统自动判断可用。
- 客人不符合后台规则时不允许享受对应优惠或票种。
- 学生票、多人票所需凭证、人数、身份、渠道、时间等条件均由后台规则定义。

## 16. 酒吧最低消费和按杯消耗

- 酒吧最低消费按时间、卡座和位置配置。
- 时间规则应支持平日、周末、节假日以及后台自定义时段。
- 不同卡座、不同位置可以设置不同最低消费。
- 原则上最低消费不按人数计算，人数只作为记录或运营参考。
- 票务权益、通票和卡座预约入场名额不允许抵扣最低消费；票务和卡座预定只解决入场/预约资格，不参与低消金额计算。
- 卡座预定者可以按卡座配置的入场名额携带客人免通票进入预定卡座所在酒吧；不同卡座允许入场人数可以不同，且不得进入其他酒吧。
- 吧台按杯销售时，每杯应配置标准出酒量或标准容量。
- 按杯销售优先按标准容量扣减库存；超过标准容量的部分作为损耗记录。
- 损耗严重时必须进入异常核查。
- P0 库存扣减强制但限定范围：整瓶、按杯标准量、赠饮/酒水兑换、积分兑换、存酒、报损、盘点差异等明确物品/数量/位置/责任人的场景必须扣减或状态转移；复杂 BOM、批次成本精算和自动补货后置。

## 17. 供应链 P0 范围

- 供应链 P0 从酒类、吧台消耗、客人存酒和常用消耗品开始。
- 常用消耗品包括纸巾、色盅、色子、杯子、杯具和类似高频使用物品。
- 其他低频物品可在 P1/P2 继续扩展。

## 18. 高风险库存和经营动作复核

- 高价值酒水报损、盘点差异、存酒作废必须上传拍照和视频证据。
- 上述动作必须主管复核后才能完成。
- 人工放行、免单、退款、调账必须进入主管复核。
- 复核层级可以后台配置，支持上一级、上两级或最高权限逐级上提。

## 19. 一体机游乐设施检修

- 一体机可承接游乐设施定期检修记录。
- 检修由工程师执行，检修单位作为供应商记录。
- 检修记录必须填写检修人员、检修单位、检修结果、时间和异常说明。
- 检修完成后必须由主管确认，游乐设施才能恢复营业。

## 20. 合同和基础定义违规处理

- 所有合同或基础定义违规都必须先卡住流程。
- 所有违规都允许更高级审核后放行。
- 放行层级可后台配置，支持上一级、上两级或最高权限逐级上提。
- 放行结果必须记录原因、审批人、审批层级和留痕。

## 21. Web 前端动作边界

- Web 前端 P0 允许少量确认动作。
- Web 前端仍以查看、查询、看板和业务确认为主，不承接复杂编辑和现场作业。

## 22. 企业微信会话保存

> 修订说明（2026-06-08 三轮收口）：原"企业微信工作会话永久保存"为上游业务拍板原始口径，与已收口的 A7/C3"可配置留存"相反，本轮就地改正并加交叉引用。依据 finding residual-scan-1、R条 A7/合规 C3。

- 企业微信工作会话留存期限可配置（非永久），到期归档/销毁/匿名化（按 A7/合规C3、data-risk §11.5）。保留"按权限查看 + 写审计"。
- 会话原文按权限查看。
- 不脱敏原文仅限最小授权 + 审批的取证/质检场景，一般展示按权限脱敏。
- 查看会话原文必须记录访问人、访问时间、访问范围和访问原因。

## 23. 多综合体和集团视图

- 未来需要集团视图和跨项目汇总视图。
- 当前优先级不高，P0 先保证所有对象都有综合体项目归属，后续按项目汇总到集团视图。
- 集团视图主要用于管理层看跨综合体收入、客流、商户、异常、结算和经营对比。

## 24. 商户侧开放范围和独立 SaaS 方向

- 商户侧在其授权业务范围内全开放。
- 商户不能查看平台全局和其他商户数据。
- 酒吧系统和游乐/乐园系统需要具备独立系统能力，未来可以分别演进为独立酒吧 SaaS 和独立乐园 SaaS。
- 不同商户进入商户侧后，只能看到和操作自己合同、空间、业务范围、员工权限允许的功能。

## 25. 日结锁定后补录

- 日结锁定后原则上不允许补录影响金额。
- 如确需补录，必须发起上级权限申请。
- 上级权限审批通过后，才允许补录并影响金额。
- 补录申请、审批、金额影响、责任人和原因必须留痕。

## 26. 员工权限最小颗粒度

- 员工权限要做到单一功能最小颗粒度。
- 一个单一功能对应一个权限点，例如“票务核销”“查看卡座预定状态”等。
- 权限必须支持完全自定义配置，可按角色配置，也可按员工单独配置。
- 职级可以影响默认权限模板和审批层级，但不能替代单一功能权限点。

## 27. 企业微信会话能力边界

- 企业微信会话能力按企业微信已有功能接入。
- 平台不重新发明会话存档能力，只负责把企业微信工作会话统一同步和存储到本系统。
- 后续实施时完成企业微信后台配置、账号绑定和同步任务即可。

## 28. 第三方接口和 SDK 接入策略

- 当前处于系统设计阶段，暂未确定第三方供应商接口资料。
- 开发顺序先完成自有系统。
- 自有系统所有内容和数据应在鉴权、授权范围和审计前提下，通过开放 API / Webhook / SDK 示例向第三方提供。
- 第三方系统的 SDK、API、接口资料后续拿到后再接入平台。
- 第三方接入分两类：一类是第三方按平台开放接口取数或回写；另一类是平台接入第三方 SDK/API。

## 29. 全链路操作留痕

- 所有有过程的业务动作都必须留痕，主动留痕和被动留痕都要进入统一事件中心。
- 酒水、礼品、高价值物料和需要追责的耗材必须有平台唯一二维码，可在入库时贴码，也可在出库时打印码。
- 酒从库房出库时，订单核验人或出库核验人必须扫码确认订单和酒水二维码。
- 如使用机器人配送，机器人到达取货点、库管交给机器人、机器人到达酒吧后厨都必须形成事件。
- 后厨接收人、服务员从后厨取走、服务员送达客人或卡座，都必须通过扫码、设备确认或必要的人工确认留痕。
- 留痕必须记录员工、设备、时间、地点、订单、物品码、结果和异常原因。

## 30. 终端开关和 SaaS 化准备

- 所有端都必须有开关接口，包括客人 App、小程序、Web 前端、工作人员平板 App、员工工作手机、员工私人手机 App、商户侧 App/Web、触摸屏一体机和移动管理端。
- 端开关支持按全局、综合体项目、商户、业务系统、模块、设备和版本控制。
- 开关关闭后，该端或模块不可用；开关打开后仍然要继续经过登录、设备可信、商户范围、角色权限、单一功能权限和数据权限校验。
- 终端开关是为了支持后续酒吧系统和乐园系统独立 SaaS 化。

## 31. 全业务过程留痕

- 留痕不只包括物品交接，也包括订单获取、销售归属、订台、服务、核销、收款、退款、异常首响、转派升级、复核关闭、人工补录和调账。
- 原则是“凡是有过程的业务动作都要留痕”。
- 订单必须能追溯来源渠道、创建人、销售人员、终端、支付结果和后续状态变化。
- 卡座和桌台必须能追溯主责服务员、协助服务员、加单人、送达人、换人记录和清台结果。
- 异常必须能追溯谁发现、谁第一个处理、谁接手、谁升级、谁复核、谁关闭以及关闭结论。
- 留痕设计要尽量自动化，优先通过登录账号、设备绑定、班次、点位、扫码、支付回调、终端动作、机器人状态、企业微信同步和第三方回调自然生成；人工只补原因、照片、视频、签名和复核意见。
- 视频监控前期不作为 P0 强依赖，但所有事件要记录点位、设备和发生时间，为后续与监控视频一一对应预留条件。

> 编号说明（2026-06-07 收口）：原标"A5"，与报告 A5=门票资格冲突，现改为子编号 **A5b**（退款细化隶属 A5 退款主题）。依据 finding decision-land-5。

- **P0 客人侧按订单/票发起退款**，内部按权益冲正与金额拆分（refund_type=full/partial/entitlement），退款记录与退款人责任、基础退款对账纳入 P0。
- **复杂退款规则引擎进入 P1**。
- 票务 PRD、finance-settlement PRD、`p0-implementation-task-list`（新增 TKT-008）口径据此对齐。

### A6 — 员工设备身份改用设备指纹/Keystore 凭证（依据 D8、phone-3/7、compliance-4）

- **废止**"安装时读取手机本机 NFC 唯一标识"（Android 技术不可行）与实体 NFC 工卡方案。
- **私人手机身份 = 安装期生成并存于设备 Keystore 的设备公钥 / 不可逆设备指纹**；换机=先解绑旧设备凭证再绑新；Root/调试/异常判不可信失效复核。
- 仅持久化不可逆哈希/公钥指纹，不存原始标识（PIPL 数据最小化）。
- 工作手机通过摄像头/扫码模块读取**外部**客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。二维码不能通过 NFC 读取；NFC 真核销=P1，厂商深度联动=P2。

## 33. 2026-06-09 市场基准复核裁决

本节用于承接已归档的市场基准与对抗式审计结论，避免市场同类系统能力被误读为 P0 立即编码范围。当前执行入口见 `final-open-decisions-and-owner-checklist-20260610.md`、`master-roadmap.md` 和 `p0-implementation-task-list.md`。

- 市场基准建议不自动扩大 P0。P0 仍以 `p0-implementation-task-list.md` 为单一权威。
- MDM/Android Enterprise 方案已拍板采用 Android Enterprise / Android Management API + 商业 MDM；工作手机/平板必须能管控预装软件、网站白名单、违规访问、Kiosk/专用设备和设备失联状态。
- 企业微信使用官方会话存档能力，管理员一次性完成后台授权和密钥配置；平台系统负责员工映射、同步、存储、质检、权限审计、失败告警和留存策略。
- 商户服务/维修/投诉/整改工单、证照/资质/保险到期深化默认进入 P1，不进入 P0 主流程；租金、物业费、能源费、公摊/CAM、应收账龄等款项 P0 先进入完整应收应付台账，P1 再做商户账单门户、催缴和费用异议。
- 酒吧拆单、合单、转台、挂账、服务费、低消差额补齐、配方成本、毛利和复杂员工提成默认进入 P1 酒吧 SaaS 增强；但 2026-06-10 新增的**卡座销售提成基础规则**进入 P0：销售人员售卖卡座按卡座消费额 15%，非销售人员按 10%，不含通票和票务权益。
- 游乐安全告知/电子免责和事故工单建议进入 P1；预约排队、团体/包场和跨项目集团视图建议进入 P2。
- 上述 P1/P2 项进入编码前，必须补独立 PRD、字段字典、API 清单、验收标准和迁移任务。

## 34. 2026-06-10 总控拍板与合同到期字段裁决

本节承接总控新拍板，作为后续产品文档、P0 任务拆分和 160 编码分派的上层口径。

- 权限点首批由平台统一预置，后续实施阶段允许边配置边补充；权限点仍按单一功能最小颗粒度定义，角色模板只是批量授权工具。
- 合同关键日期、证照/资质/保险到期字段采用 `contract-date-compliance-field-granularity-options-20260610.md` 的**方案 B：标准通用事项台账**作为 P0 编码口径。
- 方案 B 的默认落地：合同主表只保存基础摘要；合同关键日期用 `contract_key_dates` 一行一事项承载；证照/资质/保险到期事项扩展现有 `merchant_credentials` 或等价落为 `compliance_expiry_items` 通用台账。
- P0 只做提醒、阻断、升级审批、附件归档和留痕；合同 OCR、电子签章、保险理赔、复杂费用账单和资质自动校验进入 P1/P2。
- 必填证照缺失/过期、合同过期、消防或特种设备资质过期默认先阻断；允许更高级别审批放行，放行原因、审批层级、审批人、附件/证据必须留痕。

## 35. 2026-06-10 总控决策项补充执行口径

本节承接已归档的总控决策建议来源，用于把已明确口径和建议执行口径写入上层拍板记录。若后续总控另行修改，以新的总控拍板为准。

- 票务策略 P0 以“平日/周末/节假日价”为最高优先级基础价格；多人票、新人票、学生票和渠道价基于对应基础价生成，也可由运营输入固定价格策略覆盖；动态定价放到 P2。
- 通票赠酒成本由平台承担；P0 仍保留成本承担方字段，默认值为 `platform`，便于后续活动预算或单票种配置扩展。
- 酒吧合同中的“股东比例”只用于利润报表，不进入 P0 结算打款；复杂股东分润进入 P2。
- 商场平面图 P1 先做图片 + 多边形坐标；CAD/SVG 标准化导入作为 P2 或实施工具。
- 合同关键日期颗粒度采用方案 B：`contract_key_dates` 独立承载，证照/资质/保险扩展 `merchant_credentials` 或落 `compliance_expiry_items`；P0 可引入本地 AI 大模型做关键日期、风险和缺失项辅助判断，但 AI 结果必须人工确认后才能入台账、提醒、阻断或放行。
- 合同审批 P1 先做审批流和附件归档；电子签章、扫描件 OCR 和保险理赔后置。
- Android 端 P1 可支持离线查看策略摘要和普通低风险权益最小摘要；高价值酒水、退款、改期、人工放行、调账必须在线；P0 不启用离线核销。
- MDM/Android Enterprise 方案已拍板采用 Android Enterprise / Android Management API + 商业 MDM；由平台公司 IT 部门选型、采购、配置和运维；业务系统 P0 只消费设备档案、策略摘要、合规状态、启停和审计结果。
- 企业微信后台配置、账号绑定和同步任务应最大程度自动化：管理员一次性完成企业后台授权和密钥配置，系统自动做员工映射、同步、失败告警、质检复核流转和留存策略。
- AI 质检 P0 采用规则引擎最细颗粒度落地；深度语义分析、服务评分、客户意图识别和独立 Python AI 服务进入 P2。
- 第三方 SDK/API 未拿到前，P0 做双向开放 API、Webhook + 定时轮询校验、签名、幂等、重试、对账和异常补偿框架；真实供应商字段映射和联动进入 P1/P2。
- 生产账号、密钥、数据库和对象存储密码轮换 P0 先做密钥台账、到期提醒和人工轮换 Runbook；自动轮换进入 P1。
- 备份 P0 采用 NAS；预算允许时后续叠加第二台机器或云存储异地副本。
- 域名和 HTTPS：160 P0 先不绑定域名和 HTTPS，作为预生产/演示内网或受控访问环境；正式生产或外部第三方联调前再配置。
- 商户服务/维修/投诉/整改工单作为 P1 独立子域；租金、物业费、能源费、公摊/CAM、保证金/押金、应收账龄等 P0 进入完整应收应付台账，P1 再形成商户账单门户、催缴、费用异议和复杂费用规则。
- 支付通道 P0 采用聚合支付优先，保留微信支付、支付宝、银行卡等直连接口抽象；后续可因费率、资金归集或商务谈判切换直连，不改变上层订单、退款、对账和结算模型。
- 160 运维脚本允许写入 160；执行前必须 dry-run、备份、Runbook、可回滚。
- 告警渠道采用企业微信机器人 + 邮件兜底；n8n 作为 P1 自动化增强，短信/电话告警后置。
- 财务结算主口径采用多口径并存：订单、核销、合同固定规则分别形成结算依据。
- P0 做完整应收应付台账，覆盖应收、应付、账龄、到期日、责任主体、合同/订单/核销来源、收付款状态、差异、附件和留痕。
- 新增销售人员岗位；卡座销售提成基础规则进入 P0：销售人员售卖卡座按卡座消费额 15% 计提，非销售人员按 10% 计提；提成基数不含通票、票务权益、卡座预约入场名额、赠酒成本、退款、免单和不可计提调整；复杂多人分摊、阶梯提成、活动倍率和正式薪资发放进入 P1/P2。
- 经营对象、运营主体、合同主体和结算主体可以是不同名称/不同公司，但必须在同一经营对象下唯一绑定，并在合同、结算、权限、看板、第三方接入和相关流程中统一引用、统一留痕。
- 已归档全量对抗式审计中的 B/C/D/E 类事项均按建议执行：B 类进入已确认默认规则，C 类进入 P1/P2 排期池（其中应收应付基础台账前移 P0），D 类按双向开放和供应商资料后细化执行，E 类由法务/HR/财务确认模板和留存周期。
