# 综合体管理系统开发规格总文档

> 2026-07-04 逻辑一致性修订：补名词四层脚注。
> 名词四层脚注：本文「多商户/组织/项目公司/SPV」为业务概念分层（业务：平台 → 项目公司 → 管理公司·SPV → 商户）；DB 层**无 `organizations`/`org_type` 表**，四层主体统一落 `business_entities`，用 `entity_role`（文本，无 CHECK）区分角色。「场地/门店/点位」空间四级模型已作废，真实为**扁平单表 `spaces`**（`space_type` + `parent_space_id`，`status` 仅 `active`/`unavailable`）。`projects` 表是**业态场馆**（venue_type），非「项目公司」。见 merchant-space-contract-model-v0.1 §2.4/§5。

本文档是项目后续拆解、评审和编码的总入口。目标不是写概念方案，而是形成可以直接指导后端、前端、安卓端、运维和数据服务开发的系统规格。

## 1. 文档目标

完整系统文档必须回答以下问题：

- 系统有哪些业务域、子系统和模块。
- 每个模块负责什么，不负责什么。
- 每个模块有哪些核心对象、状态机和业务流程。
- 每个模块需要哪些数据库表、字段、索引和约束。
- 每个模块暴露哪些 API，入参、出参、权限和错误码是什么。
- 每个关键操作如何写入事件中心，如何审计和追溯。
- 每个模块和多综合体、多商户、权限、合同准入、票务、酒吧、游乐、第三方、安卓设备、数据分析之间如何协作。
- 第一阶段先做什么，哪些功能暂缓。

## 2. 总体技术路线

> 修订说明（2026-06-10）：下表为**正式技术栈（已拍板）**。本规格全部 `*-development-design` 均以下表 Java 路线为准。依据《统一口径基准》D10、A1，finding devtech-9、status-1。

| 层级 | 技术方向 | 说明 |
|---|---|---|
| 核心后端 | Java 21 + Spring Boot 4.x | 承接多综合体、多商户、合同准入、权限、开放平台、票务、酒吧、游乐、结算、事件中心 |
| 数据库 | PostgreSQL + Flyway | 正式主库和版本化迁移 |
| 缓存与锁 | Redis | 短期 Token、动态鉴权、限流、幂等、热点缓存 |
| 异步事件 | NATS | 业务事件、第三方回调、异步补偿、风控分析 |
| 对象存储 | MinIO | 图片、视频证据索引、附件、导出文件 |
| 管理后台 | React | 平台端、商户端、运营看板 |
| 安卓端 | Kotlin Android | 员工私人手机 App、员工工作手机、企业微信管控、酒吧点酒平板、触摸屏一体机、扫码、外部 NFC 读取、P1 预留离线核销、最低消费校验、订台、吧台买酒、游乐状态 |
| 数据分析/AI | Java 内置规则处理器（P0）；独立 Python AI 服务（P2） | P0 指标体系、基础风控规则、企业微信基础质检和经营分析由 Java 后端承接；高级 AI/Python 服务后置 |
| 运维部署 | Ubuntu 160 + Nginx + systemd + Docker Compose | 开发/预生产一体环境 |

## 3. 系统域划分

### 3.1 平台地基域

负责全系统底座：

- 多综合体、多商户、品牌、门店、场地、点位。
- 合同核心摘要、经营范围、空间范围、准入拦截和升级审批。
- 员工、账号、角色、权限、岗位、职级、薪资口径摘要、班次。
- 员工私人手机 App 注册审批、设备凭证绑定、Root/设备异常失效、公司工作手机一一对应。
- 开放平台、安全鉴权、动态地址、签名、防重放。
- 统一事件中心、业务过程留痕、服务责任链、审计、人工补录、证据链。

现有参考文档：

- `docs/foundation-systems-breakdown.md`
- `docs/foundation-database-design.md`
- `docs/java-backend-platform-foundation-development-design.md`
- `docs/open-platform-security-auth-development-design.md`

当前状态：

- 已补齐 Java 包结构、PostgreSQL/Flyway 迁移分层、REST API、DTO/Service/Repository、事件留痕和部署要求。
- 已确认：后端构建默认 Maven，登录默认 JWT + Refresh Token，ORM 先用 Spring Data JPA 起步，事件中心 P0 同步写事件表、P1 再接 NATS。

### 3.2 票务通票与权益域

负责卖票、出票、权益拆分、核销、退款、改期、渠道、结算。

核心原则：

- 通票是销售包装。
- 权益实例是核销、退款、结算和风控的最小单位。
- 票码和权益码必须具备防伪串码、二维码签名、随机串、有效期、哈希校验和事后核对能力。
- 每次核销都必须落事件、落核销流水、可追溯到商户和设备。

现有参考文档：

- `docs/ticketing-pass-entitlement-development-design.md`
- `docs/ticketing-entitlement-settlement-breakdown.md`
- `docs/ticketing-database-implementation-notes.md`

当前状态：

- 已达到较高开发设计颗粒度。
- 下一步可转入 Java 模块、Flyway 迁移、DTO、接口和测试用例设计。

### 3.6 安卓设备端域

负责员工工作手机、酒吧点酒平板、触摸屏一体机。

必须拆清：

- 终端能力开关，所有端启动和进入业务模块前必须校验后台开关。
- 酒水和可追责物品扫码交接，覆盖出库核验、机器人或人工配送、后厨接收、服务员取走和送达。

- 设备注册、领用、归还、绑定。
- 员工登录、班次、岗位权限、职级权限。
- 员工私人手机 App 注册、通知、状态查看、设备凭证绑定和 Root/设备异常检测。
- 员工工作手机扫码和外部 NFC 读取；票务/权益 P0 必须在线核验，离线核销仅 P1 预留。
- 酒吧入口年龄/人脸核验的端侧触发、结果展示、失败原因、生产阻断提示和事件留痕；真实核验由第三方供应商适配器或等效设备承接，未配置供应商时生产环境不得标记正式通过。
- 酒吧点酒平板绑定酒吧和卡座、校验最低消费、生成支付二维码或扫描客人付款码。
- 触摸屏一体机扫码展示/领取权益、订台下单、吧台买酒下单、支付引导、游乐设施状态查看和授权状态检查。
- 工作手机只允许企业微信工作沟通，每日会话上传后台。
- 预装软件清单、应用白名单、网站白名单和违规访问上报。
- 本地缓存、同步队列、冲突处理。
- MDM、Kiosk、安全策略。

## 5. 第一阶段 P0 闭环

第一阶段目标是打通“可运营、可核销、可留痕、可部署”的最小闭环。

P0 必须完成：

- Java Spring Boot 后端骨架。
- PostgreSQL + Flyway 迁移。
- 多综合体/多商户、合同准入、账号权限、开放应用、事件中心。
- 员工私人手机 App 注册、设备凭证绑定、职级权限、公司工作手机绑定。
- 票种、通票、权益实例、防伪二维码/串码、二维码核销和事后核对。
- 酒吧入场核销、桌台、基础点单。
- 游乐项目档案、容量、项目核销。
- 安卓端登录、设备绑定、扫码核销、离线队列。
- 管理后台基础页面。
- 160 部署和健康检查。

P0 暂缓：

- 复杂营销。
- 完整会员体系。
- 复杂财务结算自动化。
- 机器人智能调度。
- 视频 AI 自动识别。
- 全量数据仓库。
- 多端复杂大屏。
