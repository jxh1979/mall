## 1. 文档定位

经营看板让管理层和运营**看得懂、能追问**。它要能从总览下钻到票务、酒吧、供应链库存、游乐、商户、异常、对账和地产明细。看板不产生业务数据，只汇总展示；数据口径以各业务域与财务对账为准。

## 2. 指标分类（8 类 + 商户汇总，HTML 授权口径）

|---|---|
| 收入 | 售票收入、通票收入（可按票种、经营域、第三方渠道费、域内结算、酒吧相关门票综合服务费、权益成本承担方、未核销归属及实际尾差责任主体下钻）、酒吧收入、第三方回流收入、退款、净收入 |

## 2A. 补齐指标口径（2026-08-04，依据 BSM「欠费」条／「出租」条／「工单时效」条／「月度对比」条／「节假日对比」条／「只读分析视图（含商户健康分）」条）

> 本节按 HTML「经营看板 · 主要指标」逐条核对 §2 八类后补写缺口口径。补的是**口径定义**，不新增指标范围；与 §2 分类并行，落地承接同 §4。

### 2A.1 商户健康分（地产 / 商户类）

- **计算依据**：按**投诉与履约情况**计算。
- **处罚扣分**：商户违反运营规则的，由**城市项目公司的运营人员填写处罚记录**，**处罚即扣减健康分**；**扣分规则由后台配置**（业务参数，**按项目可配**）。
- **用途边界（不得越界）**：健康分**用于给予商户额外优惠，不作为处置依据**。
- **连续违规**：**由运营部门另行决定暂停或列入黑名单**——走运营决定，不由健康分自动触发。
- **待定**：具体计分与优惠规则**待统一的商场运营规则出台后另定**；在此之前不得自造一套分值与优惠映射。

### 2A.2 出租率（地产类）

- **铺位出租率 = 已租铺位面积 ÷ 本项目拥有的铺位总面积**。
- **分母口径**：总面积**包含空置、洽谈中、已租、即将到期、已退租、不可租六种状态**，**不因状态变化而增减**。
- **面积分别展示**：出租率卡片显示已租面积与铺位总面积；可租面积另行保留，用于可招商空置面积和既有单位面积能耗口径。不可租面积计入出租率分母，不计入可招商空置面积，也不改变能耗指标的既有分母。
- **车位出租率单独列**，不并入铺位出租率。
- **已签约还没交付的单独列**，不混在已租里。
- **已租口径（2026-10-17 CG-09 实现现状）**：已租面积＝铺位租赁状态为「已租/即将到期」的铺位面积；退租结算单开立起（不论合同是否仍生效）或租期已结束而未结清的铺位为「已退租」，不计入已租，结算完成即转空置；空置铺位明细（`listVacantSpaces`）按「已退租 > 洽谈中 > 空置」给出推导态，与铺位看板共用同一推导（`SpaceRentalDerivationSql`，PGM「合同运营细则（已确认）」）。

### 2A.3 欠费（地产 / 财务类）

- **欠了多少**（欠费总额）。
- **欠了多久**——**按账龄分档**展示。
- **本月该收多少 / 实际收回多少**，两个数并列。

### 2A.4 工单时效

- **设施工单和商户工单分行对照**：响应快不快、处理拖不拖、超时率、积压多少。
- **商户工单没有「首次响应」环节，就不显示响应指标，不拿别的数字冒充**。

### 2A.5 对比类指标

- **月度对比**：本月对上月、对去年同月；**数据积累不够就标「积累中」，不假造可比数**。
- **节假日对比**：今年春节对去年春节，**总额和日均两列一起看**；**节假日日历可给网址自动抓取，也可手工维护**。

### 2A.6 只读分析视图

- 把**机器人运行、商户健康分、员工服务分、客户意向、指标定义与指标快照**汇总成一个**「只能看、不能操作」的分析屏**。
- **发不出任何控制指令**，适合只读或审计账号安全查看。
- **某一类数据没权限时，只这一类不显示，不影响看其他**（不整屏拒绝）。

## 3A. 异常预警（2026-08-04 UD-08 / DEC-R6-11 新增；2026-08-05 DEC-R7-03 取得看板承接与管理层可见的 HTML 授权）

- **看板承接（已获 HTML 授权，DEC-R7-03）**：照 BSM 经营看板章「异常预警入口」条 现行原文——「异常预警入口：经营看板显示异常预警的入口与未处理条数计数卡片，点击进入异常预警页面；看板上的计数只是入口提示，预警的查看、转办与处置仍在异常预警页面完成。」汇集**反复注销后重新注册、同一手机号短期内注销＋注册超过阈值、高频出入场疑似借票**等账户行为异常。
- **计数口径**：看板卡片只显示**未处理条数**，该计数**仅作入口提示**，不承担统计分析口径，也不作为考核指标。
- **可见范围（已获 HTML 授权，DEC-R7-03 及其 2026-08-05 修订）**：照 BSM 留痕与异常章「异常预警页面」条 现行原文——预警「供**风控岗与管理层查看与处置**」。**风控岗与管理层同权：两者均可查看，也均可转办与处置**，不设「管理层只读」限制（DEC-R7-03 修订取消原只读收敛）。看板入口与计数卡片按同一权限口径：**风控岗与管理层可见**；商户侧不可见——账户行为异常跨商户、且涉及客人身份，不落商户视图。
- **只提示不阻断**：预警只作提示与线索汇集，**不自动阻断业务**；看板侧只做计数与下钻，**不提供任何阻断、冻结或作废的操作入口**；每条预警的查看、转办与处置结论均须留痕，处置一律在异常预警页面完成。

- **落地状态**：口径已写入 HTML 并即刻生效；看板入口、未处理条数计数卡片与下钻链路的**前端改造按排期落地**（排期登记见 `docs/prd-audit-fix-change-log-20260804.md` §7.4）。本条不再属于「无 HTML 承载」或「待批」事项。

## 4. 口径与落地承接

- **下钻**：看板支持从总览下钻到各业务域明细；同一套经营事实、按权限和数据范围展示。
- **通票收入分账下钻**：先区分域内通票和跨域组合通票。域内通票按本域规则展示；跨域组合通票展示整单只扣一次的第三方渠道费、各域份额及各域后续结算。酒吧相关门票综合服务费单列，且只有单一酒吧门票可封顶；权益成本按实际决策域主管公司展示；到期未核销款按票种和经营域展示；尾差按实际结算责任主体展示。所有金额和规则版本可追溯，后台配置不得改变主体责任边界。
- **会员积分时点**：消费积分按 `PENDING`、`AVAILABLE`、`CANCELLED`、`EXPIRED` 分开展示；只有超过退款期并转为 `AVAILABLE` 的积分计入“已确认发放”。兑换按“兑换下单—发券—核销”分别统计；发券只代表扣积分并预占库存或履约能力，核销才代表实际消耗并形成商户补偿。会员与等级口径见 `member-and-tier-product-prd-v1.0.md`，积分与虚拟券口径见 `points-and-voucher-product-prd-v1.0.md`，商户费用与补偿口径见 `merchant-points-settlement-rules-v1.0.md`。
- **数据真实性**：收入/退款/对账类指标必须从业务与财务系统取数，不手填、不伪造；第三方渠道未接入前相关指标置灰或标注未接入，不展示伪造数据。
- **实现现状（2026-10-21 第十三批 ROOT-04）**：
  - **第三方回流收入**（`revenue.thirdparty`）：只计餐饮/零售商户 POS 已入账的回流订单、且已按门店映射认定到商户的金额；映射缺失的回流单挂差异、不计；渠道团购票已在本平台出票并计入售票收入，不再计。按回流落库时间落商户营业日（10:00 起算），按商户与平台写快照并进月累计；单列展示，**不计入净收入**。统一明细为平台口径，项目级不可下钻。真实餐饮/零售回流要等各供应商接入，接入前该项如实为 0、明细为空，不造数据。
  - **采购到货**（`supply.received`）：按商品及单位分列合格接收、实到、拒收数量与到货次数，**不同单位不相加、不出合计数**；只计采购收货登记（调拨、退供、盘点、借调回库不计），按实际到货时间落库存营业日；明细到每一次到货，项目级只见本项目；实时查询，不写快照。
  - **补录数量**（`risk.manual_backfill`）：补录申请**提交即计一笔**，状态（待审、已通过、已驳回）另列；审批通过、驳回与同一提交重放都不重复计，驳回后重新提交另计一笔。当前已接入两类补录申请：锁账后补录、无可信领取时刻补证。按提交时间落治理营业日；总控卡片实时取，快照供月度对比与异常提醒；明细项目级只见本项目，不出补录原因原文。

## 4A. 数据导出授权与留痕（2026-08-04 补，依据 BSM「看板按权限看，但把数据导出带走须单独授权并留痕」条）

- **导出是独立授权点**：能看不等于能导。看板与下钻的查看权限**不自动带出导出权限**，导出须**单独授权**；未单独授权的账号即使能看到数据也不得导出（含另存、批量复制式导出入口）。
- **导出强制留痕（四要素，2026-08-05 R7 对齐 PGM「所有导出的文件一律带密码，密码不可取消、不可由导出人自行设定」条）**：每一次导出**必须留痕**，至少记录 HTML 明列的四要素——**导出人、导出时间、导出所用设备（唯一识别号，如网卡地址、主板序列号等）、导出内容范围与筛选条件（指标类/维度/时间区间/项目或商户范围）**；**导出条数**作为附加字段一并记录，但**不得用来替换上述四要素中的任何一项**。留痕只增不改，走系统统一操作留痕账，不另建一套表。
- **导出记录永久保存**：导出留痕**默认永久保存，不在任何清理范围内**——不随配置数据清理、不随留痕到期策略删除，也不提供按期自动清除的入口（PGM「所有导出的文件一律带密码，密码不可取消、不可由导出人自行设定」条；DIFF-B-026）。
- **与报表中心排期无关**：本条**不依赖 §6 的报表中心 / 自定义报表 / `report_exports` P2+ 排期**。只要看板或下钻实际提供了任何导出动作，本条即刻适用；不得以「报表中心还没做」为由放行无授权、无留痕的导出。
- **敏感范围叠加**：导出内容命中内部结算价、成本价、分账底价、企微会话原文、客人与员工个人信息等敏感数据的，按平台治理地图的高危动作口径另行叠加审批与脱敏要求（PGM「高危授权审批」条），本条不降低该要求。**客人个人信息的脱敏例外（2026-08-05 用户裁决）**：商户查询与导出**属于本商户的客户信息不脱敏**（PGM「导出文件是否脱敏」条）；**跨商户与平台侧批量导出不适用该例外**，仍按 PGM 最高权限口径执行。

## 5. 验收要点

- 8 类指标均可在看板呈现，并能下钻到对应业务明细。
- §2A 补齐口径可验收：健康分只影响优惠、不触发处置动作；铺位出租率分母含六种状态且不随状态变化增减、车位与已签约未交付单独列；欠费同时给出总额、账龄分档、本月应收与实收；商户工单不显示「首次响应」指标；对比类数据不足时显示「积累中」；只读分析视图发不出控制指令且缺权限只隐藏该类。
- 收入/退款/对账指标与财务对账日结口径一致（不另算一套）。
- 导出可验收：无单独导出授权的账号看得到但导不出；每次导出留下**导出人、导出时间、导出所用设备、导出内容范围与筛选条件**四要素（导出条数为附加字段），导出记录永久保存、不在任何清理范围内，且不因报表中心未上线而豁免。
- 不同角色按权限看到不同范围，无越权可见。
- 第三方未接入能力的指标不展示伪造数据。

## 6. 报表中心口径（2026-06-27 审计 P2 澄清）

>
> **本节的 P2+ 排期只约束「独立报表中心与自定义报表配置」，不推迟 §4A 的导出授权与留痕要求**：现阶段看板/下钻若已提供任何导出动作，§4A 立即适用（单独授权 + 导出人/时间/范围/条数留痕）。

## 7. 经营异常处置流转（2026-07-19 现行）

看板自动报出的经营异常（经营指标环比突变等）不止于「报出来」，可走**处置流转**，避免「报完无下文」：

| 处置状态 | 含义 |
|---|---|
| 已报出 | 系统按阈值自动识别并报出，待处理 |
| 已阅 | 负责人已查看、暂不处理 |
| 已处置 | 负责人已处理并给出结论 |
| 误报 | 经确认为误报，关闭且可回流优化灵敏度 |
| 已转风险告警 | 升级到风控/风险告警链继续处理 |

- 每条异常都有处理去向与责任人，全程可追溯。
- 灵敏度可调；节假日自动免报，避免误报刷屏（节假日日历可给网址自动抓取，也可手工维护）。
- 「误报」标注可作为异常检测灵敏度调优的反馈来源。

### 7.1 详细留痕：完整处置历史时间线（只增不改）

处置**不是点一个按钮改状态**：每做一次处置动作，系统就往**处置历史时间线**追加一条记录，内容包括**处置人**、**处置时间**、**从什么状态→什么状态**、**处理说明/理由**、以及「转告警」时**生成的告警单号**。这条历史**只增不改**（沿用系统统一的操作留痕账，不另建一套表），因此一条异常从「已报出→已阅→已转告警」的每一步都留得清清楚楚，而不是只看到最后一次。

处置界面点「误报 / 已处置 / 转风险告警」时会**弹框要求填写说明/理由**（误报填误报理由、已处置填处置措施、转告警填升级说明），弹框内同时**展示这条异常的完整处置历史时间线**，一眼看清它经历了什么。

### 7.2 闭环：转告警双向关联 + 闭环状态可查

- **转风险告警是真闭环，不是改个状态字**：升级会真的生成一条风险告警（落到风险告警工作台，可继续跟进/处置），并与该异常**双向关联**——异常这边记住「升级成了哪条告警」，告警那边也记住「来自哪条异常」。
- **已处置记录处置结果**：处置措施记在说明里，连同时间线构成后续复核的依据。
- **闭环状态一眼可查**：每条异常都能看到当前处置状态、处置人、以及（若已升级）关联的告警单号——去哪了、谁负责、闭没闭，看板与明细里都查得到。

> 落地承接：处置状态机与「转告警」建设 V（V306）已落；本轮补详细留痕与闭环。处置动作与历史时间线走系统统一操作留痕（`audit_events`，只增不改，事件 `analytics.metric_anomaly.disposition_recorded`），处置权限 `analytics.metric_anomaly.manage`（授予与风险告警同一批处置人，日常动作不走审批以免阻断闭环）；「转告警」复用既有风险告警机制（`analytics_risk_alerts` + 统一 `risk_alerts` 汇聚镜像），不新造告警体系、不加迁移。


## 8. KPI 可见性分层与 P0 经营总览（现行）

### 8.1 P0 经营总览卡片可下钻对账（现行）

- 经营总览由若干张汇总卡片（收入、客流、核销、会员、供应链、风险、财务、地产等口径）构成，**每一张卡片都能点开看明细对账**：卡片上的数字就是它下面明细的合计，点进去能核到每一笔，数字对不上一眼看得出（数字＝明细合计）。
- 收入/退款/对账类卡片与财务对账日结口径一致，不另算一套。订单、核销、退款、酒吧账单、库存消耗、存酒、积分、第三方回流进入对账和经营看板。

### 8.2 KPI 可见性分层（现行）

- 经营 KPI 按管理层级分口径与可见范围（BSM「谁会看」、PGM「KPI 可见性分层」）：
  - **平台级管理者**：看跨项目汇总的**平台口径 KPI 聚合**。平台级管理者按是否持有可跨项目角色判定；跨项目汇总的平台口径 KPI 与「集团下钻细则」同按可跨项目角色判定。
  - **项目级操作人员**：只看自己所在项目范围内的 KPI 和明细，**看不到其他项目**（项目作用域收紧）。
  - **全平台合计**只给平台管理员和勾选了「可以查看全部项目」的人看；只逐个勾选了项目的人，只能分别查看被选中项目各自的数据。
- 数据隔离仍是综合体（项目）级；集团高层按职位模板可跨项目查看（见 §3、地产域 PRD 集团下钻口径），集团高层经其职位模板挂可跨项目角色。
