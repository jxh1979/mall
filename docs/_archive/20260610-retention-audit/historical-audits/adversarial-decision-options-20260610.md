## 2. 票务策略最优方案

### 推荐方案

P0 覆盖六类规则，并明确价格优先级：

1. 平日/周末/节假日价是最高优先级基础价格，按日历类型、场次、有效期和票种生效。
> 本段规则已归口至 `docs/scope-wide-coding-rule-canonical-V0.01.md` §A-01，本文不再重复记载。
3. 运营也可以直接输入固定价格覆盖自动计算结果；固定价格必须保存来源、审批人、版本和生效期。
4. 多人票同一订单/同一时段/同一场次统一核销，保留 `num_people`。
5. 新人票以手机号 + 短信验证为唯一防刷主依据，系统自动判定。
6. 学生票 P0 人工审核证件 + 学信网核验留痕，不依赖外部自动接口。
7. 渠道价首批按美团、大众点评、抖音三类渠道价或券价落地。

动态定价放 P2。原因是动态定价需要客流、库存、天气、活动、转化率、竞品价和审批机制，P0 做会拖慢上线并增加财务争议。

### P0 数据口径

- 订单必须保存策略快照：基础日历价、派生价格策略、固定价覆盖标记、规则版本、价格来源、渠道、日历类型、资格判定结果、审核人、审核时间。
- 价格单位统一用“分”。
- 优惠不应覆盖原价字段，应保留原价、优惠金额、实收金额和结算基数。

## 3. MDM/Android Enterprise 方案

### 已拍板路线

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| Android Enterprise / Android Management API + 商业 MDM | 标准能力完整，支持专用设备、Kiosk、策略下发、应用管控、设备注册；后续扩展稳 | 有采购、账号、配置成本 | **已选方案** |
| Headwind MDM 自托管 | 开源/可自托管，适合低成本试点 | 功能深度、合规支持、售后能力弱于商业 MDM | 不作为当前主方案，可保留为调研备选 |
| 自研 DPC + Kiosk | 成本最低，可控性强，能满足部分专用设备锁定 | 研发和维护风险高，Android 版本兼容成本高 | 只作为兜底，不建议长期主方案 |
| 仅 App 内检测上报 | 实施最快 | 不能系统级禁止私装软件和非白名单网站 | 只能试点，不能作为 P0 正式验收 |

### 最低管理成本实施方案

1. 先采购支持 Android Enterprise 设备所有者模式的机型。
2. 选择支持 Android Enterprise / Android Management API 的商业 MDM。
3. 策略只做 P0 必需项：预装 App、禁止私装、网站白名单、Kiosk/专用设备、远程锁定、设备失联告警。
4. 系统侧只做设备档案、策略摘要、合规状态、封禁/解封留痕，不自研完整 MDM。
5. 由平台公司 IT 负责 MDM 选型、采购、配置、证书和运维；业务系统只消费策略状态。

## 4. 企业微信最低管理成本方案

### 推荐方案

企业微信后台只做一次性基础开通：企业 ID、应用 Secret、会话存档能力、可信 IP、公钥/私钥、通讯录/客户联系授权范围。之后尽量由本系统自动完成：

- 员工账号映射：手机号/工号/企业微信 userid 三字段绑定。
- 同步任务：定时拉取组织、成员、客户、会话存档状态。
- 异常告警：授权失效、员工未绑定、会话上传失败、密钥过期、SDK 拉取失败。
- 质检派单：命中规则后进入复核，不直接处罚。
- 留存策略：按会话类型配置保留期限，到期归档、销毁或匿名化。

### 账号绑定优先级

| 方式 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 手机号匹配员工 | 管理成本最低 | 手机号变更需处理 | P0 首选 |
| 工号/账号导入映射 | 稳定、可审计 | 初始整理成本稍高 | P0 同步支持 |
| 员工扫码自绑定 | 准确性高 | 员工操作成本高 | 作为异常补救 |

## 5. AI 质检边界

### P0 最细颗粒度规则质检

P0 不做“深度语义模型”，但规则颗粒度要细：

- 禁用词/敏感词：辱骂、诱导私下交易、收款绕单、承诺违规优惠。
- 金钱风险：出现个人收款码、私账、红包、转账、现金绕单。
- 服务流程：未问候、未确认需求、未告知退款/有效期/限制条件。
- 投诉倾向：退款、欺骗、投诉、报警、差评、维权等关键词。
- 高风险对象：未成年人、酒精、醉酒、受伤、设备故障、消防。
- 处理闭环：命中后生成复核任务，记录命中规则、会话片段哈希、复核人、结论和处理动作。

### P2 深度 AI

客户意图识别、服务评分、情绪分析、工单自动摘要、经营建议、异常解释建议进入 P2。是否引入独立 Python AI 服务见第 9 节。

## 6. 第三方 SDK/API、Webhook、轮询、对账和补偿

### 已拍板策略

| 能力 | P0 做法 | P1/P2 做法 |
|---|---|---|
| 字段映射 | 先建平台标准字段和供应商映射表 | 拿到 SDK/API 后补供应商字段 |
| Webhook | 先提供平台 Webhook 接收、签名、幂等、重试日志 | 按供应商事件接真实回调 |
| 轮询 | 定时轮询校验作为 Webhook 兜底和对账补漏 | 对不支持 Webhook 的供应商作为主策略 |
| 对账 | 先按订单、券码、核销、金额、时间、商户维度做基础差异 | 供应商字段齐全后做自动平账 |
| 异常补偿 | 先做人工补偿单、重试、冲正、关闭原因 | 后续自动补偿、批量重放 |

第三方采用“双向开放”方案：平台既接入机器人、视频、设备、餐饮/零售等外部供应商能力，也向授权第三方开放平台数据、事件订阅、Webhook 回调和结果回写接口。所有双向调用必须经过开放平台鉴权、签名、防重放、幂等、审计和授权范围校验。

### Webhook 与轮询对比

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| Webhook 主导 | 实时、成本低 | 依赖供应商回调稳定性 | 供应商支持签名/重试时首选 |
| 轮询主导 | 可控、容易补漏 | 延迟高、接口成本高 | 供应商不支持 Webhook 时使用 |
| Webhook + 定时轮询校验 | 可靠性最好 | 实施稍复杂 | **已选方案** |

## 7. 机器人、视频平台、设备厂商统一 API 能力

| 厂商类型 | 最优接入判断 | 建议 |
|---|---|---|
| 机器人平台 | 若提供任务 API、状态回调、签名、幂等任务号，可做 P2 真实调度；同时平台开放订单/取货/交接事件给机器人侧 | P0 只记录交接事件 |
| 视频平台 | 若提供摄像头点位、时间片段检索、截图/回放 URL、访问审计，可做 P1 调阅；同时平台开放事件时间点/点位给视频侧做检索 | P0 只记录点位/时间/设备 |
| NFC/闸机/扫码设备 | 若提供 SDK、加密卡协议、回调和离线白名单，可做 P1/P2；同时平台开放权益校验和核销回写接口 | P0 摄像头/扫码模块优先 |

判断标准：统一 API、签名、防重放、回调、重试、设备状态、审计日志、沙箱环境、接口 SLA。缺其中三项以上，不建议进 P1 主链路。

## 8. 账号、密钥、数据库和对象存储密码轮换

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| 人工台账 + 到期提醒 + Runbook | 成本最低，适合 P0 | 依赖执行纪律 | P0 必做 |
| Vault / Infisical / 1Password Secrets Automation | 自动化和审计更好 | 需要部署和运维 | P1 推荐 |
| 云厂商 KMS/Secrets Manager | 安全成熟 | 绑定云厂商、成本增加 | 上云后推荐 |

P0 至少覆盖：生产账号清单、密钥负责人、创建时间、到期时间、轮换步骤、回滚步骤、验证步骤、轮换记录。数据库、对象存储、企业微信、开放平台、支付通道、第三方渠道必须入台账。

## 9. 是否引入独立 Python AI 服务

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| Java 内置规则处理器 | 简单、部署少、P0 成本低 | AI 能力有限 | P0 采用 |
| 独立 Python AI 服务 | 模型、向量、NLP、批处理生态更好 | 多服务运维、监控、鉴权成本增加 | P2 引入 |
| 外部 AI API | 启动快，能力强 | 成本、数据出境/隐私、稳定性需评估 | 只处理脱敏摘要或内测 |

已拍板：P0 使用 Java 内置规则处理器；后续 P2 再引入独立 Python AI 服务。拆分前先定义输入脱敏、输出可解释、人工复核、审计追踪。

## 10. 备份方案

| 方案 | 成本 | 恢复能力 | 建议 |
|---|---|---|---|
| 第二台机器 | 中 | 快速恢复服务和数据库 | 后续可叠加 |
| NAS | 中低 | 适合本地大容量附件备份 | **已选 P0 方案** |
| 云存储 | 按量 | 异地容灾最好 | 预算允许时叠加 |

已拍板 P0：备份同步到 NAS。数据库每日全量备份 + 增量 WAL/日志归档，附件对象存储每日同步到 NAS，每周做一次恢复演练。正式经营后可叠加第二台机器或云存储异地副本。

## 11. 商户服务与商户账单子域

### 推荐拆分

- P1 建“商户服务子域”：维修、投诉、整改、保洁、安保、设施报修、服务评价。
> 本段规则已归口至 `docs/scope-wide-coding-rule-canonical-V0.01.md` §A-01，本文不再重复记载。
- P1 再建“商户账单子域/门户”：催缴、费用异议、复杂费用规则、商户确认和账单展示。
- 财务/对账子域负责收款、对账、差异、报表和 P0 台账；P1 商户账单子域负责商户侧服务体验和复杂费用运营。

这样拆的好处是商户门户体验清楚，账单可独立演进，财务侧只消费标准应收/实收/差异数据。

## 14. 建议总控选择

1. 票务 P0 以平日/周末/节假日基础价为最高优先级，多人票/新人票/学生票/渠道价基于基础价派生或固定价覆盖，动态定价 P2。

3. 股东比例只进利润报表，不进 P0 打款。
4. 平面图 P1 图片 + 多边形坐标，CAD/SVG P2。
5. 合同审批 P1 审批流 + 附件归档。
6. Android P1 只允许策略摘要和低风险摘要离线，高价值酒水保持在线。
7. MDM 由平台 IT 选型，采用 Android Enterprise / Android Management API + 商业 MDM。
8. 企业微信配置一次性人工开通，后续绑定、同步、告警、质检最大化自动化。
9. P0 Java 内置规则质检，P2 再拆 Python AI 服务。
10. 备份采用 NAS，后续预算允许再叠加第二台机器或云存储异地副本。
11. 160 P0 先不绑定域名和 HTTPS。
12. 合同日期颗粒度采用方案 B，并允许本地 AI 大模型做辅助分析，人工确认后落台账。
> 本段规则已归口至 `docs/scope-wide-coding-rule-canonical-V0.01.md` §A-01，本文不再重复记载。
14. P0 库存扣减强制但限定范围，复杂 BOM、批次成本精算和自动补货后置。
