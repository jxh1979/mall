# 全量文档对抗式审计与待决策清单 V0.1

生成日期：2026-06-10  
审计方式：全库关键词扫描、跨文档口径比对、产品流程反推、市场成熟系统基准对照。  
审计范围：`docs` 下 100 个 Markdown、2 个 HTML、4 个 TXT；历史原始记录和历史审计报告仅作追溯，不作为当前口径来源。

## 1. 总结论

当前文档经过本轮修正后，P0 主闭环已基本一致：票务、酒吧、游乐、平台治理、开放平台、终端、企业微信、数据风控、160 运维的关键边界已经能支撑继续拆实施任务。

本轮对抗式审计发现的主要风险不是“缺一份大文档”，而是部分旧待决策散落在不同文档里，容易让实施方误以为仍未拍板。本轮已把已确认事项从待决项中移出或改成已拍板表述。

仍需你判断的内容主要集中在：支付通道、经营/财务口径、平台治理对象边界、第三方供应商真实接口、部分 P1/P2 排期、以及少量生产运维执行授权。

## 3. 市场基准反推

| 领域 | 市场/官方基准 | 对本文档的审计结论 |
|---|---|---|
| Android 受管设备 | Android Enterprise 支持专用设备/员工设备/客户面对设备场景；Android Management API 支持策略化管理设备和应用 | 工作手机、平板、一体机必须走 MDM/Android Enterprise，不应依赖普通 App 自律 |
| 餐饮/酒吧 POS | Toast 等成熟 POS 普遍支持拆单、按座位拆分、服务费、账单管理等能力 | 酒吧拆单、合单、转台、挂账、服务费、低消差额补齐、员工提成放 P1 是合理的；P0 只要保证点单、支付留痕、库存扣减、日结闭环 |
| 库存和修饰项 | Square/餐饮 POS 常见做法是商品、规格、修饰项和库存有不同粒度，复杂配方扣减容易带来实施成本 | P0 不做复杂 BOM/配方成本，但必须扣明确数量库存，是成本和准确性的平衡点 |
| 第三方平台接入 | 成熟平台通常保留 API、Webhook、轮询补偿和对账机制 | 双向开放 + Webhook + 定时轮询校验是正确方案；真实供应商字段映射必须等 SDK/API 到位后再落 |

## 4. 仍需你判断的内容

以下不是所有都必须现在拍板；我按“会不会阻塞 P0”标出优先级。

### A. P0 前必须确认

| 决策项 | 推荐方案 | 原因 |
|---|---|---|
| 支付通道选型：聚合支付还是微信/支付宝/银行卡直连 | **已确认**：P0 选聚合支付，保留直连接口抽象 | 管理成本最低，退款/对账/扫码支付能力一次接入；直连可后续为成本或议价优化 |
| 160 运维脚本是否允许实际写入服务器 | **已确认**：允许，但必须先 dry-run、备份、Runbook、可回滚 | 文档已完备，执行授权会影响真实备份、发布、回滚能力 |
| 告警渠道 | **已确认**：企业微信机器人 + 邮件兜底 | 成本低、配置简单，适合 P0；短信/电话告警后置 |
| 财务结算主口径 | **已确认**：多口径并存，订单、核销、合同固定规则分别形成结算依据 | 综合体同时有票务、商户、租赁/联营、自营，单一口径会很快失真 |
| P0 是否必须支持应收应付 | **已确认**：P0 做完整应收应付台账，至少覆盖应收、应付、账龄、到期日、责任主体、合同/订单/核销来源、收付款状态、差异和留痕 | 财务能直接看到该收、该付、已收、已付、逾期和差异 |
| 平台治理主体边界 | **已确认**：经营对象、运营主体、合同主体、结算主体可以是不同名称/不同公司，但必须在同一经营对象下唯一绑定、统一留痕 | 覆盖现实经营/签约/开票/结算不一致，同时避免主体关系混乱 |

### B. 已确认按默认值执行

| 决策项 | 已确认执行口径 | 影响 |
|---|---|---|
| 平台自营酒吧/游乐是否建成特殊商户主体 | 已确认建成平台自营商户主体 | 页面、结算、权限、看板统一，后续多项目复制成本低 |
| 商户端是否允许自行编辑商品、桌台、场次 | P0 允许提交变更申请，平台审核后生效 | 降低误配置风险；商户完全自编辑放 P1 |
| 事件导出、视频调阅、企微原文查看审批强度 | 敏感原文/视频必须审批；普通导出二次确认 + 审计 | 平衡取证效率和合规风险 |
| 移动管理端 P0 范围 | 只处理高风险待办和主管复核，不做全后台 | 移动端适合短流程，不适合复杂配置 |
| 管理层首屏三类指标 | 收入/客流/核销为第一屏，商户表现/异常风险/结算差异为第二屏 | 先满足日常经营，再下钻风险和财务差异 |
| 日报导出 | 已确认 P0 支持 CSV/Excel 导出，复杂报表排版 P1 | 管理成本低，满足早期经营复盘 |
| 游客/会员分析 | P0 先打通游客识别和票务权益；会员分层分析 P1 | 避免会员体系过早复杂化 |
| 风险事件关闭后是否允许重开 | 允许重开，但必须记录重开原因、责任人和关联新证据 | 真实运营会出现补证据、复议、追加责任 |

### C. 已确认按建议进入 P1/P2 排期池

| 决策项 | 推荐优先级 | 理由 |
|---|---|---|
| 商户服务/维修/投诉/整改工单 | P1 独立子域 | 商业地产服务能力重要，但不应压 P0 |
| 租金、物业费、能源费、公摊/CAM、应收账龄 | **P0 进入完整应收应付台账；P1 再建商户账单门户、催缴、复杂费用规则和商户异议流程** | P0 先保证财务可管账；P1 再提升商户服务和费用运营深度 |
| 酒吧拆单、合单、转台、挂账、服务费、低消差额补齐、配方成本、员工提成 | P1 酒吧 SaaS 增强 | 成熟 POS 标配，但 P0 点酒闭环不依赖 |
| 游乐安全告知/电子免责、事故工单 | P1 | 安全和责任闭环重要，应尽快补强 |
| 游乐预约排队、团体/包场、集团视图 | P2 | 价值明确，但复杂度和运营策略依赖更强 |
| 真实闸机/NFC 硬件接入 | P1/P2，看现场采购节奏 | P0 保留标准接口即可 |
| 独立 Python AI 服务 | P2 | P0 用 Java 内置规则处理器；后续再引入深度 AI |

## 5. 已不需要再问你的事项

- 票务策略：平日/周末/节假日价为最高优先级，多人票、新人票、学生票、渠道价基于基础日期价生成或录入固定价格；动态定价 P2。
- MDM：Android Enterprise / Android Management API + 商业 MDM，由平台公司 IT 部门选型、采购、配置和运维。
- 企业微信：管理员一次性授权和密钥配置，系统自动账号映射、同步、失败告警、基础规则质检和留存。
- AI 质检：P0 规则/关键字/结构化指标，P2 独立 Python AI 服务。
- Webhook/轮询：P0 Webhook + 定时轮询校验。
- 密钥轮换：人工台账 + 到期提醒 + Runbook。
- 备份：NAS。
- 160：P0 不绑定域名和 HTTPS。
- 合同日期颗粒度：方案 B 标准通用事项台账 + 本地 AI 辅助判断。
- 低消：票务、通票和卡座入场名额不抵扣低消。
- 卡座入场：按卡座配置名额免通票进入预定卡座所在酒吧，不进入其他酒吧。
- P0 库存扣减：明确数量场景强制扣减或状态转移。
- 商场平面图：P1 先图片 + 多边形坐标，CAD/SVG 标准化导入可后置增强。
- 合同审批：P0/P1 先审批流和附件归档，电子签章/OCR/复杂合同智能化后置。
