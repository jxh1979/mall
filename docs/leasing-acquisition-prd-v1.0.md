## 0. 定位与边界
- 招商 = 地产履约链最前端：线索 → 意向 → 签约 → 自动转正式商户档案 → 喂入合同环。
- 数据隔离 = 综合体（项目）级；所有招商对象带 `project_id`。
- 不做：第三方招商代理对接（来源不含代理）；线索自动分配（本期主管手动派）。

## 2. 线索管理
- **来源（4 类，录入即打来源标签）**：主动拓展（招商员外出）/ 官网·小程序在线留资 / 老商户·合作方转介绍 / 展会·行业活动。
- **分配**：招商主管手动指派给招商员（不自动分、不抢单、不共享池）。线索带 `owner_user_id`（负责人）。
- **状态流转**：待跟进→跟进中→已转意向→洽谈中→已签约；旁支 已流失 / 已搁置（可从多数态进入，留原因）。招商线索在已签约前，可从待跟进、跟进中、已转意向或洽谈中转为已流失或已搁置；转换时必须填写原因，已签约后不得回退至未签约状态。
- **已签约守卫**：人工状态接口不得写入 `signed`，仅合同审批生效回调可置已签约；已签线索不得回退或再次创建意向。状态修改、负责人指派、转意向及跟进回写均校验该动作权限与线索真实项目范围的交集，在事务中锁定并重读原线索，避免跨项目写入及旧状态覆盖并发生效结果。前端按当前已签状态禁用回退及转意向，正常跟进和负责人维护保留；其他来源态白名单仍按独立缺口跟进。
- 「已转意向」时生成 `leasing_intent`（进入 §3）。品牌已拉黑的，既有线索也不得新建意向；确需继续的，须由具备单独授予的黑名单例外放行权限人员操作，按层级对应主管审批，申请人不得审批自己提交的申请，并记录操作人、审批人、理由、时间和关联线索或意向。**当前 `LeasingService.createIntent` 未执行该黑名单守卫或例外放行流程，属待实现；M08 不改代码。**

## 3. 意向管理（5 阶段独立流转 + 关键阶段卡控）
- 5 阶段顺序推进：初步接触 → 需求确认 → 方案报价 → 商务谈判 → 待签约；这是业务约束。**当前 `advanceIntent` 仅校验目标阶段是否在枚举中，未校验相邻顺序，属待实现；M08 不改代码。**
- **关键阶段卡控**：进入「方案报价」「商务谈判」需**主管确认**才可推进；其余阶段招商员自由推进。卡控走现有主管复核机制（留审批人+时间+原因）。
- 「待签约」→ 签约：触发 §6 转商户。
- 意向记录意向业态、意向铺位/空间、意向面积、报价租金条款（喂入转商户与合同）。
- **意向业态词表（V348 + V384）**：与商户业态同一套六值——酒吧 bar / 餐饮 catering / 零售 retail / 游乐 amusement / 演出传媒 media / 其他 other（`leasing_leads.intended_business_type` 加 CHECK `chk_leasing_leads_business_format`，线索阶段可留空）。签约转商户时该值直接落成 `merchants.merchant_type`；自动落 `other` 时必须同时指定主管公司并说明理由，未指定不得开通结算与分账。**当前签约自动建档在业态留空时会落 `other`，但未同时校验主管公司与理由，属待实现；M08 不改代码。**

## 4. 品牌/客户库（4 类 + 去重 + 黑名单拦截）
- 4 类：意向品牌 / 储备品牌 / 合作品牌 / 黑名单品牌。
- **用途**：仅作意向、储备、合作、黑名单的基础资料库；品牌名用于线索去重（建线索时按品牌查重、提示已有）。
- **黑名单**：主管可拉黑品牌；拉黑后，同品牌新建线索，以及由拉黑前既有线索新建意向均被拦截。确需继续的，须由具备单独授予的黑名单例外放行权限人员操作，按层级对应主管审批，申请人不得审批自己提交的申请，并记录操作人、审批人、理由、时间和关联线索或意向。上述既有线索转意向守卫与例外放行流程当前均属待实现。

## 5. 跟进
- 跟进记录：每次跟进记 时间 / 方式（电话/到访/微信…）/ 内容 / 下次跟进计划时间。
- **提醒**：线索 **超过约定天数未跟进**（按项目可配，出厂默认三天，后台「提醒与留存天数配置」ADM-ANA-011 可改，键 `leasing.lead_follow_up`，V219），系统提醒负责人；配置必须同时设置强制下限与上限，超出边界的值必须拒绝保存。
  - **落点（2026-07-28 用户拍板"接进工作台"）**：招商人员一进「招商工作台」ADM-LEASE-001 就先看见页首提醒条「有 N 条线索超过约定天数没跟进」，
    并有「该跟进」KPI 卡；点任一处直接聚焦到那几条线索（`?kpi=leads&subset=due`）。到期判定在后端 `GET /api/v1/leasing/leads/follow-up-due`，
    前端不复刻天数口径——后台改天数，这张单子立刻跟着变。
  - **意向侧未跟进提醒（2026-08-04 口径更正·实现待对齐，登记缺口）**：后端 `GET /api/v1/leasing/leads/follow-up-due` **只判线索**，意向侧无到期判定、工作台也无意向提醒。原「暂未接、需要时再单开」的口径**作废**——**意向与线索同属获客链、同受「超过约定天数未跟进」约束，属必须补齐的缺口**：`follow-up-due` 须补 **intent 分支**（按 `leasing_follow_ups.ref_type='intent'` 的最近跟进时间与同一套后台可配天数判定，天数口径与线索共用、前端不复刻），并在工作台提醒条与「该跟进」KPI 卡中与线索**分列可辨**。**本轮只登记口径与缺口，不改代码、不改 OpenAPI。**

## 6. 线索→正式商户档案（签约转换）
- 触发：意向「待签约」→ 签约成功。
- **自动带入字段（全部）**：联系人 + 联系方式；意向业态 + 面积 + 位置；报价租金条款；跟进历史记录。
- **四类主体（当前实现模型见 `merchant-space-contract-model-v0.1.md`）**：四类=经营对象（商户自身）/ 运营主体 / 合同主体 / 结算主体；三个主体统一落在 `business_entities`（`entity_role` 区分，无独立「项目公司/SPV」表）。
  - **当前绑定载体 = `business_entity_bindings`（`binding_type=four_party`）**，每商户至多一条 `active` 绑定（`uq_business_entity_bindings_active_merchant`；重复激活报 `409 ACTIVE_BINDING_EXISTS`）。转商户初期三主体可都指向同一 `business_entity`。
  - **可拆边界**：「后续可拆」= 新建一条 active 绑定替换旧绑定，指向不同 运营/合同/结算 主体；**不是**在 `merchants` 的 `*_entity_id` 快照列上改写。`merchants.business_entity_id/contract_entity_id/settlement_entity_id` 仅为档案快照。
  - 合同签署时另在 `contracts.contract_subject_id/operation_subject_id/settlement_subject_id` 固化该合同主体快照，与商户当前 active 绑定**可不一致**（无外键强绑），勿假定二者恒等。
- 转换时生成正式 merchant 档案，喂入合同环（合同 draft 引用该商户 + 报价条款），并把合同绑到来源意向（`leasing_intents.contract_id`，V442）；**线索不在签约时置已签约——合同审批全部通过、生效后（`ContractService.activate` 经 `ContractEffectiveLeadPort` 回调 `LeasingService.markSourceLeadSigned`）才转为已签约并留痕 `leasing.lead.signed`**（PGM「招商运营细则」，2026-10-17 CG-01 对齐）。审批驳回退回起草的，线索保持原状态。
- **实现保证（AUD-002/003 修复，2026-07-21）**：签约转换 = 一次原子业务事务——`signIntent` 公有入口 `@Transactional`，自动建商户 → 即建 `business_entity_bindings`（`binding_type` 四主体、`active`，稳定幂等键按意向派生）→ 合同 draft → 合同绑到来源意向 → 审计留痕（`leasing.intent.signed`，语义=合同草稿已起草，不表示线索已签约）；**任一步失败整体回滚，无孤儿商户/绑定/合同**。幂等重签命中同一商户与同一 active 绑定、不重复建。绑定创建仅在「无既有 `merchant_id`、签约自动建档」路径触发（带既有商户签约，其主体绑定由治理域主体绑定页管理，不在此重建）。
- **合同起草原子性（AUD-002）**：`ContractService.createDraft` 亦已 `@Transactional`——字段/空间校验前置于落库（校验失败零脏写）、空间存在性+租期重叠早检在保存前完成、幂等命中(重放)也必过业务校验后才返回既有草稿；失败草稿整体回滚，重试走完整校验、无半成品可复用。


## 6A. 签约后到期 / 变更 / 退出衔接（P2，2026-07-28）

> 闭合 BSM-0267 `expiry_exit`。招商 PRD 负责「收到签约」；租约履约/退租细节以 real-estate / 合同履约 PRD 为准，本节定义**必须闭环的交接**。

1. **意向/线索不会自动变成无限期占位**：合同生效后，关联线索状态为「已签约」（签约起草时不置，PGM「合同审批全部通过、生效后转为已签约」）；意向仍保持既有五阶段，不新增「已签约」意向终态，签约结果由关联线索与合同记录表达。
2. **合同到期前**：系统须能按可配提前期产生跟进/预警任务（到期提醒），避免静默过期。  
3. **到期路径（三选一，须留痕）**：  
   - **续约/变更**：走合同变更或新签流程，保留原合同与商户档案关联；  
   - **退租结算**：触发/转交退租与费用结清流程（租金、物业、能源、押金等以合同履约域为准）。**押金治理与退租结算细则见 `real-estate-full-chain-domain-prd-v0.1.md` §2「退租结算与押金退还」「押金治理」**（多级多部门审批全过后系统按结算清单自动落账、押金退还以算账完成为准且不早于等待期届满、押金不得日常抵扣欠费等；**2026-08-06 新口径：押金金额 ＝ 收取月数 × 签约时月租金（只乘月租）、收取月数下限三个月、清退硬线按「押金减当期欠费不足以覆盖 30 天当前月均应缴全费用」判、欠缴月数按「欠费总额 ÷ 当前月均应缴费用」折算**——H-23／矛盾7／矛盾9；**2026-08-07 新口径：上述两条清退触发条件一律以存在到期未缴款项为前提、前提与触发条件并发才启动清退测算——零欠费或尚未出账的不启动，仅有罚款欠缴的不启动（罚款仍计入欠费总额，待周期性费用逾期后一并判定）**——DEC-R8-75），本 PRD 不重复正文，避免两处口径漂移；  
   - **到期未续未退**：合同状态仍为「已到期」，不新增「待处置」状态；以任务或提醒推动续约、退租或其他已授权流程的处置。
4. **退出完成**：退租结算完成后，招商侧商户合作状态更新为「终止」。终止后进入按项目可配、上下限出厂为三十至六十天、出厂默认三十天的退出缓冲期；缓冲期内须向该商户的客人说明情况并给出处理方式：转到其他酒吧、由客人自行取走、或者退款；黑名单规则仍可拦截再入。
5. **权限/证据**：到期处置、续约、退租发起均需授权角色；关键节点写审计事件与关联合同 ID。

- 建线索同品牌已黑名单 → 拦截提示。
- 意向推进到「方案报价」无主管确认 → 阻断。
- 线索**超过后台配置的未跟进天数**无跟进 → 负责人收到提醒（业务参数，**按项目可配**，**出厂默认三天**，键 `leasing.lead_follow_up`／ADM-ANA-011；验收须同时覆盖「改配置后判定随之改变」，不得把三天写死进用例）。
- 意向签约 → 自动生成商户档案带全字段 + 四类主体指向同一主体。
- 跨综合体：A 项目招商员看不到 B 项目线索。
