# 综合体管理系统原始需求口径汇总 V0.1

## 1. 文档定位

本文用于给后续机器智能体、产品设计人员、架构人员和开发人员快速理解用户最初及持续补充的真实业务意图。

本文不是逐字聊天记录，而是把用户在沟通过程中明确表达、拍板或修正过的原始需求口径集中保存，避免只看后续开发文档时丢失业务背景。

## 2. 总体目标

用户要建设的是一个“综合体管理系统”，不是单一票务系统、酒吧 POS 系统、乐园系统或商户系统。

系统管理目标包括：

- 综合体内所有业务。
- 综合体内所有商户。
- 综合体内所有相关工作人员。
- 综合体内所有经营空间、设备、合同、权限和责任关系。
- 后续可支持多个综合体和集团视图。

当前优先围绕单个综合体做 P0 闭环，但所有核心对象都要预留综合体项目归属。

## 3. 总控和编码分工要求

- 本地会话主要负责产品设计、文档、任务拆解、进度跟踪和状态汇总。
- 所有编码工作原则上由 160 服务器上的 Codex 完成。
- 本地非编码需求、PRD、拓扑图、业务人员 HTML、文档检查可以继续完成。
- 第三方接口资料当前未确定，P0 先做好自有系统和开放接口。

## 4. 门票与购票

- 员工不能通过平板帮客人购买门票。
- 所有门票必须由客人自己购买。
- 官方购票入口 App 和小程序同步建设。
- 第三方购票首批只考虑美团、大众点评、抖音等团购购买和回流。
- 门票可以配置不同策略，包括平日、周末、节假日、多人票、学生票、新人优惠、不同平台来源优惠等。
- 新人优惠、学生票、多人票由后台设置规则，符合规则自动判断，不符合不能使用。
- 门票二维码必须具备防伪、防篡改和事后核对能力。
- 二维码按票种有效期生效，例如日票、周票、月票、年票。
- 二维码 30 秒或 60 秒刷新，截图无效。
- 门票二维码必须在线核验，P0 不做离线核验。

> 补记（2026-06-10 总控收口，覆盖 2026-06-07 C7）：实名能力作为 P0 可配置能力保留，但默认不强制实名；仅国家法令强制要求的票种/场次/场所启用"是否强制实名 + 实名核验方式 + 失败处理"。除此之外，普通门票、酒吧入场、游乐项目、团体/包场和活动票均不强制实名，也不得为运营便利扩大采集证件或人脸等敏感信息。原实名旧待决口径关闭，执行口径见票务 PRD、票务开发设计和合规要求文档。

## 5. 通票、权益和会员积分

- 通票包括酒吧通票、游乐通票、酒吧 + 游乐通票。
- 可以有酒吧、游乐、餐饮、零售的组合优惠通票。
- 餐饮和零售为第三方，因此通票中餐饮/零售部分主要是优惠或折扣。
- 官方 App 和小程序需要会员积分系统。
- 积分规则由后台定义。
- 积分可与消费、会员等级、兑换礼物相关。
- 积分兑换礼物需要扣减库存。

## 6. 酒吧经营

- 酒吧系统应能独立成为一个酒吧 SaaS 系统。
- 酒吧管理包含合同和合作形式，例如租赁、联营、自营、合作等。
- 不同合作形式有不同收益模式，例如只收租金、按比例分成、抽成等；合同摘要和准入由平台治理管理。
- 酒吧系统需要管理桌台、卡座、吧台位、最低消费、点酒、支付、赠饮核销、账单、异常和存酒。
- 酒吧最低消费按时间、卡座、位置配置，支持周末、节假日、自定义时段，原则上不按人数。
- 工作人员平板 App 只做一件事：帮助客人点酒下单。
- 平板必须定位到具体酒吧和具体卡座/桌台/吧台位。
- 如果最低消费未满足，不能提交订单。
- 下单后可以生成二维码让客人手机扫码支付，也可以平板扫描客人手机付款码支付。
- 吧台买酒支持线上支付，同时按中国法律必须支持现场现金和 POS 机。
- 吧台酒水可按杯、按瓶、按套餐或其他形式购买。
- 按杯销售按标准出酒量/容量扣减，超过标准容量部分记损耗，损耗严重进入核查。
- 门票赠送的酒水、权益领取和酒吧系统库存消耗需要打通。

## 7. 订台

- 订台入口包括官方 App、小程序、一体机和销售人员工作台。
- 订台需要支付定金。
- 订台订单需要记录来源、销售人员或设备来源、定金、到店、取消、退款等结果。

## 8. 供应链、库房和存酒

- 供应链管理必须包含供应商管理、合同管理、供应合同管理、采购周期管理和库房管理。
- 供应合同分平台自用、商户自采、平台统一采购分销给商户等模式。
- P0 供应链从酒类、吧台消耗、客人存酒、常用消耗品开始。
- 常用消耗品包括纸巾、色盅、色子、杯子等。
- 库房管理包括平台自采、酒类、消耗品、其他物品和客人存酒。
- 客人存酒使用标签，优先从瓶底贴标签；按标签显示数值、拍照、人工备注记录。
- 存酒需留客人手机号和姓名/昵称。
- 高价值酒水报损、盘点差异、存酒作废必须拍照和视频留证，并主管复核。
- 人工放行、免单、退款、调账等按可配置层级主管复核。

## 9. 全业务过程留痕

用户明确修正：留痕不只是物品交接全链路留痕。

最终口径：

- 凡是有过程的业务动作都必须留痕。
- 订单获取要留痕，例如销售是谁、谁给客人下了单。
- 卡座服务要留痕，例如谁给这个客人提供服务。
- 异常处理要留痕，例如发生异常事件时谁是第一个处理人。
- 转派、升级、复核、关闭、退款、免单、调账、人工补录都要留痕。
- 酒从库房取出、订单核验、机器人配送、后厨接收、服务员送达客人都要留痕。
- 酒在入库时贴唯一二维码，或出库时打印唯一二维码；通过二维码串起责任链。
- 留痕有主动也有被动，但要尽量避免人工额外填写。
- 优先通过业务过程自动留痕：登录账号、设备绑定、班次、点位、扫码、支付回调、机器人状态、企业微信同步、第三方回流。
- 人工主要补原因、照片、视频、签名和复核意见。
- 后续希望留痕能和监控视频一一对应；P0 不强依赖真实视频接入，但事件必须预留时间、点位、设备和摄像头候选条件。

## 10. 机器人和配送

- 酒从库房取出一般倾向用机器人配送。
- 机器人真实调度和厂家联动可以后置。
- P0 必须记录机器人或人工配送交接留痕。
- 订单核验人需要扫码留痕。
- 机器人到达酒吧后厨后，后厨接收人需要扫码留痕。
- 后厨拿给客人的服务员也需要扫码或订单确认留痕。

## 11. 游乐系统

- 游乐系统应能独立成为一个乐园/游乐 SaaS 系统。
- 游乐设施分布在综合体不同位置。
- 游乐容量 P0 按具体项目、具体场次/时段、点位/设备控制。
- 一体机可查看游乐设施开放状态、容量、异常和检查状态。
- 游乐设施需要定期检修。
- 检修单位作为供应商记录。
- 工程师在一体机填写检修记录，主管确认后才能恢复营业。

## 12. 一体机

- 一体机是触摸屏。
- 除查看状态外，还能下单。
- 一体机支持订台下单、吧台买酒下单、权益展示/领取、游乐设施状态查看、授权状态检查和定期检修记录。
- 一体机订台也需要定金。
- 一体机动作需要记录设备、点位、时间和结果。

## 13. 工作手机、员工私人手机和企业微信

- 工作手机发给员工使用。
- 工作手机可核销门票，即扫客人 App 上的二维码。
- 门票附赠酒水或权益领取时需要扫二维码，并在一体机上展示可领取权益或酒水。
- 工作手机上的微信是企业微信。
- 企业微信每天自动上传所有员工聊天内容。
- 后台对聊天内容做服务优化分析和违规内容检查。
- 企业微信工作会话永久保存（原始口述需求留痕；现行设计已裁决为可配置留存期限，非永久）。　**【已作废（2026-08-03 L-19 裁决 `DEC-CFG-2026-08-03-10`）】企微会话原文永久保存、不自动到期删除；本处销毁／留存期／到期处置规格不得实施；确需清理仅限最高权限本人插授权 U 盘密钥手动执行（逐条填写理由、先试运行预览、清理动作本身另行留痕）。原文保留仅作历史留痕。**
- 会话原文按权限查看，不脱敏（原始口述需求留痕；现行设计已裁决为最小授权 + 审批取证/质检场景可看原文，普通展示按权限脱敏）。
- 查看会话原文必须写访问审计。

- 工作手机不允许安装除预装软件之外的软件。
- 工作手机仅允许访问白名单网站。
- 白名单和预装软件清单由后台维护。
- 违规访问应通过 MDM 或等效策略直接阻止或封禁权限，并留痕。
- 员工私人手机 App 用于注册、通知、状态查看、NFC 绑定、Root/异常检测，不做现场业务。
- 员工私人手机 App 安装时申请 NFC 权限并读取手机 NFC 唯一标识。
> 2026-06-10 复核注：以上两条为原始口述需求留痕。现行设计已按统一口径 D8/A6 裁决为“私人手机 App 安装期生成 Keystore 设备公钥/不可逆设备指纹并绑定设备凭证”，不读取手机本机 NFC 唯一标识；工作手机通过摄像头/扫码模块读取外部客人二维码，NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。
- 换手机需要先解绑旧手机再绑定新手机。
- Root、调试或异常环境判为不可信并失效复核。
- 员工进入办公区时，私人手机需要寄存。
- 寄存柜不固定，流动使用，先到先选，离开拿走。

## 14. 员工、权限、职级和薪资

- 员工通过私人手机 App 注册并提交信息。
- 后台审核通过后，员工在系统中生成角色和相关信息。
- 用户权限需要按单一功能最小颗粒度配置。
- 一个单一功能就是一个权限点，例如票务核销、查看卡座预定状态。
- 权限支持完全自定义配置，可按角色配置，也可按员工单独配置。
- 职级可按 M1-M10，并可分上、中、下。
- 职级只给薪资大范围，具体薪资需要单独填写。
- 职级可影响默认权限模板和审批层级，但不能替代单一功能权限。

## 15. 平台治理、合同和准入

- 基础平台要管理综合体、商户、合同、空间、区块、设备、人员、权限和终端开关。
- 商户管理需要更多信息，包括合同管理审批、面积、租赁面积、商场区块、负责人、联系方式、第一联系人、第二联系人、每平米租金、合作形式等。
- 商场区块最好有平面图。
- 合同核心摘要和基础定义由平台治理层管理。
- 违反合同或基础定义的内容，后续流程要被卡住，或需要更高级别审计/审批。
- 所有合同或基础定义违规都要先卡住流程，但允许更高级审核后放行。
- 审批层级可逐级上提，例如上一级、上两级、最高权限。

## 16. 第三方接入

- 当前第三方供应商接口资料还没有确定。
- 系统开发先完成自有系统，再接入第三方。
- 第三方接入分两种：
  - 第三方在鉴权前提下获取或回写平台数据。
  - 平台后续接入第三方 SDK/API。
- 餐饮/零售第三方同时支持订单级和券核销级回流。
- 看板支持日、半日、小时汇总；单店小数据量场景可实时汇总。
- 美团、大众点评、抖音 P0 只做团购购票、订单回流、核销和对账。

## 17. 终端开关和 SaaS 化

- 所有端都要有开关接口。
- 包括小程序、App、Web、平板、员工端 App、商户侧 App/Web、一体机、移动管理端。<!-- 修订说明（2026-06-08 三轮收口）：保留原始措辞；终端枚举以基准 D5 十端为准（app/miniapp/web/tablet/staff_work_phone/staff_private_phone/merchant_portal/merchant_app/kiosk/mobile_admin），其中"员工端 App"对应工作手机 staff_work_phone 与私人手机 staff_private_phone 两端，"商户侧 App/Web"对应 merchant_app 与 merchant_portal。依据 finding residual-scan-8、D5 -->
- 如果接口关了，该端或模块不可用；打开后才可用。
- 开关关闭后，菜单不可见或不可用，接口拒绝业务动作并留痕。
- 终端开关用于未来酒吧系统和乐园系统 SaaS 化。
- 商户侧在授权业务范围内全开放。
- 酒吧系统和乐园系统未来可分别成为独立 SaaS 系统。

## 18. Web 前端和移动端

- 增加 Web 前端。
- 移动端 App 的展示内容可以先在 Web 前端显示。
- Web 前端可供部分业务人员在非编辑状态查看信息。
- Web 前端 P0 允许少量业务确认动作。
- 客人 App/小程序用于购票、预定、查询信息、展示验票二维码、会员积分和兑换。
- 工作人员平板用于点酒下单。
- 移动管理端可给主管看指标、待办和异常审批。

## 19. 数据分析、风控和 AI 质检

- 看板不是为了好看，而是为了判断综合体经营情况。
- 需要看收入、客流、核销、退款、异常、商户表现、对账差异、库存、供应链、第三方回流、企业微信质检。
- 销售服务分析要看订单来源、销售归属率、卡座服务责任完整率、送达确认率和异常首响时长。
- 风控需要覆盖异常核销、库存风控、财务差异、企业微信违规、服务质量和设备策略违规。
- AI 深度分析、语义质检、经营预测可后置。

## 19A. 发票与税务（法定义务补记）

> 补记（2026-06-07 收口，C6）：原始需求采集**完全未捕获"发票/开票"这一法定需求**，但面向消费者开票是法定义务（《发票管理办法》）。购票、酒吧消费、结算环节均触发开票场景，不应仅当作可选 P1。最小口径：P0 至少落"开票申请/状态/抬头/税号/税目/金额"字段与对账衔接的产品口径（见 finance-settlement PRD §6A），实际开票平台对接可 P1。依据 finding compliance-land-3、C6。

## 20. 文档与交付要求

- 目标是生成可以供分析判断的完整系统文档，并可直接用于后续编码。
- 文档要按模块拆解，颗粒度足够编码。
- 业务人员版本需要用 HTML 做成可点击的说明页，给完全不懂产品和技术的人看。
- 平台治理也需要类似业务人员 HTML 拓扑页。
- 所有相关项目内容需要打包，方便发给其他机器智能体做进一步完善和评估。
