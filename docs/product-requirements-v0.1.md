# 综合体管理系统产品需求总纲 V0.1

## 1. 文档说明

本文档用于重新从基础业务需求出发，整理“综合体管理系统”的产品总纲。

本版文档明确不是技术方案，不是数据库设计，不是接口设计，也不是编码任务书。其作用是先把产品目标、业务边界、核心对象、关键闭环和阶段范围讲清楚，为后续继续拆分子系统 PRD、页面清单、流程细化和开发排期提供统一基础。

业务事实以三份业务 HTML 为最终解释权；本文及其下游 PRD、接口、数据库、UI、测试和实现均须向 HTML 对齐，不能用当前实现反向解释业务规则。

本版整理默认前提如下：

- 之前曾过早进入编码和实现拆解，但当前需要回到最原始业务意图重新定义产品。
- 不沿用旧代码实现思路，不以现有技术结构倒推产品，而是以综合体真实经营管理目标重新梳理需求。
- P0 只定义必须先具备的产品能力，不展开具体技术实现。

## 2. 项目背景与产品定位

### 2.1 项目背景

该项目面向一个娱乐综合体/综合体项目。综合体内不是单一业态，也不是单一商户，而是由多个业务场景共同构成，包括但不限于餐饮、零售、酒吧、主题游乐设施，以及与之相关的票务、会员积分、供应链、采购、库房、存酒、现场服务、设备管理、留痕审计、结算对账和经营分析。

综合体的实际管理难点在于：

- 业态多，不同业务的经营逻辑差异明显。
- 商户多，存在自营、联营、承租、代运营等不同运营关系。
- 参与人员多，包括平台方员工、商户员工、现场服务人员、安保、巡检、客服等。
- 设备多，包括扫码设备、工作手机、机器人、监控点位等。
- 留痕要求高，很多现场动作如果不能自动记录，后续很难追责、复盘和结算。
- 经营结果复杂，订单、权益、核销、采购、库存、存酒、退款、对账、分账和运营分析相互关联。

### 2.2 产品定位

综合体管理系统的产品定位，不是单一票务系统、单一酒吧系统，也不是单一 ERP 或 POS 替代品，而是一个面向娱乐综合体的统一管理平台。

该平台的核心价值是：

- 用统一平台管理综合体内所有业务、商户、相关工作人员、设备、现场行为和经营结果。
- 在多商户、多业态、多运营主体并存的情况下，实现平台统一治理、业务相对隔离、经营数据可追踪、结算关系可落地。
- 对能自建且必须掌握的核心能力进行统一建设，重点包括通票/权益/核销、游乐基础运营、核心留痕和基础结算。
- 对成熟第三方系统优先采用对接方式，平台负责统一接入、记录、核对、补录和分析，而不是重复造轮子。

## 3. 管理目标

本系统的管理目标是：管理综合体内所有业务、商户、相关工作人员、设备、现场行为和经营结果。

围绕这一总目标，产品需要支持以下管理诉求：

- 看清楚综合体里“谁在经营什么”，包括商户、业态、项目、空间和合同关系。
- 看清楚“谁在现场做了什么”，包括员工、班次、设备、核销、服务、巡检和异常处理。
- 看清楚“卖了什么、核了什么、退了什么、欠了什么、结了什么”，形成可追溯的经营流水。
- 看清楚“哪些业务是平台自建核心，哪些业务依赖第三方”，并保证数据能回到统一管理口径。
- 看清楚“经营结果和风险”，包括收入、核销、客流、容量、异常、争议和结算差异。

## 4. 原始业务范围

### 4.1 纳入管理的主要业态

综合体管理系统的原始业务范围包括：

- 餐饮
- 零售
- 酒吧
- 主题游乐设施

这些业态都属于平台统一管理范围，但并不意味着都要由本系统完整自研。

### 4.2 自建与第三方对接边界

| 业务领域 | 产品定位 | P0 处理方式 |
|---|---|---|
| 餐饮 | 多为成熟第三方 POS/业务系统承接 | 以第三方对接为主，平台管理商户、券/权益、留痕、对账和分析 |
| 零售 | 多为成熟第三方 POS/零售系统承接 | 以第三方对接为主，平台管理商户、券/权益、留痕、对账和分析 |
| 酒吧 | 与综合体票务、权益、桌台、服务、结算关系紧密 | P0 纳入基础经营能力，但只覆盖先运营所必需的范围 |
| 主题游乐设施 | 与通票/权益/核销/容量/安全强相关 | 需要自建核心能力，作为平台产品重点 |
| 机器人 | 多为第三方服务商能力 | 平台以任务留痕、状态同步、异常处理为主 |
| 视频监控 | 多为第三方监控平台能力 | 平台以点位关联、证据索引、事件绑定为主 |
| 企业微信 | 使用官方企业微信体系与会话存档能力 | 工作手机只允许企业微信沟通，平台做每日会话归档、质检留痕、服务分析和违规检查 |

### 4.3 必须自建的核心能力

从原始意图看，以下能力不宜完全外包给第三方，需要由平台掌握核心定义权：

- 综合体项目、空间、商户、合同、人员、设备等基础管理能力
- 通票、权益、核销的统一规则与统一台账
- 会员积分、会员等级和积分兑换的统一规则与统一台账
- 供应商、供应合同、采购周期、库房、库存消耗和客人存酒的基础台账
- 主题游乐的项目、场次、容量、核销等基础运营能力
- 与综合体经营直接相关的事件留痕、人工补录、异常追踪和基础结算能力
- 员工工作手机、企业微信会话归档、设备白名单、应用白名单和网站白名单管控能力
- 统一经营视角下的分析看板和管理视图

## 5. 核心原则

### 5.1 经营组织原则

1. 系统必须支持多商户、多业态、多运营主体、多结算主体。
2. 同一综合体内不同业务可由不同公司经营，平台需要统一看全局，但不能混淆账、权、责和数据权限。
3. 平台方需要统一治理，商户侧需要边界清晰，游客/会员作为被服务对象纳入统一识别但不等于拥有后台管理权限。
4. 当前先落一个综合体，但数据结构和权限边界必须支持未来多个综合体统一管理。
5. 票务管理、酒吧管理、游乐设施管理可以拆成独立业务系统，但必须共同依赖平台治理层的综合体、商户、合同、空间、人员、设备和权限定义。

### 5.2 管理与数据原则

1. 业务隔离但平台统一管理。
2. 同一游客、同一订单、同一权益、同一设备、同一事件，在全平台内应具备统一识别关系。
3. 同一经营动作，尽量只在一个地方形成主记录，避免多系统口径长期冲突。
4. 合同和基础定义是后续业务准入依据；当票务发布、酒吧下单、供应链采购、库存出入库、游乐开放、结算或第三方接入违反合同范围、经营范围、空间范围或权限范围时，系统必须阻断或进入更高级别审批/审计。
5. 票码、权益码、核销码必须具备防伪、防篡改和事后核对能力，不能只依赖可复制的二维码图片。

### 5.3 留痕原则

1. 自动留痕优先，人工补录兜底。
2. 凡是有过程的业务动作都应留痕，包含订单获取、销售归属、订台、服务、核销、放行、退款、异常、库存变化、设备交接、人工覆盖、结算调整。
3. 人工补录必须带原因、责任人、时间和关联对象，不能成为常态化主流程。
4. 留痕设计应优先通过登录账号、设备绑定、班次、点位、扫码、支付回调、终端动作、机器人状态、企业微信同步和第三方回调自动生成，人工只补原因、证据和复核意见。
5. 视频监控 P0 不做强依赖，但所有事件必须保留点位、设备和发生时间，为后续按事件匹配监控视频预留条件。

### 5.4 第三方接入原则

1. 第三方接口必须标准化。
2. 第三方接入必须有清晰的身份识别、授权边界和安全鉴权。
3. 平台不要求替代成熟第三方系统，但要求第三方关键结果能回到平台形成统一管理口径。
4. 第三方采用“双向开放”：平台对外提供统一 OpenAPI / Webhook / SDK 示例，平台对内通过供应商 SDK/API 适配器接入聚合支付、企业微信、人脸/年龄核验、机器人、视频、设备和票务渠道。
5. 供应商未确定时，P0 只固化统一接口、适配器边界、字段映射占位、Webhook + 定时轮询校验、对账和异常补偿，不把供应商私有字段写进票务、酒吧、财务、库存等业务主模型。
6. 供应商资料到位后，只补字段映射、签名算法、错误码、状态码、对账文件和适配器实现，不重新改变已收口业务闭环。

## 6. 用户与角色画像

| 角色 | 关注重点 | 主要使用诉求 |
|---|---|---|
| 综合体业主/管理层 | 综合经营结果、风险、商户表现、客流与收益 | 看总览、看对比、看异常、看趋势 |
| 平台运营 | 日常经营运行是否顺畅 | 处理配置、监控运行、跟进异常、跨业态协同 |
| 招商/商户管理 | 商户引入、合同履约、经营表现 | 管商户档案、合同、续签、考核 |
| 财务 | 订单、退款、核销、对账、结算差异 | 查流水、对账、出结算单、做复核 |
| 票务运营 | 票种、通票、权益、售卖、核销规则 | 配票、控量、看核销、处理票务异常 |
| 酒吧运营 | 入场、桌台、消费、服务、账单 | 管营业现场、查桌台状态、查基础经营数据 |
| 游乐运营 | 项目开放、场次、容量、核销、安全 | 管项目日常运营、看场次和异常 |
| 餐饮/零售第三方商户 | 本店订单、券核销、数据回传、对账 | 看本商户数据、核对平台结果 |
| 现场员工 | 执行现场作业 | 上岗、领设备、核销、服务、补录、交接 |
| 安保/巡检 | 现场秩序、巡检、安全事件 | 做巡检、记录异常、留痕上报 |
| 客服/企业微信质检 | 会话服务质量、投诉与需求转化 | 查会话、跟投诉、做质检 |
| 系统管理员 | 平台配置、账号、权限、接入治理 | 管组织、权限、配置、接口授权 |
| 游客/会员 | 购票、入场、使用权益、获得积分、兑换礼物、接受服务 | 作为统一服务对象被识别、被记录、被分析 |

## 7. 基础对象模型

以下对象是本产品后续拆分子系统 PRD 和页面清单时的基础对象集合。

| 基础对象 | 定义说明 | 关键关系 |
|---|---|---|
| 综合体项目 | 需要被统一管理的综合体实体 | 关联空间、商户、业态、经营规则 |
| 独立业务系统 | 票务、酒吧、游乐等可独立拆分的业务系统 | 共同依赖平台治理层的项目、商户、合同、空间、人员、权限 |
| 空间/楼层/区域/点位 | 综合体物理空间与可管理点位 | 关联项目、商户、设备、视频、核销、桌台、游乐入口 |
| 业态 | 餐饮、零售、酒吧、游乐等业务类型 | 决定商户能力范围、统计口径和管理方式 |
| 商户/运营主体 | 实际经营某类业务的公司或组织 | 关联业态、空间、合同、员工、结算 |
| 合同 | 平台与商户之间的合作和结算依据 | 关联商户、空间、经营范围、结算规则、有效期、准入拦截和升级审批 |
| 员工/岗位/班次 | 在综合体内执行工作的人和排班关系 | 关联商户、设备、权限、职级、薪资口径和作业留痕 |
| 员工私人手机 App | 员工自有手机上的轻量 App | 用于注册、通知、状态查看、设备凭证绑定和审批结果查看，不承担现场业务操作 |
| 企业设备 | 公司配发或统一管理的工作设备 | 关联员工、班次、作业记录、异常事件 |
| 员工工作手机 | 公司发给员工的手持作业设备 | 关联员工、班次、门票核销、权益核销、企业微信沟通、设备策略和责任链 |
| 触摸屏一体机 | 固定点位自助服务终端，分售票型和非售票型：售票型用于授权服务人员辅助到店客人购票、取票和订单查询，绑定酒吧门口/前台时只能售卖本酒吧单店门票；非售票型用于扫码展示/领取权益、订台下单、吧台买酒下单、游乐设施状态查看和授权状态检查 | 关联票务订单、支付、出票、防伪二维码、权益、领取记录、点位、订台订单、吧台订单、游乐状态检查和设备留痕 |
| 游客/会员 | 被服务对象与消费主体 | 关联票、订单、权益、会话、核销和投诉 |
| 会员积分账户 | 游客会员的积分余额、等级和成长记录 | 关联消费、订单、兑换、等级规则 |
| 积分兑换记录 | 会员使用积分兑换礼物或权益的记录 | 关联会员、礼物、领取点、触摸屏一体机展示/领取 |
| 票 | 被售卖的票务产品 | 关联通票、权益、订单、退款、防伪票码和核对记录 |
| 通票 | 组合型销售包装 | 拆分为多个可用权益并归属不同业务 |
| 权益 | 游客实际可被使用的权利单位 | 关联票、核销、退款、结算、风控 |
| 订单/支付/退款 | 经营交易结果的核心记录 | 关联游客、商户、票、酒吧消费、结算 |
| 核销记录 | 权益被使用、放行或拒绝的记录 | 关联权益、员工、设备、时间、点位 |
| 票码/防伪串码 | 票和权益对外展示的核验凭证 | 关联二维码签名、随机串、有效期、哈希、生成/刷新/核销记录 |
| 酒吧桌台/卡座/吧台 | 酒吧基础经营空间对象 | 关联开台、订单、服务员、低消、结账 |
| 酒吧点酒订单 | 平板在指定酒吧和卡座下生成的酒水订单 | 关联酒吧、卡座、最低消费、支付和账单 |
| 供应商 | 提供酒水、消耗品、礼品或其他物品的主体 | 关联供应合同、采购周期、入库批次和结算 |
| 供应合同 | 平台或商户与供应商之间的采购和结算依据 | 关联供货范围、价格口径、账期、有效期、准入和审批 |
| 采购周期 | 从采购申请、审批、下单、到货、入库到差异处理的过程 | 关联供应商、供应合同、物品、库房和财务 |
| 库房/库位 | 存放酒类、消耗品、礼品和其他物品的管理空间 | 关联综合体空间、库管、物品批次和盘点 |
| 库存物品 | 可采购、存放、售卖、消耗或兑换的东西 | 包括酒类、消耗品、礼品、设备耗材和其他物品 |
| 库存流水 | 所有库存变化的事实记录 | 关联入库、出库、调拨、销售消耗、赠饮、报损、盘点差异 |
| 吧台消耗 | 吧台按杯、按瓶、按套餐或其他形式售卖/出品导致的消耗 | 关联酒吧订单、账单、员工、库存物品 |
| 客人存酒 | 客人购买后未喝完或暂存在场内的酒 | 关联会员、酒品、剩余量、有效期、二维码和取酒记录 |
| 游乐项目/场次/容量/安全巡检 | 游乐经营核心对象 | 关联票务权益、核销、开放状态和安全记录 |
| 第三方系统 | 餐饮、零售、机器人、监控、企微等外部能力提供方 | 关联商户、接入关系、同步结果、异常 |
| 机器人任务 | 机器人承接的配送或执行任务 | 关联订单、货物、取货点、交付点、异常 |
| 视频点位 | 监控覆盖点位和证据索引对象 | 关联空间、事件、调阅记录 |
| 企业微信会话 | 员工通过企业微信产生的工作聊天记录 | 每日自动上传后台，关联员工、游客/会员、需求、投诉、服务质检和违规命中 |
| 事件留痕 | 关键经营与现场动作的统一记录对象 | 关联业务对象、人员、设备、时间和原因 |
| 人工补录 | 对自动记录失败后的受控补救对象 | 关联原业务、责任人、审批或复核结果 |
| 结算/对账 | 商户、平台、订单、权益之间的财务确认对象 | 关联合同、流水、核销、差异 |
| 风控/分析 | 风险识别与经营洞察对象 | 依赖全量基础对象和留痕结果形成判断 |

## 8. 系统能力分层

| 能力层 | 定位 | 主要承载内容 |
|---|---|---|
| 平台治理层 | 管“谁、在哪、凭什么、能做什么” | 综合体项目、组织、商户、合同、角色权限、员工、班次、设备、基础配置 |
| 业务经营层 | 管“具体业务如何运行” | 票务、通票、权益、会员积分、核销、酒吧经营、供应链库存、游乐运营、基础订单与退款 |
| 第三方接入层 | 管“外部系统怎么纳入平台” | 餐饮、零售、机器人、监控、企业微信及其他服务商接入关系 |
| 证据留痕与风控层 | 管“出了什么事、能否追溯、风险在哪里” | 事件中心、核销留痕、人工补录、异常事件、责任链、风险预警 |
| 数据分析层 | 管“经营结果和趋势怎么看” | 经营看板、客流、核销、收入、异常、商户表现、对账结果 |
| 终端展示层 | 管“不同角色通过什么界面使用系统” | 管理后台、Web 前端、商户侧页面、现场作业端、员工工作手机、工作人员平板 App、移动端工作台、客人 App/小程序、触摸屏一体机 |

## 9. 关键业务闭环

### 9.1 商户入驻与合同闭环

目标是明确“谁被允许在综合体经营什么，以什么规则经营”。

闭环过程：

1. 创建综合体项目与空间范围。
2. 建立商户/运营主体档案。
3. 标记业态与经营范围。
4. 录入合同、合作模式、期限与结算口径。
5. 绑定对应空间、点位和适用业务。
6. 合同和基础定义生效后，票务、酒吧、游乐、结算、第三方接入等后续流程才能引用。
7. 后续流程如违反合同经营范围、空间范围、有效期、结算口径或权限范围，系统直接阻断或进入更高级别审批/审计。

闭环输出：

- 商户可运营范围
- 合同有效范围
- 后续结算与权限依据
- 业务准入拦截和升级审批依据

### 9.2 员工上岗与设备领还闭环

目标是明确“谁在什么班次、拿着什么设备、在什么区域执行了什么工作”。

闭环过程：

1. 建立员工、岗位、班次基础信息。
2. 员工在私人手机 App 中注册，提交身份、岗位申请和设备信息，并在安装期生成设备凭证。
3. 后台审核通过后生成员工账号、角色、职级、数据范围和默认权限。
4. 将员工私人手机设备凭证、公司发放工作手机和员工账号建立一一对应关系。
5. 员工进入办公区时寄存私人手机，现场只能使用公司受管工作手机。
6. 上岗时绑定员工、班次、职级、责任区域和公司设备。
7. 现场通过设备执行核销、服务、巡检、补录等动作。
8. 下班归还设备并确认待同步事项、未完成事项和异常。

闭环输出：

- 人员责任链
- 设备使用链
- 现场作业留痕链
- 私人手机注册/设备凭证绑定/公司工作手机对应关系
- 职级、权限和薪资关联依据

### 9.3 票务配置与售卖闭环

目标是明确“卖的是什么，包含什么权益，卖给了谁”。

闭环过程：

1. 配置票、通票和权益规则。
2. 明确权益归属、有效期、适用业务和使用限制。
3. 形成可售卖产品。
4. 游客通过官方 App/小程序或第三方渠道下单、支付。
5. 生成订单、票、权益、会员积分和后续可核销基础。
6. 生成带签名、随机串、有效期和哈希校验的防伪票码/二维码。
7. 记录票码生成、刷新、展示、核销、失败和异常事件，支持事后核对。

闭环输出：

- 可售卖票务产品
- 订单与支付记录
- 可被使用的权益台账
- 会员积分和等级成长记录
- 防伪票码和事后核对依据

### 9.4 游客入场与权益核销闭环

目标是明确“游客是否有资格进入或使用某项服务，使用后如何准确留痕与扣减”。

闭环过程：

1. 游客出示 App/小程序或第三方渠道票码、权益码或其他识别凭证。
2. 系统先校验二维码签名、随机串、有效期、哈希和凭证状态，判断是否可能被篡改或伪造。
3. 系统识别适用权益和使用条件。
4. 员工使用工作手机在指定点位进行核销或人工处理。
5. 记录成功、失败、放行、拒绝等结果。
6. 回写权益使用状态和后续结算依据。

闭环输出：

- 核销记录
- 权益状态变化
- 现场责任与设备留痕
- 票码防伪校验结果和事后核对证据

### 9.5 酒吧经营闭环

目标是明确“酒吧如何从入场到消费到结账形成基础经营闭环”。

闭环过程：

1. 识别酒吧入场资格并记录入场。
2. 分配桌台/卡座/吧台位并开台。
3. 工作人员使用平板绑定具体酒吧和卡座/桌台后点酒下单。
4. 校验最低消费，未满足最低消费时不能提交。
5. 通过客人扫码支付或平板扫描客人付款码完成支付。
6. 完成加单、服务、必要的人工调整或异常说明。
7. 完成结账、退款或关台。
8. 输出到结算和分析口径。

闭环输出：

- 酒吧现场经营记录
- 桌台与账单状态
- 基础收入与服务留痕
- 平板点酒订单、最低消费校验和支付记录

### 9.6 供应链与库存闭环

目标是明确“酒水、消耗品、礼品和其他物品如何从供应商进入库房，再被吧台售卖、权益领取、报损、盘点或客人存酒消耗掉”。

闭环过程：

1. 建立供应商档案和供应合同。
2. 按采购周期发起采购申请、审批、下单和到货计划。
3. 到货后由库管验收，生成入库批次和库存流水。
4. 总库、酒吧库、吧台库存、消耗品库和存酒区分开管理。
5. 吧台卖酒、赠饮、积分兑换礼物或权益领取后，记录对应库存消耗。
6. 客人喝不完的酒进入存酒管理，后续按会员、手机号、存酒码或二维码取酒。
7. 盘点、报损、报溢、存酒作废和高价值酒水异常进入复核和留痕。
8. 采购、成本、消耗、报损和盘点差异进入财务和经营看板。

闭环输出：

- 供应商和供应合同台账
- 采购周期和入库记录
- 库房、库位和库存余额
- 吧台消耗记录
- 客人存酒记录
- 盘点差异、报损和复核记录

### 9.7 游乐运营闭环

目标是明确“游乐项目如何从开放配置到游客入场再到安全责任形成闭环”。

闭环过程：

1. 建立游乐项目、开放时间、场次和容量。
2. 明确项目限制条件和适用权益。
3. 现场执行核销、放行、容量控制。
4. 记录暂停、关闭、异常和巡检情况。
5. 形成项目经营与安全视图。

闭环输出：

- 项目日常运营状态
- 场次与容量执行结果
- 核销、安全和异常留痕

### 9.8 第三方业务同步闭环

目标是明确“第三方系统虽然不在平台内运营，但关键结果必须回到平台”。

闭环过程：

1. 定义第三方商户和系统接入关系。
2. 明确同步哪些关键结果，例如订单、核销、退款、任务、会话或证据索引。
3. 接收或拉取第三方结果。
4. 标记成功、失败、延迟或差异。
5. 进入留痕、对账和分析视图。

闭环输出：

- 第三方关键业务回流记录
- 差异和异常清单
- 平台统一管理口径

### 9.9 异常补录闭环

目标是明确“自动链路失效时，如何受控地补齐事实记录，而不是让业务脱离系统”。

闭环过程：

1. 识别自动记录失败或现场特殊情况。
2. 由责任人发起人工补录。
3. 填写原因、时间、关联对象和证据。
4. 按规则进入复核或直接生效。
5. 补录结果进入原业务链路和风险链路。

闭环输出：

- 可审计的补录记录
- 对原业务结果的补足
- 异常责任和复核依据

### 9.10 日结/对账/结算闭环

目标是明确“经营结果如何被财务确认，差异如何被发现和处理”。

闭环过程：

1. 汇总订单、支付、退款、核销和第三方回流结果。
2. 按合同和主体区分平台与商户口径。
3. 进行日结、对账、差异识别。
4. 对异常差异做补录、调整或确认。
5. 形成结算单、应收应付或经营结论。

闭环输出：

- 基础对账结果
- 结算依据
- 差异处理记录

### 9.11 经营分析闭环

目标是明确“平台管理层如何基于经营事实做判断，而不是只看碎片化系统结果”。

闭环过程：

1. 聚合商户、票务、核销、酒吧、游乐、第三方和结算数据。
2. 形成按项目、业态、商户、时间、空间的经营视图。
3. 输出看板、趋势、异常和重点指标。
4. 为招商、运营、财务和管理层提供决策支持。

闭环输出：

- 管理层经营看板
- 商户表现视图
- 风险与异常提示

## 10. P0 产品边界

### 10.1 P0 定义

P0 的目标不是把综合体所有能力一次做全，而是先定义和落下“必须先具备的产品能力”，确保后续编码时有稳定边界、有明确对象、有最小闭环。

P0 明确只写产品能力，不写具体技术实现。

### 10.2 P0 必须先具备的范围

| P0 能力域 | P0 应具备的产品能力 |
|---|---|
| 基础档案 | 综合体项目、空间、区域、点位、业态、商户、运营主体的基础管理 |
| 商户合同 | 商户与合同关系、经营范围、有效期、基础结算口径、核心条款摘要、准入拦截和升级审批依据 |
| 人员设备 | 员工注册审批、岗位、班次、职级、权限、设备凭证绑定、私人手机 App、公司工作手机一一对应、设备台账、领用归还、基础责任留痕 |
| 票/权益/核销 | 票、通票、权益、防伪二维码/串码、基础售卖结果承接、基础核销、核销记录与异常处理、事后核对 |
| 会员积分 | 消费积分规则、会员等级、积分明细、积分兑换记录 |
| 酒吧基础经营 | 酒吧入场、桌台/卡座/吧台位、平板点酒、最低消费、基础账单、吧台买酒、关台结果 |
| 供应链库存 | 供应商、供应合同、采购周期、库房、物品、入库、出库、调拨、吧台消耗、盘点差异、报损、客人存酒 |
| 游乐基础运营 | 游乐项目、开放状态、场次、容量、基础核销、开放前安全巡检、阻断项暂停、整改复检、主管恢复、基础异常留痕 |
| 第三方接口预留 | 餐饮、零售、机器人、监控、企业微信等第三方接入关系与关键结果预留 |
| 企业微信会话质检 | 员工工作聊天每日归档、基础敏感词/违规检查、上传状态和复核入口 |
| 设备访问管控 | 工作手机预装软件清单、应用白名单、网站白名单、违规安装和违规访问记录 |
| 事件留痕 | 关键业务动作、人工放行、异常处理、人工补录的统一留痕 |
| 基础结算 | 面向订单、核销、合同的基础对账与结算依据 |
| 基础看板 | 面向管理层和运营侧的基础经营看板与异常视图 |

### 10.3 P0 不追求的深度

P0 只要求把最基本的管理骨架和最小经营闭环站稳，不要求在每个业务域一步做到精细化、自动化和智能化。

例如：

- 酒吧先聚焦基础经营闭环和平板点酒；供应链 P0 先做基础库存台账、吧台消耗和客人存酒，不追求完整自动补货、复杂 BOM 和供应商评分。
- 游乐先聚焦项目、场次、容量、核销和开放前阻断式安全巡检闭环；P0 不做完整预约排队、电子免责、事故工单和 AI 视频安全识别。
- 第三方系统先明确接入边界和回流口径，不在 P0 追求所有厂商一次性全量接通。
- 多综合体先保留项目隔离、数据范围和权限边界，不在 P0 追求集团级复杂组织报表。

## 11. P1/P2 方向

| 阶段 | 后续增强方向 |
|---|---|
| P1 | 预约排队、安全库存预警、保质期预警、存酒深化、杯卖扣减细化、会员积分运营活动、班次联动、更多第三方业务同步、机器人任务闭环、视频证据绑定、结算规则细化 |
| P2 | 自动风控、AI 分析、经营预测、企业微信深度语义质检、服务质量诊断、跨业态推荐、自动异常识别、游客画像深化、智能巡检辅助 |

可明确纳入后续增强方向的事项包括：

- 预约排队
- 安全库存、保质期预警、自动补货和复杂库存成本
- 机器人履约
- 视频证据
- 企业微信深度语义质检
- 会员积分运营
- 自动风控
- AI 分析

## 12. 非目标

以下内容不属于 P0 目标，避免范围失控：

- P0 不自研餐饮 POS。
- P0 不自研零售 POS。
- P0 不做完整机器人系统。
- P0 不做完整视频监控平台。
- P0 不做完整企业微信替代系统。

同时需要补充说明：

- P0 不以“覆盖所有外部系统全部细节”为目标，而是先明确统一管理口径。
- P0 不以“做出所有精细化运营能力”为目标，而是先保证基础经营、留痕和结算能闭环。

## 13. 后续拆分建议

为了便于继续拆成子系统 PRD 和页面清单，建议后续按以下维度继续细化：

- 按平台治理拆：项目与空间、商户与合同、员工与班次、设备管理、角色权限
- 按独立子系统拆：票务管理、酒吧管理、游乐设施管理可独立设计，但必须共用平台治理层主数据和准入规则
- 按业务经营拆：票务/权益/核销、酒吧基础经营、游乐基础运营
- 按第三方接入拆：餐饮、零售、机器人、监控、企业微信
- 按证据与风控拆：事件中心、人工补录、异常处理、基础风控
- 按财务经营拆：基础对账、结算、经营看板
- 按终端与页面拆：平台后台、商户侧、现场作业端、管理看板

## 14. 已确认业务规则

以下内容已经由业务侧拍板，后续子系统 PRD、页面清单、接口预留和编码任务均按此口径展开：

1. 官方购票入口 App 和小程序同步建设；所有门票必须由客人自己购买，工作人员平板不得代客购票。
2. 美团、大众点评、抖音首批只聚焦团购购票、订单回流、券/票核销和对账，其他外部营销玩法暂不进入 P0。
3. 会员积分、等级成长和兑换规则由后台定义；积分兑换礼物必须扣减库存，并进入权益领取、库存消耗、财务对账和经营看板。
4. 通票支持酒吧通票、游乐通票、酒吧 + 游乐联合通票，以及酒吧 + 游乐 + 餐饮 + 零售折扣通票；餐饮和零售由第三方承接，平台只提供优惠、折扣、券或权益。
5. 订台入口包括官方 App、小程序、触摸屏一体机和销售人员工作台，订台需要支付定金。
6. 吧台买酒优先线上支付，同时必须允许现场现金和 POS 机支付，并纳入订单、账单、日结、员工责任链和财务对账。
7. 供应合同分为平台自用供应合同、商户自采供应合同、平台统一采购后分销给商户三种模式。
8. 客人存酒使用瓶底标签管理，按标签数值记录剩余量，登记时必须拍照、填写人工备注，并留取客人手机号和姓名/昵称。
9. 游乐容量 P0 按具体项目 + 具体场次/时段 + 点位/设备控制；项目总量只作为上层汇总和安全上限。
10. 餐饮/零售第三方回流同时支持订单级和券核销级；看板支持日、半日、小时汇总，单店小数据量场景可实时汇总。
11. 票务二维码有效期按票种配置，例如日票、周票、月票、年票；二维码 30 秒或 60 秒刷新，截图无效，必须在线核验，不做离线核验。
12. 员工私人手机 App 安装期在设备 Keystore 生成设备公钥/不可逆设备指纹（device_key_fingerprint）并绑定员工；员工换手机必须先解绑旧设备凭证再绑定新设备凭证。不读取手机本机 NFC 唯一标识；工作手机通过摄像头/扫码模块读取外部二维码，NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。
13. Root/调试/异常环境以手机端可检测能力为准，检测异常时私人手机 App 失效并进入后台复核。
14. 员工进入办公区或现场作业区时寄存私人手机；寄存柜不固定，流动使用，先到先选，离开时全部拿走。
15. 职级由后台维护，可按 M1-M10 并分上、中、下；职级只绑定薪资大范围，具体薪资仍需单独填写。
16. 工作手机预装软件清单和网站白名单由后台维护，通过 Android Enterprise / Android Management API + 商业 MDM 阻止违规访问，策略命中和封禁结果必须留痕。
17. 新人优惠、学生票、多人票由后台配置规则，符合规则时自动判断可用，不符合规则时不允许享受对应优惠或票种。
18. 酒吧最低消费按时间、卡座和位置配置，支持平日、周末、节假日和自定义时段，不按人数计算。
19. 吧台按杯销售按后台配置的每杯标准出酒量/容量扣减库存，超过标准容量的部分记为损耗，损耗严重时进入异常核查。
20. 供应链 P0 从酒类、吧台消耗、客人存酒和常用消耗品开始，常用消耗品包括纸巾、色盅、色子、杯子、杯具等。
21. 高价值酒水报损、盘点差异、存酒作废必须拍照和视频留证，并经主管复核。
22. 人工放行、免单、退款、调账必须进入主管复核，复核层级可后台配置，支持上一级、上两级或最高权限逐级上提。
23. 一体机承接游乐设施定期检修记录，检修工程师和检修单位按供应商记录，检修完成后必须由主管确认才能恢复营业。
24. 所有合同或基础定义违规都必须先卡住流程，但都允许按后台配置的更高级审核层级放行，放行必须留痕。
25. Web 前端 P0 允许少量业务确认动作，但仍以查看、查询、看板和业务确认为主，不承接复杂编辑和现场作业。
26. 企业微信工作会话留存期限可配置（非永久），到期归档/销毁/匿名化（见 compliance §4 C3、data-risk §11.5）；会话原文按权限查看，不脱敏原文仅限最小授权 + 审批的取证/质检场景，查看必须写入访问审计。<!-- 修订说明（2026-06-08 三轮收口）：原始需求曾表述为"永久保存、不脱敏"，现行口径已按 A7/合规 C3 收口为可配置留存和分级查看，"永久保存"不再作为现行 P0 规则。依据 finding residual-scan-3、A7/C3 -->
27. 未来需要集团视图和跨项目汇总视图，但优先级低于单综合体 P0 闭环；P0 先保证所有对象带综合体项目归属。
28. 商户侧在授权业务范围内全开放，不能看平台全局和其他商户；酒吧系统和游乐/乐园系统应保留未来独立成为酒吧 SaaS、乐园 SaaS 的能力。
29. 日结锁定后原则上不允许补录影响金额；确需补录时必须发起上级权限申请，审批通过后才允许影响金额。
30. 员工权限按单一功能最小颗粒度配置，例如票务核销、查看卡座预定状态等；权限支持角色、基础模板、临时模板、复制模板、员工级授权/拒绝和单次有效授权。职级只影响默认权限模板、审批层级建议和薪资大范围，不能替代单一功能权限点，也不能让员工绕过具体功能授权。
31. 企业微信会话能力使用企业微信已有功能，平台只负责统一同步、存储、质检和审计。
32. 当前第三方供应商接口资料未确定，不阻塞设计；按 `third-party-supplier-integration-kit-v0.1.md` 先完成统一 OpenAPI/Webhook、供应商适配器、字段映射占位、mock adapter、Webhook + 定时轮询校验、对账和补偿框架，后续供应商 SDK/API 到位后只补真实字段与适配器实现。
33. 所有有过程的业务动作都必须留痕。除了酒水和可追责物品的二维码追踪外，订单获取、销售归属、订台、卡座服务、加单送达、核销、收款、退款、异常第一处理人、转派升级、复核关闭、人工补录和调账都要记录责任人、设备、时间、地点、订单或业务对象、结果和异常原因。
34. 所有端都必须有开关接口，终端业务全集以治理 HTML「终端开关」为最终解释权：客人 App（`app`）、小程序（`miniapp`）、Web 前端（`web`）、工作人员平板（`tablet`）、员工工作手机（`staff_work_phone`）、员工私人手机 App（`staff_private_phone`）、商户侧 Web 门户（`merchant_portal`）、商户侧 App（`merchant_app`）、触摸屏一体机（`kiosk`）、移动管理端（`mobile_admin`）；开关支持按全局、综合体项目、商户、业务系统、模块、设备和版本控制，为酒吧/乐园独立 SaaS 化预留。D5 只承接技术编码映射，不反向定义业务全集。
35. P0 做完整应收应付台账，覆盖应收、应付、账龄、到期日、责任主体、合同/订单/核销来源、收付款状态、差异、附件和留痕；商户账单门户、催缴、费用异议和复杂费用规则进入 P1。
36. 经营对象、运营主体、合同主体和结算主体可以是不同名称/不同公司，但必须在同一经营对象下唯一绑定，并在合同、结算、权限、看板、第三方接入和相关流程中统一引用、统一留痕。
37. P0 仅启用 CNY，金额统一按整数分存储和对账；保留 `currency=CNY` 字段，非 CNY 交易进入异常复核，多币种和汇率进入 P2。
38. 酒吧入场/售酒年龄核验强制接入第三方人脸/年龄核验接口或等效设备；供应商未确定前只允许测试 mock 和接口占位，生产环境不得把人工口头确认标记为正式通过。
39. 新增销售人员岗位：销售人员售卖卡座按该卡座消费额 15% 计算业务提成，非销售人员售卖或被归属为卡座销售时按 10% 计算；提成基数不含通票、票务权益、卡座预约入场名额、赠酒成本、退款、免单、抹零和不可计提调整。P0 生成可复核提成台账或应付/内部薪酬依据，工资发放、个税、多人分摊和阶梯提成后置。
40. 平台展示的所有数据、单据、对象及涉及人员和角色必须可点击追溯来源、归属和上下游，可正查反查，不允许孤岛数据。
41. 全部用户可见界面、状态、枚举、按钮、提示、报错、导出、短信、通知和日期时间必须使用中文；只有机器识别的编码、ID、单据号等技术标识可保留原样。
42. 金额计算、存储和显示统一精确到分、对客保留两位小数；分账、分摊或提成尾差由项目公司/平台承担并单列留痕，不并入任一参与方。
43. 并发冲突以先处理成功者为准；同一操作重复提交只认一次，不得重复扣款、入账、核销或消耗权益。
44. 存档用于日常下线，不需审批，历史仍可查并可恢复；删除必须先存档、填写删除理由、由另一人审批，申请人不得自审，执行后只隐藏不物理抹除，并保留查询、审计和恢复能力。删除前必须检查合同、账单、结算、订单、已发权益和库存等占用，存在占用时阻断。
45. 资金/核销/退款/调账/分红发放、提权或跨商户跨综合体、敏感数据、高危业务四类权限授出前必须先审批才生效；配置只能新增高危项或提高审批等级，不能关闭强制闸门，授权申请人不得审批自己的申请。
46. 员工岗位、职级、所属组织、所属商户或责任范围变化后，必须立即按新归属重算有效权限并使旧范围派生权限失效；不得只提示人工收回。

## 15. 已确认执行口径与实施输入

以下事项已按后续总控口径收口，不再作为开放业务问题；实施阶段只按合同、主体资料、供应商资料、账号配置和上线参数落地：

1. 经营模式支持平台自营、第三方商户联营/承租并存；以经营对象、运营主体、合同主体、结算主体唯一绑定落地。
2. 酒吧支持自营和第三方运营并存；P0 保证点酒、核销、账单、库存扣减、日结和主体绑定闭环，P1 扩展高级 POS/SaaS 能力。
3. 游乐项目可由统一运营主体或不同运营主体管理；P0 按项目/场次/点位/设备控制容量并引用主体绑定。
4. 权益核销以单项权益逐项核销和逐项留痕为准，票整体状态由权益明细汇总。
5. 人工补录、放行、免单、退款、调账等影响金额或风险的动作均按可配置主管复核执行。
6. 现场高风险岗位使用企业统一工作设备；员工私人手机只用于注册、设备凭证绑定、审批状态查看，不做现场业务。
7. 视频监控 P0 做事件点位索引和证据引用，P1/P2 再做深度回放、自动截取和智能分析。
8. 财务结算主口径按多来源并存：订单、核销、合同固定规则、第三方差异和调整单统一进入 P0 应收应付台账与日结/对账。
9. 管理层 P0 看板优先收入、客流/核销、异常风险/结算差异；商户表现和更深经营分析进入后续增强。
10. 游客/会员 P0 先打通游客识别、票务权益、积分和核销；统一会员中心保留扩展。
11. 集团视图默认 P2；P0 仅预留 `project_id` 和跨项目汇总口径，不阻塞单综合体 P0 闭环。
12. 权限初始化按权限模板机制落地：基础模板、临时模板、复制模板、有效期、单次有效、撤销和审计均为 P0；显式拒绝优先。
13. 第三方供应商未确定时不再要求业务方二次拍板；统一按供应商接入预留包执行，真实字段等供应商资料到位后补齐。
14. 币种按 CNY 单币种执行，金额单位为分；多币种、汇率和外币结算后置。
15. 酒吧年龄/人脸核验是生产上线阻断项：未完成第三方接口或等效设备接入前，只能演示 mock，不允许正式核验通过。

## 16. 本版结论

本版产品需求总纲的结论是：

- 该系统首先是“综合体统一管理平台”，而不是某个单点业务系统。
- P0 的重点是把基础档案、组织关系、合同准入、员工注册/设备凭证/权限模板、票/权益/防伪核销、会员积分、酒吧平板点酒、酒吧年龄/人脸核验生产阻断、卡座销售归属和提成台账、供应链库存、吧台消耗、客人存酒、酒水和物料全链路扫码留痕、订单/销售/服务/异常过程留痕、终端开关、游乐基础运营、第三方接入边界、供应商适配占位、事件留痕、基础结算和基础看板先定义清楚。
- 餐饮、零售、机器人、监控等能力以第三方对接为主；企业微信使用官方能力做每日会话归档和基础质检；主题游乐与通票/权益/核销属于平台必须掌握的核心能力。
- 后续所有子系统 PRD、页面清单和编码排期，都应以本总纲中的对象、闭环、边界、已确认执行口径、实施输入和后续排期作为上层约束；不再把已收口事项重新提交总控拍板。
