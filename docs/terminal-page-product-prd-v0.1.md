## 1. 文档定位

本文档按角色和使用场景拆解终端与页面。它回答“谁通过什么入口使用系统、每个入口负责什么、哪些页面 P0 必须有、手机和平板如何承担现场展示和操作”。

本文档不是视觉稿，不写前端实现，不写路由和组件。它只定义产品页面范围、角色入口和终端职责。

## 2. 终端分层

| 终端 | 使用对象 | P0 作用 |
|---|---|---|
| 管理后台 | 管理层、运营、财务、系统管理员 | 管配置、看总览、处理异常、复核和对账 |
| Web 前端 | 管理层、运营、财务、业务人员、部分商户人员 | 展示移动端和后台关键信息，支持非编辑状态查看 |
| 商户侧页面 | 餐饮/零售/酒吧/其他商户 | 看本商户经营数据、核对差异、处理本商户事项 |
| 现场作业端/员工工作手机 | 现场员工、服务员、游乐入口员工、巡检、检票员 | 上岗、领设备、核销门票、核销权益、放行、补录、巡检 |
| 工作人员平板 App | 酒吧现场工作人员、服务员 | 只做酒吧点酒下单，绑定酒吧和卡座/桌台，并自动记录销售归属和服务责任 |
| 触摸屏一体机 | 客人、现场工作人员 | 分售票型和非售票型两种模式：售票型支持授权服务人员辅助到店客人购票/订单查询（**门票为动态二维码，不提供取票功能**；2026-08-05 DEC-R7-05，照 BSM 触摸屏一体机章售票能力条 现行原文「启用售票能力的一体机可由授权服务人员登录后辅助客人购票和查询订单（门票为动态二维码，不提供取票功能）」）；非售票型承担扫码展示/领取权益、订台下单、吧台买酒下单、游乐设施状态查看和授权状态检查 |
| 移动管理端 | 管理层、运营主管 | 看关键指标、待办、异常审批 |
| 客人购票 App/小程序 | 游客/会员 | 官方购票、预定、查询信息、展示验票二维码、会员积分和兑换 |
| 员工私人手机 App | 员工自有手机 | 注册、通知、状态查看、设备凭证绑定、Root/设备异常检测，以及后台按设备类型放权的低风险功能（公告、我的工单、帮客人订位、查看考勤（考勤月历）、请假、查自己薪资、主管排班、只看我的服务收入等，见 §8.5）；不承担现场核销、点单、放行、结算、补录 |

所有终端都必须支持后台开关控制。开关可按全局、综合体项目、商户、业务系统、模块、设备和版本配置；关闭后该端或模块不可用，打开后仍继续校验登录、设备可信、商户范围、角色权限、单一功能权限和数据权限。

> 口径补充（2026-06-10）：触摸屏一体机不新增第 11 种终端，仍统一归属 `terminal_type=kiosk`；通过 `kiosk_mode=ticketing/service` 或模块开关区分“售票型一体机”和“非售票型一体机”。售票型一体机是授权服务人员辅助售票和查单的固定点位渠道（**门票为动态二维码，不提供取票功能**，DEC-R7-05），不能被实现为工作人员平板代客购票；非售票型一体机不得显示购票入口。

## 8. 客人购票 App/小程序 P0

客人购票 App/小程序 P0 必须同步支持官方购票、预定、查询信息、展示验票二维码和会员积分。门票购买主路径是客人本人通过官方 App/小程序或美团、大众点评、抖音等第三方团购渠道自助完成；少量到店服务场景下，授权服务人员可在启用售票能力的触摸屏一体机上辅助客人购票。工作人员平板 App 不允许代客购买门票。客人展示的二维码必须是可防伪、可验签、按票种有效期生效的动态码，**刷新间隔由后台统一设置、以 5 秒为单位可调、最长 60 秒**；**截图无效、必须在线核验**，而不是只包含票号的普通图片。

> 二维码口径补充（2026-08-04 对齐业务系统地图）：
> - **例外**：**纯「扫码打开一个链接」类二维码**（如扫码进入点单页面、扫码打开介绍页）**本身不代表任何权益或身份，保持固定即可**，**不在自动刷新范围内**。
> - **系统不生成「付款出示码」**：客人付款走第三方微信、支付宝，或用账户预存款经手机号加短信验证支付，故付款场景不在本自动刷新范围内。
> - **权益转赠一经完成，原持有人手里的码立即全部作废**，新持有人用自己的码——**不存在「送出去了还能自己用」**。

> 修订说明（2026-06-07）：客人端是被需求点名的订台入口且订台需定金，但原页面范围只有票务"预定入口"，缺酒吧卡座/桌台订台与定金支付页，导致"App/小程序订台+定金"无法落地（finding webmobile-6）。故下表新增"酒吧订台"与"订台定金支付"两页；定金金额单位为分(整数)（基准 D1）。

## 8.5 员工私人手机 App P0

员工私人手机 App 安装在员工自有手机上，目的是让员工完成入职注册、身份辅助绑定、通知查看，以及后台按设备类型放权的低风险功能。它不是现场作业端。

| 页面 | P0 内容 |
|---|---|
| 注册提交 | 姓名、手机号、所属主体、岗位申请、必要身份证明摘要 |
| 设备凭证绑定 | 安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹作为可信标识并绑定员工，支持先解绑旧设备凭证再绑定新设备 |
| 设备检测 | 设备指纹、系统版本、Root/调试检测结果 |
| 审批状态 | 待审核、已通过、已驳回、需复核、已失效 |
| 通知中心 | 收发工作通知、查看制度通知和排班提醒 |
| 状态查看 | 查看个人岗位、职级、权限摘要、对应公司工作手机状态 |
| 公司公告 | 手机上看公告，一键确认已读 |
| 我的工单 | 只看派给自己的工单和处理进度；另一并列出「待我提单确认」的单（本人承接提单确认的关联设备报修单，待验收或已验收、尚未确认），带「确认」「退回返工」两个按钮（第十二批操作员裁决 2026-10-21 第 13 条）；员工在后台手工建的关联设备报修单，提单员工（在后台点「新建工单」的当前登录员工）就是承接人，同样在此确认或退回（第 15 条）；本人即该单维修人的，只作派给自己的单列出、不标待我提单确认（BSM「物业服务」运营细则：责任人本人负责此次维修时由物业主管指定其他人员） |
| 帮客人订位 | 查酒吧空位，替客人预订卡座/散台（BYOD 一期已实现 `listBarTableAvailability`）。员工代订**不收定金**；**必填最晚到店时间**；业绩以**客人实际到店消费**为准记到经手员工名下——此处的经手员工即**帮该客人预订的那个人**，**业绩记名人与销售提成归属人始终是同一人**，**代录订台等经手操作只留痕、不记业绩**，**销售归属改派后业绩随提成归属一起改**；**业绩仅为统计与考核口径，本身不产生任何应发的钱——产生钱的只有销售提成、服务费、小费三条**（2026-08-19 补，依据 BSM「帮客人订位」条现文；DEC-R8-97-15）；客人超过最晚到店时间未到店的自动释放台位并记一笔**爽约**到经手员工名下，**爽约的代订不计业绩**；经手员工**爽约率超过后台配置的上限**（业务参数，按酒吧可配）自动停用其代订权限，由**店长复核后恢复**（BSM「帮客人订位」条·条目名主锚点；BSM 已于 2026-08-04 更正为“爽约”，DEC-R6-15） |
| 查看考勤 | 本人考勤月历查看；上下班打卡只在公司工作手机上做（决策台账 V0.24 裁决「只在工作手机打卡」） |

边界：

> 修订说明（2026-06-07）：统一私人手机 App 审批禁项措辞，避免"现场审批"被误读为可做远程管理审批（finding webmobile-8）；并将"NFC 不匹配"改为"设备凭证不匹配"以对齐基准 D8（私人手机身份=设备公钥/不可逆设备指纹，废止读取手机本机 NFC 唯一标识方案）。

- 私人手机 App 不允许核销门票或权益。
- 私人手机 App 不允许点酒、放行、结算、补录。
- 私人手机 App **不承接任何现场作业类审批/复核**；管理类待办审批由移动管理端承载，私人手机 App 不承载审批/复核动作。
- Root、调试环境、设备指纹变化或设备凭证不匹配时，App 自动失效并进入后台复核；能被手机端检测出的异常环境均按不可信处理。

- 私人手机 App **不承担现场核销、点单、放行、结算、补录**（原表述“不承担现场业务操作”过宽，已按 PGM「受控的十类终端」条 / BSM「帮客人订位」条 收窄）；**「帮客人订位」是后台按设备类型放权的低风险允许项**，不属于现场作业动作。

### 10.1 最低消费无法达成时的处置流程

## 12. 页面设计原则

- 管理后台适合表格、筛选、详情、复核和批量处理。
- Web 前端强调非编辑状态查看和跨端信息展示。
- 商户侧强调数据边界，只展示本商户信息。
- 现场作业端和员工工作手机强调少步骤、大按钮、强状态、弱配置。
- 正式发放的受管员工工作手机只能使用企业微信承接工作沟通，不能安装非预装软件，不能访问非白名单网站。
- 员工私人手机 App 只做注册、通知、状态查看、设备凭证绑定（设备公钥/不可逆设备指纹，基准 D8）和低风险功能（公告、我的工单、帮客人订位、查看考勤、请假、查自己薪资、主管排班、只看我的服务收入等），**不承担现场核销、点单、放行、结算、补录**。
- 工作人员平板 App 只强调酒吧点酒、最低消费校验、支付引导和员工责任绑定。
- 触摸屏一体机强调固定点位自助操作：售票型的一体机由授权服务人员辅助购票/订单查询（不提供取票），非售票型的一体机扫码、订台、吧台买酒、权益领取、游乐状态查看都要少步骤、大按钮、清楚反馈。
- 移动管理端强调待办和异常，不做复杂配置。
- 客人 App/小程序只展示客人能理解的票、权益、预定、会员积分、兑换和凭证，不展示后台术语。

## 13. P0 验收标准

- 每个核心角色都有明确入口。
- 现场作业端能完成上岗、设备、核销、补录和交接。
- 管理后台能完成配置、查询、复核、对账和看板。
- Web 前端能查看移动端和业务关键信息，并允许少量业务确认动作。
- 商户侧有数据边界，不越权看平台全局。
- 工作人员平板 App 只做酒吧点酒下单，并绑定酒吧、卡座、员工、班次、设备、点位。
- 工作人员平板 App 和工作手机动作必须能在后台查到订单销售归属、卡座服务责任、加单人、送达人、服务换人和异常第一处理人。
- 平板点酒下单必须校验最低消费，支持客人扫码支付和扫描客人付款码支付；现金/POS 机支付需要进入酒吧账单和财务对账。
- 员工工作手机能扫码核销门票、赠饮和其他权益，并能校验二维码签名、防伪串码、有效期、动态码刷新状态（刷新间隔由后台统一设置、以 5 秒为单位可调、最长 60 秒）和哈希，截图无效且必须在线核验。
- 员工工作手机能展示企业微信每日会话上传状态；正式受管设备能拦截非预装软件和非白名单网站访问，未受管设备至少要发现并上报异常，不能作为正式发放状态。
- 管理后台能查看企业微信基础质检、违规命中和复核状态。
- 员工私人手机 App 能完成注册、设备凭证（设备公钥/不可逆设备指纹）绑定、换机解绑重绑、Root/设备异常检测和审批状态查看，但不能核销、点单、放行、结算、补录或审批/复核。
- 售票型触摸屏一体机能由授权服务人员使用官方票务策略完成到店辅助购票、订单查询、库存锁定、聚合支付、出票和防伪动态二维码生成，且**不提供取票功能与取票入口**；非售票型触摸屏一体机能展示客人可领取的酒水、礼物和权益，并能形成需定金的订台订单、吧台买酒订单、支付引导、游乐设施状态查看和定期检修记录；检修由工程师填写，检修单位按供应商记录，主管确认后才能恢复营业。
- 各终端启动或进入业务模块前必须读取后台开关状态；开关关闭时不能执行对应端或模块动作，并记录访问尝试。

### 15A.1 设备生命周期状态机（实现依据：spec §10，V107）

能力描述：把 §6「设备领用/归还/异常上报」与 §11「设备管控」落到**设备全生命周期状态机**，补齐维修/挂失/报废流转，消除"设备只有领用归还、异常无终态"。经 grep 实证落于 `TerminalDeviceService`（repair/lost/scrap）+ 迁移 `V107__device_lifecycle_and_mdm_disposition.sql`。

业务规则（设备状态机）：
- **生命周期状态**：在 bound（已绑定/在用）/ returned（已归还）/ unbound / disabled 基础上补 **repair（维修中）/ lost（挂失）/ scrapped（报废，终态）**，对应 ENUM「设备状态」的维修中 / 挂失 / 报废；第十八批 K 段第 96 条（V584）再补 **pending_return（待归还）/ archived（已归档，终态）**，对应 ENUM「设备状态」的待归还 / 归档。
- 流转：bound ⇄ repair（送修/修复）；bound → lost；lost → scrapped（报废终态）；lost → returned／bound（找回：后台挂失行「找回」，原因必填，与修好的设备同一去路——工作手机、平板、一体机、扫码设备回待领用、之后照常领用，入场三道环节设备与其他现场设备回在用；found 不再停留）——按第十八批裁决 20（2026-10-29 操作员选「回待领用（推荐）」，记于决策台账、不改 HTML）。bound → pending_return（员工停岗、离职生效时名下在用的工作手机、平板、一体机、扫码设备自动转入，第十八批裁决 23「停岗离职转待归还」）→ returned（后台收回办归还，不形成下班记录）或 lost（收不回挂失）；pending_return 拒领用。scrapped → archived（后台归档，原因必填，不可恢复、不可领用，第十八批裁决 24「报废后可归档」）。
- 命名映射（产品语言 ↔ 落地代码，以代码为准）：在用→bound、领出/归还→returned、报废→scrapped；纳管侧另有 retired（纳管退役，语义不同于设备报废 scrapped）。

验收口径要点（细化 G/W/T 见 spec §10）：
- bound 设备送修 → repair；bound 设备挂失 → lost；lost 设备报废 → scrapped（终态）。

### 15A.4 设备商户归属管理（设备台账归属写入面，2026-08-01）

能力描述：设备的「所属商户」是**设备台账的管理属性**——记录这台设备当前放在哪家商户，用于台账查询、挪店留痕与设备盘点。**它不是核销归属的判定依据**：权益在哪家酒吧核销由权益本身的归属决定（ENUM「核销顺序」条 / BSM 同条：一张通票覆盖几家酒吧就为每一家各发一份独立的入场权益与赠酒权益，一家一份、互不占用，A 酒吧的赠酒只能在 A 酒吧核销）。本节把这条归属从"没人能配"补成完整写入面：后台「终端设备」页（ADM-TER-002，`/admin/terminals/devices`）+ 归属设置/更换/解除端点。经 grep 实证落于 `TerminalDeviceService.updateDeviceMerchant` + `TerminalDeviceController`（`GET /api/v1/terminals/devices`、`PUT /api/v1/terminals/devices/{id}/merchant`）+ 前端 `TerminalDevicesPage`，零迁移（`merchant_id` 列 V007/V010 已存在）。

业务规则：
- **设备挪店是常规动作，改的是设备台账上"这台设备现在在谁那里"**：设置/更换/解除所属商户一律**理由必填**，审计事件带改绑前后商户与理由，`terminal_device_status_events`（append-only，V140 防篡改）同步留痕一条——谁改的、从谁改到谁、为什么，盘点对不上时可回溯。
- **目标商户校验**：必须存在且未归档（`MERCHANT_NOT_FOUND` / `MERCHANT_ARCHIVED` 拒绝），杜绝把设备挂到退场商户头上。
- **解除归属**：解除后该设备在台账上不归属任何商户；归属未变化拒重复提交（`DEVICE_MERCHANT_UNCHANGED`）。
- **终态设备（报废）不可改归属**（`DEVICE_TERMINAL_STATUS`），与 §15A.1 生命周期终态口径一致。
- **权限从严**：沿用设备治理权限 `terminal.device.lifecycle`（高危·需审批·仅平台管理员）；台账读沿用终端模块视图权限 `terminal.switch.view`。
- **登记一步到位**：设备登记（bind）可直接携 `merchant_id`（同口径校验），免运营跑两趟；**归还后复领用不传商户时保留既有归属**——修复此前 bind upsert 把已配归属静默抹成 null 的缺陷。

验收口径要点：
- 设备绑 A 商户 → 台账归属显示 A；改绑到 B 商户 → 台账归属显示 B，改绑留痕各一条（审计 + 状态事件）。
- 理由为空拒；商户不存在/已归档拒；报废设备拒；无 `terminal.device.lifecycle` 权限 403。
- 归还再领用（不传商户）后归属不变。

## 16. 本版结论

终端页面 P0 的核心是“不同角色只看到自己该看的，只做自己该做的”。后台负责治理、合同准入、复核、企业微信质检、设备管控和终端开关，Web 前端负责查看和少量业务确认，商户侧在授权业务范围内全开放并负责本商户经营，员工私人手机 App 只负责注册、通知、状态、设备凭证绑定和低风险功能（公告、我的工单、帮客人订位、查看考勤、请假、查自己薪资、主管排班、只看我的服务收入等）且不承担现场核销、点单、放行、结算、补录，现场端和员工工作手机负责防伪核对后的门票/权益核销、企业微信工作沟通、库房和交接扫码及一线动作，工作人员平板 App 负责员工协助酒吧点酒下单，售票型触摸屏一体机负责授权服务人员辅助到店购票/订单查询（不提供取票），非售票型触摸屏一体机负责权益展示/领取、订台下单、吧台买酒下单、游乐设施状态查看和定期检修记录，移动端负责主管待办，客人 App/小程序负责官方购票、预定、查询、防伪二维码、会员积分和兑换展示。所有端都受后台开关控制，为后续酒吧和乐园 SaaS 化预留。
