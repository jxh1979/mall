> 2026-07-04 逻辑一致性修订：§10 平板端补「最低消费无法达成」时的状态转移（补收/豁免/POS·现金补齐，均留痕，平板端仅发起前两类）；§9.2 明确 Web/商户侧退款权属（款进公司统一账户，Web 与商户侧不可独立退款，只能财务/管理后台审批，服务员无退款权、仅确认收款）。

## 1. 文档定位

本文档按角色和使用场景拆解终端与页面。它回答“谁通过什么入口使用系统、每个入口负责什么、哪些页面 P0 必须有、手机和平板如何承担现场展示和操作”。

本文档不是视觉稿，不写前端实现，不写路由和组件。它只定义产品页面范围、角色入口和终端职责。

## 2. 终端分层

| 终端 | 使用对象 | P0 作用 |
|---|---|---|
| 管理后台 | 管理层、运营、财务、系统管理员 | 管配置、看总览、处理异常、复核和对账 |
| Web 前端 | 管理层、运营、财务、业务人员、部分商户人员 | 展示移动端和后台关键信息，支持非编辑状态查看 |
| 商户侧页面 | 餐饮/零售/酒吧/其他商户 | 看本商户经营数据、核对差异、处理本商户事项 |
| 现场作业端/员工工作手机 | 现场员工、服务员、游乐入口员工、巡检、检票员 | 上岗、领设备、核销门票、核销权益、放行、补录、巡检 |
| 工作人员平板 App | 酒吧现场工作人员、服务员 | 只做酒吧点酒下单，绑定酒吧和卡座/桌台，并自动记录销售归属和服务责任 |
| 触摸屏一体机 | 客人、现场工作人员 | 分售票型和非售票型两种模式：售票型支持授权服务人员辅助到店客人购票/取票/订单查询；非售票型承担扫码展示/领取权益、订台下单、吧台买酒下单、游乐设施状态查看和授权状态检查 |
| 移动管理端 | 管理层、运营主管 | 看关键指标、待办、异常审批 |
| 客人购票 App/小程序 | 游客/会员 | 官方购票、预定、查询信息、展示验票二维码、会员积分和兑换 |
| 员工私人手机 App | 员工自有手机 | 注册、通知、状态查看、设备凭证绑定、Root/设备异常检测；不做现场业务操作 |

所有终端都必须支持后台开关控制。开关可按全局、综合体项目、商户、业务系统、模块、设备和版本配置；关闭后该端或模块不可用，打开后仍继续校验登录、设备可信、商户范围、角色权限、单一功能权限和数据权限。

> 修订说明（2026-06-07）：本表的产品口径终端与基准 D5《终端类型枚举（10 端权威表）》映射如下（编码以 `terminal_capability_switches.terminal_type` 10 端为唯一权威）：管理后台/Web 前端 → `web`；商户侧页面 → `merchant_portal`（商户侧 Web 门户）；商户侧若开放移动端 → `merchant_app`；现场作业端/员工工作手机 → `staff_work_phone`；工作人员平板 App → `tablet`；触摸屏一体机 → `kiosk`；移动管理端 → `mobile_admin`；客人 App → `app`、小程序 → `miniapp`；员工私人手机 App → `staff_private_phone`。不得用"员工端"笼统合并工作手机与私人手机，不得漏"移动管理端"（依据 D5、govfam-3）。
> 口径补充（2026-06-10）：触摸屏一体机不新增第 11 种终端，仍统一归属 `terminal_type=kiosk`；通过 `kiosk_mode=ticketing/service` 或模块开关区分“售票型一体机”和“非售票型一体机”。售票型一体机是授权服务人员辅助售票、取票和查单的固定点位渠道，不能被实现为工作人员平板代客购票；非售票型一体机不得显示购票入口。

## 5. 商户侧页面 P0

商户侧页面只看本商户授权业务范围，不看平台全局和其他商户。商户侧在授权业务范围内全开放；酒吧系统和游乐/乐园系统需要具备独立系统能力，未来可分别演进为独立酒吧 SaaS 和独立乐园 SaaS。

| 页面 | P0 内容 |
|---|---|
| 商户首页 | 本商户今日收入、订单、核销、待处理差异 |
| 商户资料 | 基础档案、合同摘要、空间和联系人 |

## 8. 客人购票 App/小程序 P0

## 8.5 员工私人手机 App P0

员工私人手机 App 安装在员工自有手机上，目的是让员工完成入职注册、身份辅助绑定和通知查看。它不是现场作业端。

| 页面 | P0 内容 |
|---|---|
| 注册提交 | 姓名、手机号、所属主体、岗位申请、必要身份证明摘要 |
| 设备凭证绑定 | 安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹作为可信标识并绑定员工，支持先解绑旧设备凭证再绑定新设备 |
| 设备检测 | 设备指纹、系统版本、Root/调试检测结果 |
| 审批状态 | 待审核、已通过、已驳回、需复核、已失效 |
| 通知中心 | 收发工作通知、查看制度通知和排班提醒 |
| 状态查看 | 查看个人岗位、职级、权限摘要、对应公司工作手机状态 |

边界：

> 修订说明（2026-06-07）：统一私人手机 App 审批禁项措辞，避免"现场审批"被误读为可做远程管理审批（finding webmobile-8）；并将"NFC 不匹配"改为"设备凭证不匹配"以对齐基准 D8（私人手机身份=设备公钥/不可逆设备指纹，废止读取手机本机 NFC 唯一标识方案）。

- 私人手机 App 不允许核销门票或权益。
- 私人手机 App 不允许点酒、放行、结算、补录。
- 私人手机 App **不承接任何现场作业类审批/复核**；管理类待办审批由移动管理端承载，私人手机 App 不承载审批/复核动作。
- Root、调试环境、设备指纹变化或设备凭证不匹配时，App 自动失效并进入后台复核；能被手机端检测出的异常环境均按不可信处理。
- 员工进入办公区或现场作业区后，私人手机需要寄存；寄存柜流动使用、先到先选、离开拿走，现场操作只认公司发放工作手机。

## 9. Web 前端 P0

Web 前端是轻量展示和只读查看入口，主要用于把移动端和业务系统中的关键信息通过浏览器展示给业务人员。

| 页面 | P0 内容 |
|---|---|
| Web 首页 | 综合体概览、今日经营、公告、快捷入口 |
| 信息查询 | 票务、权益、订单、核销、酒吧、游乐、商户摘要 |
| 经营看板只读 | 收入、客流、核销、异常、商户表现 |
| 票务信息只读 | 票种、通票、权益状态、核销记录 |
| 酒吧信息只读 | 桌台状态、账单摘要、赠饮核销 |
| 游乐信息只读 | 项目开放、场次容量、核销状态 |
| 异常与待办只读 | 待复核、风险提示、差异摘要 |
| 我的权限范围 | 当前用户可查看的数据范围 |

### 9.1 Web P0 业务确认动作清单（白名单，逐条）

> 修订说明（2026-06-07）：原文仅复述"Web 前端 P0 允许少量业务确认动作"口号，未界定范围/对象/前后状态/审批/留痕，编码无依据（finding webmobile-1）。此处补"白名单逐条清单"+"排除清单"，并与 `terminal-display-layer-spec-v0.2.md` 对齐。金额一律以"分(整数)"为单位（基准 D1）。

Web 前端 P0 只承载**轻量业务确认类**动作（确认/标记/已读类，不改变核心业务对象的资金或核销结果），不承载任何现场作业类操作。每条确认动作都必须：登录态+数据权限校验、记录确认人/时间/意见、写入事件中心留痕。

| 确认动作 | 触发页面 | 操作对象 | 前→后状态 | 是否二次确认/审批 | 是否写留痕 |
|---|---|---|---|---|---|
| 对账差异确认 | 异常与待办只读 / 信息查询（对账） | 对账差异记录 | 待确认 → 已确认（差异处置不在此处，仅"我已核对此差异"标记） | 二次确认，不触发审批 | 是（`reconciliation.diff_confirmed`） |
| 异常待办标记已读 | 异常与待办只读 | 异常/待办条目 | 未读 → 已读 | 否 | 是（`todo.marked_read`） |
| 结算单查看确认 | 信息查询（结算依据只读） | 结算单 | 未确认查看 → 已确认查看（"我已查看本期结算单"，不等于商户侧结算确认/争议） | 二次确认 | 是（`settlement_bill.view_confirmed`） |

说明：

- 上述三条为 P0 白名单全集；新增确认动作须先评审并补入本清单，未在白名单内的动作 Web 端一律不出现确认按钮。
- "确认"不等于"处置/审批/撤销"。涉及业务对象状态实质变更（核销撤销、放行、退款、结算单确认/争议）的动作仍只在管理后台、商户侧或移动管理端完成，Web 端只跳转过去（见 F2 流程图）。
- 每条确认动作的字段口径见 `terminal-display-layer-spec-v0.2.md` 字段章节（确认动作类型/确认状态/确认意见）。

### 9.2 Web P0 排除清单（不可执行）

> 修订说明（2026-06-07）：明确 Web 端"非范围"边界，防止把现场作业类动作误放到 Web（finding webmobile-1/2）。

Web 前端 P0 **不可**执行以下动作（如需操作，跳转到对应端）：

- 不可核销门票/权益（只在员工工作手机/一体机/现场端）。
- 不可点酒/下单（只在工作人员平板 App / 一体机）。
- 不可放行/人工放行（只在现场端/管理后台审批）。
- 不可退款/冲正/改期。**退款权属口径**：客人所付款项（含酒吧服务费/点酒收款）进入公司统一账户代收，非直付服务员或商户；Web 前端与商户侧均**不可独立发起退款**，退款/冲正只能由**财务或管理后台按权限审批**执行；现场服务员**无退款权**，仅负责 mark-paid 确认收款。
- 不可做平台或业务配置（票种、权益、核销规则、桌台、商户、权限等只在管理后台）。
- 不可做结算单确认/争议发起（商户侧）与异常处置/复核审批（管理后台/移动管理端）。

### 10.1 最低消费无法达成时的处置流程

> 2026-07-04 逻辑一致性修订：原文只写「未达最低消费不可提交订单」，缺「客人最终仍无法/不愿补足最低消费」时的收尾路径。此处补齐三条状态转移，均须留痕。

关台/结账时若卡座实际消费仍低于最低消费要求，按以下三条之一收尾，每条都写留痕（谁操作、卡座、差额、原因、审批人）：

| 处置方式 | 说明 | 谁可发起 | 是否审批 | 留痕 |
|---|---|---|---|---|
| 补收差额 | 按最低消费与实际消费的差额补收，客人扫码/现金/POS 补齐 | 平板端服务员可发起 | 否 | 是（补收记录 + 收款事件） |
| 豁免最低消费 | 经授权对本卡座豁免最低消费差额，写异常 | 平板端服务员**发起申请**，由主管/管理后台审批 | 是（后台审批 + 写异常留痕） | 是 |
| POS·现金补齐 | 差额通过 POS 机或现金由授权员工收取并记入账单 | 平板端服务员可发起 | 否 | 是（支付方式、经办员工、对账依据） |

- **平板端仅可发起前两类**（补收差额、豁免申请）与 POS·现金补齐的账单记入；**豁免的最终确认走后台审批**（平板不自决豁免）。
- 三条处置的金额一律以「分(整数)」为单位（基准 D1）；豁免必写原因并进入异常/复核留痕。

## 12. 页面设计原则

- 管理后台适合表格、筛选、详情、复核和批量处理。
- Web 前端强调非编辑状态查看和跨端信息展示。
- 商户侧强调数据边界，只展示本商户信息。
- 现场作业端和员工工作手机强调少步骤、大按钮、强状态、弱配置。
- 正式发放的受管员工工作手机只能使用企业微信承接工作沟通，不能安装非预装软件，不能访问非白名单网站。
- 员工私人手机 App 只做注册、通知、状态查看和设备凭证绑定（设备公钥/不可逆设备指纹，基准 D8），不能承接任何现场业务操作。
- 工作人员平板 App 只强调酒吧点酒、最低消费校验、支付引导和员工责任绑定。
- 触摸屏一体机强调固定点位自助操作：售票型的一体机由授权服务人员辅助购票/取票/订单查询，非售票型的一体机扫码、订台、吧台买酒、权益领取、游乐状态查看都要少步骤、大按钮、清楚反馈。
- 移动管理端强调待办和异常，不做复杂配置。
- 客人 App/小程序只展示客人能理解的票、权益、预定、会员积分、兑换和凭证，不展示后台术语。

## 13. P0 验收标准

- 每个核心角色都有明确入口。
- 现场作业端能完成上岗、设备、核销、补录和交接。
- 管理后台能完成配置、查询、复核、对账和看板。
- Web 前端能查看移动端和业务关键信息，并允许少量业务确认动作。
- 商户侧有数据边界，不越权看平台全局。
- 工作人员平板 App 只做酒吧点酒下单，并绑定酒吧、卡座、员工、班次、设备、点位。
- 工作人员平板 App 和工作手机动作必须能在后台查到订单销售归属、卡座服务责任、加单人、送达人、服务换人和异常第一处理人。
- 平板点酒下单必须校验最低消费，支持客人扫码支付和扫描客人付款码支付；现金/POS 机支付需要进入酒吧账单和财务对账。
- 员工工作手机能扫码核销门票、赠饮和其他权益，并能校验二维码签名、防伪串码、有效期、30 秒/60 秒刷新状态和哈希，截图无效且必须在线核验。
- 员工工作手机能展示企业微信每日会话上传状态；正式受管设备能拦截非预装软件和非白名单网站访问，未受管设备至少要发现并上报异常，不能作为正式发放状态。
- 管理后台能查看企业微信基础质检、违规命中和复核状态。
- 员工私人手机 App 能完成注册、设备凭证（设备公钥/不可逆设备指纹）绑定、换机解绑重绑、Root/设备异常检测和审批状态查看，但不能核销、点单、放行、结算、补录或审批/复核。
- 售票型触摸屏一体机能由授权服务人员使用官方票务策略完成到店辅助购票、取票、订单查询、库存锁定、聚合支付、出票和防伪二维码生成；非售票型触摸屏一体机能展示客人可领取的酒水、礼物和权益，并能形成需定金的订台订单、吧台买酒订单、支付引导、游乐设施状态查看和定期检修记录；检修由工程师填写，检修单位按供应商记录，主管确认后才能恢复营业。
- 各终端启动或进入业务模块前必须读取后台开关状态；开关关闭时不能执行对应端或模块动作，并记录访问尝试。
- 酒水和可追责物品从出库到送达必须通过二维码、设备事件或订单确认形成交接留痕。
- 移动管理端能处理待办和异常复核。
- 客人 App/小程序能同步购票、预定/订台、查询信息、展示 30 秒/60 秒刷新的在线防伪验票二维码，并展示会员积分摘要和等级；积分明细、礼物列表、兑换发起和兑换记录进入 P1。
- 客人 App 和小程序的订单、票、权益、二维码状态一致。

## 15. 已确认规则和后续细化事项

已确认：

1. 官方购票入口 App、小程序和第三方平台是主路径；售票型一体机只用于少量到店服务场景，由授权服务人员辅助购票，工作人员平板不得代客购票。
2. 美团、大众点评、抖音 P0 只做团购购票、订单回流、核销和对账。
3. 积分兑换礼物需要扣减库存；客人端积分兑换独立页面和接口进入 P1，不作为 P0 验收项。
4. 平板点酒优先线上支付，同时必须允许现金和 POS 机支付并进入酒吧账单和对账。
5. 员工私人手机 App 以设备公钥/不可逆设备指纹（存于设备 Keystore）作为可信标识；换机必须先解绑旧设备凭证再绑定新设备；Root/异常环境失效复核。（依基准 D8 修订：废止"读取手机本机 NFC 唯一标识"方案）
6. 私人手机寄存柜流动使用、先到先选、离开拿走。
7. 一体机分售票型和非售票型：售票型支持授权服务人员辅助到店客人购票/取票/订单查询；非售票型承担权益展示/领取、订台、吧台买酒和游乐状态服务。售票型一体机绑定酒吧门口/前台时只能售卖本酒吧单店门票，不能售卖综合体通票。一体机订台需要定金，吧台买酒优先线上支付，现金和 POS 机必须进入账单和日结。
8. 票务二维码按票种设置有效期，30 秒或 60 秒刷新，截图无效，必须在线核验。
9. 工作手机预装软件清单和网站白名单由后台维护，通过 Android Enterprise / Android Management API + 商业 MDM 阻止违规访问并留痕。
10. Web 前端 P0 允许少量业务确认动作。
11. 会员积分、等级成长和兑换规则由后台定义。
12. 酒吧最低消费按时间、卡座和位置配置，不按人数。
13. 企业微信工作会话留存期限可配置（非永久），到期归档/销毁/匿名化（按 A7/合规C3、data-risk §11.5）；不脱敏原文仅限最小授权 + 审批的取证/质检场景，普通展示按权限脱敏，查看写审计。<!-- 修订说明（2026-06-08 三轮收口）：原"永久保存"为已确认 P0 规则断言，与 A7/C3 可配置留存相反，就地改正；2026-06-08 复核补充不脱敏原文的最小授权边界。依据 finding residual-scan-3、A7/C3 -->
14. 一体机游乐设施检修由工程师填写，检修单位作为供应商记录，主管确认后才能恢复营业。

16. 商户侧在授权业务范围内全开放，不看平台全局和其他商户。
17. 酒吧系统和游乐/乐园系统保留未来独立 SaaS 能力。
18. 所有端都必须有开关接口，支持按全局、综合体项目、商户、业务系统、模块、设备和版本控制。
19. 酒水和可追责物品从库房出库、订单核验、机器人或人工配送、后厨接收、服务员送达客人，都必须扫码或通过设备事件留痕。
20. 订单获取、销售归属、卡座服务、异常第一处理人、转派升级、复核关闭、退款、免单、调账都必须留痕，并尽量由终端动作自动生成。
21. 移动管理端 P0 只处理高风险待办和主管复核，不做全后台；普通配置和复杂编辑仍在 Web 后台完成。

后续细化：

无。后续仅根据现场主管使用情况调整移动端待办范围。

## 15A. 设备生命周期、集团多项目视图与端侧开关默认口径补充 `文档goalP1(2026-06-20)`

> 本节为产品语言的能力描述 + 业务规则 + 验收口径要点；可开发 + 可验收的权威细节（迁移号、operationId、`x-permission`、事件常量、状态机、G/W/T）以 `docs/v099-v124-feature-implementation-and-acceptance-spec-v0.1.md` 为准（本节对应该文第 10 项「MDM 门控 + 设备生命周期」、第 18 项「集团多项目视图」，端侧开关见下文 grep 实证）。先经 grep 后端/迁移核实功能真实存在再写。

### 15A.1 设备生命周期状态机（权威：spec §10，V107）

能力描述：把 §6「设备领用/归还/异常上报」与 §11「设备管控/远程锁定」落到**设备全生命周期状态机**，补齐维修/挂失/找回/报废/锁定流转，消除"设备只有领用归还、异常无终态"。经 grep 实证落于 `TerminalDeviceService`（repair/lost/found/scrap）+ `MdmService`/`MdmController`（违规处置 device_blocked 联动）+ 迁移 `V107__device_lifecycle_and_mdm_disposition.sql`。

业务规则（设备状态机）：
- **生命周期状态**：在 bound（已绑定/在用）/ returned（已归还）/ unbound / disabled 基础上补 **repair（维修中）/ lost（挂失）/ found（找回）/ scrapped（报废，终态）/ blocked（锁定/封禁，终态）**。
- 流转：bound ⇄ repair（送修/修复）；bound → lost → found（找回后可再 bound）/ → scrapped（报废终态）；违规处置 device_blocked → blocked（终态，联动设备纳管状态 blocked + **撤销设备凭证**）。
- 命名映射（产品语言 ↔ 落地代码，以代码为准）：在用→bound、领出/归还→returned、报废→scrapped；纳管侧另有 retired（纳管退役，语义不同于设备报废 scrapped）。
- MDM 违规处置闭环：服务端检测违规 → 处置（device_blocked = 封禁设备 + 撤销凭证 + 纳管状态 blocked；dismissed = 误报驳回），处置为高危需审批 + 留痕。

验收口径要点（细化 G/W/T 见 spec §10）：
- bound 设备送修 → repair；挂失设备找回 → found（可再 bound）。
- 检出违规设备 → 处置 device_blocked → 设备纳管状态 blocked + 凭证撤销 + 留痕。

### 15A.2 集团多项目视图 group-overview（权威：spec §18，V115）

能力描述：补 §4 管理后台「首页总览/看板分析」之上的**集团跨项目（多综合体）聚合只读视图**，供集团/平台管理员跨 project 看汇总指标。经 grep 实证落于 `AnalyticsController` 的 `getGroupOverview` 端点 + `AnalyticsRepository`（ETL 产出 `segment_type='project'` 维度快照）+ 迁移 `V115__analytics_group_overview_permission.sql`（仅补权限）。

业务规则：
- 跨项目只读聚合：看板聚合任务（ETL）在 platform/merchant 维度之外，按 project_id 维补 `segment_type='project'` 行（与既有维度并存不互破）；group-overview 返回平台口径 rollup 的指标合计。
- 权限隔离：`analytics.group.view`（跨商户/跨项目聚合）仅平台/集团管理员，与 `analytics.dashboard.view`（看板下钻，可下放商户）区分；商户角色无 group.view 被拒。
- 单综合体（单 project）退化：project 维 rollup = 平台口径合计，不破坏既有 platform/merchant 行。

验收口径要点（细化 G/W/T 见 spec §18）：
- 看板聚合任务已运行 → 查 group-overview → 返回 project/platform 口径指标合计；商户角色无权限被拒。

### 15A.3 端侧能力开关「默认关」口径：摄像头扫码（V097）/ 平板端侧（V098）`文档goalP1(2026-06-20)`

能力描述：承接 §2 末「所有终端都必须支持后台开关控制」与 §15 已确认第 18 条「所有端都必须有开关接口」，明确两组新端侧能力**默认关闭、后台可配、仅预留接口**的口径，避免被误读为"已默认可用"。经 grep 实证落于迁移 `V097__camera_scan_and_native_client_switches.sql` 与 `V098__device_keystore_and_tablet_switches.sql`（显式 seed `enabled=FALSE` 行）。

业务规则（默认关 + 代偿）：
- **摄像头扫码（V097，`terminal.camera_scan.enabled`，默认关）**：现场摄像头扫码硬件能力默认关闭；关闭时端侧用**文本输入凭证代偿**（手输票号/会员码/设备码），不阻断现场核销作业。
- **微信小程序 / 原生 App 客户端（V097，`customer.native_client.enabled`，默认关）**：默认关闭；关闭时走 **Web/H5 客户端代偿**（H5/Web 完成下单/查询/核销）。
- **平板终端 + 设备 Keystore 凭证绑定（V098，默认关）**：平板端侧能力与设备 Keystore 凭证绑定统一做成"后台能力开关（默认关、后台可配、仅预留接口）"；与 §8.5 私人手机设备公钥/不可逆设备指纹（基准 D8）口径一致。
- 三组均 `terminal_type='*'`（跨端通配）、`scope_type='global'`，后台开启才生效；开启/关闭受开关管理权限控制并留痕。

验收口径要点：
- 默认部署：camera_scan / native_client / 平板端侧开关均为关，端侧走文本输入 / Web 代偿，不影响 P0 现场作业。
- 后台开启对应开关 → 能力生效；关闭 → 端侧回落代偿路径。

> 待业务确认（terminal）：①设备生命周期是否需把 repair/lost/found/scrapped/blocked 状态补入 §6「设备领用」页面与 §13 验收作为正式 P0 项；②集团多项目视图 group-overview 是否需补入 §4 管理后台 / §7 移动管理端页面清单；③三组端侧开关（摄像头扫码/原生客户端/平板）的默认关口径已据 V097/V098 实证，后续若任一能力转正式实现需回当前有效入口与 OpenAPI 契约确认。

## 16. 本版结论

终端页面 P0 的核心是“不同角色只看到自己该看的，只做自己该做的”。后台负责治理、合同准入、复核、企业微信质检、设备管控和终端开关，Web 前端负责查看和少量业务确认，商户侧在授权业务范围内全开放并负责本商户经营，员工私人手机 App 只负责注册、通知、状态和设备凭证绑定，现场端和员工工作手机负责防伪核对后的门票/权益核销、企业微信工作沟通、库房和交接扫码及一线动作，工作人员平板 App 负责员工协助酒吧点酒下单，售票型触摸屏一体机负责授权服务人员辅助到店购票/取票/订单查询，非售票型触摸屏一体机负责权益展示/领取、订台下单、吧台买酒下单、游乐设施状态查看和定期检修记录，移动端负责主管待办，客人 App/小程序负责官方购票、预定、查询、防伪二维码、会员积分和兑换展示。所有端都受后台开关控制，为后续酒吧和乐园 SaaS 化预留。
