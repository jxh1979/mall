## 1. 业务背景与目标

综合体内部分业态（典型：酒吧）采用「**公司参股 + 主理人经营**」模式（2026-08-04 F5 按 BSM「部分业态（典型是酒吧）采用『公司参股 + 主理人经营』」条 改写，另见 PGM「酒吧股权、牌照、场地和资金必须分别记录」条）：

- **股权**：酒吧股权由**娱乐平台公司、主理人及其他真实股东**按**工商登记和出资协议**持有；**80%／20% 只作为新酒吧的默认建议值**，**实际以每家酒吧的工商登记比例为准**。
- **牌照**：酒吧经营牌照**登记在实际经营法律主体名下**——娱乐平台公司不因持股自动成为牌照主体。
- **场地**：由**具备物业权利的城市项目公司按有效合同提供**。
- **资金**：由**实际出资或贷款主体按真实资金关系记录**。
- **不得**把上述四项笼统写成「平台出场地、牌照和资金占 80%」——牌照、场地、资金分别归属不同的真实主体，与持股比例不是一回事。

持股分红把**每期净利润按真实持股关系**进行计算、审批和发放，并保留完整依据。此前钱都收进来了（结算流水、收入台账都有），但没有「定期把经营成果按真实持股比例分给股东」的机制——分红靠线下手工算，算错了没底账，主理人也看不到依据。

目标：分红变成一个**周期性、可审计、可追溯**的系统作业：期末算出该分多少 → 财务审阅、最高权限审批 →
生成应付款项走现有付款通道 → 主理人在商户专区看到自己那份的每一步计算依据。

## 2. 已拍板口径（2026-07-18 终稿）

1. **基数 = 净利润制（方案 B）**。**权威净利润构成（2026-08-04 对齐，依据 BSM「分红基数按『净利润』算」条、DEC-R3-2026-08-04-15）**：

   ```
   净利润 = 经营收入（含税实收口径）
          − 进货成本
          − 人工成本（含薪资、销售提成、绩效、奖金与社保，并含主理人本人的报酬
                      ——主理人本人报酬由主理人与娱乐平台公司协商确定并写入合同）
          − 归集到这家店的各项费用（能耗费、物业费、租金、门票综合服务费、
                      会员系统服务费、积分发行费，及其他已在费用台账登记的对内对外费用）
          − 该期间的各项税费（含增值税、所得税及其他应由该主体承担的税费）
   ```

   **全部扣完、税后剩下的是本期经营口径净利润，不能直接替代依法可分配金额；正式分红应付形成前须满足 §6 的法定可分配额与借款清偿前置。亏损期不倒扣主理人的钱。**

   **挂起与坏账不进净利润基数（2026-08-19 补，依据 BSM“商户核销未收售价”条现文；DEC-R8-97-08）**：**挂起订单在结清前不计入分红净利润基数**，**结清后按实际结清金额计入并归属结清所在营业日**；**转坏账核销的订单不计入分红净利润基数，也不产生销售提成**；**已核销结案后又收回的款项按收回时点单独入账，不追溯重开提成**。**实现现状（第十八批 T 段 157-R3、157-R8；第十八批裁决 38「收入与出库成本都不进分红净利润」）**：挂起订单经经理确认坏账（`bar_order_suspensions.bad_debt_confirmed_at` 非空）后，未结清账单不进酒吧收入来源（157-R3）；该单出品的出库成本由计算单另列一行`cost_inventory` 正数冲回（说明「坏账订单出库成本不计入」），计算单销货成本＝期间出库成本合计 − 坏账订单出库成本（157-R8）；未转坏账的挂起单出库成本照常计入。

   > **实现现状（如实标注，待改造缺口）**：现算式为「期间收入 − 期间销货成本（V296）− 期间费用（V297，六类费用）」，与上述权威口径存在两处差距——① **未扣减该期间的各项税费**；② **人工成本口径不完整**（薪资/提成/绩效/奖金/社保与主理人本人报酬是否已全量进入 V297 费用台账未闭合）。两项均为**待改造缺口**，改造前实现结果不得反向写成业务规则。
   >
   > **改造代价（2026-08-04 F5 补，先评估再动手）**：补「税费扣减」不是加一个减号——**必须同时**：① 在 `dividend_statements` **新增税费扣减列**（该期间各项税费，含增值税、所得税等，与代扣个税 `tax_cent` 是**两回事**，不得混用同一列）；② **重写 `chk_ds_*` 系列净利恒等 CHECK**（`chk_ds_distributable` 及净利恒等式必须把新列纳入，否则新旧单在同一张表里恒等式互斥、无法落库）；③ 制定**存量回填策略**（V299 以来的历史单无税费列，回填 0 会让历史净利与新口径不可比——须明确「历史单不重算、只按当期口径追溯」并在单上标注口径版本）。三件事缺一不可，**不得只加列不改 CHECK**。
2. **主理人分个人 / 公司两类（V308，2026-07-19 拍板 #28）**：**个人股东**（自然人真实持股）→ 税目 =
   股息红利，按方案税率代扣（默认 20%，税率可配）；**公司股东**（法人持股）→ **不代扣个税、按约定全额发放**
   （发放单据代扣额=0）。类型落方案配置 `principal_type`，历史分红单按单内类型快照追溯。
   **（2026-08-07 同步 BSM「分红税务按发放时有效的中国税法、股东身份和交易实质处理」条、ENUM「分红税务」条现文；DEC-R8-78）** HTML 侧已恢复该分类规则，现行逐字口径为——**股东为个人股东（工商登记在册的真实股东，含主理人本人）的**，其分得的款项按「股息红利」计税，**由发放的经营主体代扣个人所得税**（**安全阈值，全平台统一可配，调整须经财务、税务、法务三审并由顶层平台公司最终确认，出厂默认 20%，须同时配置上下限**），**发放时在单据上写清代扣了多少**；**股东为公司股东的，不代扣个人所得税，按约定全额发放**。与本 PRD 既有表述的三处差异须注意：① 主语由「主理人」扩为**股东（含主理人本人）**；② 代扣主体明确为**发放的经营主体**（覆盖参股游乐项目等非酒吧主体）；③ 税率参数**须同时配置上下限**——现 `tax_rate_bps` 只有默认值，**上下限配置为待补项**。本条只恢复业务口径，**不构成税务意见**；落地仍须走三份 HTML 明定的财务／税务／法务三审 ＋ 顶层平台公司最终确认。
3. **周期 = 原则上每半年分配一次（2026-08-04 现行 HTML 权威口径，依据 BSM「分红原则上每半年分配一次」条）**：
   - **分红原则上每半年分配一次。**
   - 若因**特殊情况需要整期暂不分红或暂缓分红**的，须由**主理人与娱乐平台公司协商一致后执行**，并**记录原因与协商结果**。
   - **周期可配**：按经营主体、按**财务对账的固定处理日期**设定（例如**一个月中的某几天**，此处仅为举例、不构成取值限制）；**【矛盾19，2026-08-06】分红周期一律取月及月的整数倍粒度（如月、季、半年、年），不使用周粒度**；**由于分红本身按半年一期分配，某笔结算从发生到实际参与分红可能跨越一个或多个季度**（2026-08-06 按 BSM 、ENUM  同步，**DEC-R8-07**；原「因此某笔结算可能跨季度才处理到」的因果接错对象——月级／周级的处理频率推不出跨季度，真正的原因是半年一期）。

## 3. 分红方案（配置层，`dividend_plans`）

- 挂在**商户**上（一个商户=一个经营标的），不挂合同：提成规则挂合同是「租户交平台」方向，
  持股分红是「平台分主理人」方向，主体是经营实体本身、不随租约换签中断。
- 字段：主理人账户（`principal_user_id`，发放走应付台账挂该账户）、主理人类型 `principal_type`
  （individual 默认 / company，见 §2.2）、平台比例 `platform_share_bps`（默认 8000）、代扣税率 `tax_rate_bps`
  （默认 2000，公司股东单强制生效 0）、周期类型 `period_type`（monthly / quarterly / semiannual 默认 / annual）、
  revenue_domains 保持现状（本批不裁定其是否可配）、`include_inventory_cost` 固定为 true、`expense_types` 固定为全量、税费固定扣除，成本／费用／税费均不得按方案关闭；~~自定义扣除项 `dividend_deduction_items`（子表，见 §5A）~~**【越权实现，生产禁用建议，见 §5A】**、
  生效起始日、业务目标状态（`draft` / `pending_approval` / `approved` / `active` / `ended` / `rejected`）、备注。

> **方案版本状态与实现缺口**：新版本先为 `draft`，提交后进入 `pending_approval`；由最高权限审批且提交人不得自审，驳回进入 `rejected`，通过进入 `approved`。`approved` 版本到生效起始日才转为 `active`，同一时点原 `active` 版本同步转为 `ended`，任何时点仍只有一个 `active`。当前 `dividend_plans.status` 及现有更新接口只支持 `active/ended` 且会原地更新，尚不能承载上述版本状态机，属于待改造缺口；改造完成前不得宣称方案版本链已实现。

> **多股东模型缺口（2026-08-04 F5 登记，待改造缺口）**：本配置层**只建模了两方**——`platform_share_bps`（平台比例）与其补数（主理人）。但 HTML 要求**按每家酒吧工商登记的真实持股比例在娱乐平台公司、主理人和其他股东之间分配**（BSM「娱乐平台公司、主理人和其他股东按每家酒吧工商登记的真实持股比例分配」条），且**引进参股游乐项目的参股方＝引进该项目的域主管公司**同样是分配对象之一。因此：
>
> - **现状**：`dividend_plans` 无股东列表子表，无法登记「其他股东」及其登记比例，也无法在算式与发放侧生成第三方股东的应付；`principal_user_id` 单账户模型只能承载一位主理人。
> - **缺口性质**：**数据模型待改造缺口**（不是配置缺省值问题）——加大 `platform_share_bps` 或改默认值都解决不了「多于两方」的分配。
> - **改造要点**：须新增「方案—股东」子表（股东主体、股东类型 individual/company、登记比例 bps、工商登记版本引用），劈分算式由「两方补数」改为「多方按 bps 分配 + 尾差归属规则」，发放侧按股东逐个挂应付；**80%／20% 只能作为新酒吧预填建议，必须以获批的工商登记版本生效，修改不得追溯已确认或已发放的分红**（BSM「娱乐平台公司、主理人和其他股东按每家酒吧工商登记的真实持股比例分配」条）。
> - **改造前边界**：现实现在只有「平台 + 主理人」两方的酒吧上结果正确；**存在第三方股东的酒吧不得用本引擎出正式单**，否则少分的那部分无处落账。

> **金额取整与守恒的既有结论只在两方模型下成立**：§5「主理人应得 = 可分配额 − 平台分成」取补数、尾差恒为 0 的论证依赖「只有两方」；改为多方按比例分配后**必然产生尾差**，须按通票分账同范式单列尾差列（参见 `settlement-rebuild-prd-v1.0.md` 尾差口径），不得沿用「尾差恒为 0」的结论。
- **一个商户同一时点只允许一个已生效方案版本**。任何方案调整均不得原地更新当前生效行：每次调整必须生成新版本，先存为草案，填写生效起始日，由最高权限审批且提交人不得自审；审批通过后进入待生效的 `approved`，到指定日期才转为 `active`，旧 `active` 同步转为 `ended` 并完整保留。**常规调整**只适用于生效日之后发生的业务，不追溯改变已发生业务、已生成单据及已确认或已发放分红。确需追溯的，只能按 BSM 全局追溯例外另行申请，写明范围和理由，经最高权限审批并逐笔记录影响金额；本批不新增该例外的产品入口。停用同样通过有生效日期的后续版本表达，不覆盖旧版本。

## 4. 期间作业（`POST /finance/dividends/statements/compute`）

- **手动触发端点**（与 V297 费用自动挂接同理由：上游费用挂接本身是手动出账，定时空跑会把不完整的
  费用基数算进正式单；预览也需要按需出）。kind=official 正式单 / preview 月度预览。
- 期间标签：季度 `2026-Q3` / 月份 `2026-07`。official 必须匹配方案周期类型；preview 仅对季度方案出
  （月度方案的正式单本身就是月度）。
- 对每个生效中方案（或指定商户）各算一张计算单；时窗=方案商户的营业日窗——商户是酒吧的按该酒吧营业日版本，
  否则按其所属综合体（无已批准版本按出厂起点 10:00；`BusinessDayResolver.start/end`，成本汇总同窗——三来源同窗才能恒等）。
- **幂等可重跑**：同期同商户同类别只允许一张未作废单（部分唯一索引）；重跑时 preview/draft/rejected
  作废（voided）重算=红字更正范式；pending_review/approved/paid 已进入审批流，跳过并回报原因。
  写路径统一幂等键+载荷指纹（同键不同载荷拒绝）。
- **周期可配 + 跨季度处理不算错（2026-07-19 核查 #34：现状已支持，无需改码）**：分红「会计期间」由方案
  `period_type`（季度 / 月度）+ 期间标签共同决定，是一个**固定的自然日窗口**；三来源金额按**各交易自身
  时间戳**（结账 `settled_at` / 退款 `refunded_at` / 售票 `created_at` / 费用月份桶）归入其所属期间，**不按作业
  运行日归集**。因此：财务对账按固定日子（**一个月中的某几天**；周粒度已按矛盾19 废止）而非每天触发时，某笔结算即便**跨季度才被
  处理到**，也只是落进其时间戳所属的那个期间——`compute` 端点**接受任意历史期间标签、任意时点触发**、幂等可
  重跑，**不存在「处理太晚 / 跨季度」的报错**。对账触发节奏是运维触发面（何时 POST compute），与会计期间窗口
  完全解耦。
- **五类最终标记闸（第十八批 V 段第 159 条 159-R5、159-R6，2026-11-06；ENUM 第 190 行「非最终快照的数据一律不得进入结算、分红、正式提成计算和对账关账」；DEC-R8-45）**：`DividendService.runCompute` 在周期匹配之后、作废旧单之前，调 `FinanceService.nonFinalDays` 判方案商户检查单位（酒吧按该店，其他商户按所属综合体；建档前的营业日不计）的五类最终标记。kind=official 判期间首日到末日每个营业日，有未标齐的该方案不出单、记跳过（原因「以下营业日数据尚未标记为最终，不能出正式分红单：」后列「yyyy-MM-dd 单位名：类别原词」，最多 10 行），旧草稿不作废；登记依法可分配金额后的重算同闸，被跳过时 409 `DIVIDEND_STATE_INVALID` 带此原因。kind=preview 只判该月最后一个营业日，未齐记跳过（原因「该月最后一个营业日（yyyy-MM-dd）的五类数据尚未全部标记为最终，不得生成预览：」后列明细）；月度预览另由标记接口自动生成，见 §9。跳过不是错误码。


## 4A. 跨周期维度补充（P2，2026-07-28）

闭合 BSM-0411 `cross_period`（与 §4 期间作业一致，明示验收）：

1. **正式周期 vs 预览**：默认半年正式 + 月度预览（亦可选月、季、年）；切换为月度正式时，预览规则按方案配置，不得两套正式单重叠同一官方期间。
2. **跨季/跨月重算**：已 `approved/paid` 的正式单不因后期费用调整自动重算；需冲销/作废后按权限重开期间作业。  
3. **关账锁**：正式非 preview 作业锁定费用侧期间后，跨周期补录费用不得无声进入已锁定分红基数；须走解锁/冲销策略（见既有 period-lock）。  
4. **比例/税率及其他钱类方案调整**：必须新建草案版本，由最高权限审批且提交人不得自审，并指定生效起始日；`approved` 到生效日才转 `active`，旧 `active` 同步 `ended`。常规调整只影响生效日之后发生的业务，历史单继续按单内固化版本追溯，不得原地修改当前生效版本；确需追溯仅按 BSM 全局例外另行申请、说明范围与理由、经最高权限审批并逐笔记录影响金额，本批不新增入口。
5. **权限/证据**：跨期冲销、重算、解锁须最高权限审批 + 全链路审计；配置权限不自动取得该权力。

> **酒吧来源闭环（V0.04）**：同一订单可以使用多个渠道，累计足额后才确认整单商品收入。小费及应发员工的服务费是代收款，不计入营业收入；服务费只把原经营日最新有效月结的扣留金额计入，不能叠加历次累计快照。商品退款以真实应付足额付款与批准分项为准，服务费退款通过原期月结差额处理。未收齐订单暂不计收入；服务费尚未月结、来源事实变化或已退金额缺少真实分项时，不允许确认分红。BI 仅展示已确认部分及待办原因，不能代替最终出账。本条不关闭下述票务收入和其他既有缺口。

> **期间收入取数缺口（2026-08-04 F5 登记，待改造缺口）**：上式 ticket 侧取 `issued_entitlements.allocated_revenue_cent`。该列属**已废弃的「发放即分摊」模型**——在权益发放时刻就把票款分摊到各权益上，与现行「**按核销结算**」不同源、不同时点：
>
> - **口径冲突**：发放即分摊在**未核销**时也已确认收入，而现行结算口径要求**核销才结算**（未核销款按票种所属经营域另行处理）。两者对同一张票给出的期间归属和金额都可能不同，导致分红基数与结算台账**对不上**。
> - **改造后基数**：ticket 侧应改取 **`settlement_transactions` 的已核销口径**（与结算域同一事实源、同一时窗谓词），使「三来源同窗恒等」在核销口径下重新成立。
> - **历史单处理**：**历史分红单不重算**——已 approved/paid 的单按单内快照追溯（§5 快照冻结），只在改造生效期之后的新期间使用核销口径，并在单上标注基数口径版本，避免新旧口径混在同一序列里无从分辨。
> - **改造前边界**：本条只登记缺口，**不得据现实现把「发放即分摊」反向写成业务规则**，也不得据本条认为已改造。
> - **已关闭（V0.05，FS-015）**：ticket 侧改取已确认月度分账单的已核销结算额（与结算域同一事实源）；退票只发生在完全未核销的票上、从未计入结算额，不再另扣；FS-013 后单一酒吧门票综合服务费按售出月单独计收，分红按费用行 `expense_ticket_service_fee` 扣减；期间内有月份分账单未确认（缺单或超池待特批 draft）时不得确认正式分红（409 `TICKET_SETTLEMENT_PENDING`），月度预览只计已确认月份并在明细写明。历史单按单内快照不重算，口径见 `revenue_ticket` 行说明。


### 5B. 关停结算、公司清算、支付主体与付账日（依据 BSM「酒吧关闭须完成关停结算」条及 F01）

- **门店关停与公司法定清算分开**：酒吧关闭须完成关停结算，依法核清本次分红、已算未发分红和发放保护线待释放款项。进入公司法定清算的，按依法确认的清算方案和清偿顺序处理，不得提前向股东分配剩余财产。已确认应付及待释款项的法律性质与处理由财务、法务核实，不因关店自动核销，也不一概改为剩余财产分配；相关款项须按核实结果处理并留痕后才能结案。
  > **释放衔接**：依法确认须发放或释放的款项仍须完成对应支付，不能仅将单据标为已结清。释放时核验原合法分配依据及本次支付依据，不重复扣除已在原核定金额中扣除的事项。§9 原有释放机制的实现缺口须另行验证和完成；本次文字同步不代表已经实现支付出口或完成真实公司清算。V0.05（FS-014）：手动与定时释放均核验原分红单已登记依法可分配金额及分配决议，缺失 409 `DIVIDEND_LEGAL_BASIS_MISSING`；本次支付依据随实际付款登记的凭证附件与银行流水。
- **支付主体与代扣义务人**：分红**由该酒吧公司自己从其对公账户支付**给主理人与其他股东，并由**该公司作为个人所得税的代扣代缴义务人**；不得走别家代付（会变成公司间往来，税务定性完全不同）。
  > **与配置层矛盾（2026-08-04 F5 交叉标注）**：本条要求支付给「主理人**与其他股东**」，而 §3 配置层**只建模两方**（`platform_share_bps` + 单个 `principal_user_id`），**无法登记其他股东、也无法为其生成应付**。存在第三方股东的酒吧，本条无法执行——见 §3「多股东模型缺口」。
- **发放走应付款项，落在三个付账日之一**（每月 5 / 15 / 25 日，遇**法定节假日或非银行工作日顺延至下一个银行工作日**（矛盾16，2026-08-06 统一口径）；见 `finance-settlement-product-prd-v0.1.md` §4B），**具体哪一个由该公司在分红周期配置中指定**。
- **一个周期一旦关账，该已核算月份的费用就不能再改**，避免已经发出去的分红被事后改动（现行期间关账锁见 §9）。

在 V303 默认三项扣除（亏损结转 / 欠款抵扣 / 发放保护线）之外，方案可**按需新增任意条自定义扣除项**，
配置模型可扩展（新增来源=加枚举值 + 纯算式分支，非硬编码固定项数）：

- **配置**（`dividend_deduction_items` 子表，挂方案；随方案配置整表替换，历史单靠算式明细快照留痕不受影响）：
  - `name` 名称；`source_type` 金额来源（`fixed` 固定额 → `amount_cent`；`ratio` 比例 → `ratio_bps` ×
    `ratio_basis` 基数，基数 ∈ {`net_profit` 净利润 / `revenue` 营收}）；`enabled` 开关；`sort_order` 扣减顺序。
  - 后台经方案新建/修改请求携带 `customDeductions` 列表整表落地（缺省=不改现值，空列表=清空）。
- **落账口径**（不破坏 V299 净利/劈分/税恒等，也不破坏 V303「各扣除」语义）：自定义扣除与欠款抵扣/留存
  同属「税后应得的各扣除」，在欠款抵扣之后、留存之前，对 (税后应得 − 欠款抵扣) 余额**逐项按 `sort_order`
  封顶扣减**（不透支），合计冻结在 `custom_deduction_cent`，逐项落 `custom_deduction` 算式明细行留痕。
- **发放额恒等改写**：`payout_cent = principal_net_cent − arrears_offset_cent − custom_deduction_cent −
  reserve_withheld_cent`（由 `chk_ds_payout_identity` 重写硬保证；`chk_ds_custom_deduction_range` 保证
  `0 ≤ custom_deduction_cent ≤ principal_net − arrears`，`chk_ds_payout_nonneg` 保证实发非负）。留存保护线
  的比例/固定额作用基数随之变为「自定义扣除后余额」（无自定义项时逐分等于 V303 现状）。
- **诚实边界**：自定义扣除额由平台留存（隐式=少发即留），本轮**不单独挂应付/应收台账**；如需指定去向
  （如计入某科目/挂某方应付）另立项。

## 6. 审阅审批与发放（状态机）

```
compute → draft（正式单）/ preview（月预览，只可看，不可提交/审批/发放）
draft → pending_review（提交审阅）→ approved（审批通过）→ paid（标记发放）
pending_review → rejected（驳回，理由必填）→ 修正数据后重算（旧单 voided + 新 draft）
preview / draft / rejected → voided（重跑或废弃时作废，红字更正范式）
approved / paid → voided（经办人发起作废／冲销、最高权限审批且发起人不得自审；须先完成相应冲销，见下）
```

> **职责分离**：平台财务负责出单、审阅与发起发放；持最高权限的管理者负责最终审批。平台管理员、平台 scope 或 finance.dividend.manage 均不自动等同最高权限。任何提交人均不得审批自己提交的分红单。

> **法定金额与决议前置**：所有公司股东及个人股东分红在进入 `approved` 并形成正式应付前，均须由财务引用专业财税核算结果及公司有效分配决议，核清依法可分配金额、本次分配金额及未重复扣除的依据；本次分配不得超过该金额。未完成核定或缺少有效决议的，不得审批通过、挂分红应付或待释放应付。法定弥亏、公积要求不受经营扣除开关影响；本项与税务输入及借款清偿前置并列，不新增业务状态，不用操作权限审批代替公司有效分配决议。

> **税务法定输入闸**：个人股东分红在缺少足以确定正式税额的有效法定输入时，可以生成正式业务 `draft` 并进入 `pending_review`；`draft / pending_review` 主状态不变，最终税额保持未定，并在界面与单据明确显示“待税务确认”。如展示估算值，必须标注“非正式估算，不可申报、不可发放”，且不得写入 final tax（最终税额）。税务闸本身不得阻断 `draft → pending_review`；最终 `pending_review → approved` 才硬校验并冻结发放时有效国家法律、纳税主体身份、交易实质、正式申报规则、专业财税软件回传、主管税务机关可核验结果，或经授权人员手工填写并通过审批的可核验数据，以及规则版本、有效期、正式来源和申报／计算凭证；任一必需输入缺失均不得审批通过。未依法确定正式税额的单不得创建分红应付。未形成合规应付的，不得标记 `paid`；未保存依法确定的正式税额及支付时实际代扣记录的，也不得标记 `paid`。实际申报与实际缴税结果只在对应事实发生后追加关联，禁止预填未来结果；平台保存或使用这些数据不等于已完成正式申报或会计入账。公司股东本分红代扣项为 0 的分类依据与支付时实际代扣 0 的记录同样随单留痕，其自身依法纳税事项不在本公式内。

**`voided`（已作废）态及其进入条件（2026-08-04 F5 补——原状态机漏列该态，但 §4 幂等重跑、§4A 跨周期重算、§9 关账解锁均已依赖它）**：

| 从哪个态进入 voided | 经办发起与审批 | 前置条件 |
|---|---|---|
| `preview` / `draft` / `rejected` | 有 `finance.dividend.manage` 的操作人；`compute` 重跑时由系统自动作废 | 无资金影响，直接作废并重算（红字更正范式） |
| `approved`（已审批未发放） | **经逐项授予相应作废／冲销经办权限的人发起，最高权限审批，发起人不得自审**；普通平台管理员、平台 scope 或 finance.dividend.manage 均不自动取得完整经办＋审批权 | **必须先冲销该单已挂的应付**：`ar_ap_items` 中 `source_type='dividend_payout'` 与 `source_type='dividend_reserve_withheld'` 两笔（source_id=本单 id）**均须先冲销**；存在已部分付款的应付时不得作废，须先走付款冲正 |
| `paid`（已发放） | **经逐项授予相应作废／跨期冲销经办权限的人发起，最高权限审批，发起人不得自审**；普通平台管理员、平台 scope 或 finance.dividend.manage 均不自动取得完整经办＋审批权 | **必须先冲销应付并冲正实际付款**；已实际打款的资金差额须有对应的追回或补付方案随单留痕。**已发放单不因后期费用调整自动重算**（§4A 第 2 条）——只能显式作废后重开期间作业 |

- **作废必填理由**，发起人、最高权限审批人、发起／审批时间、作废理由与被作废单 id 全程审计留痕；发起人不得审批自己的作废／冲销申请。
- **欠款抵扣的连带处置**：该单若已在审批时对主理人本人对相应法律主体的欠款执行过抵扣，作废时必须同步冲销该抵扣，否则该主理人对应欠款余额会被错误减少。商户经营主体或其他人的债务不在本分红抵扣范围内。
- **亏损结转链的连带影响**：`voided` 单**不参与**亏损结转累计（判定式不含 voided，天然回滚），因此作废后续期的 `loss_carryforward_in` 自动回到上一张已结正式单——**不需要也不允许手工改累计值**。
- **期间关账锁的连带影响**：作废即解锁（§9 关账判定式不含 voided），被该单锁住的费用月份随之解锁，可再录入/冲销。
- **voided 是终态**：作废后不可恢复，只能重新 `compute` 出新单。

- **分红前置：借款清偿优先于分红（2026-08-05 R7 第三批用户裁决落地，依据 BSM「分红前置」条、ENUM「可选扣除项」条；与 `platform-governance-prd-v0.1.md` §12C「借款清偿优先于分红」同口径）**：**存在逾期未还借款的一律不得提交分红方案**——`draft → pending_review` 提交时校验该酒吧主体名下的**逾期未还借款**，命中即拒绝提交并回显理由；当期可分配利润**必须先偿还全部到期借款本息，剩余部分才可用于分红**；分红方案提交时须随单附**借款清偿情况**。该前置**不属于三项扣除开关，也不属于 §5A 自定义扣除项**，不受任何扣除开关配置影响，后台不得关闭。
- 持股分红的方案配置、算单、审批和发放均属于资金类高危动作，须由最高权限审批；最终审批人必须与提交人分离。finance.dividend.manage、平台 scope 和 role_platform_admin 只表示各自被明确授予的功能或范围，均不得解释为最高权限身份或最终审批权。
- **approved 时挂应付**：满足上述法定可分配额及有效决议、正式税额、借款清偿和审批前置后，净发放额 > 0 → `ar_ap_items`（direction=payable，counterparty=主理人账户，
  `source_type='dividend_payout'`，source_id=计算单 id；(direction,source_type,source_id) 部分唯一索引
  防一单重挂）。实际打款走应收应付台账既有付款确认流程；`mark-paid` 登记发放完成。
   净发放额=0 的单满足上述审批前置后归档，不挂当期净发放应付；保护线待释放款仍按其依法确认结果另行记录，不以净发放为零自动核销。
- 审计事件全程留痕（10 个 operation 各配 success/failure 事件对，见 OpenAPI x-audit-event）。

## 9. 边界与后续迭代（如实留档）

- **扣除项三开关已实现**（V303，设计稿 §5：亏损结转/欠款抵扣/发放保护线）：方案级三个可选开关，
  **现有经营公式在默认全关时逐分等于 V299 现状；该实现事实不代表已经满足法定可分配额前置**（回归由 DividendMathTests `computeAllTogglesOffEqualsLegacySplit` 抽样组合断言）。
  - **亏损结转 `loss_carryforward_enabled`**（2026-07-19 用户拍板：**累计恒结转，开关只控本期扣不扣**）：
    经营亏损累计规则保留，关闭期不清零累计；该开关仅控制经营口径扣除，不能取消法定弥亏。已经在依法可分配金额中扣除的亏损不得再作为经营扣除重复计算。
    现有实现 `applied` = 开启? min(期初累计, max(净利,0)) : 0，经营候选额 = GREATEST(净利 − `applied`, 0)；该候选额不是正式法定可分配金额，须按 §5/§6 核定与审批前置承接；
    `after` = **恒** 期初累计 − applied + max(−净利,0)（关闭期把老累计+本期新亏损带下去）。累计**不另建可变台账**——
    以「已审批/已发放（approved/paid）的正式计算单」自身快照的 `loss_carryforward_after_cent` 逐期结转（`priorLossCarryforwardCent`
    **恒**取 period_start 之前最近一张已结正式单，与本期开关无关），approved/paid 单即账本：draft/preview 不计（幂等，重算稳定）、voided 天然回滚。
    本期 in/applied/after 三值冻结在单上，结转链恒等由 `chk_ds_lcf_applied`（随开关）/ `chk_ds_lcf_after`（无条件累计式）DB CHECK 硬保证。
    **累计更新时点**=审批通过（approve）——同 compute 幂等（draft 重算读的是上一张已结单，不受本期 draft 影响）。
    存量单以 `after = GREATEST(−净利,0)` 回填满足无条件 CHECK（V303 前无结转链，首个开启期从最近一张已结单 after 起接续，历史多期真累计不回溯——设计边界）。
  - **欠款抵扣 `arrears_offset_enabled`**：主理人税后应得按有效协议，先抵其本人对相应法律主体尚未结清的欠款，抵完剩余才发。债务人必须是本笔分红的主理人本人，债权人必须是协议对应的法律主体；酒吧商户公司、其他股东或任何第三人的欠款不得并入。
    计算时只汇总符合上述“主理人本人 + 相应债权法律主体”的未清欠款，并快照抵扣额 = min(税后应得, 合格未清欠款合计)，逐项保留债务人与债权主体依据。审批时若合格欠款余额已变化，不得改拿商户债务补足，须按既有快照变化规则退回重算；足额时按有效协议和既定先后顺序抵扣，剩余发放。
  - **发放保护线 `payout_floor_enabled`**（2026-07-19 用户拍板：**留存=暂扣待释放、欠主理人、非平台白拿**）：留存
    `reserve_withheld_cent` = min(抵扣后余额, max(余额×`payout_floor_bps`/10000, `payout_floor_fixed_cent`)) 本期不发放；
    **留存比例最高可至百分之百，由大股东决定**（2026-08-04 补，依据 BSM「发放保护线：按比例或固定额先留一部分不发（留存），留存比例最高可至百分之百，由大股东决定」条）；
    审批时把留存额记为**欠主理人的待释放应付**（`FinanceService.createDividendReserveWithholdingPayable`：payable, counterparty=主理人,
    source_type=`dividend_reserve_withheld`, source_id=计算单 id 一单一挂；状态沿用 pending_payment，source_type 即待释放标识）。

### 本批业务验收（2026-08-10 R13 P0 第 2 批）

1. 在 `revenue_domains` 按现状确定收入基数后，净利润必须固定减全部成本、费用与税费；不存在可关闭成本、费用、税费或租金的方案选项。`revenue_domains` 保持现状，本批不裁定其是否可配。
2. 方案调整必须生成 `draft` 新版本，提交后进入 `pending_approval`，由最高权限审批且提交人不得自审；通过后为 `approved`，到生效日起才转 `active`，旧 `active` 同步 `ended`，驳回为 `rejected`。常规调整只向后适用，当前生效行不可原地修改，旧版本完整可查；确需追溯仅按 BSM 全局例外另行申请、说明范围和理由、经最高权限审批并逐笔记录影响金额，本批不新增入口。
3. 股息红利个税不得硬编码截断或无条件 `HALF_UP`；按发放时有效国家法律、纳税主体身份、交易实质、正式申报规则、专业财税软件回传、主管税务机关可核验结果，或经授权人员手工填写并通过审批的可核验数据计算，记录规则版本、有效期、来源和申报／计算凭证。正式 `draft` 可进入 `pending_review`，两者主状态不变；正式税额未确定时在界面与单据显示“待税务确认”，估算不得写入 final tax；`pending_review → approved` 才硬校验法定输入。未形成合规应付，或未保存依法确定的正式税额及支付时实际代扣记录，任一条件不满足均不得标记 `paid`；实际申报／实际缴税结果发生后再追加，禁止预填未来结果，平台保存或使用数据不等于已完成正式申报或会计入账。平台分成、风险准备金留存比例额、自定义扣除比例原始额继续走 `MoneyRounding.bpsOf`／`HALF_UP`；自定义扣除仍是越权实现、生产禁用，准备金释放额继续向下取整，完整链保持逐分守恒。以上数据来源、状态门禁与留痕要求，是依据现行 HTML 税务处理条和 `DEC-R8-92` 作出的 PRD 产品收口，不表示用户逐项裁决了实现流程。
4. 平台财务提交、非提交人的最高权限管理者审批；普通平台管理员、manage 权限或平台 scope 均不自动取得最终审批权。`approved/paid` 作废／冲销由经逐项授权的经办人发起、最高权限审批且发起人不得自审，不要求最高权限本人亲自经办。
5. 商户公司欠 20,000 元而主理人本人无欠款时，不得从主理人 10,000 元分红中抵扣；只有主理人本人对相应法律主体的有效欠款可以抵。
