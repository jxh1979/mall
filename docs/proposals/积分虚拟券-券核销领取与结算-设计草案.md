# 设计草案：积分虚拟券 —— 券核销领取 + 结算（待立项）

> 状态：草案，待业务拍板。缘由：2026-07-08 积分兑换已改虚拟券模式（兑换只发券、不扣库存，已上 PR #100），本方案补齐"发券之后"的核销领取 + 结算闭环。

## 1. 业务模型

积分兑换 = 发一张**虚拟券**。券记录"待领取的权益"，归属某个**履约方**。客人拿券到履约方核销领取，核销时才真正扣库存/服务并结算。

**券分三类（履约方不同）：**
| 券类型 | 履约方 | 领取方式 | 结算 |
|---|---|---|---|
| ① 商户折扣券 | 某商户 / 某类商户 | 客人到商户消费时用券抵扣 | 抵扣的部分平台和商户结算 |
| ② 店内实物 / 服务 | 某商户 | 客人到店，店员核销后领实物/享服务 | 平台按内部结算价付商户 |
| ③ 平台 / 外部合作伙伴 | 平台服务台 / 外部伙伴 | 平台服务台领取；或客人到外部伙伴处核销 | 平台自营内部结转；外部伙伴需数据接口对接 |

## 2. 数据模型

- **积分券 points_voucher**（或在 customer_points_redemptions 上扩展）：id、来源兑换 redemption_id、客人 customer_id、券类型 voucher_type、履约方类型 fulfiller_type(merchant/platform/external)、履约方 fulfiller_id、权益内容 item_ref、积分成本 points_cost、结算成本 cost_amount_cent、状态 status(issued/redeemed/expired/cancelled)、有效期 expire_at、发券/核销时间。
- **券核销领取 voucher_redemption**：id、券 voucher_id、履约方、操作店员 operator_id、数量、扣库存流水 stock_movement_id、结算单 settlement_id、redeemed_at。
- **券结算台账 voucher_settlement**：id、期 period、履约方、券、积分成本、结算金额 settle_amount_cent、状态(pending/settled)。

## 3. 状态机

`发券 issued` →（客人到履约方）`核销领取 redeemed`（扣库存[实物] + 建结算 pending）→ `结算 settled`。
旁支：`过期 expired`（券到期未用）、`退券 cancelled`（返还积分）。

## 4. 结算口径

- 平台从积分池兑出券，承担"积分成本"；履约方提供实物/服务，平台按**内部结算价**与其结算。
- ① 商户折扣券：客人用券抵扣，商户少收部分由平台补（或积分成本平台全担）。
- ② 店内实物/服务：商户提供货/服务，平台按内部结算价付商户。
- ③ 平台/外部：平台自营内部结转；外部伙伴按对账结算。
- 挂靠现有内部结算体系（与通票、物业费同框架）。

## 5. 接口

- 客人端：兑换（已有→发券）、我的券列表、券二维码。
- **店员端：扫券核销领取**（POST /vouchers/{id}/redeem）——此处由**有商户范围的店员**扣库存（天然避开客人无商户范围的老崩溃点）+ 建结算。
- 平台：券结算月结、外部伙伴对账。
- 外部伙伴：核销回调 + 对账接口。

## 6. 与现有系统衔接
复用 customer_points_redemptions（兑换=发券，已落地）、inventoryService.createTypedStockMovement（核销时店员端扣库存）、内部结算体系。

## 7. 分期实施建议
- **P1**：券核销领取闭环（店员扫券→扣库存→标记 redeemed），先打通"发券→领取"，不含结算。
- **P2**：券结算台账（平台↔商户内部结算）。
- **P3**：外部伙伴数据接口 + 对账。

## 8. 决策与剩余开放问题
**已定**：①②③**三类券都做**；与库存跨主体流转两方向**并行推进**。
**剩余待你拍板（我给了推荐，可确认或调整）**：
1. 券有效期？过期券积分退不退？→ 推荐**有有效期（如兑换起 90 天），过期不退**（与存酒/票一致）。
2. 商户折扣券的抵扣成本谁承担？→ 推荐**平台承担积分成本，商户按内部结算价收平台补差**。
3. 券能否转赠他人（类似存酒转让）？→ 推荐**支持转赠**（复用存酒转让的手机号加密范式）。
4. 外部伙伴核销是"实时接口"还是"对账文件"？→ 推荐**P3 先做对账文件，实时接口按伙伴能力再接**。
