## 1. 文档定位

本文档用于重新拆解“综合体管理系统”的平台治理层产品需求。

本 PRD 承接本会话已确认的 Product Design brief：综合体管理系统不是单点票务、酒吧或游乐系统，而是一个统一管理平台。平台治理层负责先回答四个基础问题：

- 谁在综合体内经营、工作、服务或接入系统。
- 在哪里经营、工作、服务或发生业务。
- 凭什么经营、凭什么进入系统、凭什么拥有权限。
- 谁能操作、谁能查看、谁承担责任、谁留下记录。

本文件只做产品需求拆解，不做技术方案、数据库设计、接口设计、编码任务或 UI 视觉设计。它的产出目标是为后续继续拆《页面清单》《流程图》《字段字典》《子系统 PRD》和开发任务提供清晰上层边界。

## 2. 平台治理层范围

平台治理层是综合体统一管理平台的地基层。它不直接完成票务售卖、酒吧点单、游乐核销、餐饮零售交易等业务动作，而是定义这些业务动作发生前必须存在的组织、空间、权限、责任和留痕边界。

### 2.1 P0 纳入范围

| 范围 | 产品目标 |
|---|---|
| 综合体项目管理 | 定义被管理的综合体项目主体和经营基本信息 |
| 空间/楼层/区域/点位管理 | 定义综合体物理空间、经营区域、作业点位和责任边界 |
| 业态管理 | 定义酒吧、餐饮、零售、游乐、演出传媒、其他六类经营分类（ENUM「商户业态」条六值固定，不含“服务商”、不留“等”字；“服务商接入”属合作模式而非业态） |
| 商户/运营主体管理 | 定义谁在经营、谁承担经营责任、谁拥有数据边界 |
| 合同与合作关系管理 | 定义商户凭什么经营、合作模式是什么、结算口径摘要是什么 |
| 员工/岗位/班次管理 | 定义谁在现场工作、做什么岗位、什么时间上岗 |
| 企业设备管理 | 定义公司统一管理的工作手机、平板、扫码设备等设备责任链 |
| 角色权限与数据权限 | 定义谁能看、谁能改、能操作哪个项目/商户/空间 |
| 终端开关管理 | 定义受控十一类终端（客人手机应用、客人小程序、Web 前端（业务人员，客人无网页端）、工作人员平板、员工工作手机、员工私人手机、商户网页门户、商户手机应用、触摸屏一体机、移动管理端、独立经销商 Web 门户）是否开放，开关档位为全局、综合体、商户、业务系统、模块、版本/设备、灰度；枚举以 `platform-governance-product-spec-v0.2.md`「字段字典」部分 §3.1「终端开关字段」为准 |
| 平台基础留痕 | 记录治理层关键动作，形成可追溯责任链 |

### 2.2 治理层边界原则

平台治理层管“准入”和“边界”，不替代业务经营系统。

平台治理层管“责任”和“归属”，不替代财务结算系统。

平台治理层管“权限”和“可见范围”，不替代具体业务审批流的全部细节。

平台治理层管“基础留痕”，不替代完整事件中心、视频证据中心或 AI 风控系统。

平台治理层管“终端开关”。所有端是否开放、哪些商户可用、哪些模块可用、哪些设备和版本可用，都必须由后台统一配置，终端自己不能绕过开关。

平台治理层管“业务准入”。票务、酒吧、游乐、结算、第三方接入等独立业务系统在执行关键流程前，必须先校验综合体、商户、合同、空间、员工、设备和权限是否符合基础定义；不符合时应阻断，或进入更高级别审批/审计。

平台治理层按“当前一个综合体、未来多个综合体”设计。所有商户、合同、空间、人员、设备、票务、酒吧、游乐和数据权限都必须归属到明确综合体项目。

**治理顺序（2026-08-07 补，依据 PGM「治理顺序」条；REGX-16）**：一件业务能不能做，要先经过这些判断，**顺序固定**：

1. **先看对象**——这个业务属于哪个综合体、空间、商户和业态。
2. **再看合同**——合同是否生效，是否允许这个业务、位置和结算口径。
3. **再看人员**——员工是否注册、是否审批通过、是否有当前功能权限。
4. **再看设备**——工作手机、平板、一体机或扫码设备是否受管且状态正常。
5. **最后留痕**——通过、拒绝、卡住、升级审批和放行结果都要记录。

> **与实现侧闸口链的关系**：`r5-spec-T2-T3-pre-action-gates-dev-design-20260618.md` §0 的「开关 → 准入 → 权限」闸口链是**接口拦截顺序**，本条五步是**业务判断顺序**，**两者面向不同层**，并存不冲突；实现侧不得据闸口链改写本条的业务判断顺序。

## 2A. 全局原则与七类红线（2026-08-05 R7 对齐平台治理地图）

> 本章承接 PGM 全局原则区与「审批链模型与七类红线」条。本章各条为**上位原则**，本 PRD 其他章节与各业务域 PRD 的具体规则均不得与之冲突，也不得以「后台可配」为由削弱本章任何一条。

### 2A.1 原则之间的仲裁顺序（依据 PGM「原则之间的仲裁顺序」条 / DIFF-A-047）

- 各项全局原则发生冲突时，按下列顺序仲裁：**第一位是法定要求与安全红线，第二位是证据与留痕能力，第三位是可配置**。
- **位次在前的原则优先，不得以位次在后的原则为由削弱位次在前的原则**——即「业务策略一律可配置」不得用来关闭红线校验，也不得用来关闭或缩减留痕。

### 2A.2 界面全中文（所有终端零英文，依据 PGM「全局原则 · 界面全中文（所有终端零英文）」条 / L-37 / DIFF-A-048）

- 平台所有终端——后台管理端、客人手机端、现场平板与设备端、安卓终端——展示给用户的一切文字，包括菜单、页面标题、字段名、状态、枚举取值、按钮、提示、报错、导出文件表头与内容、短信与通知、日期时间等，**必须全部为中文，不得出现任何英文**（如 active/draft 英文状态、mm/dd/yyyy 英文日期格式、英文按钮或提示）。
- **可以不用中文的只有四样，没有第五样**（闭集，L-37 `DEC-R3B-2026-08-04-05/12`）：**单据号、设备编号、二维码内容、系统内部标识符**。这四样之外，凡是展示给人看的文字一律中文，**不得以「这是标识」为由保留英文**。
- 本条为强制规则，适用平台全部终端与模块，**新增页面与功能一并遵守**。

### 2A.3 同时操作以先成功为准（并发与幂等，依据 PGM「同时操作以先成功为准」条 / DIFF-A-049）

- 两个操作同时发生冲突时，**一律以「先处理成功」的那个为准**，其余自动失效并提示（如同一份已发起转赠、尚未被领取的权益，接收人确认领取、原持有人自行核销、原持有人再转赠给另一个人三者同时发生时只认最先成功的一个；支付回调、核销、充值到账同理）。
- **同一个操作被重复提交，系统只认一次，不会因为重试就重复扣款、重复入账或重复核销**（重复点击、网络重发、渠道重复回调都只算一次）。
- 唯一的例外是下文红线⑤所列情形：**持授权 U 盘密钥的最高权限可以逐笔放行，每次只对当前这一笔生效并留痕**。
- 各业务域 PRD 中的具体幂等键定义是本原则的落地写法，**不得反过来缩小本原则的适用范围**。

### 2A.4 七类红线（不可绕过、不可关闭，依据 PGM「审批链不由发起人选择档位」条与 PGM「让特殊情况可以审批放行，但必须留下原因和责任人」条（红线不因审批而放行）** / L-31 `DEC-R3-2026-08-04-42` / DIFF-A-046）

审批链中，下列七类是红线，**任何层级的审批都不得绕过**：

| 序号 | 红线内容 | 能否开放 |
|---|---|---|
| ① | 项目坐满即不再放人进 | **连最高权限持密钥也不得开放，系统不提供开放入口** |
| ② | 当天没有做过合格巡检的设施不得开放 | **连最高权限持密钥也不得开放，系统不提供开放入口** |
| ③ | 未满 18 岁一律拒入、拒售酒 | **连最高权限持密钥也不得开放，系统不提供开放入口** |
| ④ | 看不到别的商户和别的项目的数据 | **持授权 U 盘密钥的最高权限可以逐笔开放，每次只对当前这一笔生效并留痕**（L-31） |
| ⑤ | 同一笔操作重复提交不重复生效（重复点击、网络重发、渠道重复回调都只算一次） | **持授权 U 盘密钥的最高权限可以逐笔开放，每次只能对当前这一笔放行、不得整类关闭校验** |
| ⑥ | 分出去的每一分加起来必须等于收进来的，对不上就不让过账；守恒校验不通过的当日即会显现、不得跨日，财务须立即追查（涉及的相关工作人员一同追查），必须逐笔拆解、细算重算、**一律走正向更正，不得以手工冲账的方式调平** | **持授权 U 盘密钥的最高权限可以逐笔开放，每次只能对当前这一笔放行、不得整类关闭校验** |
| ⑦ | 退款只限五种情形：票种规则明确允许、活动或场次取消、平台或履约方无法提供服务、重复扣款、法律法规要求 | **持授权 U 盘密钥的最高权限可以逐笔开放，每次只能对当前这一笔放行、不得整类关闭校验** |

- **上级审批不是万能通行证。**
- **七类校验不设关闭开关**：不得通过全局、综合体、商户、业务系统、模块、版本/设备、灰度中的任何一档关闭这七类校验。**审批不得绕过与开关不得关闭，两条并列适用。**
- 七类红线的**条目清单本身不做后台可配**，增删须先经批准写入三份 HTML（L-22 `DEC-CFG-2026-08-03-09`「业务分类定义」例外）。
- **本节与 §12 第 14A 条高危授权审批是两个不同闸口，互不替代**：
  - **14A 高危授权审批闸口**校验的是「**操作人是否有权发起这个高危动作**」（资金/核销/退款/调账/分红发放、提权或跨商户跨综合体、敏感数据、高危业务、税费规则与税费调整五类），审批通过即可发起；
  - **七类红线闸口**校验的是「**这件事本身是否被允许发生**」，**不因任何审批通过而放行**；①②③类连持密钥的最高权限也没有开放入口，④⑤⑥⑦类只能由持授权 U 盘密钥的最高权限逐笔放行并留痕。
  - 一次高危业务动作可能同时经过这两道闸口；通过 14A 审批**不代表**红线校验被豁免。

### 2A.5 跨单据统一审批模型总则（2026-08-07 补，依据 PGM「审批链不由发起人选择档位」条；REGX-18）

本条是**适用于任意单据**的通用审批模型总则；§6.5.1 的合同审批与付款确认等场景是它的**实例**，本条不改变已落地的合同审批规则。

- **审批链不由发起人选择档位**：**发起单据时只需指定该事项的最终审批人，系统按组织层级自动补全从发起人到该最终审批人之间的全部直接上级节点，逐级审批**。
- **平行线审批**：**需要平行线审批的（如法务、财务），另行指定该条线的最终审批人，该条线的层级同样由系统向下自动补全**；**每个部门或业务线须预先设定其平行审批的最低起点层级**。
- **驳回**：**任一节点驳回则整单退回起草人。**
- **通用审批时限（2026-08-19 补，依据 PGM“全平台审批通用时限”条现文；DEC-R8-97-18）**：**任一业务审批节点超过后台配置的时限（业务参数，按审批类型可配，出厂默认 3 个工作日，涉钱审批出厂默认 1 个工作日，须同时配置上下限）未处理的，系统自动提醒并升级到该节点的上一级，不得默认通过，也不得默认拒绝**；**适用于退款、免单、调账、临时权限申请、高危授权、人工补录复核及其他一切业务审批**；**已有专门时限规定的（合同审批见 §6.5.1、工单）从其规定**。
- 本总则不得用于绕过 §2A.4 的七类红线。

### 2A.6 后台配置只能承载规则，不能改变 HTML 业务口径（2026-08-07 补，依据 BSM「会员身份、成长值、等级和积分分别按已批准规则计算」条；R10-U-04）

- **会员身份、成长值、等级和积分分别按已批准规则计算，后台配置只能承载规则，不能改变三份最高解释权 HTML 的业务口径。**
- **票务规则和商户消费业态规则不得混用。**

## 3. 非范围

以下内容不属于平台治理层 P0 范围：

- 不展开票务定价、门票策略、通票权益明细和核销规则。
- 不展开酒吧点单、桌台账单、存酒、库存、库房和吧台出品细节。
- 不展开游乐项目排队、预约、场次售卖、设备巡检和事故处理细节。
- 不展开餐饮 POS、零售 POS 的真实业务流程。
- 不展开机器人调度、视频监控平台、企业微信会话质检的完整能力。
- 不做财务深度结算、自动对账、分账计算和发票管理。
- 不做 AI 分析、自动风控、经营预测和复杂绩效考核。

## 4. 角色与使用场景

| 角色 | 关注重点 | 典型场景 |
|---|---|---|
| 综合体业主/管理层 | 谁在经营、空间如何使用、风险和责任是否清晰 | 查看项目、商户、合同、空间、人员、设备和异常总览 |
| 平台运营 | 基础配置和日常治理准确性 | 维护项目、空间、业态、商户、人员、设备和状态 |
| 招商/商户管理 | 商户入驻、合同关系、合作范围 | 新增商户、录入合同、绑定经营区域、跟进到期续约 |
| 财务 | 合作模式、结算口径、合同状态和责任主体 | 查看合同摘要、商户状态、结算账户和变更留痕 |
| 系统管理员 | 账号、角色、权限、数据可见边界（三档硬隔离，不可自定义配置） | 配置平台角色、商户角色、岗位权限和临时授权 |
| 现场主管 | 当班人员、设备、点位和责任链 | 排班、确认设备领还、查看现场员工和异常 |
| 商户管理员 | 本商户资料、员工、空间、合同和权限 | 维护本商户员工，查看可经营范围和可用设备 |
| 员工 | 上岗、领设备、在授权范围内执行现场任务 | 查看自己的班次、岗位、设备、可操作区域 |
| 设备管理员 | 设备台账、流转、维修、报废和责任归属 | 入库设备、分配设备、记录领还、处理丢失损坏 |
| 外包/服务商人员 | 在授权范围内登录系统执行被指派任务，不越界 | 维保单位接修维保；安保/保洁巡检打卡、上报异常；施工/装修队进场报备、验收 |
| 审计人员 | 只读核查业务与留痕，敏感证据按审批查看/导出 | 内部稽核看本综合体全量；外部审计/监管看限定范围与期间 |

角色边界补充（2026-06-29 业务确认）：

- **外包/服务商人员**是可登录系统的角色（区别于仅作台账对象的维保单位/供应商记录）：按最小权限授予，只限本综合体、只限被指派的工单/区域/任务；典型子类含设备维保单位、安保/保洁、工程施工/装修队，可按需扩展其它外包角色。
- **审计人员**分两级：内部稽核（本综合体全量只读）与外部审计/监管（限定项目/范围/期间只读）。两级一律只读、不得修改任何业务数据；查看或导出敏感证据（财务流水、人脸识别同意、个人信息、审计事件导出）必须经审批并留痕。

### 4.1 外包供应商自助下属账号管理（需求口径，代码待落地）

> 2026-06-30 拍板（业务 HTML GOV-ACC-002「外包人员与审计人员」已同步授权外部机构自助管下属、平台设上限）。在已落地的外包角色账号（V178/179，平台直发 assignee 账号）之上，补一层供应商自助管理下属的门户口径：

- **机构父级**：外部协作机构（独立于供货供应商台账；供货供应商只作采购/对账对象、零登录账号）。维保单位若既供货又派人，机构档案仍在供应商目录、账号能力另挂一层指向它，不重复登记。
- **机构管理员账号**：机构由一个"机构管理员"登录账号（角色 OUTSOURCED_VENDOR_ADMIN，data_scope=partner_org）进入自助门户，可长期反复开通/停用本机构下属人员账号、查看下属工作完成情况；管理员只管下属，不碰业务数据。
- **下属上限**：平台管理员按机构设下属账号数上限（external_partner_orgs.max_subordinates）；机构开通下属达上限即拒。
- **范围继承（2026-06-30 Q4 拍板）**：下属账号**继承机构被授权的全部范围**（机构内人员可互换），看本机构被派的全部工单/区域，**不再细到个人 assignee**；机构范围本身仍 ≤ 平台为其设定的上限。
- **账号时效**：机构与下属账号有效期随合同周期（external_partner_orgs.valid_until），到期自动停用；供货/长期合作可设长期（valid_until 空）。
- **内部稽核例外**：内部稽核=平台员工只读角色，不挂任何机构（外部审计/监管机构才走机构模型）。

落地触点：外部协作机构主体表 + 机构-下属账号关系 + 下属上限校验 + 自助门户页 + 时效到期停用任务。

## 6. 业务流程

### 6.1 创建综合体项目

1. 平台运营创建综合体项目。
2. 录入项目名称、经营定位、地址、责任主体和负责人。
3. 设置项目初始状态。
4. 项目启用后，可继续建立空间、商户、合同、人员和设备。

输出结果：形成综合体最高管理单元。

### 6.2 建立空间与点位

1. 在项目下建立楼栋、楼层、区域。
2. 在区域下建立具体点位，如入口、酒吧区、卡座、吧台、游乐入口、库房、设备柜、摄像头点位。
3. 定义每个空间或点位的用途、容量、负责人和状态。
4. 将空间点位用于后续商户经营范围、设备绑定、岗位责任区和事件留痕。

输出结果：形成“业务发生在哪里”的空间基础。

### 6.2.1 空间业务名词与 space_type 枚举对照

业务人员所说的楼栋/楼层/铺位/公区等，当前实现统一落在 `spaces` 自引用树及 `space_type` 字段上。OpenAPI `SpaceRequest.space_type` 是当前实现枚举，不拥有高于三份业务 HTML 的解释权，对照如下：

| 业务名词（HTML / 本 PRD） | spaces.space_type | 层级与关键字段 | 说明 |
|---|---|---|---|
| 综合体项目 | 非 spaces（`projects` 表） | `spaces.project_id` 指向 | 所有空间必须归属某综合体项目 |
| 楼栋 / 商场本体 | `mall` | 树根，`parent_space_id` 为空 | 一个综合体下可有多栋，各为一条 mall |
| 楼层 | `floor` | parent=楼栋；`floor_no` 记楼层号 | |
| 商场区块 / 区域 / 公共区域 | `zone` | parent=楼层 | 区块与区域同用 zone，按 parent 层级区分；未绑定商户的 zone 即公区 |
| 铺位（正式商铺） | `shop` | parent=区块/区域 | 铺位级 P0 后置、P1 落地（见 §5 区块/铺位裁剪决策） |
| 摊位 / 快闪位 | `booth` | parent=区块/区域 | |
| 酒吧桌台点位 | `bar_table` | parent=区域 | 物理点位口径，运营桌台见酒吧域 |
| 设备 / 设施点位 | `facility` | parent=楼层/区域 | 供设备绑定 |
| 其他点位 | `other` | — | 入口、摄像头点位等未归类点位 |

字段补充：`polygon_points` 存平面图多边形，`area_square_meter` 存面积。
合同绑定：合同经营范围与铺位绑定走 contract-space scope（迁移 `V080__contract_scope_and_spaces`、`V162`；空间出租状态见 `SpaceRentalStatusRecord`，用于防止同一铺位重复出租）。

### 6.3 建立业态与经营分类

1. 平台运营维护基础业态。
2. 标记业态是否允许绑定商户、空间、合同和第三方系统。
3. 对复合业态做归类说明，避免统计口径混乱。

输出结果：形成统一经营分类和统计口径。

### 6.4 商户入驻

1. 招商/商户管理新增商户主体。
2. 录入主体资质、联系人、经营类型和责任人。
3. 绑定业态和拟经营空间。
4. 状态进入待准入。
5. 待合同生效后，进入正常经营。

输出结果：明确“谁在经营”。

### 6.5 合同生命周期：录入、生效、变更与终止审批

合同全生命周期统一为：**先信息录入（或发起变更/终止申请）→ 走可配置审批流 → 审批全部通过后才发生效力**（生效 / 变更落地 / 终止）。  
新建、到期终止、变更（含续租、退租、面积/租金/范围调整、提前终止等）**各自**使用可配置审批流，不得“录入即生效”或“到期自动无审终止/无审变更”。

#### 6.5.1 新建合同（录入 → 审批 → 生效）

1. 招商/商户管理**录入**合同基本信息（草稿，未生效）。
2. 选择合作模式：自营、租赁、联营、代运营、服务商接入或其他，共六类；选择“其他”必须填写说明，**并必须在生效前指定套用哪几项收费模板并写明理由——未指定收费模板的「其他」类合同不得生效**，该阻断为生效前置条件、不设跳过入口（2026-08-05 R7 补，依据 BSM「合作模式」条「选“其他”的合同必须在生效前指定套用哪几项收费模板并写明理由，未指定的合同不得生效」/ DIFF-A-040）。
3. 录入经营范围、期限、押金、结算口径摘要和附件等条款。
4. 草稿提交后进入**可配置审批流**，按全平台统一的审批模型执行：发起时**指定这条主线的最终审批人**（默认总经理），系统按组织层级**逐级自动补全**从起草人到该最终审批人之间的全部直接上级节点；**业务、财务、法务作为平行的相关部门线**，各指定该部门的最终审批人并同样逐级自动补全至该部门**预先设定的最低起点层级**；**主线与各条平行线全部通过合同才生效**；任一节点驳回则整单退回起草。三类流程模板的阶段数与审批岗位后台可配、可以不同。（2026-08-04 用户裁决：原「业务/财务/法务同阶段并行会签」表述按统一审批模型改写。）
4a. **审批时限（2026-08-19 补，依据 PGM「合同的新建、到期终止、变更三类各走各自的审批流程模板」条现文；本项属 DEC-R8-97-18「已有专门时限规定的从其规定」分支）**：**任一审批节点超过后台配置的时限（业务参数，按合同类型可配，出厂默认 3 个工作日）未处理的，系统自动提醒并升级到该节点的上一级，不得默认通过**；**起草人与各审批人都可以查看该单据当前卡在哪一个节点上，并可在系统内向该节点的处理人发送消息提醒**。
5. **审批全部通过后合同才生效**，并固化租金、分成、物业费、能源费、押金和违约金等关键规则快照；商户据此获得经营依据。
6. 合同核心条款摘要同步生成准入规则，供票务、酒吧、游乐、结算和第三方接入校验。
7. 后续业务动作如超出合同经营范围、空间范围、业态范围、有效期或结算口径，系统应阻断或进入更高级别审批/审计。

#### 6.5.2 合同到期 / 终止（申请 → 审批 → 终止生效）

1. 合同临近到期或需终止时，由授权角色发起**终止/到期处置申请**（信息录入：原因、结算清单、押金/欠费处理意向等）。
2. 进入**可配置审批流**（可与新建流不同模板；阶段/岗位/串并行可配）。
3. **审批全部通过后**，合同才进入**已终止/到期终止**等终态；押金退还、违约金、未结清费用等按结算清单执行（与业务 HTML 退租/到期/提前终止多级审批后自动落账口径一致）。
4. 审批未完成前，不得视为合同已合法终止，不得静默关掉经营依据。

#### 6.5.3 合同变更（申请 → 审批 → 变更或终止落地）

1. 变更发起时**录入变更内容**（类型如：续租、退租、面积变更、租金调整、经营范围变更、提前终止等；不支持转租，需先终止再重新招商——与业务 HTML 一致处保持一致）。
2. 进入**可配置审批流**（可与新建/终止使用不同模板；可配）。
3. **审批全部通过后**，变更才生效：要么落到新的合同/子合同条款快照，要么完成终止；驳回则维持原合同效力。
4. 变更与终止均须保留审批人、原因、版本/快照与审计事件。

输出结果：明确“凭什么经营、如何改约、如何收场”，并形成后续流程的准入拦截和升级审批依据。

### 6.6 商户经营范围绑定

1. 在合同或商户档案中绑定项目、空间、区域、点位。
2. 设置允许经营的业态和经营单元。
3. 确认该商户可见的数据落在**本商户档**内——**数据可见边界由项目、商户、本人三档硬隔离决定，不提供自定义配置**，此处不设范围设置项。
4. 后续票务、酒吧、游乐、餐饮零售等业务按该范围归属。

输出结果：明确“在哪里经营、经营什么”。

### 6.7 员工入职/分配岗位/排班

1. 平台或商户新增员工。
2. 绑定所属组织、岗位和联系方式。
3. 分配可操作项目、商户、区域或点位。
4. 创建班次并绑定岗位和责任区。
5. 班次生效后，员工才能在授权范围内执行现场任务。

输出结果：明确“谁在什么时间负责什么”。

### 6.8 设备入库/领用/归还/异常

1. 设备管理员录入设备台账。
2. 上岗时员工领取设备，设备绑定员工、班次和岗位。
3. 下班时归还设备并检查状态。
4. 设备损坏、丢失、未归还、异常使用时形成异常留痕。

输出结果：明确“谁拿着什么设备做了什么”。

### 6.9 员工私人手机注册与设备凭证绑定

> 修订说明（2026-06-07 收口）：本节按 D8/A6 改写——废止"读取手机本机 NFC 唯一标识"，私人手机身份改为"安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint）"；仅持久化不可逆哈希/公钥指纹，不存原始标识（PIPL 数据最小化，compliance-4/C4）。依据 finding compliance-land-9/decision-land-1、D8 条。本节同时是合规 C4"员工注册审批记录同意凭据"的引用点，见 §15。

> **两条注册路径（2026-08-05 R7 第三批用户裁决落地，依据 PGM「员工注册分两条路径」条、BSM「新员工注册分两条路径」条）**：本节 1–7 步描述的**自助注册路径只适用于公司自有员工**（本人在私人手机 App 注册、提交资料后由所属公司后台审批）；**商户员工不走自助注册**，由**商户代该员工提交注册申请**，经**对应域公司**批准后账号生效——城市项目公司、娱乐平台公司或游乐公司，按该商户所属经营域确定。**在商户档案上标注为自营的商户视同公司自有**，其员工按公司自有员工路径办理（2026-08-07/08 用户裁决：「持股超过 51% 视同公司自有」整体废除，改为按商户档案上的自营标注判定；51% 既非参数也非门槛。**商户档案的「自营」标注字段属代码轮新增待办**）。

1. 员工在私人手机上安装轻量 App。
2. 员工提交姓名、手机号、身份证明、所属组织、岗位申请、紧急联系人等注册信息。
3. App 在安装期于设备 Keystore 内生成设备公钥/不可逆设备指纹（device_key_fingerprint），并记录私人手机设备信息；仅持久化不可逆哈希/公钥指纹，不读取也不存储手机本机 NFC 唯一标识。
4. 后台审核员工信息、岗位、组织归属和设备凭证绑定关系。
5. 审核通过后生成员工账号、角色、职级和默认权限；**数据可见边界不随账号单独配置**，按项目、商户、本人三档硬隔离自动派生。


> 员工账号只经两条路径生效：商户员工由商户代该员工提交注册申请，经对应域公司批准后账号生效；公司自有员工由本人在私人手机 App 自助注册提交资料，经所属公司后台审批。在商户档案上标注为自营的商户视同公司自有，其员工按公司自有员工路径办理。不另设后台手工建账号路径，也不另设「IT 管理员」岗位。
6. 系统建立员工私人手机、设备凭证（设备公钥/设备指纹）、公司发放工作手机之间的一一对应关系。
7. 员工换手机时必须先解绑旧手机设备凭证，再绑定新手机，解绑和重绑都要留痕。
7a. **同一账号多端同时登录（2026-08-19 补，依据 BSM“同一账号允许在多台设备、多个端同时登录”条现文；DEC-R8-97-19）**：**同一账号允许在多台设备、多个端同时登录**，不设同端挤下线；**收银、核销、收款、放行等现场动作，一律按执行该动作的设备绑定与该次登录会话定位到操作人并留痕**；**长短款补足、小费归属、提成归属等责任认定按动作发生时的会话记录判定，不因账号同时在别处登录而转移**。主条与全文口径见 `operation-traceability-and-terminal-switch-prd-v0.1.md` §2.2／§2.4。
8. 私人手机 App 只开放后台按设备类型放权的低风险功能，共六项（含但不限于，PGM「同一个员工 App，装在公司设备和员工自有手机上能用的功能不一样」条为开放列举；BSM「员工私人手机 App」条另含看排班）：**公告、我的工单、帮客人订位、考勤打卡、请假、查自己薪资**；此外可收发通知、查看班次、查看审批状态和个人状态。**不允许现场核销、点单、放行、结算、补录**。（依据 PGM「同一个员工 App，装在公司设备和员工自有手机上能用的功能不一样」条「员工自有手机只开放低风险功能」、BSM「员工手机端」条）
8A. 「帮客人订位」的业务口径（依据 BSM「帮客人订位」条·条目名主锚点；BSM 已于 2026-08-04 更正为“爽约”（DEC-R6-15），两侧用词一致，原「BSM 原文写作“爬约”」的差异说明已失效并删除）：
   - 员工代客预订卡座/散台**不收定金**；
   - 代订**必须填写最晚到店时间**；
   - 业绩以**客人实际到店消费**为准，记到经手员工名下——**此处的经手员工即帮该客人预订的那个人**；
   - 客人超过最晚到店时间未到店的，系统**自动释放该台位**，并记一笔**爽约**到经手员工名下；**爽约的代订不计业绩**；
   - 经手员工的**爽约率超过后台配置的上限**（业务参数，按酒吧可配）时，**自动停用其代订权限**，由**店长复核后恢复**。
   - **业绩仅为统计与考核口径，本身不产生任何应发的钱**；**产生钱的只有销售提成、服务费、小费三条**（2026-08-19 补，依据 BSM「帮客人订位」条现文；DEC-R8-97-15，下同）；
   - **业绩记名人与销售提成归属人始终是同一人——都是帮该客人预订的那个人**；**代录订台等经手操作只留痕、不记业绩**；
   - **销售归属改派后，业绩随提成归属一起改**；**爽约的代订不计业绩，也不产生销售提成**。
9. 私人手机如检测到 Root、调试环境、设备指纹异常或更换设备未审批，App 状态失效并进入复核；能被手机端检测出的异常环境均按不可信处理。
10. 员工进入办公区或现场作业区时，私人手机必须寄存；寄存柜不固定，流动使用、先到先选、离开时全部拿走；现场只允许使用公司受管工作手机。

> 说明：工作手机通过摄像头/扫码模块读取**外部**客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。上述现场核销能力不在本节范围内，不受 D8 影响。

输出结果：明确“员工身份、私人手机、设备凭证（设备公钥/设备指纹）、公司工作手机、角色权限”的一一对应关系。

### 6.10 权限分配与数据可见边界（三档硬隔离，不可配置）

> **数据可见边界不是可配置项（2026-08-19 全平台改写，依据 PGM「集团下钻细则（已确认）」条 / PGM「KPI 可见性分层」条现文；DEC-R8-97-30、DEC-R8-98-05 用户裁决）**：**职位配置模板只决定汇总与下钻到哪一层，不是可自定义的数据范围；数据范围没有后台设置项。** 本 PRD 全文原写作「配置数据范围」「设置数据范围」的表述一律按此改写为**数据可见边界（由项目、商户、本人三档硬隔离决定，不提供自定义配置）**；表格结构与字段清单保留不变。本改写不影响**功能权限**的可配置性——可配的是「能不能用这个功能」，不可配的是「能看到哪一档数据」。


1. 系统管理员创建角色。
2. 设置角色可操作功能；**数据可见边界不在此设置**——由项目、商户、本人三档硬隔离决定，不提供自定义配置。
3. 系统管理员可创建基础权限模板，模板内预设不同岗位/职级的权限勾选；**模板只决定汇总与下钻到哪一层，不是可自定义的数据范围**。
4. 模板可以复制成多个变体，例如“普通员工”复制为“普通员工01”，复制后独立维护。
5. 对临时处理事项可发放临时权限模板，必须设置有效期或单次有效，并填写授权原因。
6. 将角色、基础模板或临时模板分配给员工或商户管理员。
7. 权限变更、收回、到期、单次消耗、失效均进入留痕。
8. 员工职级、岗位、角色和薪资口径可建立关联；职级可由后台维护为 M1-M10，并可分上、中、下。P0 记录职级/岗位/权限摘要和薪资大范围，具体薪资单独填写，完整薪资计算只留接口和摘要字段。
9. 保存岗位、职责或同一商户、同一项目范围内的所属组织变更时，系统立即按变更后的岗位权限模板重算有效权限，旧岗位或旧范围派生权限同步失效；同一商户、同一项目范围内的普通模板权限随保存立即生效，超出新模板范围的增权保持未生效，审批通过后方可生效。保存所属商户或发生跨项目变更时，旧岗位或旧范围派生权限立即失效，新范围权限每次均须先审批，审批通过后方可生效；属于既有高危权限的，不得因处于岗位模板内而免除授出前审批。在上述变更触发重算时，需保留的员工单独授权必须重新校验新范围，超出新范围则暂停并重新审批。本规则不把仅职级变化、责任范围变化或任意手工模板应用列为触发条件（DEC-R8-91）。

输出结果：明确“谁能操作、谁能查看”。

### 6.11 关键配置变更留痕

1. 对项目、空间、业态、商户、合同、员工、设备、权限等关键对象进行变更。
2. 系统记录操作人、变更时间、变更对象、变更前后摘要和原因。
3. 对高风险变更进入复核流程。
4. 留痕可供后续财务、运营、风控和管理层追溯。
5. **开关配置变更同样受本节约束（2026-08-07 补，依据 PGM「留痕与审计记录不属于可被开关关闭的模块」条；R10-U-01）**：**开关配置的每一次变更——包括模块级开关——都必须记录变更人、变更时间、变更前后的取值与影响范围**；**留痕与审计记录不属于可被开关关闭的模块**，任何层级的开关关闭都不影响留痕的写入，**被开关拒绝的访问本身同样留痕**。

输出结果：形成治理层责任链。

#### 7.8.1 平台管理员与最高权限是两个角色（2026-08-04 对齐业务系统地图/平台治理地图）

- **平台管理员**是日常运维岗位，拥有系统里全部**日常功能**权限；**平台管理员人数上限由后台配置**（业务参数，全平台统一可配）。
- 下列能力**不因“平台管理员”身份自动获得**，必须**逐项单独授予并留痕**：
  1. 资金操作（退款、调账、分红发放、税费调整）；
  2. 敏感数据查看与导出（内部结算价、成本价、分账底价、企业微信会话完整原文、客人与员工个人信息）；
  3. 删除；
  4. 最终业务审批。
- 平台管理员即使同时具备业务权限，**也不得审批自己发起的上述事项**。
- **最高权限是另一个角色，全平台只设一人，即持有授权 U 盘密钥的那个人**：凭密钥可以执行系统启动、破窗登录、手动清理留存数据等最高权限动作；其权限由**密钥的物理保管**来把关，**不再另设审批环节**。
- **新功能上线前必须先归类**：归入高危类别之一，或明确定为日常功能。定为日常功能的自动同步给平台管理员，不出现“管理员反而没权限”；**没有完成归类的一律先按高危处理**，需逐项单独授予并留痕，不得因为“还没定”就当成日常功能自动放给平台管理员。**归类结果日后要改，须重新走一次同级审批并留痕。**

#### 7.8.2 保存后按岗位模板重算（2026-08-10，DEC-R8-91）

- 保存岗位、职责或同一商户、同一项目范围内的所属组织变更时，系统立即按变更后的岗位权限模板重算有效权限，旧岗位或旧范围派生权限同步失效；同一商户、同一项目范围内的普通模板权限随保存立即生效。
- 保存所属商户或发生跨项目变更时，旧岗位或旧范围派生权限立即失效，新范围权限每次均须先审批，审批通过后方可生效；属于既有高危权限的，不得因处于岗位模板内而免除授出前审批。
- 超出新模板范围的增权保持未生效，审批通过后方可生效。
- 本规则不扩展到仅职级变化，也不扩展到任意手工模板应用；现有手工授权与高危授权审批规则不因本节放宽。

## 8. P1/P2 需求方向

### 8.1 P1 方向

- 合同审批流增强：在新建/变更/终止三类可配置审批流基础上，增强审批分析、批量待办、到期预警与续约提醒。
- 平面图点位：在空间管理中加入平面图、点位标注、商户经营区域可视化。
- 租金/分成规则深化：在合同中细化租金、保底、分成、服务费等规则摘要。
- 员工绩效基础：关联班次、设备、留痕和业务结果，形成基础绩效依据。
- 跨商户权限：支持平台人员跨商户、跨业态处理特定事项。
- 设备流转增强：支持借调、跨班次交接、设备盘点和异常工单。

### 8.2 P2 方向

- 复杂组织架构：支持集团、多项目、多公司、多品牌、多门店层级。**集团下钻已由 `group-governance-rebuild-prd-v1.0.md` 承接落地（V115 集团总览权限、V169 职位角色装配、V170 高危授权审批），不再作为本 PRD 的 P2 待办**；本 PRD 仅保留“所有对象必须带 `project_id` 归属”这一治理要求。
- 设备 MDM/应用管控深化：P0 已拍板采用 Android Enterprise / Android Management API + 商业 MDM，由平台 IT 选型、采购、配置和运维；后台维护预装软件清单和网站白名单，商业 MDM 执行系统级阻断和合规状态回传。P0 后继续增强定位、批量远程锁定和工作模式。
- 自动风险提示：合同到期、资质过期、异常留痕频发、设备异常频发自动提示。
- 空间经营分析：按区域、楼层、业态、商户做经营表现对比。
- 治理质量分析：分析权限变更、人工补录、设备异常、合同风险等治理质量。

## 12. 已确认规则和后续细化事项

已确认：

1. 当前先按一个综合体落地，但所有对象必须带综合体项目归属，未来可扩展多综合体。
2. 员工私人手机 App 安装期在设备 Keystore 内生成设备公钥/不可逆设备指纹（device_key_fingerprint）作为唯一可信标识并绑定员工；废止"读取手机本机 NFC 唯一标识"方案（D8/A6，2026-06-07 收口，finding compliance-land-9/decision-land-1）。工作手机通过摄像头/扫码模块读取外部客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。
3. 员工换手机必须先解绑旧手机设备凭证，再绑定新手机。
4. Root/调试/设备异常以手机端可检测能力为准，异常时 App 失效并进入后台复核。
5. 私人手机寄存柜不固定，流动使用，先到先选，离开时全部拿走。
6. 职级可按 M1-M10，并可分上、中、下；职级只绑定薪资大范围，具体薪资单独填写。
7. 工作手机预装软件清单和网站白名单由后台维护，通过 Android Enterprise / Android Management API + 商业 MDM 阻止违规访问并留痕。
8. 合同或基础定义违规时，所有流程必须先卡住，但允许按后台配置的更高级审核层级放行。> 现状/目标（2026-06-18 收口，R5，本期 P0）：准入闸口（超范围→卡住→升级→放行）须在票务/酒吧/游乐/结算业务动作前内嵌校验；当前 `SupervisorReviewService.evaluate` 为孤立评估接口，业务域动作前尚未调用——目标为动作前强制校验。> 两个闸口相互独立（2026-07-04 澄清）：**准入闸口**校验的是「业务动作是否在合同/空间/资质允许范围内」（domain=合同/空间/资质准入），**高危权限审批闸口**校验的是「操作人是否有权发起此高危动作」（domain=操作人权限，即 group-governance §3 的 requires_approval 授权审批）。二者都以 `supervisor_review` 为统一审批载体、都可升级放行，但触发条件和 domain 不同、互不替代：一次高危业务动作可能同时经过「操作人有没有权」与「业务在不在准入范围」两道校验。本条以下逐域切入点只描述**准入闸口**。
> 准入校验逐域切入点（2026-06-18 D2 逐域细化，本期 P0）：在上述总述基础上逐域明确强制校验插入位置，业务系统执行关键动作前必须先调用准入闸口（统一走 `supervisor_review`，不再引入 `admission_audits`/`contract_admission_rules` 旧表）；任一域校验不通过→阻断动作并写留痕→按上一级、上两级或最高权限升级审批→放行落 `supervisor_review_decisions`：
>   - 票务：下单前 + 出票前两处内嵌校验（超合同、超经营范围、资质过期则卡住，升级审批通过后放行）；校验不通过→阻断并写留痕→按上一级、上两级或最高权限升级审批→放行落 `supervisor_review_decisions`。
>   - 酒吧：开台前 + 点酒/结算前两处内嵌校验（超合同、超经营范围、资质过期则卡住，升级审批通过后放行）；校验不通过→阻断并写留痕→按上一级、上两级或最高权限升级审批→放行落 `supervisor_review_decisions`。
>   - 游乐：入场核销前内嵌校验（超合同、超经营范围、资质过期则卡住，升级审批通过后放行）；校验不通过→阻断并写留痕→按上一级、上两级或最高权限升级审批→放行落 `supervisor_review_decisions`。
>   - 结算：日结/结算依据生成前内嵌校验（超合同、超经营范围、资质过期则卡住，升级审批通过后放行）；校验不通过→阻断并写留痕→按上一级、上两级或最高权限升级审批→放行落 `supervisor_review_decisions`。
9. 升级放行层级为上一级、上两级或最高权限三档，按组织汇报链解析，不折算职级档位，不设指定角色档。最高权限是持有授权 U 盘密钥的那一个人。放行原因、审批人、审批层级和证据必须留痕。口径见 `platform-governance-product-spec-v0.2.md`「字段字典」部分 §8.1。> 修订说明（2026-06-18 收口，R5）：准入审计/放行统一落 `supervisor_review`（`supervisor_review_decisions`，V057），作废 `admission_audits` / `contract_admission_rules` 两表；审批层级不再以 `admission_audits.approval_level` 字段承接，改为按组织汇报链解析、不折算职级档位，落 `supervisor_review_decisions`，与放行原因、审批人、证据一并留痕，口径以 `platform-governance-product-spec-v0.2.md` 顶部 R5 标注与 2026-06-18 业务裁决为准。
10. 权限按单一功能最小颗粒度配置，一个单一功能对应一个权限点，例如票务核销、查看卡座预定状态。

12. 权限点首批由平台统一预置，实施阶段允许边配置边补充。

14. 员工最终权限按“角色权限 + 基础模板授权 + 有效临时模板授权 + 员工单独授予 - 员工/模板显式拒绝”计算，显式拒绝优先级最高。
> **（2026-07-20 安全修复 AUD-011，补记于第 14 条）权限模板应用不是高危授权审批的例外**：`applyPermissionTemplate` 现与角色/岗位/临时授权走同一政策引擎 `requireGrantApprovalIfNeeded`——模板含任一 `requires_approval` 权限时，经模板入口批量应用一律 fail-closed 拒绝（`GRANT_REQUIRES_APPROVAL` 403），不得绕过职责分离/主管复核。高风险授权须改走 `applyGrant → reviewGrant` 主管复核流（该流按权限快照建待审请求、批准后再原子应用）；模板入口对高风险直接拒绝、无待审窗口，故审批期间模板内容变化亦无从偷换。

1. 同一空间 P0 默认一个主经营对象；如确需多个商户共享经营，必须通过空间授权范围、合同条款、责任主体和结算口径显式绑定，不得默认共享。
2. 一个商户在同一有效主体绑定下只能选择一个标准业态；需要经营其他业态时，应建立独立且可审计的经营主体或绑定关系，不得在同一商户记录上多选业态。
3. 合作模式固定为自营、租赁、联营、代运营、服务商接入、其他六类；“其他”用于前五类无法覆盖的特殊合作，必须备注说明。
4. 合同新建、到期终止、变更三类事项各自走可配置审批流；均须审批通过后才发生效力（生效/终止/变更落地），并全程留痕。
5. 员工必须绑定平台主体、商户主体或外包/服务商主体之一；临时工和外包人员允许存在，但必须有有效期限、责任主体、权限范围和告知/同意留痕。
6. 班次 P0 只作为责任留痕、设备领用和现场权限校验条件，不直接替代员工功能权限；是否在班次中可操作由“员工权限 + 终端开关”共同判断。
7. 工作手机、平板、一体机等受管设备必须领用/归还留痕；非现场或低风险岗位可不领设备，但不能执行现场核销、库存、收款等受控动作。
8. 设备异常必须进入主管复核。
9. 高风险权限、财务权限、退款/免单/调账、敏感证据查看、开放平台密钥、主体绑定关系变更必须二次确认或审批。
10. 主体绑定、合同生效/终止、准入放行、设备异常、高风险财务调整、敏感证据查看、权限提升必须进入待复核状态。
11. 平台管理层治理总览第一屏看合同/主体异常、待复核权限、设备异常、准入阻断、应收应付逾期和高风险事件；第二屏看商户表现、空间使用和集团/项目汇总。
12. 集团下钻口径以本节**已确认第 15 条**为准：已由 `group-governance-rebuild-prd-v1.0.md` 承接落地（V115 集团总览权限、V169 职位角色装配、V170 高危授权审批），不再记为本 PRD 的 P2 待办；本 PRD 仅保留“所有对象必须带 `project_id` 归属、跨项目汇总按项目口径聚合”这一要求，不阻塞单综合体闭环。

## 12A. 突发事件与现场组织（2026-08-04 对齐平台治理地图）

### 12A.1 突发事件标准处理流程（建成前五条先行生效）

平台须建立突发事件标准处理流程。**在该流程建成之前，以下五条先行生效**：

1. **叫停营业**：店长报主理人或夜班值班经理，可以让一家店**当场停止营业**。
2. **留痕**：突发事件期间以**手机网络**记录；手机网络与无线网络**同时中断**的，仅免除中断期间的实时线上记录，现场须以可用方式留证（如随身录音摄像设备、拍照/视频），网络恢复后必须将中断期间的处置过程补录进系统。
3. **对外口径**：公司指定**唯一的对外口径负责人**，其对外沟通时须携带随身**录音摄像设备**；其他工作人员**未经书面许可不得对外发言**。
4. **与客诉挂钩**：突发事件**自动生成一条最高级别客诉**，走客诉的同一闭环，**不另起流程**。
5. **分级**：突发事件的严重度**直接套用现有的风险四级**（低、中、高、严重），不另设一套。

### 12A.2 客户关怀部

- 设客户关怀部，**不区分对客与对商户**，两类一并处理。
- 职责：受理客人投诉与商户异议、监督与协调各责任部门处理、确认闭环，并负责工单处理。
- **客诉与商户异议的实体回复由涉及部门与财务部门作出，客户关怀部不代作实体判断。**

### 12A.3 夜班值班经理

- 设夜班值班经理，为**夜间现场的最高负责人**，**每天一名**，由**系统根据当日排班自动指定**。
- 凡需其批准或知会的事项，**系统自动抄送该人**，其须立即处理。
- **白天没有夜班值班经理的时段，现场最高负责人为项目负责人。**

### 12A.4 楼宇保安团队

- 设楼宇保安团队，**与安防为同一支队伍**，由**城市项目公司管理**。
- 职责：接收系统预警、调阅监控录像、核查异常出入。

## 12B. 员工排班、考勤与薪资（业务口径，2026-08-04 对齐业务系统地图/枚举速查表）

> 本章为治理层承接的业务口径，用于约束排班、考勤、请假与薪资的规则边界；具体页面与计算实现见对应业务系统文档。

### 12B.1 排班

- 主管排班：**排到几点几分**，可指定当天工作点位（如某个服务区、某片保洁区域）；主管在手机上也能排。
- 排班表最终发布**须经该主管的上一级审批**后生效。
- **班次一经开始即锁定。**
- **顶班例外**：当班有人未到、需当场顶班的，由**领班直接安排**其他工作人员顶班并在系统中记录顶班人员，**不受本条审批流程限制**，顶班不限岗位；**顶班人员按顶班记录取得该班次的小费与服务费份额**；当日属加班的另给加班费，**加班费按国家规定与本综合体的综合计算工时制度执行**。
- 员工可申请修改排班（如与他人调换班次、因病假或其他原因无法履职），由作出该排班表的负责人填写原因后修改，每一次修改同样须经该主管的上一级审批。
- **所有排班的填写与修改只能追加记录、不能删除**，修改前后的排班时间都完整保留；**考勤判定以该班次锁定时的排班为准**。
- 员工看自己未来若干天的排班，**可见天数由后台配置**（业务参数，按经营主体可配，酒吧商户作为独立经营主体同样适用，出厂默认 7 天）。

### 12B.2 考勤打卡

- **上班打卡以领取工作手机为开始**：员工到岗领到自己那台工作手机的时刻，就是上班打卡时刻。
- 三种领取方式：**用工作手机碰 NFC 标签**、**扫码**（工作手机不支持 NFC 时兜底）、**工作手机离开充电设施**；三者记的是同一个上班时刻，**取最早发生的一次**，不重复计。
- **严格口径**：晚于排班开始打卡即**迟到**，早于排班结束打卡即**早退**，**不设宽限**；以**员工所在门店／点位的当地时间**为准（不同地区按各自当地时间计算）。
- 考勤日结果：出勤、缺勤（有排班没打上班卡）、迟到、早退、请假；**无排班 = 休息**（同日多个班次并列显示）。
- **工作手机损坏或不可用**的，由**夜班值班经理**领取一台新机交付该员工，此事作为事件记录留痕；**由此造成的打卡延误视为正常上下班，不记迟到**。

### 12B.3 请假与旷工

- 请假四类：**事假、病假、年假、调休**，**主管审批**；批准后对应日期考勤自动记请假。
- **请假单五态**：**待审批、已批准、已驳回、已撤销、已销假**。
  - **已撤销**：提交人在**假期开始前**自行撤回。
  - **已销假**：已批准**且已开始**，员工**提前回岗**，由**主管确认销假并填写实际结束日期**。
  - **撤销与销假后，对应日期的考勤恢复为按实际打卡计算**；**已扣的薪资在当月薪资单中冲回并注明来源**。
- **不能重复请假**：同一员工同一时间段只能有一条有效请假（待审批或已批准），系统在提交时即拦住重叠请假。
- **旷工**：无故旷工或未请假而未到岗的一律记为旷工。**仅事故、车祸、重大疾病等特殊情况可事后补办**，且必须提交**线下出具的医疗证明**，线上出具的证明一律不予采信。
- **连续两次**无故旷工或未请假未到岗的**予以辞退**，该“连续两次”**不设时间窗口限制**。

### 12B.4 请假扣薪

- 本综合体实行**综合计算工时**。
- **只有事假（无薪假）扣薪**，按该员工当期请假工时占当期总工时的比例，从其当期应发薪资中扣减。
- **扣减后的当期薪资以零为下限，不得为负**，超出部分不再扣减也不结转下月。
- 病假不扣薪；年假、调休等带薪假不扣；参照国家规定，法定带薪假一律不扣。**班次起止跨越月份边界的**（如 1 月 31 日 22:00 至 2 月 1 日 06:00 的夜班），该班次的**工时、考勤与请假一律归属班次结束时点所在的月份，跨周同理**；**请假扣薪的分母取归属月份的当期总工时**。**销假或撤销发生在已月结定格月份之后的，在当期薪资单冲正并注明来源，不回改已定格月份**（2026-08-06 按 BSM「请假扣薪」条 同步，**DEC-R8-14**）。**只有主管批准的请假才参与扣薪。**

### 12B.5 薪资结构与绩效

- 每位员工都有一个**结构化的薪资配置**：基础薪资、全勤奖、交通补贴、餐饮补贴、绩效工资、奖金、夜班补贴等项目**逐项配置**，每一项都配有自己的计算方法与公式；基础薪资与当月出勤日期配套计算。
- **绩效工资分 A、B、C 三档**：B 档为正常绩效；A 档为达成设定条件后可取得的超额绩效；C 档为连续未达成而降级后的绩效。
- **绩效基础分由后台配置**（业务参数，按经营主体可配，酒吧商户作为独立经营主体同样适用，出厂默认 100 分）；发生违规按对应分值扣分，**当月实拿绩效 ＝ 分数 ÷ 基础分 × 所处档次 × 绩效金额**。
- **A 档的达成条件、C 档的降级判定周期与绩效评定周期均由后台配置**（业务参数，按经营主体可配，酒吧商户作为独立经营主体同样适用）；**变更须经审批并留痕、只对后续周期生效**。
- **奖金同样按配置的公式与方法计算**，其中包含相应的扣除。
- **薪资单另含小费归集与服务费归集两栏**，两栏**各自独立列示**，**全额发放给对应服务提供人并代扣个税**。
- **扣除上限**：各类扣除合计**不得超过该员工当月总薪资的 20%**（**安全阈值，全平台统一可配，调整须经人力、财务、法务三审并由顶层平台公司最终确认，出厂默认 20%，须同时配置上下限**——2026-08-19 补五要素，依据 BSM「每位员工都有一个结构化的薪资配置」条 / ENUM「薪资单构成」条现文；DEC-R8-97-04。**本项与股息红利个人所得税的 20% 是两个不同的配置项，三审组合也不同（后者为财务、税务、法务），不得共用配置或审批链**）（总薪资指基础工资、各项补贴、绩效工资与奖金之和），**超过部分不再扣减也不结转下月**。处罚扣款与请假扣薪**分栏列示、不合并**。
  - **例外一**：**收银短款不计入处罚扣款**，由当班收银员**当场补足**，不补足不能结账交班。
  - **例外二**：员工**损坏店内物品照价赔偿，不受上述上限限制**。
  - **例外三**：**请假扣薪不计入上述合计上限**，按**事假工时比例单独扣减**，**其自身以当期应发薪资为零作为下限**。
  - > **注（原登记项 R8-C03·已解除）**：§12B.4「事假扣薪按请假工时占比扣减、**扣减以零为下限**」与本条「**各类扣除合计不得超过总薪资 20%**」的组合矛盾**已于 2026-08-06 随 HTML 修订落地（DEC-R8-02）**——请假扣薪已列为 20% 上限的**例外三**（与收银短款、照价赔偿并列），其自身以当期应发薪资为零作为下限（依据 BSM 薪资配置条、ENUM「薪资单构成」条）。
- **绩效扣分**与其他涉及员工的人力操作一样，须经 **HR 与该员工直属领导、向上两到三级复核**后生效；员工可对扣分**提出申诉**，申诉同样报至 HR 与直属领导向上两到三级裁定，**过程与结论均留痕**。
- **奖惩必须写明事由**：谁录的、为什么，**都留痕**。
- **扣分的分值表由各经营公司自行配置、须经该公司总经理批准后生效**，每次改动留痕且只对后续周期生效。
- **月结定格后员工才可见**（避免中途数字变来变去）；**重新月结只重算金额、不改动单据上已锁定的配置版本**。

## 12C. 酒吧股权、牌照、场地与资金分别记录（2026-08-05 R7 对齐平台治理地图）

> 依据 PGM「酒吧股权、牌照、场地和资金必须分别记录」条 / DIFF-A-050。本节写平台侧的登记与审批口径；股东之间的法律关系（进入、退出、股权转让、回购、解散与债务承担）属法律与股东协议范畴，**本平台只作记录、不设规则**。

- **场地提供方式二选一**：以**租赁或使用权**方式提供的，按正常合同流程办理（见 §6.5）；以**内部协议**方式提供的，**必须逐份经顶层平台最高权限审批后方可生效**——**未经审批的内部协议不产生场地使用效力，也不得据以入账**。
- **内部协议必载事项**（逐项写明，缺项不得提交审批）：场地位置与面积、计价方式与金额（**免收的也须写明「免收」及其起止期间**）、使用期限，以及**采用内部协议而非正常租赁的理由**。
- **变更同样受审批约束**：内部协议的变更、续期与提前终止同样须经顶层平台最高权限审批；变更前后的内容都完整保留、**只能追加不能覆盖**；每一份生效的内部协议在**城市项目公司与使用方两边同时入账并可查**。
- **资金按真实关系登记**：股本金按实际股东出资协议记录；顶层平台、城市项目公司或其他公司另行提供资金的，**必须按增资、股东借款、公司间借款等真实关系登记，借款不得当作股权，也不得计入分红基数**。
- **借款清偿优先于分红**：任何公司向酒吧提供的借款，出借时须写明**金额、利率、还款期限与还款顺序**；酒吧当期可分配利润**必须先偿还全部到期借款本息，剩余部分才可用于分红**；**存在逾期未还借款的一律不得分红**，分红方案提交时须附**借款清偿情况**。该口径与 `dividend-engine` 分红基数计算必须一致。
- **股权与牌照分别登记**：酒吧股权由娱乐平台公司和主理人等真实股东按工商登记持有，**80%／20% 只能作为新酒吧的默认建议**，实际以每家酒吧工商登记及出资协议为准；经营牌照登记在**实际经营法律主体**名下，**娱乐平台公司不因持股自动成为牌照主体**。

## 13. 本版结论

平台治理层是综合体统一管理系统的边界层、责任层和准入层。它不直接替代业务经营系统，但必须先定义清楚综合体项目、空间、业态、商户、合同、员工注册/设备凭证、设备、权限、终端开关和留痕（"NFC"按 D8 已统一为"设备凭证"，2026-06-07 收口）。

P0 阶段的重点是把“谁、在哪、凭什么、谁能操作、谁负责”管清楚。只要这层站稳，后续票务、酒吧、游乐、第三方、结算、事件中心和数据分析才不会出现对象混乱、权限混乱、账务归属混乱和责任链断裂。

### 15.1 适用的员工数据处理与监控场景

平台治理层涉及以下对员工的数据处理与监控活动，均需履行目的必要性论证、统一告知与用途限定：

### 15.2 统一告知方式

- 上述员工数据处理与监控活动，须通过**入职协议**与**规章制度**向员工统一告知：告知处理目的、范围、方式、留存期限与员工权利。
- 告知须在员工注册审批环节取得员工知悉/同意，并在员工档案/注册审批中留存**同意凭据**（consent_version/consent_time/consent_scope，或关联 employee_notice_id 指向员工监控告知/同意记录表），见 §7.6 员工关键字段与 §9 员工注册审批页。
- 告知文本版本化管理；告知内容变更时须重新告知并更新同意凭据版本。

### 15.3 用途限定与最小化

- 员工监控数据严格用于上述声明目的，**禁止**用于声明外用途；不得将监控数据用于与岗位职责无关的画像或处置。**「上述声明目的」自 2026-08-19 起含 §15.1 定位行新增的「授权范围外敏感操作拦截」**（DEC-R8-98-08 用户批准）：核销、收款、退款、放行等敏感操作，操作设备定位落在该项目综合体授权范围之外时**一律拒绝并留痕**，绑定点位的工作手机、平板、一体机离开授权范围后同样只保留查看，Web 端同样适用；该用途属**声明内用途**，判定只发生在执行敏感操作的那一刻，不构成持续轨迹追踪，也不改变本条对声明外用途的禁止。
- 私人手机仅检测可信状态（Root/调试/不可逆设备指纹），**不采集私人手机本机 NFC 唯一标识**（D8 已废止），不读取私人手机的个人内容。
- 各类员工监控数据的留存期限必须**逐类适用已经批准的规则，不得因同属「监控数据」就一律按永久保存处理**：企业微信工作会话原文继续按 §15.1 永久保存、不自动到期删除。原始定位采样、MDM 原始采集、设备检测原始数据、绩效中间数据等三份业务 HTML **未明确规定为永久保存**的类别，本文不自行指定具体期限，也不得默认永久；统一告知须按 §15.2 如实写明该类别当时适用的留存期限，并继续遵守用途限定与最小必要。确需清理明确允许清理的数据时，按该数据类别已经批准的清理规则执行。**本条不改变 §15A.1 的导出记录永久规则，也不改变 §15C.3 的一般留痕默认永久与钱账不可删除规则。**

### 15.4 查看与处置审计

- 对员工监控数据（定位、企微会话、设备检测记录等）的**查看、导出、处置**操作须按权限控制并写入操作留痕（操作人、对象、时间、目的）。
- 高敏感查看（如调取企微会话用于纠纷取证）须经审批并留痕，可被追溯复核。
- 员工对涉及本人的监控数据享有知情权；删除/撤回同意按合规 C2/C5 口径级联处置。

## 15A. 导出与数据防泄（2026-08-04 对齐平台治理地图）

### 15A.1 强制脱敏由系统自动判定

- **导出文件是否脱敏，不由导出人判断，也不提供关闭开关**：系统按导出内容**自动判定并强制执行**。
- 凡导出内容中包含以下**任何一类**，一律强制脱敏：
  - **第一类：法律法规要求保护的个人信息，只有下面七项，没有第八项**——姓名、手机号、证件信息、人脸与生物特征、住址、支付账号、精确位置。因为脱敏由系统自动判定、没有人工把关，**这张清单必须是封闭的，不留“等”字**；**要增加一项必须先经批准写入三份 HTML，不得由后台自行添加**。
    - **员工的姓名、所属部门与所属公司不脱敏**，全体员工均可查看。
    - **员工的手机号**只对**该员工直属管理上级这条管理线上的各级岗位**、以及**顶层平台公司的管理层**不脱敏，对其他岗位一律脱敏。
    - **客人的姓名与手机号默认脱敏**；**例外：商户查询与导出属于本商户的客户信息不脱敏**（按 BSM「账户注销」条 的来源判定，2026-08-05 用户裁决；PGM「导出文件是否脱敏」条）。**跨商户与平台侧批量场景不适用本例外。**
  - **第二类：敏感经营数据**——内部结算价、成本价、采购价、毛利、分账底价、域内补贴缺口、供应链价格，以及其他被标记为敏感的数据。
- 系统在生成导出文件前先扫描内容并自动打码；导出人**无权取消、无权选择不脱敏**，也**不得通过更换导出模板、拆分字段或改变导出格式来规避**。
- **除上述「商户导出本商户客户信息」例外之外，跨商户、平台侧批量场景的未脱敏原文只允许持授权 U 盘密钥的最高权限本人导出**；每一次未脱敏导出**单独留痕**，记录导出时间、用途、接收方与实际导出内容范围。
- **每一次导出**——不论脱敏与否——都记录**导出人、导出时间、导出所用设备、导出内容范围与筛选条件**；**导出记录本身永久保存、不在任何清理范围内**。

### 15A.2 导出文件密码与可编辑版审批

- **所有导出的文件一律带密码**，密码**不可取消、不可由导出人自行设定**。
- 密码由**导出人账号、导出时刻、导出所用设备的唯一识别号**（如网卡地址、主板序列号等）以及接入网络等可查证要素**按统一算法生成，长度不超过十位**，且**可由系统反向推算**出对应的导出人、导出时间与导出设备；**导出人可以在专门的地方查到自己导出文件的密码**。
- **导出文件中的数据不可复制、不可编辑**：不得从文件中选取复制内容，也不得修改文件内容。
- 确需**可编辑版本**用于二次加工的，须**另行申请**、说明用途与接收方，经**最高权限审批**后发放；可编辑版同样带密码与暗纹并**逐次留痕**。

### 15A.3 页面暗纹与敏感页

- **后台、商户专区和员工手机端的所有在线页面都带有按同一规则生成的暗纹**；暗纹**可反向推算**：把页面的截屏图片、或对着屏幕拍摄的照片上传到系统，即可算出该页面是由**哪个账号、在哪一台设备上、于什么时间**打开的。
- **敏感页 = 页面上出现上述两类必须强制脱敏内容的页面**：敏感页上的文字**不能被选中、不能被复制**，也**不提供页面另存与打印**（防的是有人绕开导出口子直接把内容抄走）。
- **打开敏感页这件事本身也要留痕**：记下是谁打开的、什么时间打开的、打开的是哪一个页面、这一次看到的是哪些对象（哪个客人、哪个商户、哪些单据）；**这条留痕不提供关闭开关**。

### 15A.4 客人查询的唯一路径

- **手机号是查询客人的唯一路径**：凡要定位到具体某一位客人，一律只能输入手机号，并走**客人查询专门通道**，**查了谁、谁查的都留痕**。
- **姓名、昵称、卡座、订单号、存酒标签等其他字段都不得用于反查客人**；只有在通过手机号定位到该客人之后，才能看到其名下的卡座、订单号等相关信息。
- **从订单、账单、订台单、存酒单等任何单据上点开“客人”，等同于发起一次客人查询**：同样走这条专门通道、**同样先鉴权、同样留痕**，打开后**只显示脱敏信息**，不因为是从单据点进来的就直接放明文。
- **会员号即注册手机号，平台不设独立卡号体系**；**收银现场录入会员号就是录入客人手机号，该动作走客人查询专门通道并留痕**（2026-08-19 补，依据 PGM「手机号是查询客人的唯一路径」条现文；DEC-R8-97-29）。

### 15A.5 个人信息加密存放与界面脱敏（2026-08-04 对齐平台治理地图）

- **客人和员工的手机号、身份信息等个人信息，在系统里一律加密存放。**
- **员工日常界面只显示脱敏号码、不见明文**；**界面脱敏不提供关闭开关**（与 §15A.1 导出脱敏一致，均不由使用人判断、不提供关闭入口）。

## 15B. 紧急恢复（破窗机制，2026-08-04 对齐平台治理地图）

- **系统钥匙存放在专用钥匙 U 盘中托管，平时不放在线上。**
- 万一**管理员账号全部无法登录**，走「**破窗**」应急通道恢复进入系统。
- **破窗一旦使用即全程留痕，事后必须复盘审查每一步操作。**

## 15C. 配置数据存档、删除与集中清理（2026-08-05 R7 对齐业务系统地图·系统通用能力）

> 适用对象：**配置类主数据**——商户档案、票种、价格规则、酒吧商品/分类/套餐等；**业务记录**（员工档案、设施设备、商户服务工单、卡座预订等）同样适用本章。**交易类数据（订单、核销、结算流水、账单）出于税务与审计留存要求只允许存档、不允许彻底删除，纠错走冲正**（既有口径不变）。本章为平台统一能力，各业务域不得各写一套、也不得跳过。

### 15C.1 存档（先下线，依据 BSM「存档（先下线）」条 / DIFF-B-011）

- 存档＝**从各处的选择列表里隐藏、不再被新业务选用**，但**历史照样能查、能对账**；点「取消存档」即可恢复。
- **存档理由必填。**
- **逐条存档属日常操作，不用审批**；**一次性存档超过后台配置条数的，或整店、整类存档的，须经审批后执行**（业务参数，**按综合体可配，须同时配置上下限**）。
- 后台另设「**已存档内容**」页：可看到全部被存档的对象，**按分类查阅、可逐条恢复**。
- **已存档的票种、商品等不能再被拿去下单、配价、组套餐**——杜绝「明明下线了还能卖出去」。

### 15C.2 删除与删前占用检查（依据 BSM「删除（走审批·软删除）」条、「删前自动查占用」条、「业务记录也能存档删除」条 / DIFF-B-012）

- 删除一律**先存档 → 再「申请删除」并填写删除理由 → 由具备最高权限的人审批通过后执行**（**申请人不能审批自己的申请**），删除全程留痕。
- 删除是**软删除**：数据转入后台留存、前台各处不再显示，**始终留在库里可查、可审计、可恢复**；所有存档与删除的数据按分类归拢，便于按类查阅、恢复与清理。
- **删除前系统自动检查该条数据是否仍被业务占用——合同、账单、结算、订单、已发权益、库存**；**只要还有占用就拦住不让删**，避免删出「找不到主人」的记录。**该检查横跨合同、票务、结算、库存各域，为同一道平台级校验。**
- **持授权 U 盘密钥的最高权限本人发起的操作，不需要经过任何审批。**

### 15C.3 集中数据清理工具（依据 BSM「集中数据清理工具」条 / DIFF-B-013）

- 清理范围**只限「已存档、且超过设定天数」的配置数据**；**绝不碰在用的活数据**。
- 流程：选清理范围 → **先「试运行」预览会删掉多少条** → 提交 → **由具备最高权限的人审批** → 批量清理，**全程留痕**。
- 审批**不设例外，申请人不得审批自己的申请**；**持授权 U 盘密钥的最高权限本人发起的不需要任何审批**。
- 本工具与「**留痕清理**」是**两个不同入口，不可互相顶替**：留痕与审计记录默认永久保存、不自动到期删除，**不在本工具的清理范围内**。

## 15D. 系统交付与上线（2026-08-05 R7 对齐业务系统地图·系统交付与上线）

### 15D.1 上线安全加固（依据 BSM「上线生产必须换掉开发默认的弱口令」条、「上线加固要留痕」条 / DIFF-B-017）

- 最高权限口令（系统数据的总管钥匙）在测试阶段用的是方便调试的默认弱密码；**正式上线为生产环境时必须换成强密码，这是上线生产的必做一步、不可省略**，不得以任何理由跳过或延后。
- 该强密码按 §15B 的 U 盘密钥托管方式设定与保管：**密码不以明文形式留在机器磁盘上**。
- **上线加固要留痕**：换密码、启用 U 盘托管、每一次插盘启动或破窗登录，都要记录谁在什么时间做了什么，进入留痕与异常，事后可追溯。

### 15D.2 交付物：能自动识别环境的安装包 + 内附教程（依据 BSM「能自动识别环境的安装包 + 内附教程」条 / DIFF-B-018）

- 须提供一个**能自动检测运行环境的安装包**：安装时自己识别当前是测试环境还是生产环境，并**自动完成相应的配置，不用现场人员手工去分辨和调参**。
- 安装包里**附带一份简单的使用教程**：用**业务语言**写清楚怎么安装、怎么日常使用，让不懂技术的人也能照着装、照着用；**正式上线的安全加固步骤（换强密码、U 盘密钥托管）也要在教程里讲清楚**，指引现场按步骤完成。
- 上述两项为**交付验收项**，缺任一项不得判定交付完成。

## 15E. 内部部门间工单（2026-08-07 补，依据 BSM「内部工单」条；REGX-02 / REGX-03）

### 15E.1 发起（REGX-02）
