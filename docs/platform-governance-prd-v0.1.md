## 1. 文档定位

本文档用于重新拆解“综合体管理系统”的平台治理层产品需求。

本 PRD 承接本会话已确认的 Product Design brief：综合体管理系统不是单点票务、酒吧或游乐系统，而是一个统一管理平台。平台治理层负责先回答四个基础问题：

- 谁在综合体内经营、工作、服务或接入系统。
- 在哪里经营、工作、服务或发生业务。
- 凭什么经营、凭什么进入系统、凭什么拥有权限。
- 谁能操作、谁能查看、谁承担责任、谁留下记录。

本文件只做产品需求拆解，不做技术方案、数据库设计、接口设计、编码任务或 UI 视觉设计。它的产出目标是为后续继续拆《页面清单》《流程图》《字段字典》《子系统 PRD》和开发任务提供清晰上层边界。

## 2. 平台治理层范围

平台治理层是综合体统一管理平台的地基层。它不直接完成票务售卖、酒吧点单、游乐核销、餐饮零售交易等业务动作，而是定义这些业务动作发生前必须存在的组织、空间、权限、责任和留痕边界。

### 2.1 P0 纳入范围

| 范围 | 产品目标 |
|---|---|
| 综合体项目管理 | 定义被管理的综合体项目主体和经营基本信息 |
| 空间/楼层/区域/点位管理 | 定义综合体物理空间、经营区域、作业点位和责任边界 |
| 业态管理 | 定义餐饮、零售、酒吧、游乐、服务商等经营分类 |
| 商户/运营主体管理 | 定义谁在经营、谁承担经营责任、谁拥有数据边界 |
| 合同与合作关系管理 | 定义商户凭什么经营、合作模式是什么、结算口径摘要是什么 |
| 员工/岗位/班次管理 | 定义谁在现场工作、做什么岗位、什么时间上岗 |
| 企业设备管理 | 定义公司统一管理的工作手机、平板、扫码设备等设备责任链 |
| 角色权限与数据权限 | 定义谁能看、谁能改、能操作哪个项目/商户/空间 |
| 终端开关管理 | 定义 10 端（客人 App、小程序、Web、工作人员平板、员工工作手机、员工私人手机、商户侧 Web 门户、商户侧 App、一体机、移动管理端）是否开放，枚举以字段字典 §3.1 为准（对齐 D5） |
| 平台基础留痕 | 记录治理层关键动作，形成可追溯责任链 |

### 2.2 治理层边界原则

平台治理层管“准入”和“边界”，不替代业务经营系统。

平台治理层管“责任”和“归属”，不替代财务结算系统。

平台治理层管“权限”和“可见范围”，不替代具体业务审批流的全部细节。

平台治理层管“基础留痕”，不替代完整事件中心、视频证据中心或 AI 风控系统。

平台治理层管“终端开关”。所有端是否开放、哪些商户可用、哪些模块可用、哪些设备和版本可用，都必须由后台统一配置，终端自己不能绕过开关。

平台治理层管“业务准入”。票务、酒吧、游乐、结算、第三方接入等独立业务系统在执行关键流程前，必须先校验综合体、商户、合同、空间、员工、设备和权限是否符合基础定义；不符合时应阻断，或进入更高级别审批/审计。

平台治理层按“当前一个综合体、未来多个综合体”设计。所有商户、合同、空间、人员、设备、票务、酒吧、游乐和数据权限都必须归属到明确综合体项目。

## 3. 非范围

以下内容不属于平台治理层 P0 范围：

- 不展开票务定价、门票策略、通票权益明细和核销规则。
- 不展开酒吧点单、桌台账单、存酒、库存、库房和吧台出品细节。
- 不展开游乐项目排队、预约、场次售卖、设备巡检和事故处理细节。
- 不展开餐饮 POS、零售 POS 的真实业务流程。
- 不展开机器人调度、视频监控平台、企业微信会话质检的完整能力。
- 不做财务深度结算、自动对账、分账计算和发票管理。
- 不做 AI 分析、自动风控、经营预测和复杂绩效考核。

## 4. 角色与使用场景

| 角色 | 关注重点 | 典型场景 |
|---|---|---|
| 综合体业主/管理层 | 谁在经营、空间如何使用、风险和责任是否清晰 | 查看项目、商户、合同、空间、人员、设备和异常总览 |
| 平台运营 | 基础配置和日常治理准确性 | 维护项目、空间、业态、商户、人员、设备和状态 |
| 招商/商户管理 | 商户入驻、合同关系、合作范围 | 新增商户、录入合同、绑定经营区域、跟进到期续约 |
| 财务 | 合作模式、结算口径、合同状态和责任主体 | 查看合同摘要、商户状态、结算账户和变更留痕 |
| 系统管理员 | 账号、角色、权限、数据范围 | 配置平台角色、商户角色、岗位权限和临时授权 |
| 现场主管 | 当班人员、设备、点位和责任链 | 排班、确认设备领还、查看现场员工和异常 |
| 商户管理员 | 本商户资料、员工、空间、合同和权限 | 维护本商户员工，查看可经营范围和可用设备 |
| 员工 | 上岗、领设备、在授权范围内执行现场任务 | 查看自己的班次、岗位、设备、可操作区域 |
| 设备管理员 | 设备台账、流转、维修、报废和责任归属 | 入库设备、分配设备、记录领还、处理丢失损坏 |
| 外包/服务商人员 | 在授权范围内登录系统执行被指派任务，不越界 | 维保单位接修维保；安保/保洁巡检打卡、上报异常；施工/装修队进场报备、验收 |
| 审计人员 | 只读核查业务与留痕，敏感证据按审批查看/导出 | 内部稽核看本综合体全量；外部审计/监管看限定范围与期间 |

角色边界补充（2026-06-29 业务确认）：

- **外包/服务商人员**是可登录系统的角色（区别于仅作台账对象的维保单位/供应商记录）：按最小权限授予，只限本综合体、只限被指派的工单/区域/任务；典型子类含设备维保单位、安保/保洁、工程施工/装修队，可按需扩展其它外包角色。
- **审计人员**分两级：内部稽核（本综合体全量只读）与外部审计/监管（限定项目/范围/期间只读）。两级一律只读、不得修改任何业务数据；查看或导出敏感证据（财务流水、人脸识别同意、个人信息、审计事件导出）必须经审批并留痕。

### 4.1 外包供应商自助下属账号管理（需求口径，代码待落地）

> 2026-06-30 拍板（业务 HTML GOV-ACC-002「外包人员与审计人员」已同步授权外部机构自助管下属、平台设上限）。在已落地的外包角色账号（V178/179，平台直发 assignee 账号）之上，补一层供应商自助管理下属的门户口径：

- **机构父级**：外部协作机构（独立于供货供应商台账；供货供应商只作采购/对账对象、零登录账号）。维保单位若既供货又派人，机构档案仍在供应商目录、账号能力另挂一层指向它，不重复登记。
- **机构管理员账号**：机构由一个"机构管理员"登录账号（角色 OUTSOURCED_VENDOR_ADMIN，data_scope=partner_org）进入自助门户，可长期反复开通/停用本机构下属人员账号、查看下属工作完成情况；管理员只管下属，不碰业务数据。
- **下属上限**：平台管理员按机构设下属账号数上限（external_partner_orgs.max_subordinates）；机构开通下属达上限即拒。
- **范围继承（2026-06-30 Q4 拍板）**：下属账号**继承机构被授权的全部范围**（机构内人员可互换），看本机构被派的全部工单/区域，**不再细到个人 assignee**；机构范围本身仍 ≤ 平台为其设定的上限。
- **账号时效**：机构与下属账号有效期随合同周期（external_partner_orgs.valid_until），到期自动停用；供货/长期合作可设长期（valid_until 空）。
- **内部稽核例外**：内部稽核=平台员工只读角色，不挂任何机构（外部审计/监管机构才走机构模型）。

落地触点：外部协作机构主体表 + 机构-下属账号关系 + 下属上限校验 + 自助门户页 + 时效到期停用任务。

## 5. 核心业务对象

> 修订说明（2026-06-10 收口）：依 D8/A6（用户已拍板），废止"安装时读取手机本机 NFC 唯一标识"作为员工身份方案（Android 技术不可行，phone-3），私人手机身份改为"安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint）"，原"NFC 员工标识"实体改为"设备凭证"。注意：工作手机通过摄像头/扫码模块读取外部客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识，与本处废止的"读手机本机 NFC 唯一标识"是两件事。依据 finding decision-land-1/baseline-conf-1、D8 条。

> 名词四层（2026-07-04 统一）：本平台组织主体分四层——**平台**（多项目公司之上的集团视图/汇总层）→ **项目公司**（单个经营综合体的责任主体，即本文所称「综合体项目」的经营主体）→ **管理公司（SPV/业态主体）**（在一个项目公司下按业态成立的运营主体：娱乐运营平台、酒吧 SPV、中央餐饮、游乐、传媒、资产公司等）→ **商户**（在某业态下实际经营或接入的公司/主体）。下表对象据此定位；全文「综合体/集团/项目」旧混用一律校正：指单个经营体用「项目公司」，多项目汇总用「平台/集团视图」。

| 对象 | 定义 | 关键关系 |
|---|---|---|
| 综合体项目（项目公司） | 被统一管理的单个娱乐综合体经营体及其责任主体（项目公司） | 关联管理公司、空间、业态、商户、合同、人员、设备和权限 |
| 管理公司（SPV/业态主体） | 在一个项目公司下按业态成立的运营主体（如娱乐运营平台、酒吧 SPV、中央餐饮、游乐、传媒、资产公司），是「平台自营」类业务的经营与结算责任主体 | 归属某项目公司；关联业态、下辖商户/自营门店、合同主体与结算主体；商户挂在其对应业态下 |
| 业务子系统 | 票务、酒吧、游乐等可独立运行的业务系统 | 共用平台治理层的项目、商户、合同、空间、人员、权限和准入规则 |
| 终端能力开关 | 控制某类终端、某个商户、某个业务系统或模块是否开放 | 关联综合体项目、商户、业务系统、终端类型、模块、设备和版本 |
| 组织/公司 | 平台公司、商户公司、服务商公司等组织主体 | 关联商户、员工、合同和结算口径 |
| 业态 | 餐饮、零售、酒吧、游乐、服务商等经营分类 | 关联商户、空间、合同、统计口径 |
| 空间层级 | 项目、楼栋、楼层、区块（商场区块）、区域、点位等空间结构 | 关联商户经营范围、设备点位、岗位责任区 |
| 商场区块 | 原始需求点名的独立治理对象，介于楼层与区域之间的招商/经营分区 | 关联区域/点位、商户经营范围、合同；P0 必做区块级，铺位级后置 P1（详见字段字典 §5 区块/铺位裁剪决策） |
| 点位 | 入口、吧台、桌台、卡座、游乐入口、库房、摄像头位等具体位置 | 关联设备、员工、核销、巡检和事件留痕 |
| 商户主体 | 实际参与经营或承担合作责任的公司或主体 | 关联业态、合同、空间、员工、数据范围 |
| 门店/经营单元 | 商户在综合体内的具体经营单元 | 关联空间、岗位、营业状态和业务系统 |
| 合同 | 平台与商户/服务商之间的合作依据 | 关联合作模式、经营范围、期限、结算口径摘要、核心条款摘要和准入拦截规则 |
| 合作模式 | 租赁、联营、自营、代运营、服务商接入等合作类型 | 影响合同、权限、结算和数据归属 |
| 结算口径摘要 | 合同层记录的结算原则摘要 | 为后续财务系统提供依据，不负责具体结算计算 |
| 员工 | 平台、商户或服务商下的工作人员 | 关联组织、岗位、班次、设备、权限、职级、薪资口径和留痕 |
| 员工私人手机 App | 员工自有手机上的轻量 App | 用于注册、通知、状态查看、设备凭证绑定和审批结果查看，不承担现场业务操作 |
| 设备凭证（设备公钥/不可逆设备指纹） | 员工私人手机 App 安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint），作为员工私人手机的唯一可信标识 | 关联员工、私人手机 App、公司工作手机、解绑重绑记录和审批状态 |
| 岗位 | 员工职责类型，如运营、财务、店长、核销员、服务员、巡检员 | 关联权限、职级、班次、空间、设备和薪资口径 |
| 班次 | 员工在特定时间段内的工作安排 | 关联岗位、区域、设备领用和责任链 |
| 设备 | 公司统一管理的工作手机、平板、扫码枪、NFC 读卡设备（摄像头/扫码模块读取二维码，NFC 读卡设备读取外部 NFC 腕带/标签/卡用于核销）等 | 关联员工、私人手机设备凭证绑定关系、班次、点位和异常 |
| 角色 | 权限集合，如平台管理员、商户管理员、财务、现场主管等 | 关联功能权限和数据权限 |
| 权限 | 可操作功能、可查看数据、可管理空间和商户范围 | 关联角色、员工、商户、项目和空间 |
| 数据范围 | 数据可见边界，如全平台、本项目、本商户、本区域、本班次 | 约束后台和移动端看到的数据 |
| 操作留痕 | 治理层关键动作记录 | 关联操作人、对象、时间、原因和结果 |

## 6. 业务流程

### 6.1 创建综合体项目

1. 平台运营创建综合体项目。
2. 录入项目名称、经营定位、地址、责任主体和负责人。
3. 设置项目初始状态。
4. 项目启用后，可继续建立空间、商户、合同、人员和设备。

输出结果：形成综合体最高管理单元。

### 6.2 建立空间与点位

1. 在项目下建立楼栋、楼层、区域。
2. 在区域下建立具体点位，如入口、酒吧区、卡座、吧台、游乐入口、库房、设备柜、摄像头点位。
3. 定义每个空间或点位的用途、容量、负责人和状态。
4. 将空间点位用于后续商户经营范围、设备绑定、岗位责任区和事件留痕。

输出结果：形成“业务发生在哪里”的空间基础。

### 6.2.1 空间业务名词与 space_type 枚举对照

业务人员所说的楼栋/楼层/铺位/公区等，统一落在 `spaces` 一张自引用树（`parent_space_id` 表达层级）+ `space_type` 类型字段上。权威枚举取值见 OpenAPI `SpaceRequest.space_type`，对照如下：

| 业务名词（HTML / 本 PRD） | spaces.space_type | 层级与关键字段 | 说明 |
|---|---|---|---|
| 综合体项目 | 非 spaces（`projects` 表） | `spaces.project_id` 指向 | 所有空间必须归属某综合体项目 |
| 楼栋 / 商场本体 | `mall` | 树根，`parent_space_id` 为空 | 一个综合体下可有多栋，各为一条 mall |
| 楼层 | `floor` | parent=楼栋；`floor_no` 记楼层号 | |
| 商场区块 / 区域 / 公共区域 | `zone` | parent=楼层 | 区块与区域同用 zone，按 parent 层级区分；未绑定商户的 zone 即公区 |
| 铺位（正式商铺） | `shop` | parent=区块/区域 | 铺位级 P0 后置、P1 落地（见 §5 区块/铺位裁剪决策） |
| 摊位 / 快闪位 | `booth` | parent=区块/区域 | |
| 酒吧桌台点位 | `bar_table` | parent=区域 | 物理点位口径，运营桌台见酒吧域 |
| 设备 / 设施点位 | `facility` | parent=楼层/区域 | 供设备绑定 |
| 其他点位 | `other` | — | 入口、摄像头点位等未归类点位 |

字段补充：`polygon_points` 存平面图多边形，`area_square_meter` 存面积。
合同绑定：合同经营范围与铺位绑定走 contract-space scope（迁移 `V080__contract_scope_and_spaces`、`V162`；空间出租状态见 `SpaceRentalStatusRecord`，用于防止同一铺位重复出租）。

### 6.3 建立业态与经营分类

1. 平台运营维护基础业态。
2. 标记业态是否允许绑定商户、空间、合同和第三方系统。
3. 对复合业态做归类说明，避免统计口径混乱。

输出结果：形成统一经营分类和统计口径。

### 6.4 商户入驻

1. 招商/商户管理新增商户主体。
2. 录入主体资质、联系人、经营类型和责任人。
3. 绑定业态和拟经营空间。
4. 状态进入待准入或试运营。
5. 待合同生效后，进入正常经营。

输出结果：明确“谁在经营”。

### 6.5 合同录入与审批

1. 招商/商户管理录入合同基本信息。
2. 选择合作模式，如租赁、联营、自营、代运营、服务商接入。
3. 录入经营范围、期限、保证金、结算口径摘要和附件。
4. 提交财务或管理层做单级确认（P0 边界：仅"录入→确认→生效→终止"四态单级确认，不做多级审批流；多级/变更/续签审批流属 P1，见 §8.1）。
5. 合同生效后，商户获得对应经营依据。
6. 合同核心条款摘要同步生成准入规则，供票务、酒吧、游乐、结算和第三方接入校验。
7. 后续业务动作如超出合同经营范围、空间范围、业态范围、有效期或结算口径，系统应阻断或进入更高级别审批/审计。

输出结果：明确“凭什么经营”，并形成后续流程的准入拦截和升级审批依据。

### 6.6 商户经营范围绑定

1. 在合同或商户档案中绑定项目、空间、区域、点位。
2. 设置允许经营的业态和经营单元。
3. 设置商户可查看的数据范围。
4. 后续票务、酒吧、游乐、餐饮零售等业务按该范围归属。

输出结果：明确“在哪里经营、经营什么”。

### 6.7 员工入职/分配岗位/排班

1. 平台或商户新增员工。
2. 绑定所属组织、岗位和联系方式。
3. 分配可操作项目、商户、区域或点位。
4. 创建班次并绑定岗位和责任区。
5. 班次生效后，员工才能在授权范围内执行现场任务。

输出结果：明确“谁在什么时间负责什么”。

### 6.8 设备入库/领用/归还/异常

1. 设备管理员录入设备台账。
2. 上岗时员工领取设备，设备绑定员工、班次和岗位。
3. 下班时归还设备并检查状态。
4. 设备损坏、丢失、未归还、异常使用时形成异常留痕。

输出结果：明确“谁拿着什么设备做了什么”。

### 6.9 员工私人手机注册与设备凭证绑定

> 修订说明（2026-06-07 收口）：本节按 D8/A6 改写——废止"读取手机本机 NFC 唯一标识"，私人手机身份改为"安装期生成并存于设备 Keystore 的设备公钥/不可逆设备指纹（device_key_fingerprint）"；仅持久化不可逆哈希/公钥指纹，不存原始标识（PIPL 数据最小化，compliance-4/C4）。依据 finding compliance-land-9/decision-land-1、D8 条。本节同时是合规 C4"员工注册审批记录同意凭据"的引用点，见 §15。

1. 员工在私人手机上安装轻量 App。
2. 员工提交姓名、手机号、身份证明、所属组织、岗位申请、紧急联系人等注册信息。
3. App 在安装期于设备 Keystore 内生成设备公钥/不可逆设备指纹（device_key_fingerprint），并记录私人手机设备信息；仅持久化不可逆哈希/公钥指纹，不读取也不存储手机本机 NFC 唯一标识。
4. 后台审核员工信息、岗位、组织归属和设备凭证绑定关系。
5. 审核通过后生成员工账号、角色、职级、默认权限和数据范围。


> 后台手动录入工作人员入口：企业微信关闭或员工尚未完成私人手机注册时，平台管理员、IT 管理员或 HR 可通过后台手动录入工作人员。该入口必须绑定 `organization_id`；销售、商户员工和商户管理员必须绑定 `merchant_id`；必须写入初始登录凭证哈希、账号类型、同意/授权凭据或证据附件引用，并记录 `access.user.changed`。后台手动录入不能创建 `platform_admin`，也不能绕过权限模板、临时授权和审计留痕。
6. 系统建立员工私人手机、设备凭证（设备公钥/设备指纹）、公司发放工作手机之间的一一对应关系。
7. 员工换手机时必须先解绑旧手机设备凭证，再绑定新手机，解绑和重绑都要留痕。
8. 私人手机 App 仅允许收发通知、查看班次、查看审批状态和少量个人状态，不允许现场核销、点单、放行、结算等业务操作。
9. 私人手机如检测到 Root、调试环境、设备指纹异常或更换设备未审批，App 状态失效并进入复核；能被手机端检测出的异常环境均按不可信处理。
10. 员工进入办公区或现场作业区时，私人手机必须寄存；寄存柜不固定，流动使用、先到先选、离开时全部拿走；现场只允许使用公司受管工作手机。

> 说明：工作手机通过摄像头/扫码模块读取**外部**客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。上述现场核销能力不在本节范围内，不受 D8 影响。

输出结果：明确“员工身份、私人手机、设备凭证（设备公钥/设备指纹）、公司工作手机、角色权限”的一一对应关系。

### 6.10 权限分配与数据范围控制

1. 系统管理员创建角色。
2. 设置角色可操作功能和可查看数据范围。
3. 系统管理员可创建基础权限模板，模板内预设不同岗位/职级的权限勾选和数据范围。
4. 模板可以复制成多个变体，例如“普通员工”复制为“普通员工01”，复制后独立维护。
5. 对临时处理事项可发放临时权限模板，必须设置有效期或单次有效，并填写授权原因。
6. 将角色、基础模板或临时模板分配给员工或商户管理员。
7. 权限变更、收回、到期、单次消耗、失效均进入留痕。
8. 员工职级、岗位、角色和薪资口径可建立关联；职级可由后台维护为 M1-M10，并可分上、中、下。P0 记录职级/岗位/权限摘要和薪资大范围，具体薪资单独填写，完整薪资计算只留接口和摘要字段。

输出结果：明确“谁能操作、谁能查看”。

### 6.11 关键配置变更留痕

1. 对项目、空间、业态、商户、合同、员工、设备、权限等关键对象进行变更。
2. 系统记录操作人、变更时间、变更对象、变更前后摘要和原因。
3. 对高风险变更进入复核流程。
4. 留痕可供后续财务、运营、风控和管理层追溯。

输出结果：形成治理层责任链。

## 8. P1/P2 需求方向

### 8.1 P1 方向

- 合同审批流深化：支持多级审批、合同变更审批、续签提醒和到期预警。
- 平面图点位：在空间管理中加入平面图、点位标注、商户经营区域可视化。
- 租金/分成规则深化：在合同中细化租金、保底、分成、服务费等规则摘要。
- 员工绩效基础：关联班次、设备、留痕和业务结果，形成基础绩效依据。
- 跨商户权限：支持平台人员跨商户、跨业态处理特定事项。
- 设备流转增强：支持借调、跨班次交接、设备盘点和异常工单。

### 8.2 P2 方向

- 复杂组织架构：支持集团、多项目、多公司、多品牌、多门店层级。
- 设备 MDM/应用管控深化：P0 已拍板采用 Android Enterprise / Android Management API + 商业 MDM，由平台 IT 选型、采购、配置和运维；后台维护预装软件清单和网站白名单，商业 MDM 执行系统级阻断和合规状态回传。P0 后继续增强定位、批量远程锁定和工作模式。
- 自动风险提示：合同到期、资质过期、异常留痕频发、设备异常频发自动提示。
- 空间经营分析：按区域、楼层、业态、商户做经营表现对比。
- 治理质量分析：分析权限变更、人工补录、设备异常、合同风险等治理质量。

## 12. 已确认规则和后续细化事项

已确认：

1. 当前先按一个综合体落地，但所有对象必须带综合体项目归属，未来可扩展多综合体。
2. 员工私人手机 App 安装期在设备 Keystore 内生成设备公钥/不可逆设备指纹（device_key_fingerprint）作为唯一可信标识并绑定员工；废止"读取手机本机 NFC 唯一标识"方案（D8/A6，2026-06-07 收口，finding compliance-land-9/decision-land-1）。工作手机通过摄像头/扫码模块读取外部客人二维码；NFC 仅读取外部 NFC 腕带、标签、卡或设备中的权益标识。
3. 员工换手机必须先解绑旧手机设备凭证，再绑定新手机。
4. Root/调试/设备异常以手机端可检测能力为准，异常时 App 失效并进入后台复核。
5. 私人手机寄存柜不固定，流动使用，先到先选，离开时全部拿走。
6. 职级可按 M1-M10，并可分上、中、下；职级只绑定薪资大范围，具体薪资单独填写。
7. 工作手机预装软件清单和网站白名单由后台维护，通过 Android Enterprise / Android Management API + 商业 MDM 阻止违规访问并留痕。
8. 合同或基础定义违规时，所有流程必须先卡住，但允许按后台配置的更高级审核层级放行。> 现状/目标（2026-06-18 收口，R5，本期 P0）：准入闸口（超范围→卡住→升级→放行）须在票务/酒吧/游乐/结算业务动作前内嵌校验；当前 `SupervisorReviewService.evaluate` 为孤立评估接口，业务域动作前尚未调用——目标为动作前强制校验。> 两个闸口相互独立（2026-07-04 澄清）：**准入闸口**校验的是「业务动作是否在合同/空间/资质允许范围内」（domain=合同/空间/资质准入），**高危权限审批闸口**校验的是「操作人是否有权发起此高危动作」（domain=操作人权限，即 group-governance §3 的 requires_approval 授权审批）。二者都以 `supervisor_review` 为统一审批载体、都可升级放行，但触发条件和 domain 不同、互不替代：一次高危业务动作可能同时经过「操作人有没有权」与「业务在不在准入范围」两道校验。本条以下逐域切入点只描述**准入闸口**。
> 准入校验逐域切入点（2026-06-18 D2 逐域细化，本期 P0）：在上述总述基础上逐域明确强制校验插入位置，业务系统执行关键动作前必须先调用准入闸口（统一走 `supervisor_review`，不再引入 `admission_audits`/`contract_admission_rules` 旧表）；任一域校验不通过→阻断动作并写留痕→按 `staff_levels.level_rank` 升级审批→放行落 `supervisor_review_decisions`：

>   - 酒吧：开台前 + 点酒/结算前两处内嵌校验（超合同、超经营范围、资质过期则卡住，升级审批通过后放行）；校验不通过→阻断并写留痕→按 `staff_levels.level_rank` 升级审批→放行落 `supervisor_review_decisions`。

7. 工作手机、平板、一体机等受管设备必须领用/归还留痕；非现场或低风险岗位可不领设备，但不能执行现场核销、库存、收款等受控动作。
8. 设备异常必须进入主管复核；高风险异常可配置自动封禁并要求双人复核解封。
9. 高风险权限、财务权限、退款/免单/调账、敏感证据查看、开放平台密钥、主体绑定关系变更必须二次确认或审批。
10. 主体绑定、合同生效/终止、准入放行、设备异常解封、高风险财务调整、敏感证据查看、权限提升必须进入待复核状态。
11. 平台管理层治理总览第一屏看合同/主体异常、待复核权限、设备异常、准入阻断、应收应付逾期和高风险事件；第二屏看商户表现、空间使用和集团/项目汇总。
12. 集团视图默认 P2；P0 仅预留 `project_id` 和跨项目汇总口径，不阻塞单综合体闭环。

## 13. 本版结论

平台治理层是综合体统一管理系统的边界层、责任层和准入层。它不直接替代业务经营系统，但必须先定义清楚综合体项目、空间、业态、商户、合同、员工注册/设备凭证、设备、权限、终端开关和留痕（"NFC"按 D8 已统一为"设备凭证"，2026-06-07 收口）。

P0 阶段的重点是把“谁、在哪、凭什么、谁能操作、谁负责”管清楚。只要这层站稳，后续票务、酒吧、游乐、第三方、结算、事件中心和数据分析才不会出现对象混乱、权限混乱、账务归属混乱和责任链断裂。

## 15. 员工数据处理与监控合规

> 新增说明（2026-06-07 收口）：依合规 C10 与 finding compliance-land-7，android 等执行端已写"并入员工数据处理与监控合规统一告知"，但其指向的治理侧统一告知章节此前不存在（platform-governance 全文零命中监控/告知/同意），形成悬空引用。本章在治理文档侧落地"员工数据处理与监控合规"，作为 MDM、定位、设备检测、企微质检、绩效分析等员工监控类处理活动的统一告知与治理依据，并与 §7.6 员工注册审批的同意凭据字段、合规 C4/C10 配套。依据 finding compliance-land-7/compliance-land-8、合规 C4/C10。

### 15.1 适用的员工数据处理与监控场景

平台治理层涉及以下对员工的数据处理与监控活动，均需履行目的必要性论证、统一告知与用途限定：

| 监控/处理活动 | 处理的员工数据 | 处理目的 | 目的必要性说明 |
|---|---|---|---|
| MDM/工作手机管控 | 设备型号、安装应用清单、访问网站记录、违规访问留痕 | 保障公司受管工作手机仅用于合规业务、防数据外泄 | 工作手机承载现场核销/点单/结算等敏感操作，需限制非授权应用与网站，属履行用工管理与数据安全的必要措施 |
| 定位 | 工作手机/设备的位置信息 | 现场作业责任链、设备防丢、考勤辅助 | 仅用于在岗作业期间的现场责任与设备管理，非作业时段不采集 |
| 设备检测 | 私人手机 Root/调试/设备指纹（不可逆）状态 | 判断私人手机 App 是否可信，防伪冒身份 | 仅检测可信状态，不读取私人手机本机 NFC 唯一标识或其他个人内容（D8 数据最小化） |
| 企微质检 | 员工与客人的企业微信工作会话 | 服务质量与合规质检、纠纷取证 | 仅限工作会话，留存期限可配置（非永久），按合规 C3/A7 到期归档/销毁/匿名化 |
| 绩效分析 | 班次、设备、留痕、业务结果等工作记录 | 形成基础绩效依据 | 仅使用与岗位职责相关的工作记录，不做与岗位无关的画像 |

### 15.2 统一告知方式

- 上述员工数据处理与监控活动，须通过**入职协议**与**规章制度**向员工统一告知：告知处理目的、范围、方式、留存期限与员工权利。
- 告知须在员工注册审批环节取得员工知悉/同意，并在员工档案/注册审批中留存**同意凭据**（consent_version/consent_time/consent_scope，或关联 employee_notice_id 指向员工监控告知/同意记录表），见 §7.6 员工关键字段与 §9 员工注册审批页。
- 告知文本版本化管理；告知内容变更时须重新告知并更新同意凭据版本。

### 15.3 用途限定与最小化

- 员工监控数据严格用于上述声明目的，**禁止**用于声明外用途；不得将监控数据用于与岗位职责无关的画像或处置。
- 私人手机仅检测可信状态（Root/调试/不可逆设备指纹），**不采集私人手机本机 NFC 唯一标识**（D8 已废止），不读取私人手机的个人内容。
- 各类监控数据按合规 C5 个人信息分类留存策略设留存期限，到期归档/删除/匿名化。

### 15.4 查看与处置审计

- 对员工监控数据（定位、企微会话、设备检测记录等）的**查看、导出、处置**操作须按权限控制并写入操作留痕（操作人、对象、时间、目的）。
- 高敏感查看（如调取企微会话用于纠纷取证）须经审批并留痕，可被追溯复核。
- 员工对涉及本人的监控数据享有知情权；删除/撤回同意按合规 C2/C5 口径级联处置。
