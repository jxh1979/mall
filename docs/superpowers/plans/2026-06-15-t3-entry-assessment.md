## 3. 不直接进入 T3 的原因

1. T3 不是 P2-B/C/D Web 入口的自然延续。T3 涉及预测分析、集团视图、开放平台 SDK 深化、机器人/视频/设备控制闭环，以及可能的独立 Python AI 服务。
2. 机器人、视频平台、设备厂商和 AI 质检深水区依赖供应商 SDK/API、回调签名、错误码、额度、鉴权模型和对账补偿语义。当前文档只保留了适配器边界，并没有最终供应商契约。
3. 如果现在直接写 T3，容易把“只读占位/分析能力”和“生产控制能力”混在一起，后续审计会很难区分哪些是真实生产闭环，哪些只是预留。
4. T3 的安全和合规影响面更大：视频证据、AI 质检、客户意图、设备控制、开放平台 SDK、跨主体/集团级分析，都需要单独的威胁建模和验收闸口。

## 4. 推荐下一步

先创建 `T3-0 编码包`，再进入具体实现。编码包至少包含：

- T3 范围图：第一批 T3 做什么、不做什么。
- 供应商就绪矩阵：机器人、视频、设备、企业微信、AI 模型/服务、支付/渠道 SDK。
- API 契约增量：新增写接口、Webhook、轮询、SDK/mock 边界。
- 数据治理：客户数据、员工行为数据、视频证据、AI 输出留存、租户/集团聚合边界。
- 安全闸口：授权、终端/设备能力、Webhook 签名、限流、密钥轮换、审计事件、Semgrep 扫描。
- 验证闸口：后端测试、OpenAPI 覆盖、客户端路由覆盖、payload 策略、构建、安全扫描、供应商 mock 测试。

## 5. 建议的 T3 切片

### T3-A：经营分析只读深化

如果业务希望尽快看到 T3 进展，这是最稳的第一切片。

- 集团级看板和趋势对比。
- 基于现有指标字典、机器人指标、商户健康度、员工评分、客户意图做只读展示。
- 不做生产控制命令。
- 风险低，实施成本低。

### T3-B：开放平台 SDK 和 mock 深化

适合在外部供应商即将联调前启动。

- SDK 示例、mock 回调服务、签名样例、重试/补偿样例。
- 不使用真实供应商密钥。
- 风险中等，但对后续供应商协作价值高。

### T3-C：机器人/视频/设备真实控制闭环

供应商资料不到位前不建议启动。

- 机器人任务指令写接口。
- 视频证据深度链接和回调。
- 设备指令、状态回调和对账补偿。
- 必须具备供应商 API、回调签名、沙箱、错误码、额度和验收证据。

### T3-D：独立 Python AI 服务

AI 工作负载和数据边界明确前不建议启动。

- 模型/服务边界、异步任务协议、载荷最小化、审计和降级兜底规则。
- 必须先明确模型选择、部署方式、隐私边界和失败回退 Runbook。

## 6. T3 编码准入条件

满足以下任一条件，才建议进入 T3 编码：

- 选择 `T3-A`，且限定为内部只读分析切片，不依赖真实供应商。
- 已拿到对应 T3 供应商的 API/SDK 文档和沙箱凭据。
- 已生成 T3 编码包，包含 OpenAPI 增量、数据模型增量、用户故事、验收标准、边界场景、安全闸口和回滚方案。
