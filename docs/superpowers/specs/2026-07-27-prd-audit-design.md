# 综合体管理系统 PRD 全量审计设计

日期：2026-07-27
审计对象：`192.168.88.160:/home/james/complex-management`
最终版本：远端仓库 `main`

## 1. 目标

以三个现行业务 HTML 为最终业务解释权，对现行 PRD 及直接相关的业务文档进行全量审计。审计同时采用：

- 顺从性审计：证明每条权威规则是否被 PRD 完整、准确、无歧义地承接。
- 对抗性审计：主动构造反例，寻找规则缺失、相互矛盾、错误责任主体、资金或权益不守恒、权限绕过、状态不可恢复和跨域口径漂移。
- 第一性原理复核：把业务规则还原为主体、对象、触发事件、状态变化、资金或权益变化、权限、失败恢复和证据要求。

三个最终解释文件：

1. `docs/business-system-map-for-operations-v0.1.html`
2. `docs/platform-governance-map-for-operations-v0.1.html`
3. `docs/business-enum-quick-reference-v0.1.html`

PRD、业务规格、业务决策、术语和追溯矩阵不得反向解释或削弱三个 HTML。

## 2. 审计边界

### 2.1 纳入

- 三个权威业务 HTML。
- 全部现行总 PRD、领域 PRD和产品规格。
- 业务决策日志和统一业务术语。
- 需求追溯、PRD覆盖及业务规则映射矩阵。
- 当前有效文档入口和产品文档索引。
- `/home/james/codex-backups/` 中尚未合并、仍与当前权威口径一致的 PRD审计裁决。

### 2.2 排除

- `docs/_archive/` 中的历史文档。
- 开发设计、实现计划、OpenAPI、数据库设计。
- 代码实施与完成审计。
- 测试报告、运行证据、生产运维文档。
- 构建产物和机器生成快照。

排除内容只在判断一份文档是否属于现行范围时作为辅助证据，不对其进行正式逐项审计。

### 2.3 明确限制

本任务不审计代码质量、安全实现、UI、OpenAPI、数据库或测试真实性，也不依据代码反向修改业务规则。

## 3. 历史备份使用规则

`/home/james/codex-backups/` 是历史续接材料，不是当前事实源。

- 同名且哈希一致：可复用历史分析结果。
- 同名但哈希不同：快速审阅差异，只保留仍被当前 HTML 支持的结论。
- 仅备份存在：标记为历史续接材料，不自动纳入当前正式文档。
- 与当前仓库或当前 HTML 冲突：以当前三个 HTML 为准。
- 历史用户裁决未被当前 HTML 推翻：可登记为补充业务裁决。
- 历史裁决与当前 HTML 冲突：进入待裁决队列，不静默沿用。

## 4. 总体方法

采用“HTML 原子规则账本驱动、分域双重审计、域内风险优先”的方法。

不采用 PRD 驱动作为主方法，因为从 PRD 反查 HTML 会遗漏未被任何 PRD提及的权威规则。风险优先方法只用于决定每个业务域内部的检查顺序，不替代全量覆盖。

## 5. 阶段结构

每个阶段在独立分支和 worktree 中完成，验证后提交、合并并推送远端 `main`。

### 阶段 1：基线与历史续接

锁定 `main` 提交、三个 HTML 哈希和正式审计范围；快速比较备份，迁移仍有效的业务裁决，标记冲突和过期内容。

### 阶段 2：权威规则账本

将三个 HTML 拆成原子规则，记录规则 ID、原文位置、主体、对象、触发条件、状态变化、资金或权益变化、权限、异常和证据要求。本阶段不改变业务结论。

### 阶段 3：平台治理与通用规则

审计组织、项目、商户、人员、角色、权限、临时授权、外包或审计人员、终端开关、租户隔离、证据留痕和统一术语。

### 阶段 4：交易、会员、票务与酒吧

优先检查资金和权益守恒，覆盖订单、支付、退款、储值、积分、券、门票、核销、卡座、邀请、提成和库存联动。

### 阶段 5：地产、招商、合同、楼宇与供应链

覆盖空间、招商、合同、应收应付、租金、物业工单、证照、采购、库存、调拨和盘点。

### 阶段 6：游乐、终端、第三方和数据分析

覆盖安全巡检、预约或包场、终端模式与开关、供应商接入、通知、指标口径和来源真实性。

### 阶段 7：横向一致性与收口

跨 PRD 检查同一术语、状态、权限、金额、责任主体和生命周期；关闭覆盖矩阵，输出剩余待裁决事项及最终报告。

跨域问题先登记，在阶段 7 统一处理，避免同一文件被多个阶段反复改写。

## 6. 单条规则审计流程

### 6.1 权威解析

记录 HTML 文件、锚点或行号、规则原文和最小语义，不使用 PRD 反向解释 HTML。

### 6.2 第一性原理拆解

每条规则必须明确：

- 责任主体、权利主体和风险承担者；
- 被管理的业务对象；
- 触发事件和前置条件；
- 状态变化及终态；
- 金额、积分、库存、名额或权益变化及守恒条件；
- 操作、审批和复核权限；
- 失败后的补偿、撤销、重试或人工接管；
- 必须保留的业务证据。

### 6.3 顺从性状态

- `FULL`：完整一致。
- `PARTIAL`：只覆盖部分条件或边界。
- `CONFLICT`：与 HTML 冲突。
- `MISSING`：没有承接。
- `AMBIGUOUS`：存在多种解释。
- `STALE`：曾经正确，但已被当前 HTML 或新裁决取代。
- `NOT_APPLICABLE`：有明确且可验证的不适用理由。

### 6.4 对抗性反例

至少检查：

- 权限绕过或自审自批；
- 重复请求、并发操作和部分成功；
- 退款、撤销、过期、退出和跨期处理；
- 跨项目、跨商户、跨主体错误归属；
- 金额、积分、库存、名额或权益凭空增加或消失；
- 状态卡死、不可恢复或责任无人承担；
- 文档宣称完成，但规则本身不完整。

### 6.5 证据要求

每项正式发现必须包含：

- HTML 位置；
- PRD 位置；
- 冲突或缺口的最小描述；
- 业务影响；
- 建议修订文本；
- 当前处理状态。

没有直接证据的推测不进入正式问题清单。

## 7. 修订权限与裁决门

### 7.1 可直接修订

- 引用错误、失效链接和明显过期状态。
- 当前 HTML 能唯一确定结论的 PRD冲突。
- 术语不统一和追溯缺失。
- 不改变业务含义的结构或表达问题。

### 7.2 必须暂停询问

- 三个 HTML 相互矛盾。
- HTML 没有规定或无法唯一推出答案。
- 历史业务裁决与当前 HTML 冲突。
- 修订会改变计价、清算、权限、责任主体或风险承担。

每次只向用户询问一个决策问题，并提供证据、2–3 个选项、推荐答案、第一性原理依据和连锁影响。用户回答立即写入业务裁决台账。

仅当决策难以逆转、缺少上下文会显得反直觉、且确有真实取舍时，才创建 ADR。

## 8. 严重度

- `P0`：可能造成资金或权益不守恒、越权、自审自批、主体责任错误、不可恢复状态，或导致多个 PRD产生相反实现。
- `P1`：核心流程、关键边界或跨域规则缺失，可能导致业务无法闭环或验收标准错误。
- `P2`：局部覆盖不完整、追溯断裂、术语或状态不一致，但有明确替代路径。
- `P3`：不改变业务含义的引用、结构或表述问题。

## 10. 阶段 Git 与验证闭环

每个阶段：

1. 从最新 `origin/main` 创建阶段分支和独立 worktree。
2. 记录阶段开始时的提交、三个 HTML 哈希和工作区状态。
3. 完成该阶段规则映射、问题清单和授权范围内的精准修订。
4. 确认每一行改动都能回链到 HTML规则、已确认裁决或明确的一致性问题。
5. 执行文档级验证。
6. 输出“发现 → 裁决 → 修订 → 验证”对照。
7. 提交阶段变更。
8. 合并进远端 `main` 并推送 `origin/main`。
9. 验证 `main == origin/main`、主工作区干净、三个 HTML 未被意外修改、阶段交付文件已进入 `main`。
10. 所有条件满足后才开始下一阶段。

文档级验证至少包括：

- 范围和文件数量完整；
- HTML规则 ID 无重复、无遗漏；
- 覆盖矩阵引用的文件和锚点存在；
- PRD交叉引用和相对链接有效；
- 不存在未解释的 `TBD`、`TODO` 或“待定”；
- 术语、责任主体、状态、金额单位和枚举一致；
- 未修改代码、OpenAPI、数据库、测试、开发设计或运维文档；
- `git diff --check` 通过。

若阶段开始时 `main` 存在其他未提交修改，或远端在审计期间推进，暂停合并，不覆盖他人改动。
